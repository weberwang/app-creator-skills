# 界面代码草图

先用可运行的Flutter界面验证内容、布局与交互结构，避免高保真视觉投入建立在错误流程或页面骨架上。

执行前阅读[公共执行协议](../app-creator-workflow/references/professional-execution.md)。以下共用步骤不能跳过所选原生适配规定的操作顺序、资源格式与平台边界；必要的用户确认按协议执行。

## 输入

- 接受的用户流程和页面目标；Flutter工程结构与设计令牌；真实文案/样例数据；需要验证的布局疑问。

## 共用操作步骤

1. 确认已有Flutter应用入口、路由、主题、字体和可用生产组件；在现有工程上延伸，不另建脱离生产环境的Demo项目。
2. 按[UI 相对布局与定位](../app-ui-layout/references/relative-layout.md)将页面拆成语义区块，按用户优先级放入真实文案和代表性数据，标出页面跳转、状态变化和暂时占位的逻辑。
3. 使用低保真颜色、简单形状和系统/现成组件表达结构；保持可访问标签和真实点击目标，不用整屏静态图替代布局。
4. 覆盖加载、空、错误、长文案和系统字体变化，检查滚动、键盘、安全区、返回行为及最小点击区域。
5. 在项目实际Flutter运行入口执行最小构建/目标模拟环境检查，把页面截图和待确认问题交用户人工查看。
6. 记录继续做高保真/正式实现所需决定，拆除或明确标注临时数据和草图样式的清理条件。

## 关键边界

- 仅针对Flutter代码草图；更广泛的UX审核或自适应正式实现使用各自能力入口。
- 草图通过只代表结构可讨论，不等于视觉设计或产品流程已验收。

## 交付

- 可运行低保真页面、状态/导航说明、目标布局检查记录和待用户决定清单。

## 当前技术栈的原生流程

先根据仓库实际依赖与项目配置确认当前 `app-stack-*`，再打开同目录的 [native-adapters.json](native-adapters.json)。按 `when` 选择 `mode`，从 `path` 指向的本栈原生手册中定位 `section` 章节，只读取该模式及其明确需要的脚本、模板和校验器；同栈同能力的多个模式在同一本手册内维护。
使用共用读取工具：`node .agents/skills/app-skill-runtime/read-native-mode.mjs <技术栈> app-ui-code-sketch [sourceSkill]`。单模式可省略来源，多模式必须指定清单中的 `sourceSkill`；输出所选章节、直接公共依赖及按需资源路径，不递归加载其他模式。维护本技能仓库时将 `.agents/skills/` 换为 `skills/`。
若 manifest 未列当前栈，继续使用该栈 `app-stack-*` 中的原生规范/索引及适用公共流程；这本身不代表能力缺失。仅当已声明并选中的原生手册或模式章节未随安装提供时才报告阻断。公共工作流只在 `sharedWorkflows[].stacks` 包含当前栈时读取；`onDemand: true` 的参考按当前任务选择，读取器仅列出路径。不要加载其他栈模式或臆造接口；栈未确认且会影响实现时先澄清。
