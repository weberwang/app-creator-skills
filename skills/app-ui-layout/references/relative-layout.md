# UI 相对布局与定位

本规则适用于五个技术栈的游戏和应用 UI，包括页面、场景 HUD、控件及浮层内部。布局、草图、素材拆解和正式实现使用同一规则；原生组件、坐标空间与资源约束仍按当前技术栈执行。

## 还原依据与变更边界

在现有 V3 布局规格及正式可编辑源中补齐受影响依据；阶段名称不同时映射到等价职责，不新增阶段、独立文档或第二套布局系统。正式源包括场景、预制体、界面文件、声明式 UI 或组件代码及必要配置，不要求所有技术栈建立可视化编辑器。已有明确规格直接复用，小改动只补受影响项。

| 依据 | 按实际影响补齐的事实 |
| --- | --- |
| 对照条件 | 有效设计稿及版本或内容指纹、参考画布、语言、真实文案、内容状态、安全区；涉及世界画面时补充相机、光照、渲染和动画采样条件 |
| 元素关系 | 稳定身份、真实父级、定位参照、坐标空间与逻辑单位、锚点或对齐、相对位置、宽高或尺寸策略、间距及层序 |
| 图片 | 实际源帧、有效内容边界、透明留白、导入密度、切片及目标显示尺寸；无对应概念的技术栈或素材可省略不适用项 |
| 文本 | 真实字体及字重、设计字号、行高、文本宽度、换行、自动字号及最小可读字号规则 |
| 适配 | 固定约束、允许变化的属性、功能依据、触发条件、范围与极值处理；动态变化后的保持或恢复策略 |

每项依据区分“已确认目标”“测量值”“估计值”和“适配规则”，记录来源；不能把实施估计提升为已确认设计要求。无法获得准确参数时保留未知，不编造测量值。沿用已有布局字段与计划说明承载来源和缺口，不为填写这些信息复制一份节点树。确有影响结果且现有依据无法消除的歧义时集中澄清，已有明确要求无需重新审批。

还原任务不得为了方便实现或通过测试擅自改变整体比例、压缩面板、重排信息、替换视觉层级或调整图片尺寸。对目标的还原修正和已声明规则内的功能适配，在已有授权范围内继续；改变视觉目标的设计变更须记录具体差异和原因，仅在确需用户取舍时请求确认，不以“适配”“优化”掩盖变更。文本和素材的极值处理同样遵守此边界，不能因技术检查通过就视为设计目标已满足。

静态布局事实以正式源为准，预览与运行复用资源、组件和配置。响应式布局、约束求解、虚拟列表等必要计算读取同一配置，运行代码只控制具有明确功能依据的必要属性，不独立维护重复且可能冲突的静态坐标。

V5 在同一验证阶段内分别进行基准还原和适配检查，具体执行及三类验收结论见[验证与交付](../../app-creator-workflow/references/verification.md)。基准检查先在相同对照条件下核对关键元素的设计目标、正式源实际值和运行实际值，再依已声明规则检查其他视口、内容及动态状态。默认可用性模式只覆盖受影响关键项，不强制完整 fidelity 矩阵；仅明确要求 `exact` 时采用本栈完整精确对照。

出现差异时，在现有证据中按需记录元素身份、目标及来源、正式源值、运行值、差异与产生环节、是否属于已声明适配、修复及复验结果。先区分设计解释、素材生产、资源导入、布局装配、运行适配和验收遗漏，再修改对应来源，不能只校验运行是否保持了一个已经偏离设计稿的参数。

仅对可客观测量的属性使用数值检查；容差按属性、逻辑单位及参考条件确定，不采用未经论证的统一像素阈值，不把阴影、纹理或字体观感简化成矩形误差。没有真实机器可读数据和验证入口时，只能记录待查项，不声称规则已由工具强制执行。截图默认由用户人工检查；代理可采集并提供目标、实际画面与检查点，未经明确授权不分析截图或判定视觉通过。

## 相对关系

- 每个 UI 元素以实际父容器或明确允许的参照对象为依据，声明布局归属、参照、对齐或锚点、间距及尺寸策略。页面或场景根可参照实际视口、安全区等稳定边界；明确独立参照时同时保留真实父子关系。
- 位置由流式布局、容器约束、锚点、兄弟/祖先参照或其他已声明关系计算；父级、参照、内容、可用尺寸或安全区变化后重算受影响布局。不能把普通 UI 单独固定在屏幕坐标上来代替这些关系。
- 相对布局不要求所有尺寸、间距或偏移使用百分比：固定内边距、固定尺寸及相对参照的偏移可以使用；运行时或测量结果中的绝对坐标、矩形也可以记录，但它们应由声明的关系计算得到。
- CSS `position: absolute`、Flutter `Stack`/`Positioned` 等是实现方式，不自动证明或否定相对关系。普通 UI 使用它们时仍须绑定父容器或明确参照，并随参照变化保持约定关系。

## 文本宽度、缩放与换行

本节适用于五个技术栈的 UI 文本，包括新增、复用和动态文本组件。根据组件用途、语义和内容特征自行选择排版策略，不仅依据当前示例文字是否放得下；沿用已有规格记录决定，不新增逐组件审批。

涉及具体组件设置时，按本技能 `native-adapters.json` 读取当前栈原生模式及其引用的 `app-stack-<当前栈>/references/text-layout.md`。原生指南提供真实组件属性、取值、设置位置、能力缺口和官方来源；只读当前栈及已选 UI 路线，不把其他版本属性照搬到项目。示例中的宽度和字号须替换成项目配置。

- 所有文本组件必须具有由布局确定的固定宽度。宽度可以随已声明的父约束、断点或视口规则重新确定，但在同一布局条件下不随文字内容增长；禁止以内容撑宽、无限横向增长或缩放父容器代替文本适配。可用行宽扣除内边距及同组图标等占位后计算。
- 标题、按钮标签、短操作和短状态等采用固定宽度、单行自动缩放：禁止换行，内容超宽时在设计字号与最小可读字号之间自动选择能完整容纳的字号；内容变短后重新按设计字号测量，不累积缩小。不通过整体 Transform 缩放改变按钮、图标、命中区域或既有位置关系。
- 长描述、说明段落和正文采用固定宽度、自动换行：保持所设正文排版，在行宽内自然断行；高度随内容增长，或使用已声明的限高滚动区。不得为了塞入固定高度将整段持续缩小、裁掉后续行或省略必要内容；连续长词、数字串及手动换行按项目语言与内容规则处理，仍不得越界。
- 每种文本样式须在现有布局规格和正式组件配置中设置具体的最小可读字号、设计字号、逻辑单位及单行/换行模式；依据当前栈、显示密度、使用距离与项目字体层级选定下限，不以一句“保持可读”代替数值，也不跨技术栈套用统一像素值。自动缩放不得低于下限；系统字体放大等无障碍设置仍纳入适配，不能通过自动缩小抵消用户的阅读需求。
- 单行在最小字号仍放不下时，调整必要文案或正式布局宽度并重验，不擅自改成多行、截断、省略或突破字号下限。标题和按钮的单行用途不因切换语言改变；长描述在各语言中保持换行用途，按语言核对断词和行高。确有不同用途时在已有规格中说明差异，不机械将所有文本设为同一模式。
- 优先使用当前栈的官方文本测量、自动字号与换行能力；功能适配只执行正式配置的规则，遵守[编辑器布局控制权](../../app-domain-toolkit/references/editor-display-authoring.md#编辑器位置关系的控制权)，不在业务代码中重设静态宽度、父级或锚点。记录实际行宽、模式、设计/最小/实际字号及行数，验证最长文案、多语言、字体回退、内容更新、相关视口和字体放大；截图由用户人工检查。
- 原生缺少自动字号或下限时，先评估项目现有和成熟社区实现，均不满足才基于官方测量补最小有界适配；不能虚构原生属性。静态文案须校验所有已选语言，动态文案还须在内容变化时检测失败并按既定策略处理；仅记录“低于下限”后继续作为正常结果显示不算完成。不要新增一份脱离正式组件的文本清单或把文档规则表述为机器已强制执行。

## 图片尺寸

图片还原和运行时展示默认保持最终交付源帧的逻辑尺寸，宽高比例和尺寸均不改动；只有已明确采用合法九宫格的图片皮肤允许按切片规则改变显示框。这里的普通图片不包括屏幕空间装饰背景。普通图片不能通过等比缩放、非等比拉伸、`contain`、`cover`、父级缩放或修改显示宽高适配容器。图集图片以实际切片尺寸为源帧，不能用整张图集尺寸作为还原尺寸。

源帧像素与布局逻辑单位按已声明的纹理密度换算；设备 DPR、渲染画布分辨率和相机投影本身不构成图片尺寸修改授权。布局可调整位置、间距和排列，容器与文本仍按原有响应式规则处理；图片不能适配时保留事实并调整布局或重新生产合适尺寸的资源，不为通过检查篡改源尺寸。

### 技术栈的尺寸与密度

“保持源逻辑尺寸”在当前技术栈的布局坐标空间中判断，不要求所有引擎填写同一套 DPR 参数。先确定实际源帧、导入密度和坐标换算，再验证普通图片自身及中间祖先没有引入额外缩放。

| 技术栈 | 原生尺寸与密度边界 |
| --- | --- |
| Phaser Web | 区分逻辑画布、CSS 显示尺寸和 Canvas backing；设备 DPR 只参与渲染分辨率，不改变图片逻辑宽高。 |
| Three.js Web | 屏幕 HUD/DOM 使用明确的逻辑到 CSS 映射及渲染缓冲区密度；三维世界材质和相机投影按世界视口合同处理，不拿世界单位与源图片像素直接比较。 |
| Cocos Web／原生 | Web 路径可使用浏览器 DPR 合同；Creator SpriteFrame、UITransform 与逻辑空间变换决定图片还原尺寸。原生平台按引擎实际设计分辨率和显示映射，不强行读取浏览器 DPR。 |
| Unity | 按 Sprite 导入密度、所选 UI 系统的原生尺寸和 Canvas／Panel 坐标映射核对；屏幕 UI 与世界空间分开，不套 Web DPR 上限。 |
| Flutter | 按图片资源 scale／密度变体和逻辑像素确定显示尺寸；设备像素比用于逻辑到物理像素映射，不额外放大图片，也不套 Web DPR 上限。 |

共享 Web 合同中的运行 DPR 动态封顶 2、图片生产 DPR 基线 1，仅属于对应 Web 管线；生产基线不代表所有引擎的设备像素比均为 1。相机、Canvas 或屏幕映射的合理换算应保留，不能用“原尺寸”禁用正常显示映射，也不能借映射隐藏普通图片的额外缩放。

生成素材在交付前仍可按约定尺寸归一化；这不授权运行时再次缩放。九宫格须使用同一源尺寸、切片边宽和目标框，保留固定角边及独立文字、图标尺寸，不以普通整图缩放冒充九宫格。需要运行采样时检查实际显示尺寸和祖先变换；静态尺寸一致不代表真实运行效果已验收。

## 背景与宽高适配

屏幕空间装饰背景允许等比放大或缩小，统一使用 `cover-v1`：`scale=max(目标宽/源宽,目标高/源高)`，两轴使用同一个比例；按焦点与目标落点计算偏移，并限制在 `[目标尺寸-显示尺寸,0]`，避免露边。目标是完整可见视口，背景不受安全区缩小；安全区仅约束关键 UI。裁切不能带走文字、交互和玩法信息。背景独立于前景布局，不能通过缩放背景父级带动按钮和图标。九宫格皮肤仍使用切片规则，世界空间环境使用原生相机合同。

游戏初始化只选择横屏或竖屏之一：竖屏设计基准 `1080×1920` 按宽适配，横屏 `1920×1080` 按高适配，另一轴按实际可见区域展开或裁切。逻辑坐标到显示坐标的统一映射不改变普通图片的逻辑尺寸；禁止再给普通图片增加额外的内容缩放。Flutter 初始化可选横屏、竖屏或双方向，按实际父约束、宽高断点和内容重排；双方向才验证旋转与状态保持，不将游戏固定设计尺寸套用到 Flutter。DPR 只决定渲染采样与 backing 分辨率。

## 浮层本体的例外

弹窗、浮窗和 Toast 的**本体容器**可以按任务需要独立决定其相对宿主的落位；可按视口、输入位置、用户拖动结果等选位，也可以采用相对定位。其本体仍需满足项目的可见范围、安全区、遮挡、输入与生命周期要求。

该例外只适用于这些浮层自身的容器，不传递给内部任何后代。按钮、图标、文字、徽标、列表及其他内部 UI 仍须相对其父容器或明确参照布局与定位。普通 HUD、按钮和其他 UI 不因为标记为 overlay、处于 `DISPLAY_LAYER` 或使用叠层组件就获得例外；三维世界对象按各栈世界坐标规则处理。

## 验收

记录需要验证的 UI 层级、父级与定位参照、锚点或布局约束，以及适用视口和内容状态；普通 UI 出现直接依赖固定屏幕坐标时须修正。分别检查：

1. 参照或父容器移动、缩放以及视口/安全区变化时，受影响的普通 UI 维持声明的相对关系并重新布局。
2. 浮层本体移动或可用尺寸变化后，内部控件仍相对浮层内容区或各自声明的参照保持关系；长文案、动态数据和滚动不得破坏操作与可读性。
3. 对目标栈的代表性尺寸、状态和输入方式提供实际布局与交互证据。静态合同通过只能证明其已检查的字段，不能单独证明浮层本体身份、后代关系或真实运行效果；显示效果仍由用户人工检查。

## 模板与机器检查

静态校验器从输入合同或引用的节点文件读取声明的父级与定位参照，调用同一[相对布局检查模块](../scripts/relative-layout-policy.cjs)。它拒绝普通 UI 的独立定位、未知定位模式、缺失或成环的父级/参照，以及浮层内部引用外部视口或祖先的逃逸；它不自动连接编辑器或回读真实 Scene、Widget、DOM。输入应对应正式源，是否一致及是否已保存仍需通过本栈原生回读或真实运行采集核对，不能另建无关关系图或将静态通过表述为实际节点已验证。

| 工件 | 必须维护的节点事实 |
| --- | --- |
| Cocos、Phaser、Three.js 普通布局 | `regions[].parent_id`、`reference_id`、`positioning`；本体类型用受控的 `floating_root_kind` 声明并与真实区域身份绑定。 |
| 三栈效果图布局 | 使用唯一布局源中的真实父级、锚点和参照；`ui_layout.positioning` 与 `floating_root_kind` 随同一节点身份传递。Cocos 引用式合同直接校验其引用的真实节点文件。 |
| Unity | 使用 `parentElementId` 与 `layoutBinding`；本体的 `uiLayout.floatingRootKind` 必须绑定独立显示层，`positioning: absolute` 时以 `independentPosition` 记录目标落位。普通计划中的位置由既有父级和锚点关系派生。 |
| Flutter | 每个 region 声明 `parent_id`、稳定且唯一的 `flutter_key` 和 `positioning`；浮层本体还需与相同 ID、相同类型的 overlay 绑定。实现信号与高保真测量必须引用同一实际节点与参照。 |

定位模式只允许 `relative` 或 `absolute`。只有显式且合法的 `popup`、`floating`、`toast` 本体可使用后者；所有内部子孙仍须相对定位，不能重复声明本体来获得豁免。已有强制父级、锚点和参照的原生结构，在未声明独立模式时仍表示相对布局；显式非法值不能当作缺省值放行。

独立本体仍须保留必要的结构、初始几何与真实测量事实；几何矩形的存在不把其变成必须跟随宿主的普通控件。运行时本体自由落位时，内部节点继续对实际本体和内部参照验证。静态检查不代替对应用中真实节点、动态随动或显示效果的运行采集与人工验收。
