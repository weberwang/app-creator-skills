# 非游戏 App 的 Figma 设计与正式还原

本规范适用于 Flutter、Expo 的 PAGE 和 DISPLAY_LAYER，默认通过实际可用的 Figma MCP 制作高质量、可编辑设计，人工选定后还原到正式工程。ESP32 自带屏幕 GUI 可用相同路线，但以真实硬件为边界。游戏保留原来的游戏设计、三张整页候选与素材流程；Node.js 无界面服务不提供 Figma 产物。

## 目标与设计自由

从已确认需求、目标用户、主要任务、真实文案、状态和情境明确本轮代表页与范围。业务事实、必要功能、无障碍、平台能力、真实硬件约束和用户明确锁定的品牌要求属于硬约束；其余信息架构、区域布局、字体、配色、留白、组件形态与内容呈现可以探索。已有代码和组件用于理解功能及实现条件，不默认成为新设计的视觉上限。适合时复用设计系统、图标和组件，否则创建有实际用途的专属组件。

设计探索与忠实还原是不同任务。只有用户明确要求还原现有界面时，才以它为主要视觉依据；不能把探索默认执行成旧页面换色。信息足够就自主制作，不先要求批准一份文字视觉方案。不增加无关功能、虚构数据、装饰面板或营销文案填满版面，不将某次学习页的配色、字体或书本形象作为所有 App 的通用风格。

## 使用真实工具

先发现当前宿主实际提供的 Figma MCP 工具和技能，读取所选工具要求的技能，不假设工具名称、能力或授权。当前官方工具可通过可编辑 Design 文件的 Plugin API 构建和查询节点；使用 `use_figma` 前加载 figma-use，涉及可见设计时同时加载 figma-generate-design，组件/变量库按需加载 figma-generate-library；新建文件和设计转代码分别遵循 figma-create-new-file、figma-design-to-code 的前置要求。工具包发生变化时以实际声明为准，不调用凭空编造的接口。fileKey 已知后按实际工具要求创建并复用文件会话。

使用可编辑文字、组件、实例、矢量图标和自动布局组织内容；图层按职责命名。重复元素组件化；颜色、间距和圆角变量实际绑定到消费属性，不能只建立未使用 token。通过实际字体清单确认可用字体，按工具要求先加载再写文字；记录目标平台的字体实现和明确的替代理由。

禁止把整页效果图作为背景或图片图层冒充可编辑界面。照片、插画、角色或独立纹理按需生成或复用后嵌入，保留明确素材身份、来源及消费者；不把生图设为每个页面的必经步骤。生成或编辑图片遵循当前宿主 imagegen 技能及 image_generator 委派规则，不因工具存在就授权付费生图、购买素材、发布或其他受保护动作。已有明确授权不重复询问。

工具不可用时说明缺失的能力、影响和未验证范围，继续需求、内容、平台约束等独立工作；不静默退回整页生图并宣称已完成 Figma 设计。本规范的本地校验器核对冻结事实，不凭本地 JSON 假装实时连接远端。

使用控制器登记外部写入时，V2 的 PROPOSAL／REVIEW 可检查已精确授权的 `external-write`，目标限定 `figma:<实际fileKey>` 或 `figma:new:<实际团队或项目键>`；仍须匹配当前 actionId、批准范围及 F4，不自动增加授权，也不放开设备、付费或发布。宿主已有明确授权按其实际范围继续，不为同一动作重复询问。

## 方向探索与选定

首次定调或实质性改版，先研究真实内容、硬约束和可用参考的设计规律，自主选择一个有依据的方向，默认精修一个代表页 Figma 方案，以提高首轮用户确认通过率，不承诺必过。只有用户明确要求比较多个方向时才制作多方案，数量按用户要求；此时保持相同核心任务、主要内容、状态、视口、语言、文字倍率和比较条件，在布局、层级、排版、视觉语言或交互呈现上体现实质差异，不能只换颜色。先完成代表页，再扩展用户选定的方向。

建立与当前产品和受众相适应的字体层级、空间节奏、色彩和组件语言，将颜色、间距、圆角等变量实际绑定到消费属性，不固定通用配色或字体。前置考虑关键组件、最长文案、空／错误／加载状态，以及目标平台字体和设备硬件边界。送审前做一轮有界自查，检查真实节点结构、属性、变量绑定和可测布局事实并修复实际问题；截图和预览默认由用户人工检查，不自动看图、不循环自动审美审查，也不增加独立审批或强制报告。

展示实际节点链接、对应真实预览和简短取舍说明，由用户选择。允许明确组合不同候选的部分元素；组合后保存独立的可编辑选定节点及来源关系，不把组合结果算作第三个探索方向。用户未选择时保留待确认，工具成功或节点数量不构成视觉通过。

已有有效方向的局部增量不强制重做方案。引用已确认方向及实际影响范围，仅补变化的目标、状态和适配事实。方向复用不把历史运行和人工验收升级为当前通过；实质改变目标或交互方案时重新确认受影响范围。单方案不降低 V2 人工确认、原生还原证据或 V5 完整组合人工验收要求。

弹窗与 Toast 遵循[弹窗公共设计方案](../../app-domain-toolkit/references/reference-domain-display-ownership.md#弹窗公共设计方案)：全局选定稿冻结后，先确定所需弹窗公共方案，再设计 Toast。公共规则以实际绑定变量、组件和实例表达，具体业务内容按需组合；已有选定稿覆盖的设计按有效范围复用。方案确认及交接沿用下表的 V2/V3，不增加一次独立批准，也不要求代表弹窗 V5 完成后才设计 Toast。

## 沿用唯一控制器

继续使用 app-workflow-control 的六阶段、全局状态与 V0–V5，不新增设计状态机。

| 阶段 | 非游戏 App 的交付与边界 |
| --- | --- |
| V0 | 本批范围、业务目标、硬约束、可探索空间、代表页面及真实内容 |
| V1 | 正式实现相关功能与状态验证；白盒按风险选用，不成为设计的视觉上限 |
| V2 | Figma 方向探索、用户选择及正式目标冻结；选定后扩展其余页面与关键状态 |
| V3 | 从选稿直接提取组件边界、真实布局、字体、变量、图标素材、状态及适配；缺口定向补齐 |
| V4 | 在已验证工程上先试接代表组件和独立素材，再分批扩展；保留状态所有权及生命周期 |
| V5 | 当前完整运行组合、功能回归及用户人工视觉验收 |

Flutter、Expo 由控制器默认设置 `visual.designRoute:"figma-app"`。ESP32 可在初始化时使用 `--design-route figma-app`。仅设计提案可使用 `init --design-intent proposal`：仍记录 V0 范围与设计条件，V1 不伪造工程验证，V2 选定稿后可从 PROPOSAL 完成设计交付，不要求先建运行工程。此类工作项不能进入 V3–V5 或生产实现，也不能作为工程完成来源；正式实现使用具有真实 V1 功能基线的工作项。

同一选定 Figma 稿已经清楚表达结构和布局时，V3 直接使用节点与提取数据，不强制另绘低保真草图、拆解图、布局图或再次人工批准。交接补充不是第二次设计批准；只有实质改变所选目标或交互方案才重新确认。V4 实际资源和 V5 运行组合仍需各自当前证据，不由设计批准替代。

## 冻结来源与机器合同

公共 [Figma Schema](../../app-workflow-control/schemas/figma-app-design.schema.json)与控制器语义校验共同约束本地证据。模板在 [控制器 templates](../../app-workflow-control/templates/)。真实预览和结构导出在确认时保存为新版本及 SHA-256；历史冻结证据不改写。远端编辑后重新读取实际节点，对照原始结构及内容身份，不能将旧冻结确认自动当成新设计确认或当前运行通过。

领域封套的 `referenceTarget:{path,sha256}` 指向真实 Figma 预览冻结，`figmaDesignRef:{path,sha256}` 指向可编辑设计快照；位图不再是唯一设计来源。快照记录 projectId、stack、objectId、candidateId、实际 fileKey、nodeId、nodeUrl、stateId、viewport、language、textScale、previewRef、briefRef、captureRef、nodes、variables、assets。节点包括真实父子、尺寸、排布、文字、字体和消费属性；变量通过节点 bindings 关联实际值，独立图片关联实际素材范围。

`captureRef` 是真实 MCP 结构采集的原始结果或可追溯规范化导出，记录实际 toolName、capturedAt、fileKey、nodeId、stateId、viewport、nodes、variables、assets；控制器逐项核对快照与原始结构。`briefRef` 关联目标用户、主要任务、情境、真实内容、硬约束和探索空间，忠实还原模式另绑定明确现有视觉来源。

全局基线使用 `designRoute:"figma-app"`、`exploration.kind`（initial／redesign／increment）和 candidates。初始／改版默认一个，用户明确要求比较时按指定数量记录 requestedCount 和真实 userMessageRef；局部增量记录 sourceBaselineRef，改变局部目标时以 candidate.directionSourceRef 关联已确认方向，并提供 changeScope:local 和 changeReason。每个候选关联 figmaSnapshotRef 与预览 path。多方案的组合选择另记录 combination 的来源候选、明确用户决定及组合节点。游戏对应 Schema 分支和机器门仍要求原有三候选。

V2 的真实人工确认使用 `figmaDesignRef` 绑定所选稿；同稿多个已表达状态可用 `figmaTargetRefs` 精确覆盖其冻结节点，不为每张状态图再审批。新增或实质变更的目标不能伪称已有授权。V3 `figmaHandoffRef` 冻结 figmaDesignRef、layoutSpecRef、nativePlanRef、设计项到节点/状态/视口的 mappings、adaptationRules 和已解决的必要缺口；显示层交接另绑定 hostId 和 layerType。Flutter 保留原生还原计划，Expo/ESP32 保留各自布局、平台/硬件合同，复用这些信息而不重画图。

V4/V5 确认关联相同 figmaDesignRef，并继续消费实际原生产物和运行材料。平台无法表达时明确限制、替代方案及受影响范围，不静默降低目标。发现上游缺失或偏离时 RETURN 到最早受影响阶段，作废对应下游引用并保留历史。

交接不只登记节点 ID：Flutter 要求计划属性与对应节点的尺寸、间距、字体、颜色、边框和形状一致，并核对状态、视口、语言和文字倍率；平台差异引用已有明确局部决定及原因。Expo／ESP32 在原生节点 `designProperties` 或对应 mapping.nativeStyle 冻结实际提取的适用样式（typography、fill、spacing、radius、insets、colors、border、shape），与该布局节点、几何及父子关系一起核对。交接样式是正式实现应消费的规格，不是运行观测；实际源码、构建和运行仍按原生合同验证，最终显示由用户判断，不能以交接值声称运行样式已自动通过。

ESP32 快照另记录 `hardware`：实际 boardProfileRef、分辨率、colorFormat、inputMethods、fonts 和 resourceBudget；与设备资料中的色深、输入、字体及 Flash/RAM/可用 PSRAM 一致。Figma 画布、移动设备字体和桌面鼠标不能覆盖这些限制，设备运行仍须明确授权。

## 验证与人工边界

自动核对实际节点、尺寸、字体可用性、变量绑定、素材范围和可测布局事实；不把结构数量或测试通过登记为视觉质量。设计稿截图、预览以及运行截图默认由用户检查，未经明确授权不得自动分析截图或代写视觉 PASS。“用户视角审查”同样遵守此限制，可依据真实文案、节点和约束检查结构事实，不能借审查名义自动看图。

分别报告结构完成、工程验证、人工视觉结论。验证本工作流使用本地样例或测试替身，不实际创建外部设计、不付费生图、不运行真机。远端连接、实际 MCP 执行与内容真实性、实际平台字体显示、运行还原质量仍需在获得相应授权的真实任务中验证。
