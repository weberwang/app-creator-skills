# 非游戏 App 的 Figma 设计与正式还原

本规范适用于 Flutter、Expo 的 PAGE 和 DISPLAY_LAYER，默认先生成并确认效果图，再通过实际可用的 Figma MCP 忠实重建可编辑设计，提取规格并还原到正式工程。ESP32 自带屏幕 GUI 可用相同路线，但以真实硬件为边界。游戏按既有世界／界面分流，适用图片路线保留原候选数量与素材流程；Node.js 无界面服务不提供 Figma 产物。

## 目标与设计自由

从已确认需求、目标用户、主要任务、真实文案、状态和情境明确本轮代表页与范围。业务事实、必要功能、无障碍、平台能力、真实硬件约束和用户明确锁定的品牌要求属于硬约束；其余信息架构、区域布局、字体、配色、留白、组件形态与内容呈现可以探索。已有代码和组件用于理解功能及实现条件，不默认成为新设计的视觉上限。适合时复用设计系统、图标和组件，否则创建有实际用途的专属组件。

正式实现先按[系统与模块覆盖](../../app-creator-workflow/references/system-module-coverage.md)识别必要模块、规则、状态和进度并关联验收。第 4 阶段确认全局视觉方向与代表稿，V1 确认完整模块方案，V2 生成并确认模块设计稿，V5 实现与验收。

第 4 阶段基于产品规格制作并确认全局基线及代表稿。V1 确认本轮模块方案及验收，按风险使用[功能原型](../../app-creator-workflow/references/readable-functional-prototype.md#core-experience-first)验证。V2 按[正式出稿输入](../../app-creator-workflow/references/workflow.md#v2-design-inputs)从 V1 接收功能要求，基于全局基线独立制作覆盖适用流程、状态和进度的可编辑稿。已有正式确认的设计可按适用范围复用。V2 用户确认后固定版本，V3 从该确认稿提取规格。

按本次范围应用[设计依据](../../app-asset-workflow/references/interface-intent.md#design-basis)和[能力与动作语义](../../app-asset-workflow/references/interface-intent.md#capability-semantics)：从真实使用顺序与压力确定层级和关键取舍，核实现有、拟新增及待验证能力，把结论转为实际生图输入；不把未经验证的估计写成硬约束。

设计探索与忠实还原是不同任务。生成新效果图时探索视觉；用户选稿后，以该图作为重建依据。用户明确要求还原现有界面时以其指定来源为准，不能把探索默认执行成旧页面换色。信息足够就自主制作，不先要求批准文字视觉方案。不增加无关功能、虚构数据、装饰面板或营销文案，不将某个项目的视觉答案套用到所有 App。

## 使用真实工具

先发现当前宿主实际提供的 Figma MCP 工具和技能，读取所选工具要求的技能，不假设工具名称、能力或授权。当前官方工具可通过可编辑 Design 文件的 Plugin API 构建和查询节点；使用 `use_figma` 前加载 figma-use，涉及可见设计时同时加载 figma-generate-design，组件/变量库按需加载 figma-generate-library；新建文件和设计转代码分别遵循 figma-create-new-file、figma-design-to-code 的前置要求。工具包发生变化时以实际声明为准，不调用凭空编造的接口。fileKey 已知后按实际工具要求创建并复用文件会话。

使用可编辑文字、组件、实例、矢量图标和自动布局组织内容；图层按职责命名。重复元素按实际复用关系组件化；变量按真实样式和已有设计系统需要提供，已声明的颜色、间距或圆角变量须绑定真实消费属性，不要求每稿凑齐三类变量，也不创建无用途 token。通过实际字体清单确认可用字体，按工具要求先加载再写文字；记录目标平台的字体实现和明确的替代理由。

禁止把整页效果图作为背景或图片图层冒充可编辑界面。照片、插画、角色或独立纹理按需生成或复用后嵌入，保留素材身份、来源及消费者。代表页默认先生成效果图；有效已确认目标可复用，其余页面按本批范围与共享方向推进，不机械为每页重生。生成或编辑图片遵循当前宿主 imagegen 技能及 image_generator 委派规则，不因工具存在就授权付费、购买素材或发布。已有明确授权不重复询问。

工具不可用时说明缺失的能力、影响和未验证范围，继续需求、内容、平台约束等独立工作；不静默退回整页生图并宣称已完成 Figma 设计。本规范的本地校验器核对冻结事实，不凭本地 JSON 假装实时连接远端。

第 4 阶段及 V2 使用控制器登记设计外部写入时，核对 `external-write` 的具体目标、动作和已获授权范围；宿主已有明确授权按其实际范围继续。

## 方向探索与选定

第 4 阶段默认先分析、用 imagegen 生成代表页效果图、由用户选定并忠实重建可编辑 Figma，作为共同视觉基线。V2 基于基线补齐本模块页面、显示层及全部适用状态和进度，按状态、尺寸、语言和文字倍率核对模块覆盖，并由用户确认。用户明确要求比较多个方向时按其数量制作。

设计分析形成已有 brief／交付任务书：目标用户、主要任务、真实内容、关键状态 `keyStates`、平台和输入约束 `platformConstraints`；按[共同设计依据](../../app-asset-workflow/references/interface-intent.md#design-basis)形成有理由的层级、可读性及一致性方向，分清业务硬约束、视觉方向与探索空间。实际发送的提示词执行[实机运行画面约束](../../app-asset-workflow/references/style-and-production.md#runtime-view-image)，只呈现目标设备视口内的真实页面状态、内容和可操作界面。布局、字体、配色、比例、组件形态和留白由生成模型探索，代理不先把估计的视觉答案写成硬约束。已确认品牌、真实平台限制和用户明确指定的样式仍须遵守。

按[生图执行分支](../../app-asset-workflow/references/image-generation.md)交付提示词、调用本机 Codex 或使用当前宿主的生图工具，涉及生图时遵守项目的 image_generator 委派规则。保存实际图片、完整实际提示词、生成工具及版本、来源、版本和 SHA-256；使用[视觉来源模板](../../app-workflow-control/templates/app-visual-source.json)冻结。提示词交付或工具失败时等待实际原图，收到后按来源登记。提供原图供用户人工检查；按反馈修订图并保留修前版本、反馈消息与转换关系，再选稿。已有有效、已确认且本轮视觉目标未变化的效果图直接复用，核对实际文件、摘要、范围和原确认，不要求来源先完成 V5，也不继承其工程结果。

用户选择同时绑定具体图片、摘要、`visualSourceRef`、真实消息及任务书。V2 在授权范围内忠实重建并确认模块稿，V3 从确认版本提取规格。源图确认与重建预览的人工检查分别记录；模块稿变化在 V2 修订确认，全局方向变化回第 4 阶段。

需要比较时，为每个方向明确可探索的轮廓、比例、材质纹理、明暗边缘、功能色、UI 图标语言及可实现路线，保留模型对具体视觉表现的探索空间；不要提前冻结未经选稿的尺寸、字体或布局。比较条件相同不要求共享造型；各候选实际提示词完整独立，不以共同造型段落加一句风格名代替区别。生成后从真实候选提炼视觉语言。将“弱化配色、隐藏候选名称后，是否仍能辨认各方向”作为人工比较问题；机器仅拦截可确定的重复产物，不用局部布局／字体签名断言候选只是换色。提示词、节点或工具成功不证明实际差异成立。

建立与当前产品和受众相适应的字体层级、空间节奏、色彩和组件语言，按实际需要复用或建立变量并绑定真实消费属性；简单稿允许不声明变量，不固定通用配色或字体。前置考虑关键组件、最长文案、空／错误／加载状态，以及目标平台字体和设备硬件边界。送审前做一轮有界自查，检查真实节点结构、属性、变量绑定和可测布局事实并修复实际问题；截图和预览默认由用户人工检查，不自动看图、不循环自动审美审查，也不增加独立审批或强制报告。

选稿前展示真实效果图和简短取舍说明。用户明确组合候选时，先形成实际组合效果图并绑定其选择，不能只记录一段组合说明。选稿后按图忠实重建文字、布局、组件和矢量图标；插画保留为独立素材。整页效果图只供参考，不能作为背景冒充可编辑界面。通过真实节点核对内容、层级、尺寸、字体、变量、素材来源和触控容器。交付实际节点链接及重建预览，说明结构校验结果与尚未人工检查的画面，不将结构完成记为视觉通过。

重建记录明确执行方式：Figma 内置 Agent 自主设计与 `use_figma` Plugin API 执行脚本是不同能力，分别记录真实 method、toolName 及源图到节点的转换依据，不混称或伪造工具记录。零尺寸 SVG／空路径等问题按节点类型定位并定向修复，不反复重建整页。Figma LINE 的本地高度为零是合法几何，保留真实长度、旋转及描边，不能改成假矩形；绘制边界与本地尺寸分别交接，非 LINE 的无效零尺寸不因此放行。

Expo／ESP32 的直线原生布局使用正尺寸绘制容器，复用 [extractFigmaLineLayout](../../app-workflow-control/scripts/runtime/figma-native-facts.mjs) 从真实线条及已映射父节点计算边界与 `origin`。绘制器按 `origin` 将源局部端点放入容器，源样式仍保留零高度、旋转和线宽；ESP32 只对容器向外作整数像素包络，不能把容器高度当作描边厚度。原生计划与布局规格可分别冻结，不要求合并文件；沿用既有映射交接，不另建附件或批准。

已有有效确认稿的局部增量直接引用其适用范围；目标、状态或适配变化时在 V2 修订并确认模块稿。全局方向变化回第 4 阶段。当前原生还原及 V5 正式组合仍须验证。

弹窗与 Toast 遵循[弹窗公共设计方案](../../app-domain-toolkit/references/reference-domain-display-ownership.md#弹窗公共设计方案)。第 4 阶段确认全局视觉基线和公共风格，V2 生成并确认模块适用状态与进度稿，V3 从该确认稿交接。

## 沿用唯一控制器

继续使用 app-workflow-control 的七阶段、全局状态与 V1–V5，不新增设计状态机。

| 阶段 | 非游戏 App 的交付与边界 |
| --- | --- |
| 第 4 阶段 | 依据产品规格生成人工确认的代表稿和全局视觉规范并冻结 |
| 开工准备 | 本批范围、业务目标、硬约束、可探索空间、代表页面及真实内容 |
| V1 | 确认完整模块方案，包括范围、全部适用状态和进度、规则、依赖及验收 |
| V2 | 基于全局方向生成并确认模块全部适用流程、状态和进度稿，固定具体版本 |
| V3 | 从 V2 已确认稿直接提取组件边界、真实布局、字体、变量、图标素材、状态及适配 |
| V4 | 在已验证工程上先试接代表组件和独立素材，再分批扩展；保留状态所有权及生命周期 |
| V5 | 当前完整运行组合、功能回归及用户人工视觉验收 |

Flutter、Expo 由控制器默认设置 figma-app 设计路线。ESP32 可使用 `--design-route figma-app`。正式实现以已确认的 V1 模块方案进入 V2；仅设计提案按委托范围完成设计交付。

同一选定 Figma 稿已经清楚表达结构和布局时，V3 直接使用节点与提取数据，不强制另绘低保真草图、拆解图、布局图或再次人工批准。交接补充不是第二次设计批准；只有实质改变所选目标或交互方案才重新确认。V4 实际资源和 V5 运行组合仍需各自当前证据，不由设计批准替代。

## 冻结来源与机器合同

公共 [Figma Schema](../../app-workflow-control/schemas/figma-app-design.schema.json)与控制器语义校验共同约束本地证据。模板在 [控制器 templates](../../app-workflow-control/templates/)。实际图、重建预览和结构导出各自在产生时冻结新版本及 SHA-256，历史确认不改写。远端编辑后重采集实际节点并核对源图与任务书；忠实修复更新载体引用、保留有效原图确认，视觉目标、内容或交互实变才重新确认。新版本不代表用户看过重建预览或当前运行已通过。

领域封套的 `referenceTarget:{path,sha256}` 指向真实 Figma 预览冻结，`figmaDesignRef:{path,sha256}` 指向可编辑设计快照；位图不再是唯一设计来源。快照记录 projectId、stack、objectId、candidateId、实际 fileKey、nodeId、nodeUrl、stateId、viewport、language、textScale、previewRef、briefRef、captureRef、nodes、variables、assets。节点包括真实父子、尺寸、排布、文字、字体和消费属性；变量通过节点 bindings 关联实际值，独立图片关联实际素材范围。

`captureRef` 是真实 MCP 结构采集的原始结果或可追溯规范化导出，记录实际 toolName、capturedAt、fileKey、nodeId、stateId、viewport、nodes、variables、assets；控制器逐项核对快照与原始结构。`briefRef` 关联任务书。图片路线的快照通过 `reconstruction` 绑定已确认的 `sourceTargetRef`、忠实还原 `authorizationRef`、真实 method 与 toolName；`previewRef` 单独冻结重建导出，不能与原图共用同一文件身份。独立导出可以恰好同字节，不能仅凭摘要相同否定合法还原，也不能将原图文件冒充新预览。

全局基线使用 `designRoute:"figma-app"`、`exploration.kind`（initial／redesign／increment）和 candidates。初始／改版默认一张，用户明确要求比较时记录 requestedCount 和真实 userMessageRef；局部增量复用有效来源。图片候选以 `visualSourceRef` 冻结实际图及生成／提供来源，默认 generated 的 `generationMethod:imagegen`；用户指定其他生成方式时用 custom 并绑定 `sourceMessageRef/sourceScope`，用户提供图片同样保留来源消息。选稿后只需重建选中目标，不要求未选图先有 Figma。显式 `sourceRoute` 记录其他设计路线的真实指令及范围，不能用它绕过原图默认门。游戏仍保留原三候选。

第 4 阶段记录全局代表稿的来源及真实确认。V2 对模块稿分别绑定原图、来源、用户确认和重建授权，并记录实际可编辑设计版本。多状态原图以 `approvedTargetRefs` 和 `approvedVisualSourceRefs` 记录实际确认范围。V3 `figmaHandoffRef` 从 V2 确认稿提取 figmaDesignRef、layoutSpecRef、nativePlanRef 及节点／状态／视口映射，显示层另绑定 hostId 和 layerType。

V4/V5 确认关联相同 figmaDesignRef，并继续消费实际原生产物和运行材料。平台无法表达时明确限制、替代方案及受影响范围，不静默降低目标。发现上游缺失或偏离时 RETURN 到最早受影响阶段，作废对应下游引用并保留历史。

交接同时保留原始设计属性与有明确单位的规范化值，包括逐角圆角、字体、行高、字间距、渐变、透明度、图片填充和边框。混合圆角不得归零或编码进 `shape.kind`。视觉轮廓与触控容器分别映射，例如 44 高视觉框置于真实 48 高命中容器，不能伪造视觉尺寸。各栈计划与提取事实逐属性核对，平台差异引用明确决定及原因；计划值不冒充运行观测，实际源码、构建、运行及最终人工验收继续独立完成。

ESP32 快照另记录 `hardware`：实际 boardProfileRef、分辨率、colorFormat、inputMethods、fonts 和 resourceBudget；与设备资料中的色深、输入、字体及 Flash/RAM/可用 PSRAM 一致。Figma 画布、移动设备字体和桌面鼠标不能覆盖这些限制，设备运行仍须明确授权。

## 验证与人工边界

自动核对实际节点、尺寸、字体可用性、变量绑定、素材范围和可测布局事实；按[有界复核](../../app-asset-workflow/references/interface-intent.md#bounded-review)结合真实状态推演主要任务与一个适用高压或异常情境，不把结构数量或测试通过登记为视觉质量。设计稿截图、预览以及运行截图默认由用户检查，未经明确授权不得自动分析截图或代写视觉 PASS。“用户视角审查”同样遵守此限制，可依据真实文案、节点和约束检查结构事实，不能借审查名义自动看图。

分别报告结构完成、工程验证、人工视觉结论。验证本工作流使用本地样例或测试替身，不实际创建外部设计、不付费生图、不运行真机。远端连接、实际 MCP 执行与内容真实性、实际平台字体显示、运行还原质量仍需在获得相应授权的真实任务中验证。
