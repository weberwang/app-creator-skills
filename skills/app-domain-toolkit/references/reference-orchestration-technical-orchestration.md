# 三栈专业编排与交付

执行公共规则时，同时读取当前技术栈参考中的原生补充和“本栈配套资料”。各段仅适用于标注的技术栈；结构化证据不代替用户对显示效果的人工验收。

各技术栈统一使用 V0–V5；V1 是功能实现与验证，白盒可选，正式功能不必等待视觉目标。

## 最短流程

> 适用技术栈：cocos、phaser、threejs。

项目视图依次包括需求与范围、全局基线、基础工程、逐场景生产、全局集成验证及发布；单场景依次处理场景定义、拆解与布局确认、正式资源验收及正式还原与运行验收。视觉阶段通过 `visual.stage` 记录，适用门禁和证据以当前 Work Item 为准。

> 适用技术栈：cocos、phaser、threejs。

读取 Work Item、当前任务说明、当前基线和适用状态门；需要字段时按需读取 [游戏生产里程碑](./reference-orchestration-quality-gates.md)、“module-decomposition.md”（见本栈配套资料）、“game-implementation.md”（见本栈配套资料）、“delivery-artifacts.md”（见本栈配套资料） 等 reference。

> 适用技术栈：cocos、phaser、threejs。

2. 先提交最小领域提议和验收边界，完成审查后由控制面运行 `check`；已有入口、调用链、任务范围和风险事实足够时停止探索。

> 适用技术栈：cocos、phaser、threejs。

3. 实施前按当前 Work Item 和任务需要冻结绑定任务范围、基线、文件所有权、执行单元、验收命令和停止条件的实施包；实施后记录实际变更并关联当前候选验证证据。

> 适用技术栈：cocos、phaser、threejs。

4. 领域交付只在当前任务路径内进行；方案、路径或资源清单变化时更新计划并重验受影响部分，需求或范围真实变化时更新 Work Item。按实际完成情况判断，不因中途调整追补无关历史修订；最终使用公共控制器的 `run`/`check` 核对和推进状态。

> 适用技术栈：cocos、phaser、threejs。

5. 仅当用户明确要求 Git 提交时，按[最小提交规则](./git-minimal-submission.md)核对本任务运行、构建及有效引用的必要文件和实际产物，并记录提交结果；并行任务由主代理统一收尾，子代理不各自提交共享工作区。

## 交付边界

> 适用技术栈：cocos、phaser、threejs。

- 制作、架构、玩法、视觉、资源、音频、数值、QA、性能和发布工作均只能提议、审查或在当前任务内修改。

> 适用技术栈：cocos、phaser、threejs。

- 无外部副作用的本地任务按当前用户授权范围执行；外部写入、付费、真机、破坏性或外部删除及发布等受保护动作，在当前 Work Item 中核对具体目标与用户明确批准。本领域不擅自执行这些动作。

> 适用技术栈：cocos、phaser、threejs。

- V0→V1→V2→V3→V4→V5、全局静态基线、场景拆解与布局确认和高保真前置继续使用控制面的不可绕过证据门；领域文档只补充本领域事实。

> 适用技术栈：cocos、phaser、threejs。

- 不覆盖并行代理的修改，不自动回滚共享工作区；启动本地验证服务前先按[本地服务验证规则](./reference-orchestration-local-service-validation.md)查找可复用健康实例。Cocos 任务另需按本栈配套资料核对 Creator 预览说明。

## 状态与返工

> 适用技术栈：cocos、phaser、threejs。

本领域不直接迁移全局状态。证据失败优先原地 `repair`，上游事实未变时 `revalidate`，只有上游事实失效、任务范围真实变化或硬门将被绕过时才按最小范围 `return`；普通候选身份变化不触发回退，已确认事实不重复搜索或推翻。
