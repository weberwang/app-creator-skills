# 关卡内容生产与试玩调参

适用于 Unity、Cocos、Phaser、Three.js、Roblox 中实际涉及关卡、内容批次或游戏体验调整的任务。复用现有 GDD、TDD/实施计划、数值配置与 QA 记录；无关卡的配置驱动内容同样按实际内容使用生产与检查规则，只有不涉及内容生产的体验调整可仅使用试玩部分，局部修复只处理受影响范围。沿用六阶段、V0–V5、控制器和既有人工视觉确认，不增加审批、状态字段、必填文档或固定试玩次数。

<a id="levels"></a>

## 关卡与内容生产

从零复杂游戏或本批实质改变空间、路线、镜头关系时，先按[关卡与场景方案探索](game-design-exploration.md)交接结构草案与内容需求，概念图可选；按风险选择原型深度，并在实际世界场景中完成对应的正式工程空间及 V1 验证。二维动作或跳跃存在镜头、物理或手感风险时可用二维可玩占位验证，不以是否为 3D 决定原型深度。本批整体空间单次审查并获人工确认后，才进入相应正式资源生产；小修或无相关空间设计时复用有效方案，仅处理受影响范围。

1. 从已确认体验与实际机制确定本批内容目标：玩家需要理解或运用什么、进入条件、完成/失败条件、允许路径与重试成本。复用已有功能和关卡数据；一关不自动等于一个引擎场景或独立 Work Item，多个关卡可以由同一个正式场景加载不同数据。
   按[稳定机制与内容装配](../../app-creator-workflow/references/readable-functional-prototype.md#mechanism-content-assembly)选择实现方式：配置确定的关卡先复用或实现本批必要的实体组件、操作与判定机制，再由正式关卡数据提供对象、初始排列、条件和目标，经同一入口装配与运行；确定性配置不要求随机生成器。V3 交接表现资源、模板的制作与装配规格，后续按本栈生产／装配阶段接入已有机制，代表稿不成为逐关复制的固定节点树。手工关卡或固定空间保留其正式制作布局，混合关卡分别消费固定结构与可变配置，只补本批必要实现。
   选择能够体现本批真实信息量、操作压力、内容分布及关键机制使用情境的代表关卡、战斗、经营阶段或回合，作为体验与设计依据；专门覆盖异常或极端情况的边界测试夹具用于验证相应规则。两者可共享数据，但须说明各自用途与覆盖范围，不能互相冒充；新增体验风险时再补受影响关卡或状态。
2. 在 GDD 的现有内容清单记录关卡/波次/谜题/任务标识、依赖机制、教学或挑战意图、规则与数据来源，以及检查点/保存恢复的适用策略。按游戏需要采用介绍、练习、变式和组合挑战：适用时先提供低压力尝试，再观察玩家能否独立运用，随后增加干扰或组合；不以展示完教程代替掌握机制。不强制线性教学、持续变难或每关引入新机制，分支叙事、自由探索和经营周期按其目标组织。
   涉及成长或闯关时，在现有规则与交接中提前明确本批相关机制解决的玩家问题、出现或解锁条件、入口及主要状态，以及对当前布局、关卡和验证的影响；未实现机制标为提案，静态稿不能证明行为已完成。只细化本批所需内容，不要求提前完成全部关卡、道具数值、商业化或长期成长系统。
3. 明确难度来源，区分操作精度、信息量、解题步骤、资源压力、时间限制和失败损失。只改变有依据的维度，并说明与相邻内容的关系；成功率、通关时长等未定义目标时保留观测，不自造统一阈值。没有证据的难度分层标为设计假设。

   同时按体验目标安排紧张与恢复、重复与变化、获得与使用机会，检查等待、赶路、操作及重试的连续负担。节奏可由路线、停留节点、信息量或任务变化承担，不统一要求战斗或奖励，也不强制所有游戏采用同一张弛曲线。范围与扩建复用已有本批边界；空间内容按[空间秩序](game-design-exploration.md#spatial-order)预留有依据的连接条件，不提前制作尚未纳入范围的系统或全部关卡。
4. 在 TDD 确定可编辑数据/场景入口、运行消费者、必要引用和检查方式。引擎编辑器中的可配置内容遵守既有编辑器优先规则；不要建立一份与正式关卡不一致的验证地图。手工与程序生成内容都应能定位到版本、配置及实际消费的数据。
   首次建立或改变配置消费链路时，在任务允许修改的范围内，选择数量、类别、排列或规则参数等实际驱动项，只改变其正式配置、不改消费实现，保持相关输入及适用的种子等条件一致，经正式加载与创建入口核对预期运行变化，防止硬编码结果恰好与样例一致。按项目实际生效时机检查重新加载或重新进入，不强制热更新；在原验证记录关联配置来源／版本、实际条件及预期与实际结果。已有有效证据可复用，无需新增永久测试配置；临时验证值在检查后恢复为约定交付值，并核对最终交付配置的运行结果。未实际运行时保留未验证，配置存在或静态引用不证明生效。
5. 按下表对当前内容做最小检查，在 V1 验证实际机制；3D 按上述白模路径，其他内容按风险选择额外原型，可引用仍有效的证据。V2–V4 按内容分流交接模型或二维资源并试接代表模块，V5 检查正式替换是否改变视线、通行、碰撞、交互或线索可读性。最终集成验证本批内容的进入、完成/失败、重试及适用的跨关状态传递。
   本批已声明类别与必要状态的可用性、代表组合的体验与压力分别核对。复用现有内容／资源清单及有效证据，对新增或受影响类别通过正式配置读取、实体创建与行为分派入口定向验证构造、资源／状态绑定和对应关键规则或交互；存在销毁、重建或对象池时覆盖适用的清理与重用。可用现有测试驱动真实入口并断言结果，不用另写测试专用分派或假生成器代替；低概率类别也须定向覆盖，不能靠随机抽到或代表样例通过外推。未变化且已有有效覆盖的类别不重复运行，组合、密度与随机局面仍按风险取代表样本，不要求全部类别同时出场、逐类制作完整关卡或穷举全部状态组合；新增工具继续按下文工具规则选择，视觉结论仍交用户人工检查。

| 内容特点 | 必要的规则/数据检查 | 运行与人工检查的边界 |
| --- | --- | --- |
| 网格、路径、平台或探索关卡 | 入口/目标/出口及引用存在，通行、钥匙/开关等条件可满足；生成内容保留种子与配置 | 图可达不等于角色具备通过所需的跳跃/交互能力；V1 验证实际运动和规则，正式画面的方向感交用户检查 |
| 谜题、消除或分支任务 | 合法起始状态、已知解/目标路径、死局与终止策略；撤销/重排仅在已有机制中检查 | 求解器只能证明建模规则下的结论；有限样本不能证明全部随机局面可解，线索和理解成本仍需试玩 |
| 波次、敌人或策略内容 | 单位/配置引用、出生与波次条件、路径/目标、资源可达性和预算 | 静态总量正确不代表重叠波次或实际索敌正确；运行代表性高负载与失败恢复，难度和节奏由实际体验判断 |
| 检查点、重试及跨关进程 | 保存点、复位范围、扣费/奖励/解锁、一次性事件与库存一致性 | 用实际退出/恢复/重开流程检查，避免重复奖励、软锁或丢失必要道具；重试成本的体验不能由存档解析证明 |

发现内容无法完成、引用断裂、规则软锁或越界时按缺陷修复，不以调低难度目标或修改验收隐藏。需要改变已确认机制、奖励或失败成本时，按既有实质取舍流程处理；局部数据修复不引入额外审批。

## 人工试玩与调参闭环

创意与核心循环方案形成时，已按[玩家视角方案审查](game-characteristics.md#player-review)在实现前推演体验并整理关键假设。实际试玩承接其中需要真实参与者观察的问题，结合当前可运行版本继续验证与调整。

运行实例、操作、证据采集与本次会话清理按[运行验证与试玩执行](../../app-quality-review/references/runtime-validation.md)处理；本节继续负责真实参与者的体验观察和调整，不因工具采集成功代替人工判断。

玩法与数值负责验证规则和参数，QA 整理复现与观察，用户或实际参与者体验操作、节奏、理解成本与显示效果。没有真实试玩材料时可以准备任务和记录位置，结论保留未验证；不虚构玩家、样本、反馈或满意度，也不把代理纸面演练当作玩家试玩。

按[设计依据与问题形成](game-characteristics.md#design-method)及[类型体验验证](game-characteristics.md#type-experience)，从本批风险选择需要观察的任务。书籍或作者经验只帮助提出假设，不能替代本游戏规则和玩家证据；适用问题并入下面同一次试玩与复验，不额外安排逐类型审查。

1. **确定本次问题和条件。** 从现有体验目标提出可观察问题，例如“新玩家能否独立找到出口”或“重复失败后的重试是否过长”，说明预期行为及什么观察会使假设存疑；不要只问“是否好玩”或从作者偏好倒推答案。记录候选/内容/参数版本、输入和平台、起始状态、任务及需控制的种子/难度；参与者经验与已接受的提示按实际需要记录。首次接触和熟练后的任务按问题选择，复测时区分学习效应，不把提示后成功合并为首次独立理解。不为一次内部检查自动招募用户、开展商业实验或添加遥测 SDK。
2. **保留原始观察。** 在既定任务说明及参与者所需支持下，先观察玩家自行理解和行动，避免边操作边解释预期答案；记录停顿、走错、反复误操作或放弃等行为，再询问其当时的理解。必要提示按实际需要提供并记录时机与内容，不将提示后完成视为独立理解。在现有 QA 材料记录尝试次数、完成/失败、耗时和提示等实际适用数据，并保留原话或运行轨迹。将“连续三次走错路”“参与者说难找”“推测对比不足”分开，说明观察者是否给予提示。截图和录屏可以采集并附检查点，显示、可读性及视觉结论由用户人工检查；未经明确要求不自动分析。
3. **定位问题来源。** 区分规则缺陷、内容设计、输入/时序、表现可读性、性能与数值因素。先用日志、参数和可复现操作确认工程事实，推测仍标假设；不将一次失败或单人偏好推断为普遍结论。将类型问题落到具体情境，例如谜题是规则误解还是目标难辨、卡牌是单项不懂还是组合难追踪、经营是计划中的资源取舍还是非预期软锁，再确定要调整哪个来源。实际结果与预先定义的目标比较；无目标、样本不足或条件不同则说明局限。
4. **形成有界调整。** 每项候选说明观察依据、调整假设、参数/内容差异、预期影响、副作用及回退条件；优先单因素，确需多项联动时记录因果无法独立归因的限制。数值复用[参数与模型规范](balance.md)，不借助镜头/特效掩盖规则或输入问题；未授权改变的规则继续保持。
5. **同条件复验并收敛。** 保留旧候选与证据，在尽量相同的内容、输入、种子、初始进程及任务下复验，必要时标明学习效应和样本差异。按[变更回归清单](game-characteristics.md#regression)检查受影响规则及完整周期，分开记录工程结果和人工反馈。使用既有目标/风险判定改善、无可辨收益、退化或未验证；达到本次目标或证据不足以继续调整时停止，记录剩余问题，不无限润色或反复要求用户确认无关内容。

试玩记录可直接复用现有 QA 表格中的版本/条件/任务、客观观察与原始证据、体验反馈、调整假设/配置版本、复验及未确认项。没有新调整时只记录观察与结论；不强制建立 A/B 平台或独立试玩报告，也不把参数合法、模拟通过和构建成功写成“好玩”或“平衡已通过”。真机、外部服务、发布等仍遵守既有授权边界。

## 专项检查方法与工具选择

先复用实际项目的引擎校验、单测、数据工具与日志；确有重复执行或覆盖缺口时再补最小脚本。选型沿用[官方优先的技术方案约定](../../app-creator-workflow/references/professional-conventions.md#solution-selection)，以实际版本核实能力。下面规定需要什么输入与结果，不提供脱离项目规则的通用求解器、模拟器或网络框架。

| 需求 | 最小输入和可复用方法 | 输出与证明范围 |
| --- | --- | --- |
| 可达性/死局 | 正式关卡数据、运动/交互规则与目标；复用项目路径查询、已知解回放或适用求解器 | 失败关卡、路径/解或反例；说明抽样/搜索范围，图搜索未建模的动作不能视为已验证 |
| 随机生成 | 生成器版本、种子集合、随机状态/调用条件和约束；复用固定种子回放、批量不变量检查 | 可重放失败种子、样本规模及失败分布；同种子跨算法不承诺同结果，抽样不是全局证明 |
| 卡牌/策略结算 | 权威状态、输入、费用与效果顺序；复用规则单测和事件轨迹 | 结算前后状态、触发链与终止检查；不以动画轨迹代替规则，也不自动穷举全部卡组 |
| 长周期经济/时间 | 集中参数、产消公式、初始进程与时间权威；复用可控时钟、周期计算和极端情景 | 上限、可达性、重复领取/回拨反例及实际回读；模型不代表真实玩家行为或操作系统生命周期 |
| 联机消息/重连 | 现有协议、操作身份、权威及恢复规则；复用本地传输注入和日志对照 | 延迟/乱序/重复/断线条件下的本地结果和待对接缺口；无真实服务不能报告端到端通过 |

新增工具的输入必须来自正式消费者或明确记录的测试替身，至少用一个有效样例和一个可触发的已知错误检查工具是否确实执行规则；保留命令、版本、退出结果及反例。未实现、未运行和不适用分别说明，不以文件存在、演示动画或声明 PASS 代替检查。工具与试玩结果继续写入当前实施计划和 QA 证据，无需新审批或控制器字段。
