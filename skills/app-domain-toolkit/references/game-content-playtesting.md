# 关卡内容生产与试玩调参

适用于 Unity、Cocos、Phaser、Three.js、Roblox 中实际涉及关卡、内容批次或游戏体验调整的任务。复用现有 GDD、TDD/实施计划、数值配置与 QA 记录；没有关卡的游戏可仅使用试玩部分，局部修复只处理受影响范围。沿用六阶段、V0–V5、控制器和既有人工视觉确认，不增加审批、状态字段、必填文档或固定试玩次数。

<a id="levels"></a>

## 关卡与内容生产

1. 从已确认体验与实际机制确定本批内容目标：玩家需要理解或运用什么、进入条件、完成/失败条件、允许路径与重试成本。复用已有功能和关卡数据；一关不自动等于一个引擎场景或独立 Work Item，多个关卡可以由同一个正式场景加载不同数据。
2. 在 GDD 的现有内容清单记录关卡/波次/谜题/任务标识、依赖机制、教学或挑战意图、规则与数据来源，以及检查点/保存恢复的适用策略。按游戏需要采用介绍、练习、变式和组合挑战；不强制线性教学、持续变难或每关引入新机制。分支叙事、自由探索和经营周期按其目标组织。
3. 明确难度来源，区分操作精度、信息量、解题步骤、资源压力、时间限制和失败损失。只改变有依据的维度，并说明与相邻内容的关系；成功率、通关时长等未定义目标时保留观测，不自造统一阈值。没有证据的难度分层标为设计假设。
4. 在 TDD 确定可编辑数据/场景入口、运行消费者、必要引用和检查方式。引擎编辑器中的可配置内容遵守既有编辑器优先规则；不要建立一份与正式关卡不一致的验证地图。手工与程序生成内容都应能定位到版本、配置及实际消费的数据。
5. 按下表对当前内容做最小检查，在 V1 验证实际机制；可引用仍有效的机制证据，白盒可选。V2–V4 依原流程设计和制作适用的正式表现，V5 检查正式资源是否改变视线、通行、碰撞、交互或线索可读性。最终集成验证本批内容的进入、完成/失败、重试及适用的跨关状态传递。

| 内容特点 | 必要的规则/数据检查 | 运行与人工检查的边界 |
| --- | --- | --- |
| 网格、路径、平台或探索关卡 | 入口/目标/出口及引用存在，通行、钥匙/开关等条件可满足；生成内容保留种子与配置 | 图可达不等于角色具备通过所需的跳跃/交互能力；V1 验证实际运动和规则，正式画面的方向感交用户检查 |
| 谜题、消除或分支任务 | 合法起始状态、已知解/目标路径、死局与终止策略；撤销/重排仅在已有机制中检查 | 求解器只能证明建模规则下的结论；有限样本不能证明全部随机局面可解，线索和理解成本仍需试玩 |
| 波次、敌人或策略内容 | 单位/配置引用、出生与波次条件、路径/目标、资源可达性和预算 | 静态总量正确不代表重叠波次或实际索敌正确；运行代表性高负载与失败恢复，难度和节奏由实际体验判断 |
| 检查点、重试及跨关进程 | 保存点、复位范围、扣费/奖励/解锁、一次性事件与库存一致性 | 用实际退出/恢复/重开流程检查，避免重复奖励、软锁或丢失必要道具；重试成本的体验不能由存档解析证明 |

发现内容无法完成、引用断裂、规则软锁或越界时按缺陷修复，不以调低难度目标或修改验收隐藏。需要改变已确认机制、奖励或失败成本时，按既有实质取舍流程处理；局部数据修复不引入额外审批。

## 人工试玩与调参闭环

创意与核心循环方案形成时，已按[玩家视角方案审查](game-characteristics.md#player-review)在实现前推演体验并整理关键假设。实际试玩承接其中需要真实参与者观察的问题，结合当前可运行版本继续验证与调整。

运行实例、操作、证据采集与本次会话清理按[运行验证与试玩执行](../../app-quality-review/references/runtime-validation.md)处理；本节继续负责真实参与者的体验观察和调整，不因工具采集成功代替人工判断。

玩法与数值负责验证规则和参数，QA 整理复现与观察，用户或实际参与者体验操作、节奏、理解成本与显示效果。没有真实试玩材料时可以准备任务和记录位置，结论保留未验证；不虚构玩家、样本、反馈或满意度，也不把代理纸面演练当作玩家试玩。

1. **确定本次问题和条件。** 从现有体验目标提出可观察问题，例如“新玩家能否独立找到出口”或“重复失败后的重试是否过长”。记录候选/内容/参数版本、输入和平台、起始状态、任务及需控制的种子/难度；参与者经验与已接受的提示按实际需要记录。不为一次内部检查自动招募用户、开展商业实验或添加遥测 SDK。
2. **保留原始观察。** 在现有 QA 材料记录尝试次数、完成/失败、耗时和提示等实际适用数据，并保留原话或运行轨迹。将“连续三次走错路”“参与者说难找”“推测对比不足”分开，说明观察者是否给予提示。截图和录屏可以采集并附检查点，显示、可读性及视觉结论由用户人工检查；未经明确要求不自动分析。
3. **定位问题来源。** 区分规则缺陷、内容设计、输入/时序、表现可读性、性能与数值因素。先用日志、参数和可复现操作确认工程事实，推测仍标假设；不将一次失败或单人偏好推断为普遍结论。实际结果与预先定义的目标比较；无目标、样本不足或条件不同则说明局限。
4. **形成有界调整。** 每项候选说明观察依据、调整假设、参数/内容差异、预期影响、副作用及回退条件；优先单因素，确需多项联动时记录因果无法独立归因的限制。数值复用[参数与模型规范](balance.md)，不借助镜头/特效掩盖规则或输入问题；未授权改变的规则继续保持。
5. **同条件复验并收敛。** 保留旧候选与证据，在尽量相同的内容、输入、种子、初始进程及任务下复验，必要时标明学习效应和样本差异。按[变更回归清单](game-characteristics.md#regression)检查受影响规则及完整周期，分开记录工程结果和人工反馈。使用既有目标/风险判定改善、无可辨收益、退化或未验证；达到本次目标或证据不足以继续调整时停止，记录剩余问题，不无限润色或反复要求用户确认无关内容。

试玩记录可直接复用现有 QA 表格中的版本/条件/任务、客观观察与原始证据、体验反馈、调整假设/配置版本、复验及未确认项。没有新调整时只记录观察与结论；不强制建立 A/B 平台或独立试玩报告，也不把参数合法、模拟通过和构建成功写成“好玩”或“平衡已通过”。真机、外部服务、发布等仍遵守既有授权边界。

## 专项检查方法与工具选择

先复用实际项目的引擎校验、单测、数据工具与日志；确有重复执行或覆盖缺口时再补最小脚本。选型沿用[官方优先的技术方案约定](../../app-creator-workflow/references/professional-conventions.md#solution-selection)，以实际版本核实能力。下面规定需要什么输入与结果，不提供脱离项目规则的通用求解器、模拟器或网络框架。

| 需求 | 最小输入和可复用方法 | 输出与证明范围 |
| --- | --- | --- |
| 可达性/死局 | 正式关卡数据、运动/交互规则与目标；复用项目路径查询、已知解回放或适用求解器 | 失败关卡、路径/解或反例；说明抽样/搜索范围，图搜索未建模的动作不能视为已验证 |
| 随机生成 | 生成器版本、种子集合、随机状态/调用条件和约束；复用固定种子回放、批量不变量检查 | 可重放失败种子、样本规模及失败分布；同种子跨算法不承诺同结果，抽样不是全局证明 |
| 卡牌/策略结算 | 权威状态、输入、费用与效果顺序；复用规则单测和事件轨迹 | 结算前后状态、触发链与终止检查；不以动画轨迹代替规则，也不自动穷举全部卡组 |
| 长周期经济/时间 | 集中参数、产消公式、初始进程与时间权威；复用可控时钟、周期计算和极端情景 | 上限、可达性、重复领取/回拨反例及实际回读；模型不代表真实玩家行为或操作系统生命周期 |
| 联机消息/重连 | 现有协议、操作身份、权威及恢复规则；复用本地传输注入和日志对照 | 延迟/乱序/重复/断线条件下的本地结果和待对接缺口；无真实服务不能报告端到端通过 |

新增工具的输入必须来自正式消费者或明确记录的测试替身，至少用一个有效样例和一个可触发的已知错误检查工具是否确实执行规则；保留命令、版本、退出结果及反例。未实现、未运行和不适用分别说明，不以文件存在、演示动画或声明 PASS 代替检查。工具与试玩结果继续写入当前实施计划和 QA 证据，无需新审批或控制器字段。
