# 模块拆分与交接

执行公共规则时，同时读取当前技术栈参考中的原生补充和“本栈配套资料”。各段仅适用于标注的技术栈；结构化证据不代替用户对显示效果的人工验收。

各技术栈统一使用 V0–V5；V1 是功能实现与验证，白盒可选，正式功能不必等待视觉目标。

## 模块划分、审计与决策边界

> 适用技术栈：cocos、phaser、threejs。

新建模块、首次实现模块，或改动职责、公开契约、状态所有权、依赖方向、持久化或平台边界时读取本文件。模块划分不是按文件夹或类名分组，而是冻结可独立说明、实现、测试和替换的职责边界。

## 划分模块

> 适用技术栈：cocos、phaser、threejs。

1. 从已批准 GDD、TDD 和代码事实提取玩家行为、状态变化、平台能力、资源依赖、失败路径和验收证据；优先扩展边界清晰的现有模块。

> 适用技术栈：cocos、phaser、threejs。

2. 建立候选模块图，记录职责与非目标、公开入口和输入/输出、状态/数据所有权、生命周期、错误与降级、资源/平台依赖、允许/禁止依赖、测试边界和负责人。

> 适用技术栈：cocos、phaser、threejs。

3. 规定单向依赖和调用契约。公共代码和公共正式资源只有被至少两个已确认场景稳定复用，或属于启动运行必需时才提取；消除或明确处理循环依赖、双向状态写入、无边界 `common`/`utils`、公共素材库、全局事件和绕过公开入口的访问。

> 适用技术栈：cocos、phaser、threejs。

5. 把每个模块、场景、共享基础和集成点拆成实施单元，按数组位置记录单元 ID、类型、范围、并行模式/并行组、负责人、互斥写范围、状态所有权、验收命令或证据；同一非空并行组的 PARALLEL 单元必须在数组中连续出现并视为一个顺序阶段，串行单元必须写明原因，禁止只写笼统的“可并行”。

> 适用技术栈：cocos、phaser、threejs。

6. 主动识别安全并行：`SHARED` 契约/入口和 `INTEGRATION` 单元强制串行；`MODULE`、`SCENE`、`DISPLAY_LAYER` 可在依赖满足且写范围与状态所有权互斥时并行。`SCENE` 与 `DISPLAY_LAYER` 必须位于不同 Work Item 和 Implementation Package；后者的 `hostSceneId` 只标识运行上下文。SERIAL 单元的 READY 需要其前面全部单元有当前有效 PASS Unit Result，PARALLEL 单元的 READY 只需要其并行组首项之前全部单元有当前有效 PASS，同组 peer 不互相等待，不得手工自填。

> 适用技术栈：cocos、phaser、threejs。

7. 场景与模块使用同一粒度规则逐个标注。当前共享工作区可依独占所有权并行；不得自动创建 worktree，只有人工明确要求时才按既有规则使用。

## 场景与公共基础边界

> 适用技术栈：cocos、phaser、threejs。

- `SHARED` 定义为项目最小骨架，提供稳定契约和最小 Boot/Preload 生命周期；`MODULE` 可承载共享规则、状态和功能切片。纯工程工作按任务范围、实施包和工程证据推进，不要求先选视觉图。公共 V1 可直接实现并验证场景功能，白盒按需选择；正式视觉资源生产、显示层组合和运行验收分别按公共 V2–V5 的目标、布局、导入及运行门检查。SCENE 与 DISPLAY_LAYER 各自绑定当前对象的确认和证据，不能以其他场景的确认代替。

> 适用技术栈：cocos、phaser、threejs。

- `gameplay` 与 `supporting` 是完整场景覆盖的分类；各场景的实际顺序由计划制定者冻结。每个 `SCENE` 只闭环自身玩法、画面和常驻 HUD；modal/popup 等弹窗由独立 DISPLAY_LAYER Work Item 闭环，不影响场景验收。

> 适用技术栈：cocos、phaser、threejs。

- 场景之间通过公开服务、状态仓库或明确消息契约协作，不直接读取或写入另一 Scene 实例的内部状态。

> 适用技术栈：cocos、phaser、threejs。

- 单场景逻辑和资源归属具体场景；只有满足公共提取条件的内容才能标记为 shared。

## 审计与审核

> 适用技术栈：cocos、phaser、threejs。

模块候选按统一 “审核漏斗”（见本栈配套资料） 执行：F0 范围与流程，F1 规格一致性，F2 架构/QA 领域质量，F3 工程验证；F4 只处理外部写入、付费、真机、破坏性或外部删除、发布等受保护的具体操作。首次模块或边界变化先审计事实，不机械停止或 grilling。

> 适用技术栈：cocos、phaser、threejs。

在生产实现前，先用代码、配置、权威工件和确定性执行关闭事实。若实质范围、风险、验收、依赖或不可逆架构选择阻断候选模块图形成，可在候选前 grilling 并绑定决策 ID/工件版本；已有候选时，候选相关 F4 必须在 F3 后。没有未决用户决定时直接继续。

## 实现与变更

> 适用技术栈：cocos、phaser、threejs。

1. 在 `docs/TDD.md` 记录已确认模块清单、依赖矩阵、候选身份和审核结论；F4 只链接精确集成/发布决定。不得把沉默、功能范围批准或旧候选批准扩张为当前架构或实现决定。

> 适用技术栈：cocos、phaser、threejs。

2. 实现发现边界变化时停止直接受影响范围并更新模块图。只有无法从事实确定且存在实质架构/数据/产品取舍时才 grilling；否则依当前任务继续并重跑受影响门。模块内部、私有实现无需 grilling。

> 适用技术栈：cocos、phaser、threejs。

3. 逐模块验证公开契约、单一状态写入所有者、禁止依赖、错误边界和可复现集成证据。模块只有边界与实现一致、测试通过、下游使用公开入口且无未批准依赖时才可标为“已实现”。
