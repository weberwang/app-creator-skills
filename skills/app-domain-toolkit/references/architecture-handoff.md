# 工程架构与模块交接

本规范是列入迁移清单的技术栈共用的完整规则。每段标明适用栈；执行时同时读取本栈技能的原生约束与“本栈配套资料”，资料路径和具体工具由栈入口维护。公共状态与授权仍由 app-workflow-control 管理。

## 完整流程

### 输入与边界（phaser、threejs）

读取全局 Work Item、模块审计、依赖能力档、服务边界和项目权威工件。按 F0 范围与流程、F1 规格一致性、F2 架构质量、F3 工程验证、F4 集成/发布决策提交结果，不自行改变全局状态。

### 原生平台插件选型（phaser、threejs）

- 实现原生平台功能前先检查项目已采用的插件；满足需求时直接复用。需要新增能力时优先评估 Capacitor 官方插件或能力提供方的官方插件，再评估维护活跃、许可适用且满足需求的社区插件；领域 Skill 已指定插件时遵守该领域合同。

### 原生平台插件选型（phaser、threejs）

- 只有现有插件无法满足明确需求时才补充自建原生插件或直接原生实现；在 TDD 和实施包记录已评估插件、具体能力缺口与最小自建范围，避免重复实现插件已经提供的能力。

### 原生平台插件选型（phaser、threejs）

- 启动主题、Manifest、权限声明等必要宿主配置仍在原生工程维护。沉浸式全屏、系统栏控制和生命周期恢复等运行时能力同样优先使用插件，插件覆盖不了的部分再补最小原生代码；插件优先不降低冷启动首帧和恢复行为的验收要求。

### 执行与交接（phaser、threejs）

在实现前划分并审计模块，记录职责与非目标、公开输入/输出、状态所有权、生命周期、允许/禁止依赖、失败边界、测试和实现顺序；首次模块先完成模块门与 grilling，再按 F0-F4 写入 TDD。全局阶段、视觉硬门和场景前置以“控制模型”（见本栈配套资料）、“状态、阶段与停止门”（见本栈配套资料）及对应 Schema 为准；本领域只补充模块边界。

### 执行与交接（phaser、threejs）

任务内新增模块、拆分职责或调整实现方案时同步更新计划与所有权，定向验证受影响部分。只有目标、对外行为或用户需要决定的实质设计取舍发生变化时才创建 Change Request 并请求决定；只有带副作用的 A4-A6 操作进入 F4 批准门。

### 执行与交接（phaser、threejs）

在 TDD 按需记录核心、移动平台、数据/API、复杂玩法、高级视觉和商业能力档；每项包含启用原因、拒绝的轻量方案、运行时性能与平台风险、验证命令和所有者。涉及服务时记录契约版本、认证授权、幂等/重试/超时、兼容、迁移/回滚、测试、监控与备份恢复；服务端不在范围时只记录外部依赖、所有者和客户端边界。

### 执行与交接（phaser、threejs）

在 TDD 定义本地服务身份、默认模式、主机/端口和健康检查。启动开发或预览服务前检查监听进程、命令行、项目根目录与健康状态；身份一致且健康时直接复用，不得重复启动。
