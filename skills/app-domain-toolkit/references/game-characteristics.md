# 游戏特点识别与专项验证

适用于 Unity、Cocos、Phaser、Three.js、Roblox 游戏的需求、玩法实现与质量审核。类型用于发现风险，实际存在的机制决定检查范围；混合类型组合选用，局部增量只更新受影响部分。普通应用、设备 GUI 和无界面服务器不因共用编排入口承担游戏检查。

沿用当前 GDD/技术设计、Work Item、实施包及证据清单；游戏特点识别本身不单独新增阶段、专用控制器字段、审批或独立登记文件。复杂场景的实际生产范围与覆盖按[分批生产](incremental-production.md)处理。下文表格是现有规格和用例的内容示例，不是机器 Schema；不要向控制器 JSON 添加未声明字段。具体引擎接口和测试命令仍由当前 `app-stack-*` 及实际工程确定。

<a id="identify"></a>

## 游戏特点识别

新游戏在需求与全局基线中识别特点；已有项目先读现有规则、配置和测试，仅补当前功能真实缺失的信息，不为换素材或局部修复重做全游戏分类。

特点识别与[系统模块覆盖](../../app-creator-workflow/references/system-module-coverage.md)共用原始需求和 GDD：由核心循环反向确定必要经济、战斗、成长及支持模块，逐项说明实际适用性；本批实施前补齐规则设计，并将模块关联到执行任务与验收命令。类型分析或文字审查本身不能代替必填 `systemCoverage`，不默认新增所有类型系统。

| 维度 | 从实际规则中确定的内容 |
| --- | --- |
| 核心操作与体验 | 玩家反复执行什么，成功/失败如何发生，一局或一个周期如何结束、重试；类型名称与体验假设分开 |
| 时间与输入 | 实时、回合、节拍或离线累计；输入顺序、动作窗口、暂停与恢复，以及实际使用的时间权威 |
| 空间与内容 | 连续物理、网格、路径或纯规则；镜头/碰撞/可达性约束；手工关卡还是程序生成 |
| 结算与随机 | 效果优先级、连锁终止、随机来源及复现条件；预览、预测与已确认结果的区别 |
| 进程与状态 | 局内/局外成长、资源产消、保存时点、重试损失、撤销或离线收益，仅记录已存在的机制 |
| 权威与平台 | 单机或联网，谁决定状态与结算；目标输入、平台生命周期和资源预算 |

将特点关联到具体规则、受影响功能/对象、主要风险和验收预期；事实引用来源，建议、假设与未决项明确区分。只澄清会影响方向或实现的实质缺口，不要求用户逐项确认维度。某维度未涉及当前任务时可略去；会决定专项选择但尚不清楚的事实保留未决，不能按“不适用”消除。

多个特点冲突时，以已确认的核心操作与规则裁决，例如节奏判定不能被装饰性顿帧改变，联机预测不能提前确认抽牌结果；仍有玩法取舍时按现有决定流程处理，不新设类型审批。

涉及关卡/内容批次或体验调整时，按[关卡内容与试玩调参](game-content-playtesting.md)交接教学/挑战意图、正式数据、最小检查、实际观察和同条件复验；专项工具按当前项目实际规则选用，不预建通用框架。

<a id="player-review"></a>

## 玩家视角的方案审查

游戏创意与核心循环方案形成后、进入相关机制实现和正式视觉制作前，先在需求与全局基线阶段完成本次玩家视角审查。已有项目在核心循环、玩法规则或体验目标变化时审查受影响范围。策划依据目标玩家、游玩情境和当前方案逐步推演体验，QA 从推演中的风险整理验证问题，结论写入现有 GDD 或方案评审记录，沿用 F1/F2。

输入至少包括目标玩家与经验、目标平台及操作方式、预期游玩情境、一句话体验、核心循环、成功与失败、重试和持续游玩动机。依据已有调研与项目事实填写，缺失信息标为假设。沿“首次进入 → 理解目标 → 执行操作 → 获得反馈 → 成功或失败 → 重试或继续”推演一个完整周期，再检查连续重复后的变化。自由探索、叙事或放置游戏按实际体验组织周期。

新游戏或核心循环变化时，先选择能体现预期体验的最小完整循环，明确行动、反馈、结果及再次行动的理由，并将其作为本批 V1 与人工体验观察的重点，再依据结果决定后续内容与系统的扩展。每项实质设计说明希望玩家产生什么行为、能感知什么后果，以及如何观察是否有效；写入原 GDD 的相关规则和验证问题，不新增固定表单。已有项目的局部内容或表现调整复用有效循环，不借此重做全游戏或转为商业 MVP 实验。

设计代表画面前，在现有方案中明确本批核心循环、当前阶段、玩家主要判断、操作压力和相关机制，选用能体现本批真实体验的关卡、战斗、经营阶段或回合；代表内容与边界测试各自表达的范围按[关卡与内容生产](game-content-playtesting.md#levels)交接。结合该情境先确定任务、信息主次与状态关系，再探索美术语言；不能默认最简单的测试样例就是代表画面，也不能仅给功能白模替换材质而沿用测试布局。

| 玩家问题 | 方案阶段检查内容 |
| --- | --- |
| 我为什么想开始？ | 主题、目标和核心动作如何吸引目标玩家，差异点能否通过实际规则被体验到 |
| 我知道接下来做什么吗？ | 玩家当时能获得哪些信息，当前目标、可执行操作及其价值是否清楚，环境与反馈能否支持下一步行动 |
| 我的行动有什么价值？ | 操作、选择、表达或探索如何产生可理解的结果；存在选择时，成本、收益、风险或后续处境是否形成可感知的取舍，不以选项数量代替选择价值 |
| 成功和失败是否讲得通？ | 规则是否一致，反馈能否帮助理解失败原因和可调整的方法，重试成本是否保留学习与再次尝试的空间并符合目标体验 |
| 我为什么愿意继续？ | 核心循环再次发生时有哪些变化、挑战、成长或期待，重复过程的负担来自哪里 |
| 游戏如何使用我的时间与注意力？ | 等待、重复操作、教学、信息量及实际商业化中断对连贯体验的影响 |

每项判断关联具体规则和玩家处境，记录预期感受、推演依据、发现的问题、影响与调整建议，以及仍待验证的假设。按游戏目标选择相关问题，例如放松体验可重视流畅与表达，策略体验可重视取舍与后果。方案中的逻辑矛盾、缺失目标或循环断点先在策划中修正；涉及手感、响应、空间、节奏等实际体验的问题转为 V1 优先验证项，理解成本、重试意愿和重复疲劳等转为后续真实参与者观察任务。每项后续任务明确观察什么、在何种条件下判断、结果会影响哪个设计决定。

案头推演记录为设计判断与待验证假设，引用真实反馈时保留来源。实际参与者的行为、原话、样本与满意度仅依据真实观察记录。完成本次审查的条件是相关循环已推演、发现的问题有处理去向、关键假设已交接到验证计划。评审沿用现有方案质量检查与实质取舍流程，已有授权内继续修订及实施。

<a id="design-method"></a>

### 从设计依据形成可验证问题

以下采用作者公开文章、讲稿及可核实的书籍介绍／节选，资料核对日期为 2026-11-17；不以书名或作者声望替代项目证据，也不声称已逐章核实整本书。后文的具体用例是本工作流据此作出的应用推导，并非原作者规定的通用验收清单。

- Hunicke、LeBlanc、Zubek 的 [MDA](https://www.cs.northwestern.edu/~hunicke/pubs/MDA.pdf)区分机制、运行中的动态行为与玩家体验；其中 Aesthetics 指交互引起的情绪体验，不仅是美术。应用时将本批最不确定的体验目标关联到玩家行为、触发机制和可观察后果，例如“能理解一次失败并调整下一次尝试”；规则正确、反馈更强或画面精致均不能单独证明该目标。
- Jesse Schell 的[《The Art of Game Design: A Book of Lenses》作者工作室介绍](https://schellgames.com/art-of-game-design)以不同视角提出设计问题；Tracy Fullerton 的[《Game Design Workshop》第四版公开第一章节选](https://www.routledge.com/rsc/downloads/Game_Design_Workshop_Chapter_1.pdf)强调观察真实玩家及尽早获得反馈。应用时只选当前风险需要的问题，明确想观察什么、什么现象会使原假设存疑，再按[试玩闭环](game-content-playtesting.md#playtest)准备最小任务、观察和复验；不逐个填写所有设计透镜或另建研究阶段。

已有有效结论按版本、规则、内容和参与者情境核对后复用。经验性原则用于选择检查，不直接规定统一时长、成功率、难度曲线、玩家数量或商业指标；目标由当前项目确定，未知时保留假设及观测。

## V1 专项验证

在当前功能切片中，先验证[玩家视角方案审查](#player-review)交接的关键假设及最可能使方案失效的机制，再扩展其他适用检查。按空间、镜头、物理和手感等实际风险选择验证深度：风险高时优先使用正式工程中的可玩白模，二维动作或跳跃可用可交互的二维占位；规则风险可先用数据模型或最小交互验证，成熟机制复用仍有效的实现和证据。实际世界场景仍按[内容分流](game-design-exploration.md#implementation-routes)完成适用的 V1 空间验证；维度本身不要求为局部或无空间变化任务重建有效白模。操作、时序、碰撞和空间结论需要实际运行，离线计算仅证明模型。选择下表与当前机制相关的行，再按已确认规则写出预期，不为覆盖示例添加新机制或统一阈值。

以下类型重点仅供选择，混合类型按实际机制组合：整理、消除、解谜关注规则、可解性、目标辨识、空间压力与操作；动作、射击关注输入手感、镜头、常规交战、多敌压力和反馈遮挡；平台跳跃、探索关注尺度、通行、路线、镜头与新能力区域；经营、养成关注资源循环、成长阶段、操作频率与瓶颈；卡牌、策略关注回合流程、关键决策、组合复杂度与信息负担。无对应机制时不补造内容。

新游戏或核心循环变化时，优先打通上述最小循环的真实操作、状态变化和必要反馈，核对重复执行及成功、失败或继续路径；后续扩展依据工程结果和人工体验观察中的相关结论安排。新增设施、关卡数量或正式美术不代替核心体验验证；功能正确、构建成功或代理推演均不能证明好玩、愿意重试或持续游玩，也不把人工体验结论未定扩大为无关工程全部停工。

| 特点或类型入口 | 实施前明确的规则 | V1 优先验证的风险与代表性用例 |
| --- | --- | --- |
| 动作、平台跳跃、射击 | 输入缓冲与取消窗口、移动/碰撞、命中及重复伤害规则、镜头与瞄准关系 | 连续/同时输入、窗口边界、边缘碰撞与高速穿透；在项目支持的不同帧率下检查规则时序和结果符合预期；中断/恢复不残留输入或判定 |
| 解谜、消除 | 合法操作、胜负、死局策略、连锁终止；存在时定义撤销/重排 | 已知解复现、非法操作不改状态、无可用操作的处理、连锁能终止；撤销/重排不损坏目标或资源。随机或物理机制不能凭有限样例宣称全局可解 |
| 卡牌、回合制、战棋 | 阶段交接、费用与目标、效果优先级、连锁/递归边界、隐藏信息 | 同时触发、目标失效、重复提交、资源不足、回合结束；预览与结算一致或按规则解释差异，信息不提前泄露 |
| 塔防、即时策略 | 路径与阻挡、索敌切换、波次/胜负、单位规模与预算 | 堵路/路径失效、目标死亡切换、波次重叠与漏怪结算；以当前预算内代表性负载检查规则及性能，不以平均 FPS 代替峰值数据 |
| 经营、放置、增量 | 时间权威、产消/容量、离线收益上限与领取策略、数值范围 | 无时间增量、长间隔、时钟回拨/跳变、重复领取、存档恢复；核对资源守恒或明确的产消规则、溢出及进程可达性，模型计算与游戏实际状态分别验证 |
| Roguelike、程序生成 | 生成器/配置版本、种子及随机状态、地图约束、构筑叠加、局内外进程 | 固定条件重现、入口/出口可达、异常组合、生成失败的既定处理、死亡/重开状态隔离；批量检查记录种子集合和样本规模，不把抽样通过说成所有种子正确 |
| 联机、合作、对战 | 权威状态、允许预测范围、操作关联标识、同步及重连/结算策略 | 延迟、乱序、重复消息、断线重连、迟到结果、状态收敛与一次性结算；模拟传输只证明本地协议行为，真实服务未测则保留未验证 |
| 节奏、音乐 | 判定时钟、校准偏移、输入时间戳、音画同步与暂停策略 | 判定窗口边界、不同帧率/音频延迟条件、暂停恢复和音频中断；记录实际偏差及约定容差，表现效果不得改写判定时基 |
| 竞速、驾驶、物理模拟 | 步进/时间策略、控制与接触、检查点及圈数/计时规则 | 不同步长下稳定性符合项目预期、碰撞/重置、漏过/逆向通过检查点、重复冲线；不强求浮点物理跨平台逐位确定性 |
| 叙事、分支选择 | 分支条件、变量、选择后果、存档/读档及跳过策略 | 关键分支可达、快速推进/跳过不重复结算、读档恢复分支状态；恐怖或探索项目再按已定目标交接线索、节奏与人工体验检查，不添加战斗或奖励机制 |

玩法拥有状态与判定，数值负责公式/随机情景，动画与反馈消费已定义事件，QA 核对规则及用例覆盖。数值专项复用 [数值平衡](balance.md)；动态反馈按适用栈复用[反馈指南的类型矩阵](reference-feedback-design-guide.md#类型适用矩阵)，其效果候选不自动变成玩法要求。

记录本切片已验证的机制约束、输入/初始状态、运行环境、操作或时间轨迹、预期与实际、证据位置和剩余假设；随机用例同时保留种子、配置及必要的随机状态/调用顺序。同一机制的有效证据可跨对象引用，但要说明实际覆盖范围。

V1 的功能结果可供受影响对象进入后续设计；尚未证实且会改变该对象操作、空间或时序的约束，应先验证或解决，其他工作继续。V2–V4 制作不替代功能验证，V5 以正式资源重验受影响的判定、输入、时序和状态；手感、可读性及显示效果由用户人工检查。未经明确授权不自动分析截图或发起真机验收。

<a id="type-experience"></a>

## 按类型深化体验验证

本节补充上表的工程用例，按本批真实机制和[设计问题](#design-method)选用；混合游戏组合相关项，无对应机制时不补造功能。代表情境与边界夹具仍分开，记录复用现有 GDD、实施计划和 QA 材料，不新增必填表或全类型测试套件。

### 整理、消除与解谜：理解规则及形成推理

依据 Patrick Traynor 在 [GDC 2024 的《System-Centric Puzzle Design in Patrick's Parabox》讲稿](https://media.gdcvault.com/gdc2024/Slides/GDC%2Bslide%2Bpresentations/Traynor_Patrick_SystemCentricPuzzle.pdf)对机制组合、玩家尝试与理解过程的讨论，以及 Jonathan Blow 的[《About the Blue Mazes》](https://www.the-witness.net/news/2010/10/about-the-blue-mazes/)对亲自解题过程的说明，作如下项目化检查：

- **代表情境**：按当前风险选取接触本批规则及与既有规则组合的内容，区分首次接触与已练习条件；整理／消除同时核对代表密度下的目标辨识、有限空间和操作选择，不默认最小测试局面代表真实体验。
- **工程依据**：从正式规则与数据重放已知解、失败及项目已有的撤销／重试路径，保留状态和输入轨迹；求解步数、状态数量和可解性只证明模型范围，不能独自衡量玩家理解或难度。
- **人工观察**：观察实际玩家先看什么、尝试什么、在哪种状态反复误判，再询问其理解的规则与因果。分别记录独立领悟和提示后完成；区分线索不足、目标难辨、规则误解及操作困难，不把降低复杂度、去掉文字或增加提示当作统一答案。

### 动作与射击：控制响应、威胁判断与遭遇节奏

依据 Michael Booth／Valve 的 [2009 年《The AI Systems of Left 4 Dead》公开讲稿](https://cdn.cloudflare.steamstatic.com/apps/valve/2009/ai_systems_of_l4d_mike_booth.pdf)中对遭遇变化和压力起伏的设计讨论，结合本游戏的输入与战斗合同应用：

- **代表情境**：复用现有敌人和场景，先建立可辨因果的操作基准，再选择本批常规交战、威胁叠加及战后恢复情境；变化随机时保留配置、种子及实际事件，不用极端围攻代替全部日常战斗。
- **工程依据**：重放输入、瞄准／镜头映射、命中与伤害时序、资源消耗和中断，核对正式反馈叠加时规则仍一致；已有取消、无敌或缓冲窗口才检查其边界，不能为了套用清单引入这些能力。
- **人工观察**：让实际玩家判断威胁来源、可用行动、受击与失误原因，记录反馈遮挡、持续压力、等待或重复负担。区分难度、遭遇频率与可读性问题；不复制《Left 4 Dead》的导演系统、休息时长或固定张弛曲线，也不靠加特效代替响应修复。

### 平台跳跃与探索：能力边界、空间可达及路线理解

依据 Maddy Thorson 的[《Celeste & Forgiveness》](https://www.mattmakesgames.com/articles/celeste_and_forgiveness/index.html)、[《Celeste & TowerFall Physics》](https://www.mattmakesgames.com/articles/celeste_and_towerfall_physics/index.html)，以及 Guerrilla 设计师 Daniel Wewerinke 在 [GDC 2024 的环境谜题讲稿](https://media.gdcvault.com/gdc2024/Slides/GDC%2Bslide%2Bpresentations/Wewerinke_Daniel_CreatingEnvironmentalPuzzles.pdf)，按项目实际能力应用：

- **代表情境**：选择当前能力下的常规通路、相关边缘或落点，以及本批新能力影响的区域；支持多入口时才选择不同接近方向，教学允许沿项目意图采用线性路线。
- **工程依据**：以真实角色尺度、镜头和碰撞验证通行；若已有离边宽限、输入缓冲、移动平台或推挤，分别覆盖窗口前／内／后、站乘、脱离、反向及夹压等相关状态。二维可玩占位同样适用，不照搬《Celeste》的窗口数值、坐标系统或碰撞算法。
- **人工观察**：观察玩家能否预测落点、理解可达与不可达、辨认路线及新能力用途，并区分未看到线索、能力判断错误和输入失败。图连通或一次跳跃成功不代表整段路线和手感通过；不自动增加导航标记、容错能力或开放路线。

### 经营与养成：资源循环、成长反馈与可行动性

依据 Ernest Adams、Joris Dormans 的[《Game Mechanics: Advanced Game Design》公开节选第 4 章](https://ptgmedia.pearsoncmg.com/images/9780321820273/samplepages/0321820274.pdf)关于内部经济、反馈和相互依赖的分析，以及 Soren Johnson 的[《Old World: Yields》开发笔记](https://www.designer-notes.com/old-world-designer-notes-5-yields/)，应用于实际资源与成长机制：

- **代表情境**：走通本批资源获得、消耗／转换、投资及下一次可行动的周期；涉及解锁时观察解锁前后入口、操作频率和瓶颈的变化，不要求先做完整长期成长系统。
- **工程依据**：用正式参数与初始进程比较短期消耗、长期积累及相关低资源／上限情境，保留流入、流出与状态轨迹；存在资源与生产能力互相依赖时，检查失去关键资源后是否按既定规则失败、恢复或继续。正反馈放大差距可能是设计目标，不统一要求消除失败、无限可恢复或所有曲线平稳。
- **人工观察**：观察玩家能否理解当前瓶颈和下一步选择、等待中是否仍有预期行动，以及重复操作是否成为无意的最优路径。模型收益或余额正确不证明节奏合适；配置计算、实际存档／恢复及真实玩家对负担的反馈分开，参数细节复用[数值平衡](balance.md)。

### 卡牌与策略：有意义选择及组合信息负担

依据 Mark Rosewater 的[《Decisions, Decisions, Part I》](https://magic.wizards.com/en/news/making-magic/decisions-decisions-part-i-2009-07-27)与[《New World Order》](https://magic.wizards.com/en/news/making-magic/new-world-order-2011-12-05)对决策代价及规则理解、场面追踪、策略深度的区分，并参考 Soren Johnson 的[《Playing the Odds》](https://www.designer-notes.com/game-developer-column-9-playing-the-odds-3/)，应用于当前回合与信息合同：

- **代表情境**：选取本批典型回合及费用、手牌／单位或敌情变化后的相关局面，说明选择前可知信息、可执行动作、短期与长期代价，不把按钮或可选项数量等同于决策价值。
- **工程依据**：核对合法行动、费用、目标、触发次序及结算状态；随机存在时按项目承诺保留初始条件与随机轨迹，核对公开说明与实际规则一致，保护设计要求隐藏的信息。代表对局用于寻找疑似支配路径，不凭少量模拟证明全局平衡或概率正确。
- **人工观察**：分别判断玩家能否理解单项能力、追踪同时生效的状态，以及据此作出取舍；记录误判、提示依赖和反复无意义操作。是否需要限制某种优势策略取决于当前体验目标，不强制采用《Magic》的稀有度分配、公开全部概率或维持统一胜率。

## QA 用例映射

QA 从本次特点和已确认规则推导用例，沿用已有测试计划/用例与证据记录。每个会影响验收的特点关联规则来源、具体功能/对象、检查方式及结果；可以多条特点共用一个用例，也可以一个特点关联多条用例，不按类型机械凑数量。

用例至少可追溯到前置状态、输入/操作、可观察预期、实际结果与证据；时序、随机、负载或联网用例追加实际需要的环境、版本、时间、种子、样本规模或网络条件。复用项目既有编号，不要求新编号体系或文件。未确定预期时报告规则缺口，不能用实现结果反推正确答案。

以下是同一功能在既有计划中的映射示例，只有项目确实包含这些机制时才采用：

| 特点 → 规则来源 → 功能 | V1 用例及预期 | 正式组合后的回归 |
| --- | --- | --- |
| 卡牌＋随机 → GDD 当前费用/触发顺序 → 出牌结算 | 固定初始手牌、种子和输入顺序；重复提交同一次操作，费用与效果只按规则结算一次，日志可复现触发次序 | 正式动画加速/跳过、切场景或恢复后，不改变结算及卡牌去向 |
| 放置＋保存 → 当前时间/收益上限规则 → 离线领取 | 用可控时钟覆盖零间隔、回拨和超过上限，重复领取不重复入账；分别记录公式结果与实际余额 | 完成一次保存、退出、恢复、领取周期，核对库存和下一次累计起点 |
| 联机＋动作 → 当前权威/预测规则 → 命中结算 | 注入延迟、重复及迟到消息，预测表现与可信结果可区分，最终状态按规则收敛且不重复伤害 | 正式表现、中断及重连后重放同类操作；未接真实服务的范围仍标未验证 |

在现有 V1 记录专项功能证据，V5 验证正式资源与运行组合的影响，最终集成覆盖范围内完整的一局或业务周期：开始、推进、成功/失败、重试及适用的保存/恢复与跨场景衔接。长周期和极端组合按当前风险选取，不把局部单测或离线模拟视为完整游玩通过。

测试等级、命令与结果沿用[验证与交付](../../app-creator-workflow/references/verification.md)：分别报告通过、失败、未运行及人工待确认；不适用的候选检查说明机制不存在的依据，不给未执行用例填写 PASS。自动验证状态、公式、事件和协议等工程结果，用户检查手感、节奏与实际显示；人工意见未取得时保留待确认，不新增审批。

规则、参数、生成器、时基、权威协议或正式表现改变时，按下文回归清单沿这份映射重验受影响用例和必要的完整周期，保留未受影响的有效证据。只修改测试计划不等于执行测试；出现失败按现有 repair/revalidate 闭环处理。

## V1 到正式组合的回归清单

在当前 TDD/实施计划和 QA 记录中，关联本次变化、受影响的规则/消费者、既有 V1 用例和后续验证位置。GDD 保持规则来源，TDD 记录实现与计划，QA 记录实际执行及证据，使用已有编号互相引用；QA 文档尚未建立时沿用当前验证材料，不为本清单强制初始化可选文档。

1. 比较实际变化：检查代码、配置、正式资源元数据及绑定，判断其是否写入玩法属性、改变事件触发/顺序、影响输入命中或生命周期。表现标签、文件扩展名和“只是换皮”的描述不能代替影响核查。
2. 按下表选择相关回归，沿真实依赖扩展到共用消费者及跨场景链路。用例记录前置、输入、预期、实际及证据，命令来自目标工程；范围变化时更新原计划和测试等级，不增设审批。
3. 分别记录可复用的旧证据、当前重验结果和未验证项，不改写旧输出。无法确定影响时先检查写者、事件及消费者，仅对仍不明确的范围保留未验证；当前失败按 repair/revalidate 修复，只有上游目标或范围真实失效才按原流程 return。

| 实际变化 | 需要重验的用例与阶段 | 可继续引用的证据及边界 |
| --- | --- | --- |
| 动画时长、速度、根位移、事件或中断 | 回放原 V1 输入轨迹，核对伤害/费用发生时刻、动作窗口、位移写者、取消/暂停/重入；V5 用正式动作重复检查。改变规则先更新对应玩法范围 | 仅表现变化且判定/位移/事件来源未变时，可引用未受影响的纯规则单测；旧运行片段不证明新动作接入。手感与节奏仍待人工检查 |
| 碰撞体、角色尺度、地形、路径或镜头 | V1 中受影响的接触、可达性、索敌、目标/瞄准映射；V5 复核正式场景及高低速/边缘条件；共享资产按实际消费者扩展 | 与空间无关的公式可复用；换模型未改碰撞也须核对真实绑定。不能由单个测试场景推断所有关卡可达 |
| 按钮/拖拽区域、HUD 布局或输入层序 | V5 真实输入命中、拖拽落点、世界坐标转换、模态输入隔离，覆盖项目已支持的代表性视口；规则同时变化时再回到受影响 V1 用例 | 纯规则测试可保留；旧布局的命中证据不能证明新布局。显示效果按既有视觉流程由用户确认 |
| 时钟、步进、全局时间、暂停或系统恢复 | V1 的窗口边界、帧率变化、暂停叠加、时钟跳变及离线收益；V5/集成验证正式反馈/音频与保存恢复。只选实际存在的机制 | 未依赖时间的结算可复用；可控时钟只证明注入条件下逻辑，不证明系统音频延迟或未运行的平台生命周期 |
| 随机调用、生成器、配置或构筑组合 | 保存版本、种子及随机状态/调用条件，重放代表性种子与失败种子；检查地图约束、抽取/掉落与局内外重置，共用随机流的消费者一并回归 | 未涉及随机的规则可复用；同一个种子不能保证算法/调用顺序改变后结果相同，新版本应满足已定规则。抽样规模与未覆盖种子明确保留 |
| 费用、掉落、容量、成长或离线参数 | 重算受影响模型及极端情景，V1 核对实际扣费/收益、上限与重复领取；集成覆盖适用的保存、恢复和一个完整周期 | 未变接口、独立输入映射等证据可复用；表格重算不能替代实际运行。目标区间未知时报告数据，不自行给出平衡通过结论 |
| 联机权威、预测、消息标识或恢复协议 | V1 注入延迟、乱序、重复、迟到和断线，检查收敛及幂等结算；V5/集成重验正式反馈、重连和跨场景状态交接 | 独立纯规则可复用；本地网络模拟与真实服务证据分开，未接真实服务不能标记端到端通过 |
| 场景切换、保存点、对象池或资源替换 | 当前功能退出/重进、取消后迟到回调、订阅与输入清理、实例重用及状态回读；最终集成重放受影响的完整一局/周期 | 未变的资源导入检查可引用；仅重新构建不证明旧状态已清理或保存恢复正确 |

例如“连击动画缩短但规则未改”，先核对动画事件是否仍参与正式伤害接线，再决定受影响的动作轨迹回归；“随机地图加入同一个随机流”，需核对是否扰动既有抽牌/掉落的规则与复现条件。对未变化消费者保留已有证据，不因新候选或进入 V5 就重做全项目 V1。

维护本流程、模板或读取链时，可按[典型任务演练](game-characteristics-exercises.md)核对代理在不同任务中的选择与交接。该演练用于技能维护，不是游戏项目的新阶段或验收门。
