# 三栈具体拷问策略

执行公共规则时，同时读取当前技术栈参考中的原生补充和“本栈配套资料”。各段仅适用于标注的技术栈；结构化证据不代替用户对显示效果的人工验收。

各技术栈统一使用 V0–V5；V1 是功能实现与验证，白盒可选，正式功能不必等待视觉目标。

## 全局控制接入

> 适用技术栈：cocos、phaser、threejs。

控制面边界：在当前 Work Item 范围内提议和审查并记录决定；受保护外部动作的具体授权按当前公共控制面处理。

> 适用技术栈：cocos、phaser、threejs。

Grilling 只形成 `USER_DECISION` 澄清记录。将用户选择回写 Work Item、需求、架构、视觉等权威工件或独立决定记录，清除对应未决标志；产品选择不能当作受保护动作批准或改写 `action.approval`。

> 适用技术栈：cocos、phaser、threejs。

只让用户决定不能从代码库、配置、现有权威工件或确定性执行确认的事项。不要阻塞纯事实查询、专业可判定缺陷或已确认的低风险执行。

## 进入方式

> 适用技术栈：cocos、phaser、threejs。

1. 读取当前阶段的计划、设计、技术方案、验收、实现和已确认决定，区分事实缺口、专业问题与用户取舍。

> 适用技术栈：cocos、phaser、threejs。

2. 先通过代码、配置、现有文档和实际执行关闭事实；专业质量交给独立审核。只有仍存在会实质改变范围、优先级、体验、架构、风险、验收、依赖、视觉方向、成本或发布授权的用户决定时才进入 grilling。

> 适用技术栈：cocos、phaser、threejs。

3. 首次模块或边界变化先检查代码、配置、契约和证据；仅当仍存在实质用户取舍时进入 grilling。记录必须绑定 Work Item、当前门、基线与失效条件，不得虚构候选身份。

> 适用技术栈：cocos、phaser、threejs。

4. 无产品定义时从目标用户、首次价值、范围、商业约束和风险开始；已有定义时只追问缺口、冲突、假设或依赖，不重复已有结论。

> 适用技术栈：cocos、phaser、threejs。

5. 新阶段、新页面、首次模块或边界变化本身都不是触发器。

> 适用技术栈：cocos、phaser、threejs。

6. 视觉方向、预算、签名强度或实现/资产成本仍需取舍时才做开放式视觉拷问。已有明确适用基线时不重复确认。

> 适用技术栈：cocos、phaser、threejs。

7. V2/V3 已有明确需求或冻结基线，且候选不存在产品方向、玩法语义或上游结构取舍时不提问。指定效果图忠实还原默认使用 `visual_validation.mode=usability`，小幅位置、尺寸、边距和换行差异可直接修复并重验；只有产品方向、玩法语义、上游结构变化或明确 `exact` 需求时，才说明影响与候选方案并请求一次确认。发布决定按当前发布 Work Item 和具体动作的明确授权记录。

> 适用技术栈：cocos、phaser、threejs。

8. 不存在用户决定时直接继续原任务，不生成占位记录。

## 对话规则

> 适用技术栈：cocos、phaser、threejs。

- 一次只问一个问题；每个问题说明影响、推荐答案及理由。

> 适用技术栈：cocos、phaser、threejs。

- 从根决定到依赖决定逐层推进，只展开当前范围相关分支。

> 适用技术栈：cocos、phaser、threejs。

- 回答暴露冲突或新依赖时先处理冲突，再回到原分支。

> 适用技术栈：cocos、phaser、threejs。

- 不把推荐伪装成事实，也不把未回答或沉默视为同意。

> 适用技术栈：cocos、phaser、threejs。

- 用户对所问取舍作出明确、无冲突的回答，即满足该问题的确认要求，无需另行确认复述。只有回答仍存在实质歧义时继续澄清；未获得必要回答前暂停直接受影响工作，无依赖工作继续。沉默不构成回答或批准。

## 完成与记录

> 适用技术栈：cocos、phaser、threejs。

用户明确回答后，汇总实际决定、未决项、依赖、拒绝项和下一步，更新权威工件并恢复原任务中已解除阻塞的工作，不以汇总或交接说明替代执行。高影响外部操作须在当前 Work Item 的 `action.approval` 中关联用户明确批准的具体动作、目标和用户消息引用；普通产品决定不建立额外批准记录。不得记录凭据、个人数据或受限合同全文。`AUTO` 与视觉人工确认的区别统一遵循“控制面不可绕过约束”（见本栈配套资料）。
