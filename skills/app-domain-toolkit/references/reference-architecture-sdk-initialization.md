# 第三方 SDK 独立管理与初始化

适用技术栈：unity、cocos、phaser、threejs、flutter、expo、esp32、nodejs。项目接入或调整第三方 SDK 时统一读取本规范，再按当前技术栈补充入口路径与原生要求；没有实际采用的 SDK 不创建占位文件，也不因此引入依赖。

示例中的相对脚本和文件路径按当前技术栈的原生资料与项目约定解析；运行前核对已安装的专业资源位置。

## 文件职责

- 每个第三方 SDK 使用独立的管理或适配文件，负责自身的配置校验、平台分流、初始化调用、完成回调、幂等状态、操作身份、失败分类、重试与释放。不得把多个 SDK 的实现堆在同一个 `SdkManager`、`initialize-sdks` 或其他总控代码文件中，也不能只把同一文件内的私有函数改名当成拆分。
- 应用可以保留唯一装配入口，负责创建或注入各 SDK 管理器、连接公开接口并分别投递初始化任务。入口不持有各 SDK 的具体 API 调用、回调处理、初始化状态机或恢复计时器；各 SDK 的实现和状态只在自己的文件中维护一份。
- 一个 SDK 内确有不同职责时再拆分配置、桥接、状态或平台适配；优先复用现有模块，不为统一目录或命名创建空壳、无用基类或另一套管理框架。公共文件仅放确实共用的接口、类型或纯工具，不混入不同 SDK 的具体实现。
- 渠道 SDK 同时遵循[按引擎定义接口与渠道实现](../../app-release/references/channel-platform-integration.md#按引擎定义接口与渠道实现)：各引擎分别定义统一能力接口，每个已选渠道用独立文件实现，业务只调用注入的能力接口，由唯一入口根据实际运行平台选择对应实现。渠道实现与 SDK 管理职责重合时复用其独立文件；组合多个 SDK 时委托各自管理器，不重复维护初始化与恢复状态。
- 微信小游戏与 CrazyGames 使用[可复用的具名渠道实现](../../app-release/references/channel-sdk-reuse.md)，方法、参数、结果和回调明确；只处理渠道专属能力，不重新封装引擎基础接口，也不用通用字符串调用或反射句柄替代逐项实现。
- 广告加载/展示、支付交易、登录界面、埋点业务和隐私交互仍归各自业务模块；业务层通过注入的能力接口读取状态、调用能力或请求单个 SDK 重试，不在页面、场景、构造函数或模块导入时再次启动 SDK，不复制初始化状态和重试器。
- 唯一装配不等于串行等待：各 SDK 分别投递，单 SDK 的导入失败、异常、重试或不回调不阻止无关 SDK 与应用首帧；只等待自身真实的官方前置，不建立无关 SDK 或整批就绪屏障。SDK 导入不产生自动初始化副作用。

## SDK 不阻塞应用流程

所有 SDK（包括引擎原生 SDK、渠道 SDK、统计、异常、归因、广告和隐私能力）均不得成为启动、首帧、资源加载、进入游戏、场景切换、结算或继续游戏的等待条件。唯一入口分别投递初始化并立即返回，不在这些流程中 `await initialize()`、等待整批任务、轮询就绪或展示 SDK 加载遮罩；超时只结束该 SDK 的诊断等待，游戏不必等到超时才继续。

- 授权未知、拒绝、撤回或必需前置未完成时，立即跳过需要授权的 SDK 操作并返回受限结果；不等待用户选择、不锁住游戏、不把隐私弹窗或 CMP 完成作为游戏入口。以后收到项目现有策略变化时，只恢复对应 SDK，不能让游戏重新进入加载等待，也不能伪造同意或绕过厂商必需前置。
- SDK 具体实现可以异步观察自己的真实回调，但等待只存在于 SDK 内部；单 SDK 同步抛错、异步失败、永不回调或诊断处理器抛错，都不能阻断其他任务和游戏。SDK 错误由相应能力的结果或隔离诊断报告，不向游戏启动链抛出整批失败。
- 广告加载、刷新和重试只在后台进行。触发展示仅检查当前缓存与策略：未就绪、受限、无填充、已有展示或失败时立即返回不可用并继续既有流程，不临时加载后等待、不排队等待初始化、授权、加载或网络，不用广告 Loading 覆盖游戏。
- 插屏广告不可成为过关、结算、退出或下一局的必经步骤。激励广告由用户主动选择，仅真实奖励回调兑现对应可选奖励；不可用、取消或失败时结束本次尝试，继续正常玩法，不扣除参与成本、不伪造奖励、不等待迟到回调才能继续。广告已展示时由厂商视图接管画面，项目只按实际展示生命周期暂停和恢复必要音频/输入，不能额外延长暂停。
- Banner 未加载、布局不安全或失效时保持隐藏且不留空白等待区。加载与销毁结果均不得成为场景切换的前置；迟到结果由原所有者清理，不能弹出过期广告或覆盖新场景。

## 隐私流程与 SDK 解耦

所有 SDK 均遵守本节，包括广告、统计、崩溃上报、登录、支付、推送及提供同意管理能力的 SDK。解耦指职责和依赖分离，不代表绕过隐私条件提前初始化。

默认不编排隐私弹窗、隐私中心、同意管理、撤回或重新征求同意等业务，不自动创建对应工作项、页面、模块、占位代码或引入同意管理 SDK。仅在用户明确要求或已确认的项目需求纳入范围时实施；下述隐私模块的职责和业务验证只在该范围内适用。已有隐私业务不因本规则被删除或停用，不因普通 SDK 接入、升级或工程初始化擅自扩展。

已选渠道有明确的强制隐私／授权交互时，按[渠道接入](../../app-release/references/channel-platform-integration.md#隐私与商业能力)在当前方案中明确必要范围并满足，不能以默认规则跳过官方前置；未满足时保持相应能力受限或阻断相关候选，不扩建无关隐私中心或伪造同意。

- 隐私流程由独立模块唯一管理告知、选择、同意版本、持久化、撤回及重新征求同意。SDK 管理器不得展示隐私弹窗、写入用户同意或把初始化成功当作用户同意；隐私模块不得直接调用具体 SDK API、持有其初始化状态或等待 SDK 全部就绪。
- 隐私模块只输出按用途区分的授权快照与变更通知，至少区分未决定、允许、拒绝和撤回。组合层订阅通知，通过注入的能力接口把可执行策略传给各 SDK 管理器；SDK 管理器负责映射厂商参数及执行自身启停。隐私模块和 SDK 模块均依赖公共契约，不互相导入实现。厂商同意管理 SDK 也通过适配器提供能力，不成为应用隐私状态的唯一权威。
- 每个 SDK 在方案中登记初始化、数据采集、网络请求、标识符读取、业务调用分别需要的授权用途，以及依赖导入、原生自动启动和后台任务的副作用。初始化本身需要授权时，在授权满足前不得导入有副作用的模块或启动 SDK；仅在有明确依据证明初始化无此副作用时，才可先初始化并保持受限。关闭 Manifest、Provider、插件注册或静态初始化中的绕行入口；无法关闭时阻断该 SDK 接入。
- 未决定、拒绝、撤回或授权读取失败时，对需要授权的操作默认禁止，不假定全部用途已获允许。隐私选择不等待广告、统计等无关 SDK 就绪；受限或失败只影响对应能力，不阻塞基础界面及无关 SDK。系统权限、平台授权和应用隐私同意分别判断，不能相互替代。
- 授权变化只更新受影响的 SDK。撤回时立即阻止新的受限操作，取消排队请求并按厂商能力停止采集、释放或切换受限模式；不能停止时明确禁用该能力并记录限制，不宣称已停止。使用授权版本或操作身份拒绝旧回调，防止撤回后继续发送、发奖或恢复旧授权操作；重新同意按当前策略幂等恢复，不重启无关 SDK。

## 归因与广告直接启动和调用

Unity、Cocos Creator、Phaser、Three.js、Flutter 和 Expo 项目按已确认需求及实际受支持的原生目标接入广告或归因；不声明厂商 SDK 支持全部栈或终端。Unity、Cocos、Phaser、Three.js 的 Android/iOS 复用[移动 SDK 具体实现](mobile-sdk-integration.md)：Firebase Analytics 处理统计与事件，Crashlytics 处理异常，AppsFlyer 处理归因；广告顶层聚合在 AdMob 与 AppLovin MAX 中显式二选一。其他栈按实际依赖核实引擎路线。采用 MAX 时聚合网络为 AppLovin、Google AdMob、Mintegral、Pangle、Unity Ads、DT Exchange（Fyber）和 Verve Group（PubNative）；原生归因使用 AppsFlyer。CrazyGames、微信和抖音小游戏按[渠道平台规范](../../app-release/references/channel-platform-integration.md#隐私与商业能力)使用适用的平台接口，不把 MAX／AppsFlyer 作为通用宿主依赖；ESP32 等仅在平台能力核实后处理明确需求。启动装配入口分别投递已接入 SDK 的任务；每项只等待锁定平台、版本和已采用流程的官方真实前置，不增加无关登录、首屏或归因回调屏障。启用 MAX 内建同意流程时，相关 MMP、分析 SDK 是否等待其结束按官方要求处理；其他无关 SDK 和游戏继续。参考 [Android 官方流程](https://support.applovin.com/en/max/android/overview/terms-and-privacy-policy-flow)与 [iOS 官方流程](https://support.applovin.com/en/max/ios/overview/terms-and-privacy-policy-flow)。

业务触发归因事件或广告请求时调用对应能力接口，应用层不增加无关等待屏障。不因普通 SDK 接入擅自新增隐私业务；项目已采用或官方要求的 CMP（包括 UMP）及其真实前置必须遵守。`hasUserConsent=false` 不证明用户完成选择，也不单独证明所有地区和渠道允许请求。适配器按实际 SDK、隐私与网络条件返回结果；未就绪、无填充、离线或展示失败按既有回退处理，不阻塞调用方，也不伪造成功。

授权限制只作用于实际需要授权的数据或操作。能以受限模式执行的初始化、归因或广告请求按适用配置发起；没有适用路径时保留真实限制和原因。集成验证覆盖缺少应用隐私流程、官方前置满足和未满足、无关 SDK 先后就绪及各自失败隔离；存在官方依赖时验证依赖顺序，不将其伪称独立。

## 工作流接入

1. 需求与全局基线：盘点实际 SDK 的版本、用途、授权前置与自动启动路径，登记现有授权来源、能力接口及各 SDK 所有者。默认不新增隐私业务；需求明确包含时才登记隐私流程所有者、交互范围和对应实现，不新增总控状态机。
2. 基础工程与功能实施：复用现有授权来源，通过与具体 SDK 解耦的策略接口接线；没有有效授权来源时，仅将需要授权的能力保持受限，不伪造已同意、不以接入 SDK 为由自动补建隐私业务。需求明确包含隐私业务时再独立实现并验证其交互。局部新增 SDK、变更用途或调整版本时仅复核受影响策略。
3. 集成与发布准备：验证实际 SDK 在授权缺失、拒绝、策略读取失败及迟到回调下仍遵守限制，检查网络、标识符访问、后台行为和失败隔离；已有授权变更来源时验证撤回等实际支持状态。仅在隐私业务属于确认范围时覆盖首次选择、持久化、版本失效与重新同意等业务流程，不为测试补建业务。记录真实证据和未验证项，不以缺少隐私页面视为无关 SDK 的全局阻断，也不以文档检查代替行为验证。发布候选仍检查最终用途配置和自动启动路径。

## 幂等、回调与失败隔离

同一 SDK 的重复入口复用自己的有效请求或已完成状态；配置替换、禁用或释放使旧回调失效，单 SDK 重试不重启其他 SDK。只有真实完成回调或官方明确的就绪信号才能确认成功，不能以入口返回、另一个 SDK 成功或超时推断成功。初始化恢复与业务运行期恢复分别持有状态和计时器。

- 诊断只记录 SDK 身份、平台、阶段和脱敏错误分类；不记录 SDK key、凭据、设备标识或完整原生异常。

## 交付与验证

在 TDD 或技术规格中登记装配入口、各 SDK 独立实现文件、公开接口、状态所有者、配置来源、官方前置和恢复责任。验收应检查入口是否保持轻量、实现是否按 SDK 分文件、状态是否唯一，以及单 SDK 失败、重复初始化、迟到回调、重试和释放是否相互隔离。

本仓库只交付 Skill 指导文件时执行文档、链接及仓库回归检查；不得将这些检查描述为真实 SDK 集成通过，也不要求真实 SDK 调用、真机、外部控制台配置或发布。
