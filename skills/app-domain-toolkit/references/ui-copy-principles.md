# 界面文案通用原则

适用技术栈：cocos、phaser、threejs、unity、roblox、flutter、expo、esp32。适用于游戏和应用中所有用户可见文案，包括标题、按钮、弹窗、引导、奖励和状态反馈。

## 最少必要文字

设计和实现界面时，只保留玩家或用户理解当前状态、做出决定或执行操作所需的文字。图标、数字、位置或上下文已能清楚表达同一信息时，删除重复文案。文字本身就是任务内容时，按任务需要保留。平台要求展示的文字按适用规范保留。

1. 按真实业务在已有设计规格中列出当前界面会出现的状态。逐项明确用户需要认出什么、此时可以执行什么动作、动作会产生什么结果。付费、观看广告、授权、删除等条件和后果必须在操作前就能被识别。
2. 优先用图标表达动作或资源类型，用数字表达当前数量、变化量或奖励。图标含义不明确时，补最短的可见文字。按[同一控件的状态表达](#control-state-expression)设计各状态，并区分当前值与操作带来的变化。可见文字精简后，仍提供完整的无障碍名称和状态语义，让屏幕阅读器读出适用的动作、条件和金额。
3. 对带图标的按钮和状态提示，在可编辑源中临时隐藏待检查的文案。按目标显示尺寸，结合相邻控件和典型使用场景做[人工遮字检查](../../app-asset-workflow/references/interface-intent.md#将去字检查放进现有审阅)。视觉线索已能表达同一信息时，删除重复文案，并收回为它预留的空间。
4. 删字会让用户猜测状态、用途、结果、代价或风险时，先调整图形、位置或状态反馈。仍需说明操作、原因或后果时，保留能消除歧义的最短文字。用户需要读到精确数值时，保留对应的数值及必要单位。

不设统一字数上限。所有用户都需要看到的关键信息须在界面上明确呈现。

在 V2 单次用户视角审查中，逐项检查删掉这段文字后，用户能否理解当前状态、做出决定并知道下一步怎么做。能就删，并收回预留空间。不能就保留最短的明确表达。代理核对可编辑源中的节点、文案、尺寸、布局和状态等事实。V5 按确认稿核对实际文案、状态切换时的布局、命中范围和屏幕阅读器语义。运行验收发现可精简的文案时，先更新确认稿和对应拆解，再按新目标验收。用户结合确认稿、实际界面及适用的遮字版本确认显示效果。

阶段 5 游戏模块的生图示意遵循[玩家视角与广告示意](../../app-asset-workflow/references/style-and-production.md#player-view-generation)。广告入口的可见提示只用无字广告图标。图标难辨时调整形态或位置。

例如，补金币弹窗将金币图标与当前余额放在一起，领取按钮显示小号广告图标和「+500」，无障碍名称为「看广告领取 500 金币」。金币结算可用金币图标和「+20」表示当前奖励，可选按钮用小号广告图标和「x3」表示通过观看广告获得三倍奖励。

例如，游戏道具栏用循环箭头标识重排、三件同类商品标识消除、雪花时钟标识冻结。各按钮显示图标和库存角标，冻结生效时在主倒计时旁显示冻结图标与剩余冻结时间。将评审标注放在游戏画面外。

### 同一控件的状态表达

- 同一控件切换状态时复用位置、尺寸和点击范围。是否响应输入按实际可用性决定。状态差异优先通过轮廓、符号、填充、角标等可辨特征呈现，颜色用作辅助。
- 优先复用共用图形与组件。确需独立图片时，只为实际用到的状态生成变体，保持各图的画布尺寸、对齐基准、比例和风格一致。
- 收藏可用空心星与实心星表达，展开与收起可用不同方向的箭头。操作受限且用户需要知道如何恢复时，在对应状态直接提供必要的原因或可执行的下一步。
- 状态提示只在相关状态出现。等待时锁定对应按钮，奖励实际到账后再显示成功，失败时用一句短提示说明结果和可用操作。取消后直接恢复可操作状态，仍需告知玩家其他结果时再补提示。

## 表达选择

在拟稿和布局前按[最少必要文字](#最少必要文字)确定当前状态需要显示的内容。将面向审阅者的说明放进设计文档，从界面里删除重复标题、装饰标签和复述操作的说明段落。副标题、二级说明、说明卡和空泛宣传语默认不占位。仅在特定状态有用的说明就在该状态显示。

- 图标标识对象、资源或操作条件，数字表达数量、倍率或进度。需要文字时，用短名称、短动作或短状态，如「领取」「升级」「已满」。结合当前场景和相邻信息理解控件，单个控件无需复述完整规则。
- 同一含义在不同页面、HUD、弹窗和反馈中保持一致，只有对象、显示状态、数据或语气确有区别时才调整表达；动作与结果分别对应真实操作和已发生的状态，不能混淆。
- 奖励、消耗、数量、倍率和进度优先用对应图标与数值；增减保留正负号，倍率使用 `x{value}`，进度可用 `3/10` 或进度条。上下文已明确基准时优先表达变化关系，结果反馈再显示真实结果；倍率、最终总额与额外增量不能混用。
- 数值要与对应图标相邻并形成同一信息组；余额、价格和变化量使用清晰上下文区分，不能靠颜色或孤立数字猜含义。
- 「免费」等描述必须符合当前实际条件，不能将有货币或道具消耗的操作标成免费。观看完成即可复活且无需消耗货币或道具时可用「免费复活」，并按[最少必要文字](#最少必要文字)让用户在操作前识别观看要求。

| 意图 | 优先表达 | 含义已明确时可省略的重复说明 |
| --- | --- | --- |
| 金币奖励 | 金币图标 `+100` | 获得 100 金币 |
| 钻石消耗 | 钻石图标 `-20` | 消耗 20 钻石 |
| 奖励倍率 | 奖励图标 `x3` | 获得三倍奖励 |
| 收集进度 | 目标物图标 `3/10` | 已收集 3 个，还需收集 7 个 |

示例仅说明如何运用通用原则，不限定适用场景，也不固定项目的资源、数值或界面内容。应先识别当前上下文和表达意图，再选择图标、数字与短文案的组合，不机械套用示例。

## 静态文本的可见表现

本节的强制位图路线适用于 Cocos、Phaser、Three.js。Unity 默认先评估 UniText，按[完整还原标准](../../unity-development-workflow/references/visual-decomposition-routes.md#完整还原的判断标准)核实后确定原生或图片，未核实则待验证，并保持统一 JSON 文案源，异常时由用户选择修复或回退 TMP，不强制转位图；Flutter、Expo 静态与动态文本均可使用各自原生文本组件。其他文案表达、本地化和可访问语义规则继续适用。

适用三栈的所有静态文本统一使用位图字体或独立文字图片，按具体显示效果选择路线。静态指文案在已定义的语言和状态下固定，包括标题、按钮标签、固定说明及预先定义的提示。语言或固定状态切换使用对应资源变体。实时数值、玩家名称、用户输入、服务器内容和含运行时插值的文案属于动态内容，不能因当前一帧未变化就判为静态。

采用位图方案前，先查找接近目标效果的源字体，优先检查项目已有字体，再按字形轮廓、字重、字面比例、字距及目标尺寸的可读性比较候选，同时核对来源、使用许可和所选语言的字形覆盖。选定后登记为项目全局字体，统一供各场景、页面、显示层的文字图集与文字图片制作使用。

全局字体在现有视觉规格和资源登记中维护字体文件、版本、字重、语言覆盖及消费引用。字号、颜色、描边和阴影由统一文本样式定义，各组件复用同一字体来源和样式。多语言缺字时明确登记配套字体及语言范围，并验证风格一致性。特殊艺术字需要额外造型时，以全局字体为制作基础；确需更换字体时在现有设计规格中记录适用范围和依据。

V2 随全局视觉目标确定字体，V3 引用该字体并选择位图字体或文字图片路线，V4 从登记的源字体制作正式资源，V5 核对实际使用的图集或图片及语言变体。既有全局字体贴合当前目标时直接复用，字体调整时同步更新受影响的制作源、图集、图片与正式绑定，并重验对应显示效果。

| 路线 | 选择依据 | 正式交付 |
| --- | --- | --- |
| 位图字体 | 字形、字距和排版可用一套字形图集表达，复用文字较多，或需要换行与阅读尺寸适配 | 覆盖所选语言的字形图集、字形度量和排版配置，核对实际渲染组件支持的尺寸及效果 |
| 文字图片 | 目标依赖专属字形、纹理、跨字装饰、复杂光影或定制组合，整段固定图形更能还原效果 | 按语言、状态和显示尺寸制作独立文字图片，保留透明边缘、定位尺寸和可编辑制作源 |

按以下顺序作出选择，并把依据记入已有规格：

1. 先判断效果是否依赖整段造型。专属字形、跨字火焰或装饰、整体纹理与光影难以用独立字形组合还原时，选择文字图片。
2. 效果能用同一套字形及排版表达时，再看复用需求。多个标签共用风格、需要组合文字、换行或多语言排版时，优先位图字体。统一的描边或阴影可由合适的位图字体资源表达，须按目标核实效果。
3. 两条路线都能满足目标时，结合字形复用、语言变体数量、资源体积和维护成本选择。候选在实际显示尺寸与背景下核对字形、字距、边缘清晰度及缩放可读性，交用户人工检查。位图字体仍达不到目标的整段效果时，使用独立文字图片。

例如金属立体且带跨字火焰的「胜利」适合文字图片，同一风格的「设置」「返回」「确定」及固定说明段落适合位图字体。「开始游戏」采用统一字形样式时可用位图字体，采用专属艺术字造型时可用图片；根据实际设计选择。

V2 对照目标画面确定字形和效果，V3 在现有文案、布局与资源规格中为静态文本记录路线、选择依据、文案键、语言/状态变体、逻辑显示尺寸和资源消费者。图集复用能力与图片的整体造型按目标取舍，素材已满足要求时直接复用。普通字体或 SDF 文本的可见渲染须按本规则切换到选定的位图路线，不能以字体资产存在纹理图集作为已使用位图字体的依据。

V4 生产并导入正式图集或文字图片，逐语言核对字形、拼写、透明边缘、排版和实际目标尺寸的清晰度。V5 核对真实加载资源、语言/状态切换、缩放与适用的字体放大，并提供目标对照和检查点，由用户人工判断显示效果。位图字体与图片均须满足已有宽度、断行和阅读尺寸约束；图片按已声明的尺寸变体或重新排版处理阅读尺寸变化。

可见文字资产与文案语义使用同一文案键。控件保留可访问名称、角色、状态、焦点和实际命中，文字图片作为该控件的视觉部件，独立交付并绑定到正式节点。整屏背景不能代替控件结构。涉及选择、复制或辅助阅读时，提供对应文本语义与操作入口，并核对语义文字和当前可见语言一致。变更文案或翻译时同步更新图集覆盖或图片变体、制作源、正式绑定及相关验证。

## 错误提示形式

各栈游戏与应用统一按以下规则选择提示形式；按事件是否需要用户确认、是否来自后台任务判断，不以异常类型或 SDK 原始错误级别决定。

| 场景 | 统一形式 | 行为要求 |
| --- | --- | --- |
| 普通业务错误，如操作失败、条件不满足、当前服务不可用 | Toast | 简短说明当前结果或可行下一步，不抢焦点、不阻断输入 |
| 需要用户确认、选择或明确处理后才能继续 | 弹窗 | 明确确认或选择按钮及后果，按实际模态行为隔离输入并恢复焦点；不能用自动消失的 Toast 替代 |
| 后台加载、预加载、自动刷新和重试失败 | 静默 | 不弹 Toast 或弹窗，不用声音、震动或遮罩提醒失败；保留脱敏诊断及既有恢复策略 |

Toast 不按文案或错误码去重，相同提示的每次有效触发均立即显示，不排队、不替换正在显示的实例。业务层仍通过操作身份拒绝重复、迟到或已失效的结果回调，避免同一结果被重复投递；这不合并不同有效触发的相同提示。前台操作失败已经提示后，后续后台重试失败仍保持静默；后台任务失败不能仅因其日志级别较高升级成弹窗。用户主动操作在当前状态下被拒绝时，按其业务结果选择 Toast 或确需确认的弹窗，不把后台每次重试作为新的用户操作。

复用项目现有统一 Toast 和弹窗组件；业务模块返回稳定错误码或结构化结果，由 UI 层映射为本地化短文案，不直接展示异常堆栈、SDK 原始消息或敏感参数。Toast 的独立实例、复用、消失与输入行为沿用[公共显示结构约定](reference-domain-display-ownership.md#游戏层内容层hud浮窗与弹窗)。

在现有功能规格或反馈矩阵中记录事件的提示类型、文案键、确认动作及结果回调有效性规则。验证覆盖普通业务失败、需要确认的失败、后台加载与重试失败、重复回调及前台失败后自动重试；技术检查不替代用户对实际显示效果的人工验收。

## Toast 视觉任务

新建客户端需要 Toast 时，第 4 阶段先定全局视觉基线和所需[弹窗公共设计方案](reference-domain-display-ownership.md#弹窗公共设计方案)，确认公共风格。V2 生成并确认 Toast 模块的全部适用状态稿。沿用公共材质、字体、颜色、间距和动效语言，明确自身外观、位置及上飘淡出。没有弹窗需求时直接继承全局视觉规则。已有项目按有效范围复用设计、组件与证据；外观、布局或可见行为有变化时从本轮模块 V1 推进。业务消费统一接口，由 UI 层映射本地化文案。

Toast 使用独立 `DISPLAY_LAYER` 工作项，声明 `layerType=toast`、稳定 `objectId` 和单一实际 `hostId`，执行普通视觉任务路线。基础工程先提供正式工程中可运行的根宿主、浮窗挂载入口和验证入口，Toast 在该上下文验证自身行为，宿主无需完成正式画面。项目计划按“第 4 阶段确认全局基线和公共风格 → V1 确认方案 → V2 生成并确认模块稿 → V3 拆解 → V4 准备 → V5 完整实现及验收”记录依赖与交付引用；设计先后不要求不同对象处于相同 V 阶段。早期业务功能实施及 V1 不等待 Toast 视觉交付，按[可辨识的功能原型](../../app-creator-workflow/references/readable-functional-prototype.md)提供当前用例必需的最小反馈；正式提示接入复用完成的统一组件。

| 阶段 | Toast 的交付与验证 |
| --- | --- |
| 开工准备 | 明确统一接口、文案输入、实例所有者、实际宿主、挂载层和消费模块，以及当前需覆盖的状态 |
| V1 | 规划显示与消失、相同提示并发、空闲实例复用、旧回调隔离、宿主退出清理及输入透传，并确定验收用例 |
| V2 | 沿全局视觉基线和适用弹窗公共方案制作并确认模块中的 Toast 设计，覆盖背景、文字、颜色、起始落位及出现、停留、消失的视觉目标 |
| V3 | 按本栈路线完成拆解和布局交接，明确文本宽度、长文案与本地化、屏幕安全区、上飘空间和尺寸适配；Figma 已选稿清楚表达的结构与布局直接提取，不重复确认。Toast 本体落位及内部节点遵循[公共相对布局](../../app-ui-layout/references/relative-layout.md) |
| V4 | 在正式组件中接入背景、字体等所需资源，保存正式源与绑定，检查实际消费者。采用原生组件或矢量时记录对应路线及资源适用范围 |
| V5 | 在绑定的实际宿主验证正式组合、动画、层序、连续尺寸变化与重入，交用户人工确认显示效果后供业务模块复用 |

共享代码和资源由同一所有者维护。其他真实宿主接入时验证其挂载、层序、输入与生命周期，按本宿主记录结果。既有视觉确认仅按同对象、同宿主的有效复用规则引用。Toast 自身 V1 使用可控的真实调用验证，后台任务仍遵守静默规则。

## Toast 独立实例与复用

每次有效提示请求独占一个 Toast 实例，文案相同也立即显示，允许多个实例同时播放，不去重、不排队、不覆盖或重置其他活动实例。实例独立持有展示身份、文案、位置、透明度、动画和计时器，不以一个共享视图轮换承载并发提示。

允许通过对象池复用已经结束展示的空闲实例；池中无空闲实例时按需创建，不能等待其他提示结束。回收时停止动画、取消计时器并解绑订阅；再次使用时重置文案、位置、透明度和展示身份。完成、关闭或延迟回调须核对本次展示身份，旧回调不得隐藏、移动或回收已被复用的新展示。宿主退出时统一取消和回收其活动实例。

验证相同文案连续触发、多实例同时播放、空闲实例复用及旧回调到达；逐实例检查生命周期隔离，显示效果仍由用户人工验收。

## Toast 上飘与淡出动画

各栈 Toast 统一使用以下默认时间线，每个实例独立播放；参数在统一 Toast 组件中集中配置，不在调用方分别实现。

| 阶段 | 时长 | 位置与透明度 | 缓动 |
| --- | --- | --- | --- |
| 出现 | 180ms | 起始位置不变，透明度由 0 到 1 | `easeOutCubic` |
| 停留 | 1800ms | 位置不变，透明度保持 1 | 无 |
| 消失 | 500ms | 从停留位置向屏幕上方移动 200 个逻辑单位，同时透明度由 1 到 0 | `easeInCubic` |

上飘与淡出在消失阶段同时开始、同时结束，不额外增加入场位移、缩放或弹跳。200 个逻辑单位按项目既有 UI 逻辑坐标与视口适配映射，不能当作物理像素、世界单位或额外乘设备像素比；向上方向按当前技术栈坐标系换算。起始落位预留上方运动空间并检查安全区及裁切，小视口无法完整容纳轨迹时在布局规格中明确处理，不擅自改小位移。

动画结束后仅回收本次展示实例；复用前恢复起始位置、透明度和展示身份，取消旧动画及计时器，旧完成回调不得回收新展示。同样内容每次有效触发仍立即播放独立动画，不去重、不排队，不等待其他 Toast 完成；动画期间不抢焦点、不拦截输入。

启用“减少动态效果”时取消位移，保留淡入、停留和淡出。验证分别核对时间线、逻辑位移、透明度终值、多实例并发、复用重置及旧回调隔离；实际上飘效果、安全区和阅读体验由用户人工检查，不以技术检查代替视觉验收。

## 规格与交接

在现有产品或场景规格中按场景与状态区分内部规格和用户可见表达：内部规格记录规则、条件、计算、操作后果、设计理由与验收说明，用于理解和实现功能，不直接作为画面文字来源；用户可见表达记录图标或图片、数字或符号、必要短标签、允许出现的文字及其显示条件，无需文字时明确为空。动态数值标明数据来源、格式与效果图示例值，必要引导标明何时出现。

交接每组可见表达时，记录其依赖的场景、相邻信息、操作对象、图标含义与适用状态，明确哪些信息已由上下文表达、哪些需要文字补充。相关数值与变化关系读取同一业务规则；图标作为独立视觉元素交接，不把图标的内部描述绘制成文字。控件移位、组件复用或状态变化时，重新核对上下文是否仍足以说明其含义。

### 文字样式交接与验收

V3 在现有布局或原生设计合同中逐节点登记确认稿保留的可见文字，绑定来源节点或源图区域及适用状态。字体、字号、字色和透明度须有明确目标或无法核实的原因。逐项记录设计中可核实的字重、字距、行高、对齐、换行、描边和阴影等样式。多个节点可以引用同一个样式定义，节点、来源和状态仍各自可追溯。仅有位图参考时，按源图区域登记文字，并区分可核实属性与待人工确认的字形及效果。原型默认值和估计值只可作为未确认的参考。无可见文字的目标在现有设计合同中说明范围后跳过样式验证。

V4 与其他资源同批还原文字。逐项对照 V3 冻结的文字节点，把正式文字组件或独立文字图片放进当前模块的实际资源组合，核对位置、内容、有效可见性及可实测样式。按钮文案、数字、状态文字和图片字标按各自的节点和适用状态核对。将当前候选的实际读数纳入同一次 V4 资源验收。已有原生试装记录时复用其冻结引用，其他路线以 `textRestorationRef` 绑定资源评审。缺件、空白、隐藏或缺少实际读数时先修复再交接。业务调整需要删字时，先更新并确认受影响的设计目标，再更新实现。

V5 将 V4 已还原的文字接入正式场景或页面，从同一 V3 冻结目标逐项反查正式运行，核对实际组件或图片资源、可见内容、有效显示状态和样式。固定文字对照确认稿原文，动态或本地化文字对照当前语言和测试数据。可见性以当前状态自身及父级的实际显示为准。组件缺失、文字为空、图片未显示、读数缺项或样式有差异时，按节点和状态说明原因并保留为未完成。将原生读数关联到当前候选、设计来源和已有运行证据。用户在既有人工确认中核对实际画面及遮挡、裁切情况。
