# 性能预算、定位与优化复验

本规范适用于 Unity、Cocos、Phaser、Three.js、Flutter、ESP32 与 Node.js。确定性能预算、排查卡顿／加载缓慢／内存增长、实施已纳入范围的优化或审核优化结果时读取；各栈的原生工具、指标和证据要求由本栈规范补充。沿用已有计划、工作项与证据，不新增控制器字段、状态、独立审批或强制测量脚本。

## 触发、范围与预算

- 已明确要求的性能任务、当前范围内实测超预算、可重复的持续退化或卡顿／泄漏问题进入定位与定向修复。发现问题先记录证据与影响，不因此展开全项目优化；普通开发仍落实必要的资源、生命周期与有界并发约束，不为每次改动启动完整性能专项。
- 在已有技术方案或任务计划中说明目标平台、关键用户流程／服务负载、预算来源、当前基线、拟改善指标、允许改动范围、不可牺牲的功能／视觉条件及停止条件。没有明确预算时记录基线和待定目标，可以定位问题及报告相对变化，不能自行给所有项目设定 60 FPS、固定内存上限或将自拟阈值当作验收标准。
- 区分必需验证、已授权优化与额外可选工作。已批准范围内的普通本地测量、修复与复验连续推进，不重复征求同一选择；发布时额外检查、优化和图集处理仍按[性能与图集选择](../../app-release/references/release-readiness.md#性能与图集选择)分别采用用户的真实选择。编写或应用本规范不等于批准生成图集、改写图片、外部压测、付费、发布或真机运行。

## 按瓶颈选择指标

只测与任务、平台和关键流程相关的指标，不要求每项齐全，也不为凑指标安装工具。

| 方向 | 按需记录的指标与边界 |
| --- | --- |
| 启动与加载 | 进程／页面启动到首个可用画面、场景切换、弹出层首次打开及缓存命中耗时；明确起止事件，区分下载、解码、初始化、挂载与真正可交互 |
| 帧稳定性 | 帧耗时分布、卡顿次数与持续时间、适用的分位值及主线程阻塞；记录采样数与统计口径，平均 FPS 不能掩盖长帧 |
| 内存与资源 | 稳定占用、加载／切换峰值、反复进出后的趋势、缓存和 GPU 资源；区分已分配、驻留、保留及可回收数据，不能只凭单次占用或释放后未立即下降判定泄漏 |
| 渲染与 UI | Draw Call、批次、过绘、可见对象、粒子／阴影、纹理及 UI 更新／布局／重建；根据实际工具区分 CPU 与 GPU 成本，节点更少或批次下降本身不等于帧耗时改善 |
| 包体与传输 | 实际构建体积、首屏下载、重复资源、压缩／解码／解析成本；磁盘文件大小不能直接代表运行纹理或解码内存 |
| 服务端 | 指定负载下吞吐、响应延迟分位值、错误／超时率、事件循环、CPU／GC／内存、并发及队列；同时记录请求组合与依赖条件，单次响应时间不代表容量 |
| 嵌入式设备 | Flash、内部 RAM／PSRAM、运行峰值、最大连续可分配空间、缓冲、解码、刷新／传输及输入响应；主机模拟、静态 size 和板卡实测分别记录 |

## 建立可比较基线并定位

1. 复用项目已有采集工具与实际锁定版本，先检查可复用进程／服务／编辑器；确认没有适用实例后才启动新服务。只在授权目标上采样，服务端负载优先使用本地或已授权隔离环境，不默认对生产或外部依赖施压。
2. 记录源快照、资源／内容版本、工具与平台／设备、构建和采样模式、视口／分辨率、场景或数据规模、输入／负载、网络／依赖及缓存条件。按影响补充后台负载、温度／功耗状态等条件，不把开发模式、模拟器、静态估算或另一平台数据冒充目标性能。
3. 分开测冷启动与热启动、资源首次加载与缓存命中；记录准备过程、预热、采样窗口、重复次数、统计口径和原始输出。内存问题覆盖进入前、加载峰值、稳定运行、退出及多轮重入，结合资源引用和生命周期排查，不用强制 GC 或清缓存后的孤立数值掩盖真实运行成本。
4. 沿实际慢路径区分 CPU 计算／更新、GPU 绘制、磁盘／网络 I/O、解码解析、布局和资源驻留等原因，利用时间线、采样、计数或引用证据缩小范围；观察事实、根因假设与已证实原因分开记录，不凭代码观感选择优化手段。
5. 噪声较大时在可比条件下重复采样并报告波动范围；样本不足以支持分位值或趋势时明确限制。考虑 profiler、日志、调试覆盖和采集本身的开销，必要时减少干扰后复测。缺少目标环境时交付定位结果和未验证项，不伪造性能通过。

## 定向优化与成本取舍

优先修复已定位的重复加载／解码／计算、无效逐帧更新、重复布局／订阅、未停止任务、泄漏或无界队列。再围绕剩余瓶颈调整算法、数据访问、局部更新、调度、并发与资源组织；复用现有能力，按[技术方案选型顺序](../../app-creator-workflow/references/professional-conventions.md#solution-selection)决定是否需要新机制。

| 手段 | 采用前须说明并在复验中核对的代价 |
| --- | --- |
| 缓存与预取 | 命中收益、所有者、适用预算、失效／释放条件、冷启动和带宽／内存峰值；不能只优化重开而隐藏首次加载退化 |
| 对象池与复用 | 分配／GC 是否确为瓶颈、池容量、状态重置、空闲驻留与任务解绑成本；不能把对象池作为所有节点或实体的默认架构 |
| 图集、合批与实例化 | 实际批次及帧耗时收益、材质／采样限制、加载粒度、独立更新、纹理尺寸与驻留；批次减少不保证更快 |
| 压缩、LOD 与质量调整 | 包体、下载、解码、CPU／GPU、内存和显示效果的变化，不能只报告文件变小 |
| 异步、分帧、限流与批处理 | 总耗时、主线程响应、排队延迟、吞吐、顺序、取消和失败恢复；不能把阻塞换成长时间无反馈或丢失任务 |

- 场景及弹出层遵循[统一加载规范](reference-domain-display-ownership.md#场景与弹出层统一加载)：弹窗缓存模板、图片与依赖，关闭销毁实例并停止任务，业务状态及数据单独管理。不能以性能为由缓存弹窗运行实例、保留关闭后的更新或自动按空闲时间淘汰资源；释放共享资源前确认其他消费者。ESP32 的有界资源缓存仍按其原生预算和明确策略执行，不把桌面／浏览器驻留方案直接照搬到受限设备。
- 图集按场景、弹出层与共享资源的实际生命周期和消费者划分，避免打开小弹窗就加载大量无关资源。生成／更新须有明确选择，使用当前栈已有工具，验证映射、切片／帧元数据、采样／边缘、实际加载、峰值内存和合批收益；不为性能任务自动打图集。图片改写仅在[图片优化](../../app-image-optimization/SKILL.md)要求的明确请求范围内执行。
- 不以性能为由擅自改变正确性、交互时序、数据一致性、可访问性、已确认视觉、素材尺寸、动画精度或质量预算。确需改变体验或视觉目标时说明差异及取舍，按既有变更与确认流程处理；视觉表现仍由用户人工检查，不把截图分析当成默认验收方式。

## 同条件复验与停止

- 每轮围绕一个瓶颈或一组紧密相关改动实施，保留改动前后快照。用同一采集方法、构建／采样模式、场景、输入、缓存条件和统计口径对照；无法保持条件时说明差异，不直接作因果结论。覆盖受影响的冷／热路径、首次／缓存命中及重复进入，不能仅挑有利样本。
- 除目标指标外，复验可能被转移的成本，例如加载时间、峰值内存、包体、帧稳定性、队列延迟、错误率及退出清理；运行受影响的功能／生命周期回归。优化修改代码或资源后，按[验证约定](../../app-creator-workflow/references/verification.md)推荐并自动执行适用 T0–T3，测试通过不能代替性能采样，性能数字改善不能代替功能正确。
- 达到约定目标且必要回归通过后停止；收益无法与测量波动区分、问题并非该原因或引入更大代价时，撤回本轮无效优化并保留结论。撤回只针对本轮所有权内的改动，不重置工作区或覆盖他人修改。仍未达标或受环境／权限限制时说明现状、证据和剩余瓶颈，不临时放宽预算或将未验证写成通过。
- 服务端容量测试的负载与时长有界，错误、资源耗尽或影响隔离环境之外时停止并清理；真机、外部写入／压测及其他受保护操作仍需对应明确授权。已有授权范围内的普通复验无需新增批准。

在已有报告中按需增加以下对照，无须建立第二份长期性能账本或新 schema；原始数据引用当前工作项证据，目标达成、相对改善、无可辨收益、退化与未验证分别报告。

| 流程／指标及单位 | 目标／基线来源 | 优化前 | 优化后 | 采样条件与波动 | 改动与副作用 | 原始证据／结论 |

## 接入现有工作流

性能任务按[三项最小约定](../../app-creator-workflow/references/output-files.md#每项任务的最小约定)明确改善目标与结果、涉及修改／采样文件的路径、完成条件和验证方式；已有预算与方案直接引用，不逐任务重填负责人、批次或消费者。实际测量仍须保留可比条件、基线／优化后原始数据及复验结论，按需记入已有报告和当前证据；工具要求的身份／路径和采样所需版本不能省略，不另建强制报告或任务文档。

| 阶段／岗位 | 本规范中的职责 |
| --- | --- |
| 全局基线与架构 | 为目标平台和关键流程选定适用预算、负载、所有者及不可牺牲条件，复用既有有效基线 |
| 基础工程 | 保留可复现运行及按需采样入口，落实加载、缓存、任务和资源释放边界；不默认安装整套性能工具 |
| 功能实施 | 在当前范围遵守资源与更新约束；发现瓶颈后按证据定向修复，不混入无关优化 |
| 质量与集成 | 按实际风险覆盖关键组合、切换／重入和资源峰值，比较前后数据并执行受影响回归，保留未测目标 |
| 发布准备 | 汇总当前候选性能证据，额外检查／优化／图集按真实选择执行；输入改变后重建受影响候选并复验，不宣称已发布 |

客户端显示变化沿用当前增量的 V0–V5；纯非视觉优化按实际影响处理，不重做无关视觉确认。Node.js 使用模块／接口／任务及集成证据，不创建场景或视觉验收；ESP32 主机与设备证据严格区分。不增加统一强制 FPS、全量压测、图集生成或自动真机验收。
