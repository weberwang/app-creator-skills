# 多状态与多步骤的分批生产

适用于需要分批实现和验收的游戏大场景、长游戏流程、复杂页面或跨页面用户流程。沿用[统一工作流](../../app-creator-workflow/references/workflow.md)、功能切片、现有 Work Item 和 V1–V5，不建立第二套状态机。简单局部修改继续使用已有任务，不因本规范增加范围文件、审批或占位工作项。Node.js 等无界面服务按实际模块和接口推进，不凭本规范增加页面或视觉要求。

## 明确总范围与本批范围

先读已确认的产品需求、现有场景／页面规格、正式工程和已完成证据。只对实际存在或已确认的玩法、业务步骤和交互建模；未知且会改变范围或体验的决定按现有流程向用户澄清。把事实、假设和待定项分开；存档、联机、随机生成、区域流式加载、支付及其他外部能力只在项目确有需要时纳入，不预先引入机制或依赖。

在已有权威需求或场景／页面规格中明确：

| 内容 | 按实际需要记录的最小事实 |
| --- | --- |
| 总范围 | 用户／玩家要完成的任务、必须覆盖的对象和路径、完成条件与本期不做项 |
| 区域或分区 | 实际场景区域、页面分区或步骤宿主的用途、入口出口、邻接关系、共享对象和已有正式源；不因页面存在就强制划分区域 |
| 业务状态 | 状态含义、进入条件、允许的操作、退出结果、权威数据所有者和必要清理；暂停或弹窗等正交职责按实际关系表达 |
| 运行步骤与转移 | 实际初始／前置状态、玩家或用户操作、触发事件、期望状态及可观察结果；按需求补充失败、取消、分支、重试或恢复 |
| 验证与视觉目标 | 每条必要行为关联现有 `caseId`、实际对象及证据；只为需要独立确认的区域、镜头或有实质显示差异的状态建立视觉目标 |

区域、状态、步骤和视觉目标可以多对多关联。不要强制生成它们的笛卡尔积，不将动态数值的每个取值都当成独立状态或设计稿；不把 `stateId`、非空截图或计划命令视为状态转移已经实际验证。业务状态是游戏／应用的运行事实，控制器状态与实施单元顺序则是开发进度，两者不得相互代替。

游戏大场景与长流程先在现有 GDD／场景规格中明确整体骨架：区域与连接、核心机制、能力／任务／资源的解锁依赖、主要进程和完成条件。按已确认规则检查循环前置、关键资源断供及无法继续的组合，区分设计推演与实际运行；未知部分保留假设，不提前细化所有关卡、数值或资产。总范围明确不等于所有区域已完成。

每批再明确可玩的主路径与代表区域，以及与已实现邻区的连接、共享状态与资源接口。尚未实现的邻区只交接确需预留的连接条件和未覆盖范围，不因全景规划要求提前搭建其白模或声称路径可运行。当前和后续批次沿用同一正式场景源与单写者，区域边界或共享实现变化时按真实消费者和连接范围复验。

## 选择并完成一批

每批实施前直接执行[系统与模块覆盖](../../app-creator-workflow/references/system-module-coverage.md)：沿同一权威需求区分本批、后续与排除项，识别本批必要系统、规则和前置，并将设计来源、实施或复用任务及验收命令写入本批 `systemCoverage`。前批完成只证明其实际范围；后批仍需自己的覆盖映射和适用性验证，不能只继承页面、场景或历史 PASS。已有跨批依赖保留真实工作项链，不以删依赖或改为未决隐藏必要能力。

1. 按已确认需求和当前工作项选择前置已满足、可验证的玩家／用户路径。识别限制这条路径的风险及不确定性，前置不足时先完成最小必要能力。采用[白模与正式实现循环](../../app-creator-workflow/references/readable-functional-prototype.md#core-experience-first)时，开始前核对后批白模所需的前置均可在正式实现前完成。没有产品决定依据时不默认登录、商店或其他无关功能优先。
2. 按当前可实施范围确定对象、必要状态与步骤、输出路径、依赖和完成条件；这沿用[三项最小约定](../../app-creator-workflow/references/output-files.md#每项任务的最小约定)，按[增量影响](../../app-creator-workflow/references/professional-conventions.md#incremental-change-impact)核对真实消费者与所需回归，分工和依赖只在实际协作或存在先决条件时补充。涉及共同文件、场景、Place、路由或共享资源时明确唯一写者及集成顺序；互不冲突且依赖满足的部分可并行。
3. 在同一正式工程中实现当前切片并验证进入、操作、业务与数据结果和本批适用异常，检查状态写者、输入与异步回调、退出清理，沉淀必要的可重复回归测试；存在保存／恢复或联机时再覆盖对应机制。V1 可以使用真实功能或可辨识白盒，不等待其他对象的 V5；隔离探索明确临时范围和替换条件，不在后续批次重写已满足质量要求的机制。已有有效结果只在仍覆盖当前条件时复用。
   游戏世界按[本批可玩范围与交接](../../app-creator-workflow/references/readable-functional-prototype.md#大场景本批可玩范围与交接)落实代表区域、主路径及相邻接口，验证实际覆盖范围并复用有效白模与机制；未来区域和测试夹具不冒充已运行结果。
4. 核对本批实际完成范围、证据和未覆盖部分，再根据就绪条件选择下一批。范围或冻结的执行内容变化时，按现行规则修订受影响的工作项与证据。已确认范围全部实现并通过整体验证后收口。

例如游戏的已确认目标是“探索 → 收集 → 解锁 → 战斗 → 结算”：若入口和收集是本批优先范围，先交付可进入区域、有效收集、解锁条件及相应失败处理；战斗与结算保留为未完成范围。下一批在同一场景接入战斗和结果，再验证先前步骤到战斗的衔接。若战斗规则是最大技术不确定性，可先定向验证战斗，不能把临时样本冒称整条路径通过。App 分步编辑可同样先交付并验证“输入 → 校验”，再接入“提交 → 返回结果”；每批引用同一页面的正式源和实际数据所有者。

## 大场景与长游戏流程的推进

以下约束并入已有批次计划、场景规格与 QA 用例，不增加阶段、审批、调度台账或固定批次数：

1. **按连续玩家流程选批。** 一批可跨区域，也可只覆盖区域的一部分；以实际进入状态、主要行为、完成／失败结果和退出／恢复边界确定范围，不按地图面积、文件或资产数量分批。先验证最大不确定性，再接回真实玩家路径；后续区域复用有效机制、组件和正式内容入口，不逐区重建玩法。
2. **按模块制作，由宿主集成。** 依据现有场景组织拆出可独立编辑的区域内容、模板、配置和资产，明确坐标／尺度、连接口、状态交接及资源所有权。现有计划记录各部分当前成果、待验收范围和下一步，允许依赖明确且路径互斥的制作错峰推进；共享宿主由唯一写者顺序集成。同一对象仍按既有工作项和阶段验收，不按区域另造 `SCENE` 或阶段状态；子场景、分块及加载策略按本栈与实测需求选择。
3. **降低后期状态复现成本。** 到达问题现场需要长时间游玩、跨批累积或随机条件时，按[长流程状态复现与运行断言](../../app-quality-review/references/runtime-validation.md#long-flow-validation)复用测试存档、快照、种子、回放和适用的可控时钟；确有缺口再补最小项目能力。直达状态只支持定向检查，连续进入、跨区与保存恢复仍须实际验证。
4. **逐批延长集成路径。** 每批验证本批连续路径及适用的失败／重试／恢复、受影响的已实现邻区连接，以及穿过已有内容的必要关键路径；复用仍有效的无影响证据，不等全游戏完成才首次联调。单对象内的组合使用该对象现有用例；跨对象或共享机制按现有功能范围和 `feature` 集成组织，不为每批强制新建集成工作项。最终仍由 `final` 集成核对必要完整路径，分段或历史通过不能替代当前组合。
5. **按规模变化提前安排验证。** 区域往返、并存实体／资源增加、长链触发或重复重试可能引入累计成本时，在实施前确定代表路径、负载和需观测的持续运行风险，按[性能规范](performance-optimization.md)记录预算来源、基线、采样窗口／循环次数及停止条件；没有目标时报告观测与待定项。密度、加载粒度或共享生命周期变化后复验对应风险，不自设统一时长、帧率或内存阈值，不默认启动完整优化专项。跨批的成长、难度和重复负担按[人工试玩](game-content-playtesting.md#playtest)连续观察，局部体验不能外推为长期体验通过。

## 多页面推进顺序

App 包含多个页面时按业务切片分批实现。每个实际页面保留自己的 `PAGE` 工作项和 `objectId`。第 4 阶段按[版本视觉范围](../../app-workflow-control/references/version-visual-gate.md)生成并冻结覆盖整版流程与状态的设计稿，第 5 阶段 V2 只核对确认该稿，V3–V5 按实际依赖分批。

### 批内顺序与代表页

1. **选择本批路径**：从总范围选一条有价值且可验证的用户路径，列出实际页面、必要状态、共享能力和前置依赖；按依赖安排页面队列，不按目录、菜单顺序或页面数量平均分配。沿用已有计划记录当前阶段、下一步及阻塞原因，不增加调度账本。
2. **确认全局视觉**：第 4 阶段根据产品规格建立并由用户确认全局视觉基线和代表稿，[Figma App 默认一张代表页效果图](../../app-ui-layout/references/figma-app-design.md#方向探索与选定)用于确定方向。
3. **确认模块方案及设计**：V1 确认本轮全部约定的导航、参数、规则、进度、状态、结果、恢复和验收。V2 生成并确认覆盖模块全部适用状态和进度的设计稿，V3 拆解对应确认稿，V5 完整实现并验收。
4. **先试接代表组件**：优先选择能暴露公共组件、关键状态及适配风险的正式样本推进 V3–V5。Figma App 从已确认稿提取规格，适用图片路线分别确认拆解与布局。已有等效验证仍有效时直接复用。
5. **按依赖分批实施**：各页执行自身 V3 交接、V4 资源及 V5 正式组合验证。所需接口及方案已明确，路径和所有权互斥时可并行。受阻消费者等待其实际前置，独立工作继续。
6. **验证正式跨页路径**：在本批相关页面正式组合后，按既有集成流程回归导航、数据、状态、输入、加载／错误及返回恢复，再依据总范围选择下一批；全部必要范围完成后进行最终集成。代表页通过、单页 V5 或共享组件通过均不能代替整条路径验收。

例如“列表 → 详情 → 编辑 → 返回”，第 4 阶段确认代表页和全局风格；各模块在 V1 明确流程与状态，在 V2 生成并确认适用设计，再按依赖推进 V3–V5。

### 共享部分复用

- 全局视觉基线、公共导航、组件、资源和业务状态各保留一份正式来源及明确所有权。跨页面常驻导航框架仅在确需独立视觉验收时使用自己的 `PAGE`；仅属页面内部的导航留在该页，瞬态层按已有 `DISPLAY_LAYER` 规则处理。职责划分沿用[导航框架与共享路由](../../app-workflow-control/references/function-dependencies.md#导航框架与共享路由)。
- 复用已验收的公共组件和资源，不逐页复制实现或重新生产相同素材；每页仍验证自己的内容、状态、适配及与共享框架的实际组合。共享功能证据仅覆盖其实际验证的行为与对象，不扩大为目的页全部功能通过。
- 共享视觉规则和实现可跨页面消费，但不能把代表页的 V2/V3 人工确认或 V4/V5 结论直接当作另一页面的验收。`reuse-visual` 仍只继承同项目、同技术栈、同对象中未变化且有效的前置确认，不跨 `objectId` 继承页面确认。
- 共享接口、组件、资源或基线真实变化时，先确定消费者和影响范围，再安排生产与受影响页面回归；只处理变化部分，不重新设计全部页面，也不沿用已经失效的组合结论。

### 并行条件

多个页面只有同时满足以下条件才并行；不足时先交接必要前置或将冲突写入串行安排，不能仅因属于不同页面就默认并行：

- 当前阶段依赖的功能证据、共享视觉规则、组件接口及资源规格已经明确；不存在互相等待 V5 的循环依赖，也不消费另一任务尚未确定的结果。
- 页面代码、布局、资源及证据输出路径所有权互斥。路由注册、公共组件、主题、共享状态和资源清单等共同文件保持唯一写者，由其先交付所需变更或按顺序集成；不得让各页面代理并发改写。
- 所需运行宿主、编辑器和验证资源可以安全复用或隔离；同一物理编辑器、共享场景及配置保持单写者。并行不授权额外启动服务或真机验收。
- 已明确每项交付、验收范围及集成顺序，每页按自身阶段满足工程门与人工确认。不同 `PAGE` 的调度不要求对齐阶段；同一实施包内的执行单元则继续遵守[实施批次与结果状态](../../app-workflow-control/references/implementation-execution.md)的 `parallelGroup`、路径互斥和依赖规则，不把多个页面混装为同一个视觉对象。

## 累计对象与视觉增量

同一正式游戏场景使用稳定 `sceneId`／`objectId` 和一份权威场景内容；同一生产批次内，一个正式对象由一个对应 `SCENE` 工作项承载。后续生产批次可为同一对象建立新的工作项，沿用正式场景、共享资源及已确认的视觉基线，不按区域、状态、步骤或目标图复制运行场景。App 保留 `PAGE` 和独立的 `DISPLAY_LAYER`，复杂页面跨批沿用同一正式页面及对象身份；跨页面任务以实际 `PAGE`、`DISPLAY_LAYER` 和共享 `MODULE` 组合，不虚构游戏场景。

每批在 V1 确认实际变化与完整模块方案。新增或变化的模块稿在 V2 制作并确认，布局或素材增量可复用仍有效的依据；全局方向变化回第 4 阶段。纯逻辑／数据工作按实际范围验证。工程检查、截图采集和用户人工显示确认分别记录。

需要拆解与布局分别确认的图片路线在 V3 完成这些确认，非游戏 App 从已选 Figma 节点提取交接，无图 3D 世界交接已有模型／替换规格。3D 低风险批次正常生产和导入，高风险批次先验证首件或复用有效证据，再推进依赖批次。其他路线按[代表性接入与分批协作](../../app-asset-workflow/SKILL.md#代表性接入与分批协作)完成适用的样本与真实组件试接，再按已明确接口并行生产代码与素材，每批及时导入及检查消费者。3D 仅调整空间且模型及制作依据未变时，按[已有模型与证据复用](../../app-workflow-control/references/world3d-scenes.md#model-sample-reuse)关联有效来源，当前空间、工程与正式组合仍单独验证。验证失败先修正依赖范围，V5 完成整个对象或流程的正式验收。

图片路线已有视觉目标的实现、布局、素材或目标变化可继承的具体阶段见[视觉确认增量复用](../../app-creator-workflow/references/workflow.md#视觉确认的增量复用)；无图 `world-3d` 不使用 `reuse-visual` 自动继承阶段批准，可在[当前场景合同](../../app-workflow-control/references/world3d-scenes.md)引用并核对仍有效的场景源、模型、规格和方向。各路线每次仍需明确当前范围并验证受影响功能，不因复用而重跑无关视觉设计，也不继承旧的当前工程或运行通过结论。

图片路线大场景最新批次的视觉目标清单应覆盖以前仍有效的目标及本批新增／变化目标。只继承身份、场景、范围、状态、视口及目标文件均未变化的对应 V2／V3 真实确认；新增或变化目标正常确认，累计覆盖清单重新核对。同一 `SCENE` 本批图片目标共用 V 阶段，不能把每张图当独立对象。二维世界还须按[二维空间合同](../../app-workflow-control/references/multi-target-visual.md)核对空间规格、布局运行与人工空间确认，图片目标覆盖不能代替这些空间依据。无图 `world-3d` 以场景领域合同的 `scopeIds` 标识实际空间覆盖，不在世界根级声明图片 `visual.targets`；常驻 HUD 另按[同场景 HUD 合同](../../app-workflow-control/references/world3d-scenes.md#persistent-hud)维护 `visual.hud.scopeIds` 与图片 `visual.hud.targets`，不能拿 HUD 目标代替世界空间范围。各路线均须核对本批和累计实际覆盖，V4 素材、V5 正式运行和场景衔接按当前版本验证；历史场景工作项和确认链用于追溯，旧的工程或运行 PASS 不能代替当前组合回归。

## 批次完成与整体收口

最终集成在实施前通过 `systemCoverageMappings` 将参与对象、共享功能来源、生产前批及 V1／功能重验保留的来源包逐项关联到本次用例、单元与命令，详见[系统覆盖的最终闭环](../../app-creator-workflow/references/system-module-coverage.md#最终集成的系统覆盖闭环)。未通过视觉对象间接消费的必要模块，在最终范围 `systemSources` 显式列出其冻结工作项与实际消费对象。每条用例的结果须指向该单元已登记的命令输出，不能用独立 PASS 声明替代真实执行关联；最终用途及范围在实施后不可改标绕过。

绑定生产总范围时，最终来源还必须覆盖该范围的每个批次和对象；没有前置依赖关系的独立历史批次通过 `productionSources` 显式登记同范围的已完成来源，不通过给最终工作项伪造单批 `productionDependencies` 绕过。共享包中的各需求分别关联实际消费者，同源映射合计覆盖全部消费者。

本批完成只证明实际声明的功能、对象及证据范围。保留总范围、已完成和未完成部分，明确每项必要路径、状态转移、步骤、视觉目标及其实际证据，不以当前已经列入的事项倒推出完整范围。只有内容与依赖发生实际变化才更新受影响范围，不覆盖旧证据或重算旧摘要来冒充新验证。

每批收尾沿用[持续迭代与可接手收尾](../../app-creator-workflow/references/workflow.md#持续迭代与可接手收尾)，核对必要回归、当前项目说明、临时实现及下一批入口；实际改动存在职责或状态退化时在相关范围内修正。已有事实直接引用，不新增覆盖账本、维护评分或完整归档要求。

最终使用现有 `INTEGRATION` 工作项，在当前正式候选中覆盖已确认的必要完整路径、关键状态与转移、相关对象及适用的失败／重试／恢复。游戏检查实际区域、镜头、资源生命周期、共享状态及场景／弹窗交接；App 检查页面导航、数据、输入、键盘、加载与错误状态及返回恢复。最终集成与人工视觉／体验结论分别记录，缺失、未运行、失败或待用户检查的范围不能标成整场景／整流程通过。

按项目实际需要测量资源、内存、帧耗时和加载收益，再决定区域分块、预取或缓存；不得因场景较大就默认创建流式加载系统、图集或额外 SDK。系统启动屏与应用内加载仍分别遵守各自的公共规范。

## 原生实现与交接

- Unity／Cocos：按项目实际 Scene、Prefab／节点、资源身份与编辑器单写者执行，正式源和引用必须保存并回读；不同批次不得复制场景或并发覆盖共享资产。
- Phaser／Three.js：按实际世界、镜头、画布／DOM、资源加载和销毁生命周期执行，不能用不同视图的独立背景图替代同一运行世界。
- Roblox：同一 Place 可承载多功能或数据关卡；分别核对 Edit 正式源与 Client／Server 的状态权威和同步。跨 Place 是不同运行上下文，不能假设旧实例自然延续。
- Flutter／Expo：按实际页面、导航栈、数据与状态所有权处理分步表单、异步结果、键盘／安全区和返回恢复；原生与 Web、模拟和真机按实际环境分别记录。

实现顺序、所有权、范围、命令与实际结果沿用当前计划、实施包和证据；不要另建角色总控或平行的覆盖账本。具体领域格式与平台 API 按所选栈原生规范确定，真实设备、外部写入、付费、签名、上传和发布仍需对应明确授权。

## 按需绑定机器范围

涉及跨批解锁、多区域共享状态或长路径依赖时，实施前在已有需求或工作项中明确是否使用生产范围绑定；不绑定时说明由哪些现有规则、用例和 QA 记录维护覆盖，不另写评估报告。同场景或同页面跨批未绑定总范围时，最终范围在 `productionSources` 显式登记需要保留的同对象、同类型已完成前批，最新对象与各前批的需求分别进入 `systemCoverageMappings` 并关联当前最终用例和命令；历史 PASS 不代替当前运行，控制器也不能推断未登记的前批或原始需求是否完整。多状态、多步骤范围需要由控制器核对时，使用[生产范围模板](../../app-workflow-control/templates/production-scope.json)建立项目内结构化总范围，绑定同一项目和技术栈；按照模板记录实际对象、必要状态、步骤、状态转移和生产批次。实际需要时通过 `regions` 声明区域，并在所属对象状态的 `regionIds` 中引用，不为 App 强制创建区域。`objects` 中 `SCENE.targetIds` 表达整个范围需要覆盖的场景目标身份：图片路线由 `visual.targets` 记录截至本批纳入的累计图片目标；无图 `world-3d` 由当前场景领域合同的 `scopeIds` 对应该总范围内的空间身份，不使用世界根级 `visual.targets`。`world-2d` 另以 `visual.sceneDesignRef` 关联含独立 `scopeIds` 的二维空间合同及其布局、运行和空间确认；它们不能由图片覆盖替代。最终集成时按实际路线分别核对总范围；首批不要求提前完成未来目标。3D 常驻 HUD 的 `visual.hud.scopeIds`／`visual.hud.targets` 属于同一宿主内的独立 HUD 合同，不与世界 `scopeIds` 互换。PAGE／DISPLAY_LAYER 沿用各栈单目标合同。每个必要步骤或转移引用对应实际行为的 `caseId`；批次只列本批承担的对象、步骤和转移。没有该机制时不要制造占位状态或步骤。

初始化生产工作项时以 `--production-scope <项目相对范围 JSON>` 和 `--production-batch <批次 ID>` 绑定范围文件及本批身份；最终 `INTEGRATION --integration-purpose final` 使用相同 `--production-scope` 而不指定批次。实际批次存在 `dependsOn` 时，通过 `--production-dependencies <项目相对 JSON>` 提供前置数组，每项写 `{batchId, workItemRef:{path}}`；没有前置批次无需提供。初始化可先声明项目内计划创建的前置工作项路径，不为此生成占位文件。执行 `plan` 冻结前，所引用的前置须真实存在、已完成且项目、技术栈、总范围和批次身份一致；控制器自动冻结该实际完成版本的 SHA-256，不以未完成版本当作有效前置。

有顺序要求的用户路径通过总范围的 `paths` 声明 `pathId`、有序 `stepIds` 和 `caseId`，批次用 `pathIds` 纳入当前范围。重试需要重复执行某步骤时，在列表中保留重复项；覆盖记录及最终行为结果的 `paths` 必须记录同一实际顺序和重复次数，不能仅用步骤集合表示路径走通。声明的区域须被同一对象的业务状态引用，不能把孤立区域留在总范围而永远不验证；这项静态关联仍不证明玩家实际走遍区域。`DISPLAY_LAYER` 对象还须声明并核对实际 `hostId` 和 `layerType`。

长流程在已有规则／QA 中按进入与退出状态分段复用用例，必要分支分别明确实际条件和顺序。可将各段 `paths` 分配给实际生产批次，在最终 `integrationScopeRef.cases` 冻结完整链路用例，由项目测试断言真实顺序并保留连续运行证据；控制器不会自动把分段组合成完整路径。需要对完整路径使用生产范围的顺序核对时，`paths.stepIds` 须展开真实步骤，不能填入子路径 ID、条件表达式或省略循环次数；每条已声明路径至少由一个批次完整纳入，跨批完整路径安排给承担组合验证的实际批次，并列入它重验的步骤／对象。不要求早期批次运行未来内容，也不把分段证据拼接为连续运行通过。范围尚未确定的后续路径保留在权威需求的待定范围，确定后按下述范围变更规则重新绑定，不制造可通过的占位步骤。

前置批次只涉及一个显示对象时，可引用该对象的已完成工作项；涉及多个显示对象时，须引用覆盖整批的无视觉 `MODULE` 或 `integrationPurpose: feature` 集成，不能用其中一个页面或场景代替整批完成。前置功能就绪与各显示对象的视觉验收分别成立，汇总工作项不代替后续正式组合验证。

白模循环在冻结范围和计划前检查跨批依赖，确保后批白模所需的前置可以在正式实现前完成。若绑定生产范围且需要机器核对跨批前置，使用同一冻结范围内确实完成、覆盖前置批次的 `MODULE` 或 `feature` 集成。单对象 V1 结果只支持该对象的功能基线。已有冻结依赖要求某个正式对象先完成 V5 时，先按既有范围变更规则调整受影响计划，解决依赖冲突后再采用两轮路线。

`plan` 将范围、批次及适用依赖绑定到实施包和执行计划，后续改变或换绑必须重新建立受影响的计划与验证，不能在结果中缩小范围。进入实施及后续检查持续核对前置完成状态和冻结摘要；前置完成只是前置结论，不代替当前版本运行验证。总范围变更后重新绑定并验证受影响范围，不能静默把旧范围下的批次当作新范围已就绪。小范围任务和没有该输入的现有工作项继续使用原流程。

沿用原范围已声明的批次推进，不为更新开发进度改写总范围。实际范围变化时保留旧冻结来源，先在已有计划列明新增／变化项、消费者和需要重新建立的来源链；当前依赖仍要求同一冻结范围，不能声称自动继承另一摘要的批次。工程事实或测试证据仅在仍覆盖当前条件时引用，受影响部分重新执行，不能通过改写旧工作项或摘要迁移结论。

已绑定范围的视觉工作项在 V1 和 V5、无视觉 `MODULE`／早期 `feature` 集成在完成本批前，提交当前 Evidence Manifest 中唯一 `production-coverage` PASS 记录，字段形状见[生产覆盖模板](../../app-workflow-control/templates/production-coverage.json)。覆盖记录绑定总范围、工作项、批次、实施包及适用视觉阶段；`cases` 按 `caseId` 记录真实覆盖的 `objectIds`、`stateIds`、`stepIds` 和状态转移身份。每个 case 的原始运行输出以 `evidenceRef: {path,sha256}` 引用当前 `evidenceRoot` 中独立、非空文件，且该文件也应列入当前 Manifest 的 PASS 证据。V2–V4 不要求提前提交未来的运行结果。

最终集成的现有 `integrationScopeRef` 文件须以 `productionScopeRef: {path,sha256}` 绑定工作项所用的同一总范围，并引用当前已完成的累计对象；SCENE 的累计 `targetIds` 须与总范围一致，PAGE／DISPLAY_LAYER 仍执行各自单目标合同。最终集成继续使用现有行为结果文件，其 `production` 记录声明本次实际覆盖的 `stateIds`、`stepIds`、`transitions` 及当前 `evidenceRoot` 内原始输出 `evidenceRef`；原始输出须列入当前 Manifest 的 PASS 证据，范围与 case 不得遗漏必要对象或 `caseId`。所有模板均为填写指导，不是验收结果；原始数据、环境和人工确认必须来自真实执行。控制器核对文件、身份和覆盖关系，无法独立判断日志事件或截图内容是否真实发生。
