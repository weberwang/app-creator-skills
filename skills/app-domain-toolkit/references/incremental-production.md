# 多状态与多步骤的分批生产

适用于需要分批实现和验收的游戏大场景、复杂页面或跨页面用户流程。沿用[统一工作流](../../app-creator-workflow/references/workflow.md)、功能切片、现有 Work Item 和 V0–V5，不建立第二套状态机。简单局部修改继续使用已有任务，不因本规范增加范围文件、审批或占位工作项。Node.js 等无界面服务按实际模块和接口推进，不凭本规范增加页面或视觉要求。

## 明确总范围与本批范围

先读已确认的产品需求、现有场景／页面规格、正式工程和已完成证据。只对实际存在或已确认的玩法、业务步骤和交互建模；未知且会改变范围或体验的决定按现有流程向用户澄清。把事实、假设和待定项分开；存档、联机、随机生成、区域流式加载、支付及其他外部能力只在项目确有需要时纳入，不预先引入机制或依赖。

在已有权威需求或场景／页面规格中明确：

| 内容 | 按实际需要记录的最小事实 |
| --- | --- |
| 总范围 | 用户／玩家要完成的任务、必须覆盖的对象和路径、完成条件与本期不做项 |
| 区域或分区 | 实际场景区域、页面分区或步骤宿主的用途、入口出口、邻接关系、共享对象和已有正式源；不因页面存在就强制划分区域 |
| 业务状态 | 状态含义、进入条件、允许的操作、退出结果、权威数据所有者和必要清理；暂停或弹窗等正交职责按实际关系表达 |
| 运行步骤与转移 | 实际初始／前置状态、玩家或用户操作、触发事件、期望状态及可观察结果；按需求补充失败、取消、分支、重试或恢复 |
| 验证与视觉目标 | 每条必要行为关联现有 `caseId`、实际对象及证据；只为需要独立确认的区域、镜头或有实质显示差异的状态建立视觉目标 |

区域、状态、步骤和视觉目标可以多对多关联。不要强制生成它们的笛卡尔积，不将动态数值的每个取值都当成独立状态或设计稿；不把 `stateId`、非空截图或计划命令视为状态转移已经实际验证。业务状态是游戏／应用的运行事实，控制器状态与实施单元顺序则是开发进度，两者不得相互代替。

## 选择并完成一批

1. 从已确认目标选首条有价值且可验证的玩家／用户路径，识别限制这条路径的高风险、最大不确定性和真实前置依赖；前置不足时先完成最小必要能力。没有产品决定依据时不默认登录、商店或其他无关功能优先。
2. 按当前可实施范围确定对象、必要状态与步骤、输出路径、依赖和完成条件；这沿用[三项最小约定](../../app-creator-workflow/references/output-files.md#每项任务的最小约定)，按[增量影响](../../app-creator-workflow/references/professional-conventions.md#incremental-change-impact)核对真实消费者与所需回归，分工和依赖只在实际协作或存在先决条件时补充。涉及共同文件、场景、Place、路由或共享资源时明确唯一写者及集成顺序；互不冲突且依赖满足的部分可并行。
3. 在同一正式工程中实现当前切片并验证进入、操作、业务与数据结果和本批适用异常，检查状态写者、输入与异步回调、退出清理，沉淀必要的可重复回归测试；存在保存／恢复或联机时再覆盖对应机制。V1 可以使用真实功能或可辨识白盒，不等待其他对象的 V5；隔离探索明确临时范围和替换条件，不在后续批次重写已满足质量要求的机制。已有有效结果只在仍覆盖当前条件时复用。
4. 核对本批实际完成范围、证据和未覆盖部分，再选择下一批。范围变更时先更新受影响事实及计划；不因目录或文件数量决定下一步，不自动循环润色。已确认范围全部实现并通过整体验证后收口。

例如游戏的已确认目标是“探索 → 收集 → 解锁 → 战斗 → 结算”：若入口和收集是本批优先范围，先交付可进入区域、有效收集、解锁条件及相应失败处理；战斗与结算保留为未完成范围。下一批在同一场景接入战斗和结果，再验证先前步骤到战斗的衔接。若战斗规则是最大技术不确定性，可先定向验证战斗，不能把临时样本冒称整条路径通过。App 分步编辑可同样先交付并验证“输入 → 校验”，再接入“提交 → 返回结果”；每批引用同一页面的正式源和实际数据所有者。

## 累计对象与视觉增量

同一正式游戏场景使用稳定 `sceneId`／`objectId` 和一份权威场景内容；同一生产批次内，一个正式对象由一个对应 `SCENE` 工作项承载。后续生产批次可为同一对象建立新的工作项，沿用正式场景、共享资源及已确认的视觉基线，不按区域、状态、步骤或目标图复制运行场景。App 保留 `PAGE` 和独立的 `DISPLAY_LAYER`，复杂页面跨批沿用同一正式页面及对象身份；跨页面任务以实际 `PAGE`、`DISPLAY_LAYER` 和共享 `MODULE` 组合，不虚构游戏场景。

每批只对实际可见变化从本次 V0 定义范围并完成 V1 功能验证。新增显示目标按适用范围完成 V2–V5；布局或素材增量按实际影响复用仍有效的前置确认；纯逻辑／数据工作不强制进入视觉链。全局三候选只用于首次选择视觉方向，不为每个区域、步骤或状态重新生成三套风格。V2–V5 的工程检查、截图／录屏采集与用户人工显示确认分别记录，代理未经明确要求不分析截图或代填视觉通过。

V3 拆解与布局分别确认后，按[代表性接入与分批协作](../../app-asset-workflow/SKILL.md#代表性接入与分批协作)在 V4 前段完成必要的少量样本与真实组件试接，再按已明确接口并行生产代码与素材，每批及时导入及检查消费者。复用可靠方案时只补变化部分，不逐批重做同样样本；试接失败先修正依赖范围，不将首次装配风险留给 V5，也不把样本通过当作整个对象或流程已验收。

已有视觉目标的实现、布局、素材或目标变化可继承的具体阶段见[视觉确认增量复用](../../app-creator-workflow/references/workflow.md#视觉确认的增量复用)；每次仍需明确当前范围并验证受影响功能，不因复用而重跑无关视觉设计，也不继承旧的当前工程或运行通过结论。

大场景最新批次的视觉目标清单应覆盖以前仍有效的目标及本批新增／变化目标。只继承身份、场景、范围、状态、视口及目标文件均未变化的对应 V2／V3 真实确认；新增或变化目标正常确认，累计覆盖清单重新核对。当前批次目标仍共用 V 阶段，V4 素材、V5 正式运行和场景衔接按当前版本验证。历史场景工作项和确认链用于追溯，旧的工程或运行 PASS 不能代替当前组合回归。

## 批次完成与整体收口

本批完成只证明实际声明的功能、对象及证据范围。保留总范围、已完成和未完成部分，明确每项必要路径、状态转移、步骤、视觉目标及其实际证据，不以当前已经列入的事项倒推出完整范围。只有内容与依赖发生实际变化才更新受影响范围，不覆盖旧证据或重算旧摘要来冒充新验证。

每批收尾沿用[持续迭代与可接手收尾](../../app-creator-workflow/references/workflow.md#持续迭代与可接手收尾)，核对必要回归、当前项目说明、临时实现及下一批入口；实际改动存在职责或状态退化时在相关范围内修正。已有事实直接引用，不新增覆盖账本、维护评分或完整归档要求。

最终使用现有 `INTEGRATION` 工作项，在当前正式候选中覆盖已确认的必要完整路径、关键状态与转移、相关对象及适用的失败／重试／恢复。游戏检查实际区域、镜头、资源生命周期、共享状态及场景／弹窗交接；App 检查页面导航、数据、输入、键盘、加载与错误状态及返回恢复。最终集成与人工视觉／体验结论分别记录，缺失、未运行、失败或待用户检查的范围不能标成整场景／整流程通过。

按项目实际需要测量资源、内存、帧耗时和加载收益，再决定区域分块、预取或缓存；不得因场景较大就默认创建流式加载系统、图集或额外 SDK。系统启动屏与应用内加载仍分别遵守各自的公共规范。

## 原生实现与交接

- Unity／Cocos：按项目实际 Scene、Prefab／节点、资源身份与编辑器单写者执行，正式源和引用必须保存并回读；不同批次不得复制场景或并发覆盖共享资产。
- Phaser／Three.js：按实际世界、镜头、画布／DOM、资源加载和销毁生命周期执行，不能用不同视图的独立背景图替代同一运行世界。
- Roblox：同一 Place 可承载多功能或数据关卡；分别核对 Edit 正式源与 Client／Server 的状态权威和同步。跨 Place 是不同运行上下文，不能假设旧实例自然延续。
- Flutter／Expo：按实际页面、导航栈、数据与状态所有权处理分步表单、异步结果、键盘／安全区和返回恢复；原生与 Web、模拟和真机按实际环境分别记录。

实现顺序、所有权、范围、命令与实际结果沿用当前计划、实施包和证据；不要另建角色总控或平行的覆盖账本。具体领域格式与平台 API 按所选栈原生规范确定，真实设备、外部写入、付费、签名、上传和发布仍需对应明确授权。

## 按需绑定机器范围

多状态、多步骤范围需要由控制器核对时，使用[生产范围模板](../../app-workflow-control/templates/production-scope.json)建立项目内结构化总范围，绑定同一项目和技术栈；按照模板记录实际对象、必要状态、步骤、状态转移和生产批次。实际需要时通过 `regions` 声明区域，并在所属对象状态的 `regionIds` 中引用，不为 App 强制创建区域。`objects` 中 SCENE 的 `targetIds` 表达整个范围需要覆盖的视觉目标；当前批次的 `visual.targets` 记录截至本批已纳入的累计目标，不要求首批提前完成未来目标。PAGE／DISPLAY_LAYER 沿用各栈单目标合同。每个必要步骤或转移引用对应实际行为的 `caseId`；批次只列本批承担的对象、步骤和转移。没有该机制时不要制造占位状态或步骤。

初始化生产工作项时以 `--production-scope <项目相对范围 JSON>` 和 `--production-batch <批次 ID>` 绑定范围文件及本批身份；最终 `INTEGRATION --integration-purpose final` 使用相同 `--production-scope` 而不指定批次。实际批次存在 `dependsOn` 时，通过 `--production-dependencies <项目相对 JSON>` 提供前置数组，每项写 `{batchId, workItemRef:{path}}`；没有前置批次无需提供。初始化可先声明项目内计划创建的前置工作项路径，不为此生成占位文件。执行 `plan` 冻结前，所引用的前置须真实存在、已完成且项目、技术栈、总范围和批次身份一致；控制器自动冻结该实际完成版本的 SHA-256，不以未完成版本当作有效前置。

有顺序要求的用户路径通过总范围的 `paths` 声明 `pathId`、有序 `stepIds` 和 `caseId`，批次用 `pathIds` 纳入当前范围。重试需要重复执行某步骤时，在列表中保留重复项；覆盖记录及最终行为结果的 `paths` 必须记录同一实际顺序和重复次数，不能仅用步骤集合表示路径走通。声明的区域须被同一对象的业务状态引用，不能把孤立区域留在总范围而永远不验证；这项静态关联仍不证明玩家实际走遍区域。`DISPLAY_LAYER` 对象还须声明并核对实际 `hostId` 和 `layerType`。

前置批次只涉及一个显示对象时，可引用该对象的已完成工作项；涉及多个显示对象时，须引用覆盖整批的无视觉 `MODULE` 或 `integrationPurpose: feature` 集成，不能用其中一个页面或场景代替整批完成。前置功能就绪与各显示对象的视觉验收分别成立，汇总工作项不代替后续正式组合验证。

`plan` 将范围、批次及适用依赖绑定到实施包和执行计划，后续改变或换绑必须重新建立受影响的计划与验证，不能在结果中缩小范围。进入实施及后续检查持续核对前置完成状态和冻结摘要；前置完成只是前置结论，不代替当前版本运行验证。总范围变更后重新绑定并验证受影响范围，不能静默把旧范围下的批次当作新范围已就绪。小范围任务和没有该输入的现有工作项继续使用原流程。

已绑定范围的视觉工作项在 V1 和 V5、无视觉 `MODULE`／早期 `feature` 集成在完成本批前，提交当前 Evidence Manifest 中唯一 `production-coverage` PASS 记录，字段形状见[生产覆盖模板](../../app-workflow-control/templates/production-coverage.json)。覆盖记录绑定总范围、工作项、批次、实施包及适用视觉阶段；`cases` 按 `caseId` 记录真实覆盖的 `objectIds`、`stateIds`、`stepIds` 和状态转移身份。每个 case 的原始运行输出以 `evidenceRef: {path,sha256}` 引用当前 `evidenceRoot` 中独立、非空文件，且该文件也应列入当前 Manifest 的 PASS 证据。V2–V4 不要求提前提交未来的运行结果。

最终集成的现有 `integrationScopeRef` 文件须以 `productionScopeRef: {path,sha256}` 绑定工作项所用的同一总范围，并引用当前已完成的累计对象；SCENE 的累计 `targetIds` 须与总范围一致，PAGE／DISPLAY_LAYER 仍执行各自单目标合同。最终集成继续使用现有行为结果文件，其 `production` 记录声明本次实际覆盖的 `stateIds`、`stepIds`、`transitions` 及当前 `evidenceRoot` 内原始输出 `evidenceRef`；原始输出须列入当前 Manifest 的 PASS 证据，范围与 case 不得遗漏必要对象或 `caseId`。所有模板均为填写指导，不是验收结果；原始数据、环境和人工确认必须来自真实执行。控制器核对文件、身份和覆盖关系，无法独立判断日志事件或截图内容是否真实发生。
