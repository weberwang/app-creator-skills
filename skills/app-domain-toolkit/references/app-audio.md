# 非游戏 App 音频工作流

适用于 Flutter、Expo 等非游戏客户端已确认的音频需求；ESP32 仅在现有硬件及需求支持声音输入／输出时使用。普通页面、按钮或反馈不自动启用音频，不默认添加点击音、背景音乐或成功提示音。Node.js 无界面服务不按本规范创建播放器、录音界面或客户端音频服务。

## 用途分流

先从已确认需求判断本批是否涉及音频，没有需求就跳过音频专项。用途可以组合，但只建设当前路径需要的能力：

| 用途 | 本批需要明确的内容 |
| --- | --- |
| 提示音与操作反馈 | 业务事件、触发／结束条件、限频、并发、静音及可理解的视觉／文本替代反馈 |
| 音乐、播客、课程等内容播放 | 内容来源、播放状态、进度、切换、跨页所有权、前后台及中断恢复策略 |
| 录音、朗读与语音交互 | 输入／输出、使用时所需权限、开始／完成／取消、结果归属、中断及失败恢复 |
| 系统通知与定时提醒 | 交由实际平台通知／调度能力处理，明确触发与取消条件；不靠页面播放器或假设后台计时常驻来替代 |

音频功能和声音素材分开安排。播放已有课程、用户录音或系统语音时，不强制制作音效、配乐、变体或混音总线；确需声音素材时才安排设计与制作。重要业务结果不能仅靠声音表达，静音、权限不可用或播放失败时仍可理解和操作。

## 方案与代表用例

在现有产品规格、技术设计或音频计划中明确本批目的、事件／内容来源、触发与结束条件、状态所有者、重复与中断策略、静音、前后台行为、失败恢复、资源来源及验证条件；已有事实直接引用，不为每页、每段音频创建独立计划或审批。

选择能覆盖主要风险的一条代表路径，先验证实际能力再推广：

- 提示音可验证“触发 → 连续操作 → 静音”，检查重复疲劳、限频和是否误报业务结果。
- 内容播放可验证“播放 → 切页 → 系统中断 → 恢复”，检查进度、实例与用户主动暂停是否保持有效。
- 录音可验证“开始 → 取消／完成 → 返回”，检查输入释放、迟到回调、结果归属和失败恢复。

已有正式方案覆盖当前条件时直接复用；不用所有页面逐一验证同一底层机制。代表用例只证明实际覆盖的条件，目的页业务、不同平台及权限状态仍按影响验证。确定需要制作声音时，先交能代表用途和风险的可试听样本，再按已定方向扩展；已有合格素材直接复用，不按事件数量强制生成变体。

## 生命周期与所有权

跨页面持续播放由应用级或明确的业务会话所有者持有，页面读取状态并发送播放、暂停、切换和停止指令，不各自创建第二个播放器。页面专属短音效由其消费者负责清理。录音与语音任务按会话管理输入、输出、订阅和取消；迟到回调不得写入已退出页面或替换新会话结果。只按实际需要拆职责，不预建完整音频框架。

先在方案中选择用途对应的生命周期策略，再配置和验证所选平台的实际能力：

- **上下文短音频**：提示音、页面专属声音在离开上下文或进入后台时按方案停止／取消，失效请求不排队回前台补播；返回页面不重播旧提示。
- **持续内容播放**：明确切页是否续播、是否需要后台播放、用户操作与系统中断后的恢复方式。仅在需求包含且目标平台配置、权限及运行证据支持时启用后台播放；未满足时按已声明的暂停／恢复策略处理，不能因媒体用途就宣称后台已支持。
- **录音与语音会话**：明确页面退出、后台、权限失效及系统中断时是结束、取消还是允许继续，并核对目标平台实际限制；不得默认后台录音或自动重启已取消的会话。

暂停与恢复沿用[通用生命周期约束](audio.md#后台暂停与恢复约束)：区分用户主动操作、生命周期和系统中断，重复通知幂等，仅处理仍有效的请求。用户主动暂停、停止、取消或已结束的会话不能被回前台事件复活。游戏跨场景背景音乐的持续播放规则不自动用于 App 内容队列或录音。

## 阶段与多页面协作

音频能力在相关 V1 验证实际行为，代表样本可在需要判断体验时提前探索。纯音频／逻辑改动使用现有 `MODULE` 或资源实施单元，不要求视觉 V2/V3；新增播放器、录音控件或其他可见表现时，所属页面／显示层继续执行其适用 V0–V5，声音样本或功能通过不能替代页面验收。

多页面沿用[多页面推进顺序](incremental-production.md#多页面推进顺序)，按当前消费者复用音频服务、状态和资源，不为每页复制实现或声音素材。音频代表路径可结合代表页验证，但不要求每个页面有声音，也不把某页 V5 当作共享音频功能来源的前置门。

事件、接口、状态和素材规格明确后，页面实现与素材制作可并行；共享音频服务、平台配置及资源清单保持唯一写者。共享能力变更后核对实际消费者，只回归受影响路径。素材制作优先复用合法且合格的文件；确需制作时使用实际可用的项目工具或素材渠道，记录来源、许可、制作输入和必要转换，不把游戏音效预设当作录音、语音合成或完整配乐能力。

本规范随公共资料交付，不表示当前栈已声明 `app-audio` 原生专项模式。实施前核对当前项目依赖、版本和该栈实际原生／插件规范；未声明能力时不调用 `read-native-mode` 的 `app-audio` 路线，不借用游戏引擎接口或新增虚构适配器。需要外部服务、上传或付费时仍须对应明确授权。

## 验证与交付

按本次范围分别记录三类结果，不用一类通过代替另一类：

- **文件技术检查**：有实际文件时检查可解码、格式、声道、时长及适用边界、静音／削波和大小，保留来源与许可。纯平台语音或流式内容不为检查制造本地文件，按其真实来源和执行记录验证。
- **实际运行行为**：验证本批所需首次播放／录音、连续操作、重复指令、静音或音量、取消、切页、失败及适用中断恢复；涉及后台、权限或音频路由时记录实际平台、配置和覆盖条件。模拟与 Web 结果不冒充原生目标结果。
- **用户人工听感**：提示音关注辨识与重复疲劳，内容播放关注可听度与衔接，录音／语音关注清晰度与业务可用性。已有素材可先单独试听，接入后再检查实际上下文；没有用户反馈时保持待确认，不由文件指标代写听感通过。

交付复用已有工作项、技术设计和资源记录，列明实际实现、文件／内容来源、命令及原始结果、人工反馈和未覆盖范围。代码、配置或文件存在不证明声音已播放／录制；未运行、未试听、权限未验证及后台能力未验证分别说明。普通本地验证不自动发起真机运行、外部写入、上传或发布。
