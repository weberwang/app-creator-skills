# 游戏实施与集成

执行公共规则时，同时读取当前技术栈参考中的原生补充和“本栈配套资料”。各段仅适用于标注的技术栈；结构化证据不代替用户对显示效果的人工验收。

各技术栈统一使用 V0–V5；V1 是功能实现与验证，白盒可选，正式功能不必等待视觉目标。

## 游戏实现规则

> 适用技术栈：cocos、phaser、threejs。

瞬态弹窗建立独立 DISPLAY_LAYER Work Item；缺参考上下文时停留在弹窗自身前置门，不写入宿主场景 `deferred_layers`。场景只完成自身画面和常驻 HUD，弹窗未完成不影响场景 V5。弹窗正式代码仍需自己的 V3/V4、冻结宿主公开接口和互斥所有权。

## 默认实施闭环

> 适用技术栈：cocos、phaser、threejs。

在当前用户任务、Work Item 适用门禁及视觉阶段的边界内，以最小充分事实实施：入口、关键调用链或契约、范围、主要风险和验收目标明确且无直接冲突后停止探索。需要实施包时，先绑定任务范围、文件所有权、验收和停止条件，再按包执行；可逆本地任务可记录合理假设，缺少完全证明不单独阻塞。任务内方案、路径和资源清单可随实施更新计划，并重验实际受影响部分。

> 适用技术栈：cocos、phaser、threejs。

实施包冻结后按包执行；需求或范围变化、实质冲突或无法实施时处理受影响范围。顺序为：最小事实确认、冻结候选边界及适用实施包、实施、核对实际变更、推荐并自动执行适用等级验证、依据失败证据修正、完成。已确认事实不重复探索；返工须由测试、类型、构建、运行、需求、安全、越界、可复现缺陷或硬门失败驱动。普通候选身份变化只重验受影响范围，不自动 RETURN；非阻塞发现和其他可行方案作为未覆盖项或后续事项记录。用户决定、真实证据、视觉人工验收及受保护动作的明确授权继续生效。

3. 每个场景 Work Item 在公共 V1 完成当前功能范围的实际验证，白盒按需选择；公共 V2 确认 scene master/reference target、宿主上下文和视觉合同，公共 V3 先完成拆解确认，再完成布局确认，公共 V4 完成正式资源验收。

4. 公共 V5 消费公共 V3 已确认的布局目标和公共 V4 已验收资源，按冻结执行单元完成正式组合、运行态视觉接入及功能回归。跨场景功能应尽早实际验证；最终正式组合完成后再做联合验收。无副作用本地集成可按任务执行，外部写入、付费、真机、破坏性或外部删除和发布仍按具体动作核对用户明确授权。

## 基础显示约束

> 适用技术栈：cocos、phaser、threejs。

- 项目目标包含 Android 时，必须同步修改原生宿主：启动主题、启动画面切换后的 Activity 主题及运行窗口均不显示 Android 窗口标题栏或 ActionBar；从冷启动首帧开始到游戏运行全程不得出现应用标题或标题栏占位，不能仅在 Web 页面或首场景加载后隐藏。

> 适用技术栈：cocos、phaser、threejs。

- Android 游戏采用沉浸式全屏，隐藏系统状态栏和导航栏；进入前台、窗口重新获得焦点及原生界面返回后恢复全屏。系统手势临时唤出的系统栏按平台行为自动收起，不得因此改变无标题栏要求。全屏后仍按实际安全区处理刘海、挖孔和手势区域，保持画布尺寸、布局与触控坐标一致。

> 适用技术栈：cocos、phaser、threejs。

- 在基础实施包和 TDD 中记录显示模块所有权、Android 启动/运行主题与窗口配置、全屏生命周期以及验收项。Web 目标完成视口铺满；只有实际采用 Android 宿主时才实施原生配置，不因本约束额外引入 Android 平台。

> 适用技术栈：cocos、phaser、threejs。

- 基础工程验证检查启动与运行主题、Activity 配置、全屏恢复路径和视口适配，并执行适用的定向测试或构建。运行验收覆盖冷启动、启动画面切换、后台返回、窗口焦点恢复和方向变化；没有实际运行证据时明确记录未验证项，不得用源码检查或构建成功宣称启动/运行显示已验收，也不得自动发起真机验收。

## 单场景完成闭环

> 适用技术栈：cocos、phaser、threejs。

每个 `SCENE` 聚合自身完成事实：公共 V1 实际验证当前功能，公共 V2 确认视觉目标与还原草案，公共 V3 确认拆解及布局，公共 V4 验收正式资源，公共 V5 完成正式组合及运行验收。modal/popup 等 `DISPLAY_LAYER` 建立独立 Work Item 和实施包；其上下文和宿主分别验证，不能由宿主确认替代。

> 适用技术栈：cocos、phaser、threejs。

场景和显示层分别记录 `functional_status`、`resource_status`、`integration_status`、`lifecycle_cleanup_status` 和 `verification_status`。这些字段是领域完成事实，不得冒充或驱动全局状态。显示层复用公共 V0–V5 对象阶段及当前 Work Item 的适用 F0–F4 门禁，不建立第二套全局状态机；只有功能、资源、宿主集成、生命周期清理和验证五项均关闭、所有资源归属明确且证据绑定当前候选时，显示层或场景整体才完成。

## 场景与显示层效果图产物

> 适用技术栈：cocos、phaser、threejs。

- `scene master`：基础场景、常驻 HUD/导航/状态栏和默认状态；互斥 modal、popup、drawer、toast 不得同时塞入主图。

> 适用技术栈：cocos、phaser、threejs。

- `contextual layer images`：每个瞬态层的 required state 都单独出图，但必须包含宿主场景、遮罩/层级、显示层和当前状态，并绑定实际宿主目标、显示层目标和 viewport；孤立组件图只能作为 V4 生产参考。

> 适用技术栈：cocos、phaser、threejs。

- `V3 component × state plan`：在拆解确认阶段独立拆解组件和状态；V5 在正式场景组合并验证，重放打开→交互→关闭→底层状态/焦点恢复轨迹。

## 增量流程

> 适用技术栈：cocos、phaser、threejs。

1. 冻结玩家行为、模块契约、所有权、验收、服务复用和 V0 类型。模块边界变化先查事实，仅实质取舍触发模块审计和 grilling；带外部副作用的动作按当前 Work Item 的精确授权与 F4 要求处理。

> 适用技术栈：cocos、phaser、threejs。

2. 公共 V1 定义并实际验证状态、输入、规则和反馈；可以直接实现正式功能，也可按需使用低保真草图或白盒，不以白盒为必经门。指定效果图还原时，公共 V2 生成或接收并确认 scene master/reference target、宿主上下文、参考身份、视口、状态、对比条件和还原草案，并声明 `visual_validation.mode=usability|exact`（默认 `usability`）。默认允许合理位置、尺寸、边距和换行差异；改变产品方向、玩法语义或上游结构，或明确要求 `exact` 时处理相应用户决定。

> 适用技术栈：cocos、phaser、threejs。

3. 场景 V3 基于冻结效果图输出拆解图、技术 JSON、coverage、布局/placement 三方绑定、component×state、显示层规划、文本拆解和生产方案；经用户确认的 `visual-decomposition-confirmation/1.0` 是包含场景/集成单元的正式视觉生产边界。基础阶段的 foundation-only 包不属于场景 V3；纯工程包无需等待全局静态基线，具有视觉依赖的基础包仍须先完成全局静态基线冻结。`usability` 仍需拆解图确认和关系证据；只有 `exact` 或明确全覆盖需求时才要求逐状态/逐区域完整矩阵。

> 适用技术栈：cocos、phaser、threejs。

原子部件数量、重复实例、独立位图与图集限制和热区合同按[效果图拆分规范](./reference-asset-effect-image-splitting.md)执行。标注图右侧栏包含该图的原子图片要求，左侧原图只保留框和编号/placement 标记。
7. 公共 V1 可直接实现并验证功能，白盒按需选择；公共 V5 按公共 V3 拆解与布局、公共 V4 正式资源组合正式 Scene，由玩法和美术协作完成结构化接入、动态验收和低保真清理；正式资源绑定场景/覆盖区域，效果图模式以不可变 fidelity case 绑定双方 SHA 与同条件证据。
8. F0 校验任务范围与流程，F1 校验当前候选与既定规格一致，F2 由独立 QA、玩法、技术或视觉角色检查领域质量，F3 只验证当前候选的工程证据，F4 按当前 Work Item 核对受保护动作的具体授权与结果。功能与视觉阶段的 `USER_DECISION` 不能替代专业缺陷修复。

## 受控并行实现

> 适用技术栈：cocos、phaser、threejs。

实施并行边界和 READY/委派校验以“模块划分”（见本栈配套资料）及控制面 Schema 为准：`SHARED`/`INTEGRATION` 强制串行，`MODULE`/`SCENE`/`DISPLAY_LAYER` 仅在依赖满足且文件与状态所有权互斥时并行；`DISPLAY_LAYER` 绑定实际宿主上下文并独立安排，不要求执行顺序紧邻宿主或等待宿主完成 V5。

## 视觉证据

> 适用技术栈：cocos、phaser、threejs。

参考与运行图在相同视口、运行时动态设备像素比（封顶 2）、状态、轨迹、语言、随机种子和时间点采集，并记录实际有效 DPR、ROI、验证模式、稳定帧和遮罩。默认 `usability` 使用代表性视口和关键状态，完整 viewport、ROI/叠加/像素差及全矩阵仅在 `exact` 或明确需求时作为严格证据；生成式、动画与 VFX 不能只用像素差判断。明显越界、裁切、关键遮挡、不可读或交互失效不得通过；静态高保真、资源齐全、源码检查和构建成功不能单独证明游戏性。

## 回退

> 适用技术栈：cocos、phaser、threejs。

玩法契约或结构事实失效时返回受影响视觉阶段并使受影响决定失效；模块边界变化仅在存在实质取舍时进入 grilling。修订后按当前 Work Item 重跑实际受影响的 F0–F3，受保护副作用按具体动作和目标核对授权。视觉拆解的真实用户确认及回执保持绑定相应工件，实施代理不得伪造或擅改确认；Git 提交或基线变更仅在用户明确要求时执行。

> 适用技术栈：cocos、phaser、threejs。

场景与显示层分别维护自己的功能、视觉目标和验收；公共 V1 可先实现并验证功能，白盒按需使用。公共 V2 冻结经确认的 scene master/reference target 和必要宿主上下文，公共 V3 完成拆解、布局和生产方案，公共 V4 验收正式资源，公共 V5 验证正式组合和功能回归。原生目标、素材生成和确认记录须绑定实际场景与目标；全局基线不能替代对象确认，上游事实变化时按受影响范围重验。
