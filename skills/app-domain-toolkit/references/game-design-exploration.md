# 游戏关卡与场景方案探索

<a id="explore"></a>

适用于 Unity、Cocos、Phaser、Three.js 和 Roblox：从零设计具有空间、路线或镜头关系的复杂游戏，或本次增量实质改变这些关系时，在需求／全局基线及对象 V0 明确本批范围，进入相关 V1 实现前形成本批关卡结构草案和关键玩家视角概念图，并等待人工修改或确认。按一条可验证玩家路径及其关键区域分批，先覆盖影响本批决策的范围，不要求一次设计所有关卡。已有方案仍有效时引用并只探索变化部分；局部修复、无空间设计需求或不影响相关关系的任务说明复用或不适用，不强制生图。

<a id="roles"></a>

## 职责与输入

产品／玩法设计提供体验目标、核心行为与机制、玩家能力、功能关系、解锁进程、目标平台与输入及本批范围；设施清单只是输入，不能直接充当空间方案。设计依据区分用户已确认事实、产品约束、设计提案、估计尺度和待验证假设；标明来源，未知数值不伪装成测量值或已确认要求。

- **关卡设计师**负责将要求转为可游玩的空间：区域拓扑、入口与出口、主支路线，玩家、其他角色及物资的流动关系，操作与停留空间、目标和条件、教学与挑战节奏、扩建与解锁关系。按玩法处理敌人或谜题、检查点、失败与重试路径，交付可读的结构草案与图例、尺度假设及需运行验证的问题。
- **场景设计师**负责在同一空间方案上建立整体环境：空间层级、建筑或环境组团、边界与地标，统一尺度、模块连接与造型语言，体块、疏密、高低、留白、视线及遮挡。结合实际玩家镜头推敲构图、光照、视觉引导与环境表达，再交付对应结构草案的关键视角概念图，说明辨路、识别和交互风险。

两项是设计职责，可由当前代理承担，也可在宿主支持且允许时按既有协作规则委派；主代理负责整合、冲突裁决和交接。涉及位图生成或编辑时，按当前宿主的 imagegen 技能、工具及图片委派约束执行；实际工具不可用则说明缺失及影响，不声称已生成。首次全局视觉方向或方向候选仍先遵循[产品市场调研](../../app-creator-workflow/references/professional-conventions.md#product-market-research)；早期空间概念不自动成为全局视觉方向或正式候选。

<a id="sequence"></a>

## 推荐顺序与设计依据

产品与玩法约束 → 空间结构草案 → 尺度及环境／建筑规则 → 布局、体块与镜头推敲 → 关键视角概念图 → 结合功能验证修订 → 正式视觉目标、拆解与制作。

前期步骤允许相互迭代，按本批可验证路径推进，不要求先完成全部关卡或全部三维场景。复杂空间任务在生图前必须已有可审阅的结构草案及必要的尺度、镜头假设；仅有设施清单、方位描述、风格关键词或长提示词不能宣称完成空间设计。关键空间关系由关卡／场景设计职责先确定，生图据此探索和表现视觉效果。

关卡设计与场景设计是持续迭代的设计任务，不以产出草案或生成图片自动结束。每轮方案交给用户修改或确认，等待人工反馈；未获确认时在现有任务记录中保持待定，不自动确认、定稿、关闭设计任务或推进依赖该方案的工作，可继续不依赖未决设计的工作。人工确认只覆盖当前范围与版本，不终止后续设计职责；功能验证、范围变化或新问题仍可触发下一轮修订，修订后继续等待人工修改或确认。沿用已有人工确认环节，不增设逐图、逐字段或逐步骤审批。

结构草案按问题选择平面、拓扑、剖面、体块或组合表达，标注区域与相邻关系、入口／目标／出口、主支路线、地标、交互和流动，并给出必要图例与尺度依据。不强制制作三维白盒；无支路、战斗或检查点时不虚构。程序生成关卡表达生成约束、代表性路径与种子策略，不假定唯一地图。

按[空间秩序](#spatial-order)建立适用规则，完成[生图前结构检查](#structure-check)，再按[视角与状态](#views)确定本张稿范围。这些依据按实际需要扩充到现有 GDD／场景规格或视觉设计记录，图与附件引用同一来源；不要求另建报告、固定数量文档或无用途模板。

<a id="spatial-order"></a>

## 建立空间秩序

按项目适用性建立并解释规则，不能只列设施位置：

- **总体骨架**：入口、主路、支路、区域、节点及边界如何形成层级，主要玩家路径如何贯通。
- **尺度系统**：以角色尺寸和实际行为为依据，估计通路宽度、设施间距、工作面、模块尺寸与退让关系；说明单位或相对角色比例、估计依据及验证方式。
- **组团关系**：有行为联系的功能如何共同形成建筑、院落、平台或环境区域，人员与物资如何在组团内外流转，避免每项功能孤立占一个装饰点。
- **模块规则**：重复单元的结构、连接接口、间距、朝向及允许变化；扩建与解锁如何接续已有结构。
- **主次与节奏**：主要地标、次要设施、重复单元、开放空间和环境填充之间的关系，以体块、疏密、高低及留白支持停留、行动和视觉引导。
- **区域差异**：在统一尺度与造型体系内，依据玩法、空间和环境特征区分区域；视线、遮挡及地标帮助玩家辨路。

秩序不等于强制对称、统一朝向、全部矩形、固定网格或复制同一建筑。自然场景可用地形、水系与植被形成边界和节奏；室内可围绕房间、门洞与操作净空组织；战斗关卡可围绕遭遇、掩体与视线组织；经营场景可围绕服务、排队及物流组织。只采用当前项目需要的规则，不统一套用经营钓场方案。

<a id="structure-check"></a>

## 生图前的结构检查

依据草案、规则和镜头参数，至少回答以下适用问题；不适用项简述原因，尚无运行证据的结论保持假设：

- 去掉装饰与材质后，区域、通路和主次是否仍然清楚？
- 设施是否围绕行为关系组织，相关功能之间的流动是否合理？
- 角色是否有停留、操作、排队、通行和交付空间，是否存在冲突？
- 重复模块是否遵循一致尺度与连接方式，允许的变化是否明确？
- 扩建或解锁后是否延续既有结构，是否破坏原有路线？
- 实际玩家镜头及目标视口下，是否存在明显遮挡或识别风险，哪些需要运行验证？

结构检查可使用明确设计参数和草案中的关系推演，不能把未经验证的推演写成运行通过。截图或生成图的显示判断交用户人工检查；未经明确要求不自动分析截图，也不以文件生成、格式检查或工具成功代替视觉验收。检查结论和未决问题留在原规格，不新增逐字段或逐步骤审批。

<a id="views"></a>

## 选择视角与状态

在原场景规格或视觉设计记录的视图条目中，按每张稿的目的明确：

- 用途：总览、正常游玩视角或局部设施设计。
- 所属场景与区域、玩家位置、镜头位置及方向、目标视口；总览或局部稿无对应玩家位置时说明观察范围。
- 对应经营／关卡阶段和少量关键可见状态。
- 必须表达的内容、相邻视图或共享地标，以及未覆盖范围。

总览解释整体空间，正常游玩视角检查玩家实际可见内容，两者不能相互替代；局部设施稿不能证明整个区域成立。关键玩家视角应对应结构草案，表达必要环境、目标、地标与主要遮挡；纯氛围图不能独自表达关卡结构。游戏自身不使用空间移动或玩家视角时按实际情况说明不适用。

尊重用户要求的交付数量；只要一张图时选最有价值的视角并说明覆盖边界，不自动扩成全套视图，也不为展示全部功能将所有内容缩进一张图。游戏有状态变化时只选符合本张目的的少量代表状态，不将全部正常、异常和解锁状态同时堆入画面；未画到的内容和状态不等于从产品范围删除。探索稿数量与正式首次全局方向候选分开处理，不能将单张探索稿冒充已完成正式方向选择。

不同视图沿用同一空间依据，保持共享地标身份、相对尺度、连接和路线关系一致。正式多视图目标的登记和确认继续按[多张场景设计稿](../../app-asset-workflow/references/multi-image-scene-design.md)执行，本节不新增逐图审批。

## 交接与讨论

将草案、规则、视图条目、图例、实际文件路径及待验证问题关联到现有 GDD／场景规格和项目输出位置，交给用户修改或确认；用户未回复不构成确认，工具或代理检查通过也不构成确认。提示词、不同视图、资源拆解与工程装配引用同一套空间事实，不复制为重复清单、第二套状态机或独立审批账本。

生成结果偏离产品约束或空间依据时，明确指出偏差及影响：表现错误返修受影响的图；确需调整空间时先修订原方案并核对关联视图；涉及玩法、目标或范围变化时沿用既有决定与 F1/F2。不能默默修改玩法、倒推产品规则或捏造用户确认。有效设计直接复用，局部修改只重做受影响范围。

草案和概念图用于探索与沟通，可能随实现验证调整；它们不是 V2 正式视觉确认、V3 精确布局、正式资源或运行验证证据。方案文件或工具返回成功不代表画面已由用户检查；显示判断仍由用户人工完成，未经明确要求不自动分析截图。

<a id="handoff"></a>

## 接入后续流程

V1 接收本批方案与待验证假设，按风险使用白盒、临时资源或实际功能验证运动、导航、可达性、视线、相机、碰撞、交互、操作体验、机制、重试及适用性能；静态地图或概念图不证明这些行为与性能。V1 继续负责功能验证，不要求全部正式美术完成后才能实现功能。将真实运行结果及仍未验证的问题回写现有计划，关卡／场景设计职责按结果修订受影响草案并交接，不另建状态或要求白盒成为所有任务必经产物。

相关功能完成 V1 后，V2 以已验证约束和更新后的草案为输入，沿用[多张场景设计稿](../../app-asset-workflow/references/multi-image-scene-design.md)及首次全局方向三候选规则，制作和确认正式视觉目标；已有有效基线按既有规则复用。V3 分别确认拆解和布局，V4 制作导入正式资源，V5 检查正式组合和运行并交用户人工验收。早期方案被修改或复用均不自动继承这些阶段的确认或证据。
