# 游戏关卡与场景方案探索

<a id="explore"></a>

适用于 Unity、Cocos、Phaser、Three.js 和 Roblox 中具有空间、路线或镜头关系的游戏设计与增量。先形成结构草案和内容需求，按[3D、2D 与 UI 分流](#implementation-routes)选择风险验证；第 4 阶段确认全局方向，V1 确认完整模块方案，V2 生成并确认模块设计，V5 完整实现与验收。已有方案、场景与资源按有效范围复用。

<a id="v1-scene-design-task"></a>

## V1 触发场景与关卡设计

游戏世界 `SCENE` 进入 V1 时，主动尝试启动场景与关卡设计。先读取本批目标、场景范围、已有 GDD、空间方案与已确认版本，核对来源和适用范围。新增场景或空间、路线、镜头、关键玩法发生实质变化时，在当前 V1 任务中拆解或修订对应的设计工作。已有设计的范围、版本和依据仍适用时，记录复用结论并补齐本批差异。无法判断的事实或设计问题写回现有 GDD、场景规格或当前任务，按已有流程处理。仅在当前已授权范围内开始设计，沿用现有工作项和人工确认。

设计借鉴工业产品设计对使用情境、尺寸接口和生产可行性的要求，按[策划范围与验收](../../app-creator-workflow/references/professional-conventions.md#planning-scope-and-acceptance)落实到游戏空间。结合玩家类型、平台、输入与游玩情境明确核心目标和操作流程，确定空间尺度、模块连接和交互接口，核对引擎、运行性能、资源制作及目标平台约束。记录方案取舍、依据、假设和可验证的验收条件，并将空间草案、状态及路线交给后续白模或平面布局工作。已确认的全局方向及场景设计按实际范围沿用，变更时遵循现有返修规则。

该任务适用于 `world-3d` 与 `world-2d` 游戏世界。纯游戏 UI、HUD、菜单及非游戏 App 沿各自设计流程处理。3D 世界 V1 须搭建或复用有效白模，2D 世界禁止白模并使用适用的平面布局。控制器给出的设计任务提示用于引导执行，设计和用户确认以实际工作及已有记录为准。

<a id="roles"></a>

## 职责与输入

产品／玩法设计提供体验目标、核心行为与机制、玩家能力、功能关系、解锁进程、目标平台与输入及本批范围；设施清单和测试关卡只是输入，不能直接充当正式产品结构或空间方案。按[验证依据与产品设计依据](../../app-creator-workflow/references/readable-functional-prototype.md#design-handoff)区分已证实的空间／接口约束和为复现而安排的夹具布局。设计依据区分用户已确认事实、产品约束、设计提案、估计尺度和待验证假设；标明来源，未知数值不伪装成测量值或已确认要求。

大场景与长游戏流程沿[总范围与本批范围](incremental-production.md#明确总范围与本批范围)先说明区域连接、核心机制与解锁依赖的整体骨架，再按[连续玩家流程](incremental-production.md#game-progression)确定本批路径，关联代表区域、已实现邻区、共享对象及必要连接接口；未来区域只保留有依据的边界与待办，不提前细化全部空间或生产全部资产。区域是同一正式场景的内容范围，视图是观察范围，两者不要求一一对应，也不因一张图无法容纳就复制运行场景。跨视图、区域或批次出现的同一元素按[共享设计依据](../../app-asset-workflow/references/asset-provenance.md#shared-design-elements)保持设计身份、造型及固定空间关系，沿用已确认来源和允许变体。

在现有 GDD／场景规格中，先按[共同设计依据](../../app-asset-workflow/references/interface-intent.md#design-basis)结合本批核心行为、输入方式、镜头与使用压力，说明视觉引导、HUD 和环境表现的任务收益及代价，区分约束、方向与探索空间；涉及生图时将适用结论转成实际提示词。再按[信息理解与承载语义](../../app-asset-workflow/references/interface-intent.md)明确“玩家需要判断什么 → 场景提供什么线索 → 玩家可以做什么 → 操作后有什么反馈 → 仍需保留哪些精确信息”，再决定文字、布局与美术表现。世界物件、地面区域、角色附属表现、场景浮层与屏幕 HUD 分工明确；位置交互在原规格中交接承载面、朝向、空间归属、触发范围和显示状态，不默认用标签或屏幕卡片解释。必要金额、数量、错误、确认文案和无障碍语义保留，每项可见文字说明其补足的信息缺口。

- **关卡设计师**负责将要求转为可游玩的空间：区域拓扑、入口与出口、主支路线，玩家、其他角色及物资的流动关系，操作与停留空间、目标和条件、教学与挑战节奏、扩建与解锁关系。按玩法处理敌人或谜题、检查点、失败与重试路径，交付可读的结构草案与图例、尺度假设及需运行验证的问题。
- **场景设计师**负责在同一空间方案上建立整体环境：空间层级、建筑或环境组团、边界与地标，统一尺度、模块连接与造型语言，体块、疏密、高低、留白、视线及遮挡。结合实际玩家镜头推敲构图、光照、视觉引导与环境表达，交付空间规则、搭建依据和内容需求；按需补充关键视角概念图，说明辨路、识别和交互风险。

两项职责共同核对玩家的使用情境、关键交互路径和空间接口，说明各方案在可读性、性能、制作和维护成本上的取舍。每项待验证结论关联适用的场景范围、验证方式及可观察结果，供 V1 白模或平面布局及后续验收使用。

两项设计职责可由同一执行者承担，按[协作与交接](../../app-creator-workflow/references/handoffs.md)安排工作，主代理负责整合、冲突裁决和交接。涉及位图生成或编辑时，按当前宿主的 imagegen 技能、工具及图片委派约束执行；实际工具不可用则说明缺失及影响，不声称已生成。首次全局视觉方向或方向候选仍先遵循[产品市场调研](../../app-creator-workflow/references/professional-conventions.md#product-market-research)；早期空间概念不自动成为全局视觉方向或正式候选。

<a id="implementation-routes"></a>

## 按 3D、2D 与 UI 分流

第 4 阶段按空间方案确认并冻结全局方向及代表稿。V1 明确模块空间、规则、状态与进度方案，3D 世界场景搭建或复用有效白模并按风险运行验证；V2 生成并确认模块设计，V3 从该确认稿提取资源规格，V4 准备资源，V5 完整实现与验收。全局方向实质变化回第 4 阶段。

所有真实 3D 世界场景在 V1 搭建或复用有效白模，按空间、镜头、物理、手感或规则风险选择运行验证。2D 世界使用平面布局、正式工程及功能用例，不搭建二维白模或可玩占位白模；HUD、菜单与 App 按原界面流程推进。已有有效机制与证据按范围复用。混合场景分别处理，使用三维世界几何的 2.5D 内容按 3D 世界处理。

| 内容 | 空间与功能验证 | 确认后的正式生产 |
| --- | --- | --- |
| 3D 世界场景 | V1 明确空间与功能方案，搭建或复用有效白模，按风险选择运行验证 | V2 基于全局方向生成并确认模块设计，V3 明确模型规格，按风险安排首件验证及分批制作或复用模型 |
| 2D 世界场景 | 按需制作平面布局，直接使用正式工程和功能用例，不制作白模 | 布局与相关功能确认后制作、复用和替换二维资源；只对确需图片生产的内容走对应流程 |
| UI，包括 3D 游戏的 HUD、菜单、弹窗及世界空间 UI | 沿用现有界面设计、布局、交互及原生实现流程；在真实宿主检查组合，但不增加世界场景白模步骤 | 原有 UI 目标、拆解／布局、素材生产及人工验收继续适用 |

所有 3D 世界场景均须在进入 V2 前具备覆盖本批的白模，已有有效白模可直接复用。运行验证按风险安排，空间规格、设计确认、适用首件和正式运行依旧完成；运行环境缺失时如实保留未验证范围。

控制器以同一 `visual.designRoute` 区分世界与界面：游戏 `SCENE` 默认 `world-2d`，三维世界显式选择 `world-3d`，纯菜单等界面场景显式选择 `game-ui`。两类世界都在 V1 明确空间与功能方案，按本批风险验证并记录必要空间确认；界面继续原图片与布局流程。分类随功能基线冻结，机器核对记录，分类仍须符合实际内容。

前期设计稿中的游戏内容只记录本批需要的用途、预计尺寸／数量、交互及共享模块等信息，不按稿逐物件切图、拆图或生成单体资产。按区域、建筑、设施组织可编辑节点及稳定身份属于必要空间组织，不能一并省略；记录留在原场景规格，不提前铺满正式生产规格。UI 按原流程，图片任务仍受宿主生图技能、工具及委派约束。

同一 3D 世界的常驻 HUD 仍归真实场景宿主，按[常驻 HUD 交接](../../app-workflow-control/references/world3d-scenes.md#persistent-hud)引用原 UI 图片目标、布局、资源与人工确认；世界空间范围与 HUD 视图分别记录，共用对象阶段。没有 HUD 不增加图片任务，不能把常驻内容改成瞬态层或另造游戏场景。

## 推荐顺序与设计依据

产品与玩法约束 → 判断、线索、行动与反馈设计 → 空间草案与内容需求记录 → 尺度、环境规则及镜头推敲 → 第 4 阶段确认全局视觉方向 → V1 确认完整模块方案并按需验证空间风险 → V2 生成并确认模块设计稿 → V3 资产规格 → 按风险验证首件并分批替换 → 功能复验与人工显示验收。

前期步骤允许相互迭代；已确认约束内的搭建与功能实现可以并行，涉及未确认实质取舍的依赖仍等待人工反馈。“本批整体场景”指当前约定的完整可游玩范围、主要路线、功能组团、操作空间、镜头及少量代表状态，包括与已实现邻区相关的实际连接，不等于全部关卡、所有解锁阶段或美术完成。未来区域的接口约定不等于该区域已可玩。空间与功能基线的确认只覆盖实际审阅的范围、版本及已证实关系，不将测试数据、入口或坐标自动提升为正式设计要求，也不代替后续正式布局、视觉目标和最终显示确认。

正式美术稿前先确认本批代表内容、玩家任务、信息主次及状态关系有足够依据；仅为白模换材质不构成产品结构设计。确需探索多个方向时，保持相同核心内容、代表状态与比较条件，集中比较造型、比例、材质、明暗、边缘和图标语言，而非只换颜色；候选数量沿用实际路线。主方向确定后复用于其他状态，按受影响范围增量补充，不提前为全部状态生产多套风格资产。

关键视角概念图仅在确实有助于讨论时制作；没有图片也可用可审阅的空间规格或草案表达方案，3D 世界按本批范围使用白模。确需生图时先有结构、尺度和镜头依据，不能凭设施清单、方位描述、风格词或长提示词宣称完成空间设计。

关卡设计与场景设计是持续迭代的设计任务，不以产出草案或生成图片自动结束。每轮方案交给用户修改或确认，等待人工反馈；未获确认时在现有任务记录中保持待定，不自动确认、定稿、关闭设计任务或推进依赖该方案的工作，可继续不依赖未决设计的工作。人工确认只覆盖当前范围与版本，不终止后续设计职责；功能验证、范围变化或新问题仍可触发下一轮修订，修订后继续等待人工修改或确认。沿用已有人工确认环节，不增设逐图、逐字段或逐步骤审批。

结构草案按问题选择平面、拓扑、剖面、体块或组合表达，标注区域与相邻关系、入口／目标／出口、主支路线、地标、交互和流动，并给出必要图例与尺度依据。3D 世界场景在 V1 搭建或复用白模，2D 按平面方案和正式工程验证。图例、编号、阶段说明和白模调试标签仅服务设计沟通，不直接搬入正式视觉稿。程序生成关卡表达生成约束、代表性路径与种子策略。

按[空间秩序](#spatial-order)建立适用规则，在搭建及可选生图前完成[结构检查](#structure-check)，按[视角与状态](#views)确定本次表达范围；正式生产前读取[资产与替换交接](#production-handoff)及[既有工具合同边界](#tooling-boundary)。这些依据按实际需要扩充到现有 GDD／场景规格或视觉设计记录，图与附件引用同一来源；不要求另建报告、固定数量文档或无用途模板。

<a id="spatial-order"></a>

## 建立空间秩序

按项目适用性建立并解释规则，不能只列设施位置：

- **总体骨架**：入口、主路、支路、区域、节点及边界如何形成层级，主要玩家路径如何贯通。
- **尺度系统**：以角色尺寸和实际行为为依据，估计通路宽度、设施间距、工作面、模块尺寸与退让关系；说明单位或相对角色比例、估计依据及验证方式。
- **组团关系**：有行为联系的功能如何共同形成建筑、院落、平台或环境区域，人员与物资如何在组团内外流转，避免每项功能孤立占一个装饰点。
- **模块规则**：重复单元的结构、连接接口、间距、朝向及允许变化；扩建与解锁如何接续已有结构。
- **主次与节奏**：主要地标、次要设施、重复单元、开放空间和环境填充之间的关系，以体块、疏密、高低及留白支持停留、行动和视觉引导。
- **区域差异**：在统一尺度与造型体系内，依据玩法、空间和环境特征区分区域；视线、遮挡及地标帮助玩家辨路。

秩序不等于强制对称、统一朝向、全部矩形、固定网格或复制同一建筑。自然场景可用地形、水系与植被形成边界和节奏；室内可围绕房间、门洞与操作净空组织；战斗关卡可围绕遭遇、掩体与视线组织；经营场景可围绕服务、排队及物流组织。只采用当前项目需要的规则，不统一套用经营钓场方案。

工程中的地块、网格、节点和功能分区是逻辑组织，不要求逐一显式描边或贴标签。例如七块逻辑地块可呈现为连续地形与自然路径，只有玩法确实依赖格子判断的捕鱼区域才突出网格。正式玩家视图优先呈现当前行为、可操作目标与下一步的空间关系；结构总览与资产陈列不能替代实际游戏视图。

<a id="structure-check"></a>

## 搭建与可选生图前的结构检查

依据草案、规则和镜头参数，至少回答以下适用问题；不适用项简述原因，尚无运行证据的结论保持假设：

- 去掉装饰与材质后，区域、通路和主次是否仍然清楚？
- 设施是否围绕行为关系组织，相关功能之间的流动是否合理？
- 角色是否有停留、操作、排队、通行和交付空间，是否存在冲突？
- 重复模块是否遵循一致尺度与连接方式，允许的变化是否明确？
- 扩建或解锁后是否延续既有结构，是否破坏原有路线？
- 实际玩家镜头及目标视口下，是否存在明显遮挡或识别风险，哪些需要运行验证？
- 每个判断由哪些物件、动作、空间关系或状态变化支持；可见文字补足什么，是否混入白模调试标签和任务解释？
- 位置交互的承载面、朝向、归属、触发范围及显隐是否匹配机制，例如站入自动付款的费用区是否贴地并关联待解锁区域，而非被改成悬浮说明牌？
- 工程逻辑分区是否被不必要地全部画出，是否为了展示全部设施牺牲当前操作与下一步的可读性？

结构检查可使用明确设计参数和草案中的关系推演，不能把未经验证的推演写成运行通过。截图或生成图的显示判断交用户人工检查；未经明确要求不自动分析截图，也不以文件生成、格式检查或工具成功代替视觉验收。检查结论和未决问题留在原规格，不新增逐字段或逐步骤审批。

<a id="views"></a>

## 选择视角与状态

3D 世界的 V2 空间和机位使用同一 V1 白模、空间规格及相机路径表达，不按区域规模或相机数量要求固定数量的设计稿。需要上下文预览时，视图关联原场景、相机位置及目标、区域、视口、状态和设计文件，沿用同一空间、尺度、地标位置、全局方向和共享模型身份。机位改变时允许透视和遮挡随空间变化；空间或状态变更先回写模块规格，再更新受影响的视图。

场景有常驻 UI 时，按实际二维元素及必要状态确定一张或多张目标并沿用共享 HUD 来源。存在世界上下文预览时，相同状态和视口的各机位引用同一 HUD 目标，组件、锚点、位置、尺寸、样式和层序一致；视口或玩法状态改变时应用同一来源已明确的适配或显隐规则。实际设计和适用预览交用户人工检查，沿用现有 V2 模块设计确认。字段见[场景设计合同](../../app-workflow-control/references/world3d-scenes.md#world-camera-designs)。

在原场景规格或视觉设计记录的视图条目中，按草案、白模查看视角或可选概念图的目的明确，不要求每个条目对应一张生成图片：

- 用途：总览、正常游玩视角或局部设施设计。
- 所属场景与区域、玩家位置、镜头位置及方向、目标视口；总览或局部稿无对应玩家位置时说明观察范围。
- 对应经营／关卡阶段和本张代表瞬间；在原方案中覆盖相关的未选择、已选择、进行中、完成、离开与恢复状态，交接每种状态的出现、消失、对象变化与反馈，不适用时说明机制原因。
- 必须表达的内容、相邻视图或共享地标，以及未覆盖范围。

总览解释整体空间，正常游玩视角检查玩家实际可见内容，两者不能相互替代；局部设施稿不能证明整个区域成立。关键玩家视角应对应结构草案，表达必要环境、目标、地标与主要遮挡；纯氛围图不能独自表达关卡结构。游戏自身不使用空间移动或玩家视角时按实际情况说明不适用。

探索稿尊重用户要求的交付数量。正式 V2 的图片目标覆盖本轮全部二维元素及适用必要状态，一张能清楚容纳时使用一张，不够时拆分多张并保持同源。3D 场景无二维内容时可仅以空间、方向和状态规格完成 V2；机位预览按需选择，未在单张画面表达的状态和进度由同一模块的适用设计及规格覆盖。

例如选择工具后自动作业时，方案应说明选中后如何启动、对象如何变化、完成后如何收尾、离开及恢复如何处理，不常驻暗示需要反复点击的动作按钮。进度优先由对象变化、覆盖范围、剩余目标与结果表达，只有明确缺口时才增加进度条或说明。单张概念图只交付代表瞬间；动作、时序和状态切换在原方案交接并于实现后验证，不能用静态图片宣称动画或交互成立。

不同视图沿用同一空间依据，保持共享地标身份、相对尺度、连接和路线关系一致。图片场景目标按[多张场景设计稿](../../app-asset-workflow/references/multi-image-scene-design.md)登记确认；已有三维机位预览沿本模块 V2 清单确认。

## 关卡与场景方案的单次审查

本批关卡与场景方案完成适用的搭建及必要功能验证后、提交用户确认整体场景前，由主代理组织一次联合审查，按宿主现有协作规则选择是否由独立审查者承担。两类设计依据同一份空间方案和搭建结果审查，不分别重复一轮，也不扩展到每张图、未变化区域或全游戏。复用已有[结构检查](#structure-check)及玩家视角审查依据，检查本批最终方案是否仍一致；同一方案的[当前设计稿单次用户视角审查](../../app-asset-workflow/references/art-review.md#当前设计稿的单次用户视角审查)合并在这一轮中，不另起重复审查。尚无运行环境时只能审查草案，不能将其写成搭建与整体运行已确认。

审查以产品约束、现有 GDD／场景规格、结构草案、尺度及镜头参数和已有验证记录为依据：核对玩法意图是否落实为路线、流动、停留与操作空间，空间秩序、节奏及扩建是否自洽，不同视图与代表状态是否一致，覆盖边界及待验证假设是否清楚。镜头下的遮挡与识别风险仅根据明确参数、可编辑结构和已知事实推演；截图、概念图及运行画面的实际显示仍交用户人工检查，未经明确要求不自动看图。

将具体问题的位置、依据、影响、处理及仍需运行验证的事项简述在原设计或交接记录中，不另建报告、评分表、控制器状态或审批。只修本轮发现且已授权范围内的问题；实质玩法或范围取舍按已有决定流程处理。修改后展示实际方案和未解决项，等待用户修改或确认；无问题也直接交用户，不将代理审查记为人工确认或运行通过。

修改后自主定向复验失败项及实际变化的玩法行为、空间结构与受影响路径，必要时重新推演相应情境，不等待用户另行要求；已有未变化结论继续复用。重新生成、版本变化、换代理或续接不自动开启全量审美评议；用户明确要求完整再审时按实际范围执行。截图与实际显示继续按人工授权规则检查，定向复验不代替用户确认或运行证据。

## 交接与讨论

将草案、规则、视图条目、图例、实际文件路径及待验证问题关联到现有 GDD／场景规格和项目输出位置，交给用户修改或确认；用户未回复不构成确认，工具或代理检查通过也不构成确认。提示词、不同视图、资源拆解与工程装配引用同一套空间事实，不复制为重复清单、第二套状态机或独立审批账本。

生成结果偏离产品约束或空间依据时，先查设计原因，再确定返修范围。用户指出标签过多、交互不直观或风格相似时，检查信息链、空间承载与状态语义或候选视觉语言是否存在共同问题，不只删掉点名文字或换配色重生。共同原因影响多处时一并修订相关规格与提示词；局部执行错误只返修受影响的图。保留已经认可的视角、玩法和空间关系；确需调整空间时先修订原方案并核对关联视图，涉及玩法、目标或范围变化时沿用既有决定与 F1/F2。不能默默修改玩法、倒推产品规则或捏造用户确认。

草案和概念图用于探索与沟通，可能随实现验证调整；它们不是 V2 正式视觉确认、V3 精确布局、正式资源或运行验证证据。方案文件或工具返回成功不代表画面已由用户检查；显示判断仍由用户人工完成，未经明确要求不自动分析截图。

## 接入后续流程

在 V1 定义本批空间、内容需求、规则、状态、进度、依赖和验收。3D 世界场景搭建或复用白模，按风险运行验证运动、导航、可达性、视线、相机、碰撞、交互和性能；2D 使用平面布局及正式工程与功能用例。真实验证结果与剩余问题回写原规格，完整功能在 V5 实现并验收。

按[本批可玩范围与交接](../../app-creator-workflow/references/readable-functional-prototype.md#大场景本批可玩范围与交接)规划连续玩家路径、邻区接缝、动态内容、解锁、重试／恢复及负载。V1 交接本批边界、共同尺度／坐标、连接接口、模板与配置来源及风险；需要验证的高风险项记录实际结果，模块完整实现及验证在 V5 完成。

V1 方案确认后，V2 基于第 4 阶段的全局方向生成并确认覆盖本模块全部适用状态和进度的设计，3D 保留可追溯的空间基线、风格与材质／造型依据；确实采用图片目标时沿用[多张场景设计稿](../../app-asset-workflow/references/multi-image-scene-design.md)及对应候选规则，不将它们扩张成前期逐物件生图。V3 按[正式资产与替换交接](#production-handoff)明确模型或二维资源规格，UI 仍按原拆解与布局确认；3D 在 V4 按风险验证首件并分批生产与导入，正式宿主替换按本栈装配阶段执行（如 Unity 在 V5），V5 复验正式组合及运行并交用户人工显示验收。白模或早期方案的确认不自动继承这些阶段的确认和证据。

<a id="scene-production-units"></a>

## 整体空间与制作单元

由正式引擎工程维护整体空间，模型按模块或有关系的组团组织。已确认的空间规格及适用白模中的区域、道路、角色尺度、镜头、交互位置和接口作为共同依据。制作工具按本栈原生路线选择：选用 Blender 的路线可在制作工作区保留整场参考装配；Roblox 可在 Studio 直接制作原生 Part／Model 或程序化模型，外部网格路线按实际需要使用外部工具。玩法、导航、碰撞及最终运行统一在引擎核验。本节适用于 3D 世界，2D 与 UI 沿各自流程。

| 情况 | 制作粒度 |
| --- | --- |
| 有复用、交互、扩建、独立动画或分区加载的场景 | 按建筑模块、设施、地形区块或组团制作；需独立变化或独立生命周期的部分保留独立身份与接口。 |
| 规模小、边界稳定、复用少的静态房间或固定场景 | 可在同一制作场景整体制作，保留有用途的层级、交互件及交付边界。 |
| 全景环境或建筑组团的整体推敲 | 在当前制作工具中组合模块并检查关系，有效布局变化回写原空间方案。 |

拆分依据是玩法与消费边界、复用及变更频率、碰撞／LOD／加载需求、材质和制作所有权，不按画面里每个物件机械拆文件，也不为减少文件数把整场合成一个不可独立替换的网格。一个制作单元可以包含墙、屋顶等相关网格；门、可交互设施或独立变化部分按实际需求保留。共享地标、模块间距和连接关系仍按同一整体设计核对。

V3 在已有模型规格中明确本批制作单元、适用的首件组合、源对象或原生模型、交付范围、局部 Pivot 与场景放置的对应，以及接缝、连接和允许变化；场景封套声明 `productionRisk:low` 或 `high`。只补当前任务需要的信息。同一源可组织多个单元，运行时粒度按消费者确定。可编辑源、导出路径和正式场景各保持唯一写者。

执行顺序沿用现有阶段：V1 完整模块方案确认，3D 世界搭建或复用白模并按风险运行验证 → V2 模块状态和进度设计稿人工确认、V3 制作单元与模型规格 → V4 低风险正常生产与导入，高风险先验证首件或复用有效证据后扩批 → V5 正式场景替换并检查区域及整体关系。替换按已登记的局部／场景变换处理，避免重复应用偏移或缩放。细化表现时保留有效玩法和碰撞／导航代理，源模型与白模依据保留可追溯版本。

小场景选择整体制作仍沿用上述确认、风险判断和验收；局部修改只重做受影响单元。需要改动通路、占地或连接等已确认空间事实时，回原方案修订并等待人工确认，不新增按文件、模块或制作方式逐项审批。

<a id="production-handoff"></a>

## 正式资产与替换交接

V1 确认模块方案并按需验证空间风险后，V2 基于全局方向确认本批空间和状态设计，二维元素按实际范围制作一张或多张目标，同一 HUD 和菜单沿用共同界面来源。V3 从已确认的三维空间及实际交互和消费边界拆分本批场景模型或组团，按需引用已有视图；同一对象保持同一稳定模型 ID，记录位置、尺寸、单位、轴向与 Pivot、占地／轮廓、连接接口、允许缩放、用途和预算，并按需注明碰撞、LOD、材质、动画或骨骼。

每个模型或组团按[模型来源与交接](../../app-3d-modeling/SKILL.md#模型来源与交接)选择已有本地可用模型、项目授权的可用生成 API 或 Blender 手工／脚本制作。登记来源与版本、使用授权、实际源与输出及其身份、模型规格、引擎导入和消费者；API 记录真实输入、服务版本、可获取的参数与输出，回读并验证目标格式。已有有效模型直接复用。按当前栈支持的格式及原生流程接入，能力或许可缺口保留待处理。

先按[整体空间与制作单元](#scene-production-units)确定整体制作或模块／组团制作的范围，再安排以下交接。制作源与引擎资源的组织分别按用途确定。

按实际职责和依赖，在现有工作项、实施包或任务说明中安排以下工作；按当前栈 profile 的 `capabilitySkills` 和能力清单发现已安装入口，未声明的能力不跨栈冒用。普通任务可由同一执行者承担，不强制新建任务文档、工作项或代理：

| 工作 | 触发与交接 |
| --- | --- |
| 模型来源与制作 | V2 方向与 V3 模型规格已确定后，V4 按[三维几何建模](../../app-3d-modeling/SKILL.md)复用本地模型、使用授权且可用的生成 API 或用 Blender 制作。高风险批次使用[样本单元依赖](../../app-workflow-control/references/implementation-execution.md#sample-dependencies)，由首件在目标引擎先验证。按实际来源及本栈原生路线交付模型、真实可用的源、UV、法线、材质槽及所需 LOD 网格与碰撞代理。 |
| 材质与贴图 | 模型的适用 UV、材质槽及方向明确后，按需交给现有 `app-3d-texturing` 能力及本栈实际管线；回传源版本、材质／通道、贴图和导出结果。原生适配以清单为准，没有映射时结合公共能力和本栈规范，不虚构导入器或着色器。涉及图片生成或编辑时遵循宿主图片技能与委派规则；无贴图需求的模型不强制制作。 |
| 首件验证 | 高风险批次先制作或复用可暴露风险的最小正式组合，按需包含多个相邻模块，在目标镜头和适用运行环境中核对尺寸、接口、加载、材质和受影响玩法。已有证据和用户决定仍覆盖当前范围时可复用。首件及适用审阅通过后再补齐依赖批次，技术结果和用户显示判断分别记录。 |
| 分批制作与导入 | 复用有效依据和资源，分批完成模型及所需材质；各批回传真实来源、导出版本、导入／读回结果、消费者及未验证项。当前 `world-3d` 工作项的 V4 完成时，模型规格中声明的本批模型均须有对应资源和验收证据。 |
| 正式替换 | 由当前栈的资产接入负责人和正式场景唯一写者落实原生导入、LOD 切换、正式资源替换及运行核对。本栈将宿主装配限定 V5 时，V4 完成资源级导入与适用的首件组合验证。保留已确认的位置、尺度、接口和层级，回传实际场景／节点、资源版本和运行证据。 |

工具和场景文件保持各自唯一写者，互不冲突的制作工作可在依赖明确后并行。建模保留几何、UV 与材质槽的所有权；贴图或材质使用约定的派生版本，不能静默改动上游结构。沿用既有资源清单、实施包和证据，不新建审批账本；控制器校验阶段材料，并不自动派发任务或证明样本发生在批量制作之前。

三维高风险及适用的二维／UI 样本验证安排在依赖它的批量工作之前：复用现有实施单元的 `sequence` 与 `dependsOn`，先记录实际技术结果及适用用户决定，再激活依赖该结果的稳定批次；仍有效的依据可以引用。三维低风险批次正常生产和导入。二维静态图片在前置满足后一次编排整批独立条目，不能用整批提交跳过适用样本试接，也不因此新增逐图等待。执行批次只约束计划和结果登记顺序，不能证明计划外是否提前生产或替用户确认画面。

需要机器核对的制作范围在原实施包按[样本依赖检查](../../app-workflow-control/references/implementation-execution.md#sample-dependencies)声明样本／批量职责、覆盖范围和当前制作依据；批量单元显式依赖已覆盖该范围的样本单元。新样本在实际通过时冻结技术结果及适用人工决定，复用样本先核对当前版本和消费者；不要求普通工程任务填写这些声明，也不把未声明的行为推断为已验证生产。

每批替换后复验受影响的通行、碰撞、交互、镜头遮挡和适用性能，当前完整组合由用户检查显示效果。需要改变占地、连接或路线等已确认空间事实时，回到受影响的空间规格及适用白模修订并等待人工确认；工程复验不重置单次设计审查。2D 交接精灵／图块等所需资源、锚点、层序与适用切片规则，UI 保留其现有设计与生产流程。

## 既有工具合同的边界

控制器已提供显式 [world-3d 无图场景合同](../../app-workflow-control/references/world3d-scenes.md)，仅游戏世界 SCENE 可选择：以空间规格、白模、单次审查、人工空间／方向确认、模型规格、导入和实际运行记录替代图片目标及 V3 拆图／布局图硬门。白模运行按风险选择。2D、UI 和原图片路线继续执行其原生合同；控制器验证记录与文件身份，实际引擎、模型几何及显示效果须按适用范围验证。

若其他合同仍缺少适用表达，明确说明需适配的工件及受阻阶段，保留人工待定并暂停依赖该缺口的正式生产，继续不受影响工作；不擅自恢复前期逐物件生图或虚构批准。无图路线沿用原状态机和工程门，资源可按当前合同复用，但不自动继承旧图片或其他工作项的批准；UI 及现有图片还原路线的要求继续有效。
