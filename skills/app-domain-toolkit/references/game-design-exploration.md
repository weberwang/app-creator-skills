# 游戏关卡与场景方案探索

<a id="explore"></a>

适用于 Unity、Cocos、Phaser、Three.js 和 Roblox：从零设计具有空间、路线或镜头关系的复杂游戏，或本次增量实质改变这些关系时，在需求／全局基线及对象 V0 明确本批范围，进入相关 V1 实现前完成本批关卡结构草案和关键玩家视角概念图。按一条可验证玩家路径及其关键区域分批，先覆盖影响本批决策的范围，不要求一次设计所有关卡。已有方案仍有效时引用并只探索变化部分；局部修复、无空间设计需求或不影响相关关系的任务说明复用或不适用，不强制生图。

<a id="roles"></a>

## 职责与输入

产品／玩法策划提供体验目标、核心机制、玩家能力、目标平台与输入、范围、已有决定及待验证假设。缺少具体数值时写明暂定值与来源，不把推测写成已确认事实。

- **关卡设计师**负责将目标和机制转为可游玩的空间方案：确定区域拓扑、入口与出口、尺度假设、主支路线、目标和条件、教学与挑战节奏、敌人或谜题、检查点、失败与重试路径。交付可读的结构草案与图例，标明交互、视线、通行以及关键风险；说明哪些空间与规则假设需要 V1 验证。
- **场景设计师**依据同一结构草案和玩家路径设计环境：确定关键地标、镜头位置与朝向、构图、光照、环境叙事、层次及视觉引导。交付关键玩家视角概念图，标明对应区域、玩家位置、相机与可见状态、关联地标和尺度假设，并说明哪些表现会影响辨路、遮挡或交互。

两项是设计职责，可由当前代理承担，也可在宿主支持且允许时按既有协作规则委派；主代理负责整合、冲突裁决和交接。涉及位图生成或编辑时，按当前宿主的 imagegen 技能、工具及图片委派约束执行；实际工具不可用则说明缺失及影响，不声称已生成。首次全局视觉方向或方向候选仍先遵循[产品市场调研](../../app-creator-workflow/references/professional-conventions.md#product-market-research)；早期空间概念不自动成为全局视觉方向或正式候选。

## 形成可讨论的方案

1. **结构草案**：按玩法选择俯视图、剖面图、拓扑图或组合，标注区域及相邻关系、入口／目标／出口、玩家路线、地标、主要交互、遭遇或谜题、检查点和预计尺度。按实际游戏类型选择内容；无支路、战斗或检查点时不虚构。若以程序生成，示意其生成约束与代表性路径，记录种子策略而非假定唯一地图。
2. **关键视角概念图**：选择本批玩家路径上能说明空间决策的一个或多个真实玩家视角，展示必要环境、目标、地标及主要遮挡，并对应结构图的区域、相机、朝向和状态。保持不同图的共享地标、相对尺度和路线关系一致，标出尚未解决的冲突；纯氛围图不能独自表达关卡结构。游戏自身不使用空间移动或玩家视角时，本项按实际情况说明不适用。
3. **交接与讨论**：将图、图例、实际文件路径、覆盖与未覆盖区域、共用地标、已确认事实、设计假设和待验证问题关联到现有 GDD／场景规格及项目输出位置，供用户查看与讨论。影响目标、玩法或范围的实质取舍沿用既有决定和 F1/F2；已有决定直接引用，不为每张草案增设审批或捏造用户确认。

草案和概念图用于探索与沟通，可能随实现验证调整；它们不是 V2 正式视觉确认、V3 精确布局、正式资源或运行验证证据。方案文件或工具返回成功不代表画面已由用户检查；显示判断仍由用户人工完成，未经明确要求不自动分析截图。

## 接入后续流程

V1 接收本批方案与待验证假设，按风险使用白盒、临时资源或实际功能验证运动、可达性、视线、相机、碰撞、交互、机制和重试；静态地图或概念图不证明这些行为。将真实运行结果及仍未验证的问题回写现有计划，关卡／场景设计职责按结果修订受影响草案并交接，不另建状态或要求白盒成为所有任务必经产物。

相关功能完成 V1 后，V2 以已验证约束和更新后的草案为输入，沿用[多张场景设计稿](../../app-asset-workflow/references/multi-image-scene-design.md)及首次全局方向三候选规则，制作和确认正式视觉目标；已有有效基线按既有规则复用。V3 分别确认拆解和布局，V4 制作导入正式资源，V5 检查正式组合和运行并交用户人工验收。早期方案被修改或复用均不自动继承这些阶段的确认或证据。
