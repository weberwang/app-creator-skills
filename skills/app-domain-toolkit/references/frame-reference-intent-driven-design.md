# 帧动画意图与设计依据

执行公共规则时，同时读取当前技术栈参考中的原生补充和“本栈配套资料”。各段仅适用于标注的技术栈；结构化证据不代替用户对显示效果的人工验收。

## 从玩法与意图推导动作设计

> 适用技术栈：cocos、phaser。

在动作分析阶段读取本文件，将结论写入既有时间轴设计工件。四类动画和两条来源路线共用此方法；类型相关的运动与造型仍读取对应分类参考。以下流程是对动画原理和开发实践的综合应用，不是能自动算出最佳时长的公式，方案确认按下述流程执行，不新增全局阶段、报告或 schema。

## 从观看体验开始构思

> 适用技术栈：cocos、phaser。

由“动画导演／动作指导”（见本栈配套资料）负责整体构思：简单任务由专业设计师兼任，复杂任务独立委派。先回答“观众为什么愿意看、应感到什么、最有表现力的变化在哪里”，再细化时间轴、专业运动与资源参数；观看体验包括安静细腻、幽默、优雅或强烈爆发，不统一追求更大幅度和更多动作。

> 适用技术栈：cocos、phaser。

根据已有任务合理推导表演手段，主动考虑姿态对比、身体朝向与空间变化、透视、遮挡、节奏反差和跟随运动。转身、侧身、旋转、翻腾、形变与位移可以自然成为构思的一部分，不因未被逐项指定就默认禁止；具体采用哪些取决于表现目的。角色性格与能力未详尽定义时，可记录合理设计假设形成方案，只有涉及无法推导的玩法事实或行为权限才暂停询问。

> 适用技术栈：cocos、phaser。

先设计核心表演与完整运动范围，再安排画布、关键帧、采样和批次。模型生成或逐帧一致性难题优先通过补足关键状态、明确轨迹、改进提示词和修素材解决；不自动删去旋转、侧身或复杂过渡来换取静态一致。真实基线用于延续身份和风格，不把参考图的单一姿态与朝向当作表演上限。

## 先建立设计依据

> 适用技术栈：cocos、phaser、threejs。

每个动画分别说明玩法作用、表现意图、玩法时间约束和真实视觉参考，区分已有事实、设计建议与未定义事项：

> 适用技术栈：cocos、phaser。

| 依据 | 需要说明的内容 |
| --- | --- |
| 玩法作用与观看者 | 谁触发、谁观察、玩家应理解什么、是否需要立即操作或应对；装饰动画也说明服务的环境或情绪目的 |
| 表现意图 | 要表达的性质及可观察手段，例如敏捷对应快速响应与释放，沉重对应承重和惯性，危险对应清楚的准备与方向；不只写“流畅、有力、好看” |
| 玩法时间约束 | 读取当前输入、状态、伤害、交互或 UI 合同，记录首次反馈、生效、已定义的取消/衔接窗口和结束条件；不适用项省略，未定义项标待确定 |
| 视觉与运动依据 | 当前真实美术基线、参考运动和类型规则，以及哪些运动规律或夸张手段适用于此对象；参考时长不自动等于游戏时长 |

> 适用技术栈：cocos、phaser、threejs。

首次可见响应、生效时点、控制锁定与动画结束是不同概念。例如攻击开始出现准备姿态可以证明按键已响应，但不等于伤害已经生效；收势仍在播放也不必然意味着禁止输入。表现方案沿用已有机制，不自行增加取消、连击、伤害或锁定。需求确需改变机制时，先将玩法变更交回负责的工作项决策。

## 设计师交付与验收检查点

> 适用技术栈：cocos、phaser。

各职业按对应分类参考补充专业判断，共用交付写入当前 Work Item 的既有设计工件，后续制作与验收直接复用，不另建报告或扩展 schema。每个动画须能沿“设计依据 → 设计决定 → 阶段/事件 → 可观察检查点”追溯；不适用的检查项说明原因，缺失的依据和素材标为待确定或未验证，不用空泛评价填满清单。

> 适用技术栈：cocos、phaser。

时长、阶段比例、保持时长、循环周期、FPS、帧数、运动幅度、色彩/亮度变化及尺寸等设计参数，按当前任务的玩法响应、对象性质、视觉风格、显示条件和已有资源预算分别推导。当前方案应给出可制作的具体建议值与理由，但本工作流不设通用数值、固定阶段数或统一阈值。采样受离散帧位约束时按“游戏时间先于来源”（见本栈配套资料）处理；来源路线的工具限制与既有生成规格仍按对应合同执行，不能反向作为动画设计的默认参数。参数或素材更新后同步相关检查点与受影响交接，不保留失效结论。

> 适用技术栈：cocos、phaser。

检查点先关注“完整播放能否感到预期情绪与节奏”“动作亮点是否清楚且自然”，再定位“承重阶段是否出现无因滑动”“事件生效时关键峰值是否已清晰出现”“状态退出后是否残留旧提示”等问题，并给出关联阶段和观看条件。合理的转向、遮挡、透视缩短、速度反差和设计形变不因单帧差异被判错。检查记录绑定当前方案/候选版本、实际素材路径、具体偏差与用户结论，区分通过、待修正和未验证；缺少相邻动作、实际宿主或重复触发情境时保留未验证项。设计自查和文件/时序检查不能替代用户对真实素材的视觉验收，不自动分析截图或启动真机验收。

## 从关键事件推导时间轴

> 适用技术栈：cocos、phaser。

1. **把表演构思转为关键状态。** 从目标感受和亮点出发，围绕任务作用选择初态、关键变化、事件姿态和终态，组织朝向、空间、形状和节奏的演变；攻击可使用准备、释放与收势，机关可使用解锁、展开与就位，UI 可使用响应、结果与退出。只采用实际需要的阶段，不把攻击阶段模板套给所有类型。

> 适用技术栈：cocos、phaser、threejs。

2. **确定时间约束。** 将已有生效时点、反应窗口和切换条件放到游戏时间轴；已定义的总时长或循环周期作为约束，在其范围内设计阶段。没有数值时，根据玩法特点和意图推导合理时长并记录依据；只有玩法事件、时长或行为权限确实缺失且无法推导时才询问，并只暂停受影响动作。不先选统一总时长，再等分阶段。

> 适用技术栈：cocos、phaser、threejs。

3. **分别设计时序与姿态间距。** 时序决定阶段、关键姿态和保持持续多久；姿态间距决定相邻帧之间的位移、转动或形变幅度。同一总时长也可以表现匀速、加速、减速或快速释放，不能仅靠调整 FPS 代替运动设计。

> 适用技术栈：cocos、phaser、threejs。

4. **安排注意力与连接。** 必须识别的状态留出可读时间，关键事件获得与玩法重要性相称的突出程度，辅助运动不过度抢注意力。按对象性质确定过渡、跟随、循环闭合或结束去向；重量感不只靠拉长动作，响应快也不等于所有阶段都压缩。

> 适用技术栈：cocos、phaser、threejs。

5. **确定总时长与采样。** 总时长未定义时，在阶段和事件成立后汇总建议总时长或循环周期；已有时长约束时，核对阶段和事件是否满足该约束，冲突时报告并修订受影响设计，不自行覆盖玩法要求。再选择能表达关键变化的 FPS 与帧位，按“游戏时间先于来源”（见本栈配套资料）处理量化冲突；各动画独立推导，合批只组织来源，不统一节奏。

> 适用技术栈：cocos、phaser、threejs。

在既有阶段表中逐段说明“区间 → 关键姿态/运动 → 玩法事件 → 表现意图与理由 → 检查点”，参数采用当前候选的实际建议值，不使用通用阶段百分比。无玩法事件的阶段明确说明其表现作用。

> 适用技术栈：cocos、phaser、threejs。

例如，一个意在敏捷响应的玩家攻击，可把首次姿态变化与实际命中分别安排；需要玩家躲避的敌人攻击，则围绕既有应对窗口设计准备、方向与释放。这些是推导思路，不规定固定毫秒数，也不据此改变原玩法窗口。

## 方案完成后阐述设计理念

> 适用技术栈：cocos、phaser。

动作方案设计好后、开始制作真实素材前，主动用简短中文向用户阐述设计理念，不等用户追问。四类动画和两条来源路线都适用；多个动作分别说明各自的目标感受，共用方向可以合并介绍。说明围绕“希望给人什么感觉 → 哪些动作设计产生这种感觉”展开：

> 适用技术栈：cocos、phaser。

- **目标感受与作用。** 说明希望玩家感到轻快、沉稳、紧张、松弛、危险或安心等什么具体感受，以及它如何服务当前角色、场景或交互目的；不只写“流畅、有力、好看”。

> 适用技术栈：cocos、phaser。

- **动作与感受的因果。** 选取当前方案中最关键的姿态、重心、轨迹、加减速、停顿、跟随或收尾，解释它们怎样共同形成目标感受。只讲实际采用的设计，不罗列全部动画原理。

> 适用技术栈：cocos、phaser。

- **节奏与取舍。** 说明准备、关键变化和结束之间的节奏对比，以及在已有玩法时间约束下为何这样安排；无需把完整毫秒表、FPS 或提示词搬给用户。

> 适用技术栈：cocos、phaser。

- **效果与性能。** 按“效果与性能平衡”（见本栈配套资料），简要说明推荐的采样与显示精细程度、必须保留的关键表现，以及为加载、内存或同屏并发做了什么取舍。使用与当前方案相关的参数和理由，完整预算留在内部工件；尚未实测的收益明确标为预期。

> 适用技术栈：cocos、phaser。

- **观看重点。** 给出后续真实素材中可以观察的具体表现，让用户知道从哪里判断感觉是否成立。此处描述预期，实际效果仍由用户审阅真实素材后判断。

> 适用技术栈：cocos、phaser。

例如：“这次拔刀希望给人克制、突然爆发的感觉。准备时压低重心并保持刀身稳定，释放时让刀路迅速展开，随后用身体和衣摆的短暂跟随交代惯性，再收稳姿态。观看时重点感受释放前后的速度反差，以及收势是否仍显得可控。”这只是表达方式示例，不规定所有动作都采用拔刀节奏、停顿或跟随。

> 适用技术栈：cocos、phaser。

设计理念同步保存在既有设计工件，制作提示词与逐阶段检查点沿用同一意图。阐述后暂停等待用户明确确认当前动作方案；确认前不推进正式提示词、素材生成或具体实现。收到确认后，在确认范围及已有操作授权内继续，并在既有设计工件记录方案版本、用户确认和适用动作；沉默、等待时间或先前的生成授权不能代替本次方案确认。真实素材交付时可简短提醒对应感受和检查点。同目标返修若调整了表现手段或节奏取舍，补充说明本次调整怎样服务原目标；若改变已确认的目标感受或核心动作方案，重新阐述并等用户确认后继续，已确认方案内的局部纠错按原返修流程执行。

## 带入现有阶段与交接

> 适用技术栈：cocos、phaser。

验收依据复用当前工件，分别保留设计意图、结构/时序核对和人工观察结论。反馈要能定位到阶段或事件，例如“输入后没有可见响应”“预告方向看不清”“峰值晚于生效”“收势被截断”，而非只有“节奏不对”。

> 适用技术栈：cocos、phaser。

返修按问题归因：阶段长度或事件错位修时间映射；姿态、轨迹或幅度不足修关键帧和相邻过渡；运行时额外等待修接入逻辑。同一目标下的纠错直接返修并展示前后对照，更新内部时间轴记录；目标感受、核心动作方案、玩法语义或来源路线实质变化时须重新确认。实际素材变化仍按来源路线重新人工验收。
