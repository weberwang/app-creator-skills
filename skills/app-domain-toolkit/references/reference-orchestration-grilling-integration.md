# 编排中的用户取舍与拷问

执行公共规则时，同时读取当前技术栈参考中的原生补充和“本栈配套资料”。各段仅适用于标注的技术栈；结构化证据不代替用户对显示效果的人工验收。

各技术栈统一使用 V0–V5；V1 是功能实现与验证，白盒可选，正式功能不必等待视觉目标。

## 拷问与 F4 集成

> 适用技术栈：cocos、phaser、threejs。

总控先从用户请求、代码、配置、现有权威工件和确定性执行确认事实。只有无法确定且会改变产品范围、用户可见行为、视觉方向、预算、合规或数据边界的实质取舍才调用 `$grilling`。首次模块或边界变化不得机械触发。F4 按当前 Work Item 处理受保护动作的明确授权与真实结果。

## 一般触发边界

> 适用技术栈：cocos、phaser、threejs。

1. 候选形成前先区分可探索事实与阻断候选的用户决定。前者继续探索；后者可直接 grilling，记录决策 ID、权威工件版本、范围、理由和失效条件，不虚构候选 SHA。

> 适用技术栈：cocos、phaser、threejs。

2. F0 处理范围与流程合规，F1 处理规格一致性，F2 处理专业质量，F3 处理工程验证；F4 按当前 Work Item 核对外部写入、付费、真机、破坏性或外部删除、发布等受保护动作的具体授权。无外部副作用的本地任务按已授权范围执行。

> 适用技术栈：cocos、phaser、threejs。

3. 新模块和模块边界变化仍按风险/变化执行模块审计、技术和 QA F2；若候选形成被实质架构决定阻断，可按第 1 条先 grilling；已有候选时则按第 2 条执行。证据完整且无用户决定时直接继续。

> 适用技术栈：cocos、phaser、threejs。

4. 未获结论前只冻结直接受影响范围，无依赖工作继续。结论绑定当前候选身份；修订候选只让覆盖事实变化的决定失效。

## 条件用户确认

> 适用技术栈：cocos、phaser。

- 已有明确需求或冻结基线，且候选不存在可见偏差或实质取舍：V2/V3 的额外产品取舍可记录 `AUTO`；这不替代全局选图、V3 拆解、独立布局或 Spine 批次人工确认，统一遵循[公共控制面不可绕过约束](../../app-workflow-control/SKILL.md#不可绕过约束)。

> 适用技术栈：cocos、phaser、threejs。

- 指定效果图忠实还原中，专业质量修复、工程适配或提升游戏感只有改变产品方向、玩法语义或上游结构时，才列出影响与候选方案并请求一次 `USER_DECISION`；默认 `usability` 下小幅位置、尺寸、边距和换行差异可直接修复并重验。

> 适用技术栈：cocos、phaser、threejs。

- 新方向、多种同等有效方案、用户可见结构/交互变化或高返工成本取舍：请求一次精确确认。

> 适用技术栈：cocos、phaser、threejs。

- 发布里程碑的外部发布和受保护风险接受，按当前 Work Item 中具体目标与动作核对用户明确授权。

> 适用技术栈：cocos、phaser、threejs。

不得无条件要求低保真与高保真两次批准。一次确认只覆盖所列取舍，不替代 V3 拆解/布局确认，也不豁免缺证与专业缺陷；外部动作仍按副作用单独批准。

## 记录

> 适用技术栈：cocos、phaser、threejs。

候选前决定记录决策 ID、权威工件版本、问题、影响、依据、推荐、用户结论、日期和失效条件；候选相关决定改为绑定候选身份。V2/V3 分别使用 `AUTO` 或 `USER_DECISION` 记录。旧候选选择、沉默、继续工作或参考输入不能替代当前选择。控制面仅索引决定，详细事实留在各自权威交付物；产品决定不替代受保护动作的明确授权。
