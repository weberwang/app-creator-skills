# 决策拷问

供五栈工作流共用。先读事实，再问真正需要用户判断的问题；不因首次实现、新阶段或新模块机械触发。受影响状态归 [app-workflow-control](../app-workflow-control/SKILL.md)，不另建审批流程。

## 执行

1. 读取当前目标、已有 PRD/GDD、技术设计、页面/场景、视觉方向、验收与有效用户决定。没有 PRD 时从目标用户、问题、首次价值和 MVP 开始；有 PRD 时只追问缺口、冲突和关键假设。
2. 用仓库、配置、引擎只读接口和现有证据确认可验证事项；分清事实、假设、未知和决策。能调查得出的技术版本、现有行为或文件位置不能交给用户回答。
3. 按依赖和影响一次问一个实质问题，给出影响、二至三个互斥选项、推荐与理由。问题聚焦当前阻断，不为无关远期功能扩展范围。
4. 明确回答后复用该决定；记录真实用户消息引用、对象、选择、范围、拒绝项、风险、验收和下游影响。已有明确回答不再要求用户重复批准文字摘要；回答含糊或冲突时只追问当前问题。
5. 决定闭合后更新当前权威文档及控制器 `grillingRef` 记录，再继续受影响任务。没有待决事项不制造“无需拷问”的占位记录。

## 按阶段关注

| 阶段 | 实质问题 |
| --- | --- |
| 需求 | 用户价值、MVP、非目标、成功标准、时间/商业约束 |
| 全局基线 | 状态所有权、架构取舍、技术栈、视觉签名及制作预算 |
| 基础工程 | 数据、安全/隐私、第三方依赖、初始化与故障隔离 |
| 对象生产 | 页面/场景边界、状态、交互、视觉目标、资源和实现成本 |
| 集成 | 回归范围、性能预算、风险接受、证据缺口 |
| 发布 | 交付目标、来源许可、签名/上传/分发范围与用户放行 |

技术问题加载所选 `app-stack-*`，不预设所有栈使用 Unity 的目录、坐标、设备或 UI 系统。视觉问题加载 [素材工作流](../app-asset-workflow/SKILL.md)，用真实候选支持判断。

Cocos、Phaser、Three.js 任务需要具体追问策略或阶段条件时，按需读取[拷问策略](../app-domain-toolkit/references/reference-orchestration-technical-grilling.md)和[编排中的用户取舍](../app-domain-toolkit/references/reference-orchestration-grilling-integration.md)，再读取当前栈的原生补充；Unity 与 Flutter 使用各自原生规范。

## 停止与恢复

未决问题只阻断直接依赖它的实现或批量生产；独立调查和其他已授权工作继续。用户未回答、沉默、超时、推荐默认值、代理审查和本地 JSON 均不能当成用户批准。普通实现调整不重开决定；目标改变、用户撤回或授权越界时只重开受影响部分。

产品/视觉决定不等于真机、付费、外部写入、签名、上传或发布授权。记录用户决定不代表控制器能验证用户身份；实际操作仍核对宿主对话和明确授权。具体记录结构见控制器 templates 与 schemas，避免自创第二套机器格式。
