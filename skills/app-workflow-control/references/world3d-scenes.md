# 3D 世界场景控制合同

仅五个游戏技术栈的世界 `SCENE` 可显式使用 `init --design-route world-3d`。未指定时使用二维世界 `world-2d`；纯游戏界面用 `game-ui`，保留原图片流程。PAGE、DISPLAY_LAYER 和 Figma 不可借此跳过原门禁。设计方法仍维护在[关卡与场景方案探索](../../app-domain-toolkit/references/game-design-exploration.md)，本页只说明控制器接线，不新增状态机、审美评分或审批轮。

## 工作项与依据

沿用 V1–V5、F0–F4、实施包、命令结果和 Evidence Manifest。V1 确认完整模块方案并按风险选择空间验证，V2 生成并确认模块适用空间、状态及进度设计，V3 按确认版交接。三维设计使用 `visual.domainEvidenceRef:{path,sha256}` 指向[三维场景合同](../schemas/world3d-scene.schema.json)，正式候选使用非空 `visual.candidateId`。此路线按适用规格表达状态和进度。

合同绑定当前项目、技术栈、工作项、场景、候选、阶段及 `scopeIds`，每份源、规格、审查、人工消息和运行材料使用项目内真实非空文件及 SHA-256。以[场景模板](../templates/world3d-scene.json)理解字段，不能把占位路径、摘要或 APPROVED 当成实际证据。范围绑定生产总范围时，`scopeIds` 对应其中的 `targetIds`，最终集成仍须完整覆盖。

| 阶段 | 替代图片硬门的必要事实 | 保留的控制边界 |
| --- | --- | --- |
| 开工准备 | 声明真实 3D 世界及本批范围，记录空间和内容需求 | 不自动生成审批、运行或资产 |
| V1 | 三维空间与模块完整方案、流程进度、状态和验收 | 每个 3D 世界场景搭建或复用有效白模，按风险选择运行验证 |
| V2 | 基于同一白模和全局方向确认空间及适用状态规格；图片目标覆盖本轮所有二维元素及必要状态 | 用户确认模块设计；按需提供机位预览，控制器核对已登记的来源 |
| V3 | 按同一世界拆分模型，交接稳定身份、单位、尺寸、原点、接口和 `productionRisk` | 以确认的空间规格及已有视图为制作依据，二维元素沿既有图片与 UI 流程 |
| V4 | 正式模型来源与输出、导入和消费者记录及资源人工验收，高风险批次先验证首件 | 原工程／导入证据类别；Unity 等原生约定的正式宿主装配仍在 V5 |
| V5 | 正式场景源、实际运行及当前模型消费绑定、用户显示验收 | `modelBindings` 与本工作项冻结模型规格一一对应；场景中其他未纳入本批的模型不重复登记。原工程／视觉证据类别及最终完整组合，不以白模或样本替代 |

二维与三维世界在 V1 确认模块方案，按风险选择实际运行和必要人工空间确认。所有 3D 世界场景在 V1 搭建或复用有效白模，2D 使用平面布局与正式工程，不使用白模。V2 基于已确认全局方向生成并确认本模块的空间、状态和进度设计。HUD 和菜单不单独制作白模。

进入 V2 前须提供覆盖当前范围的 `spatialSpecRef` 和 `blockoutRef`。V2 起提供空间审查与人工确认。`blockoutRunRef` 按风险选择，填写时须绑定相应白模；正式场景在 V5 仍须提供实际运行与用户显示确认。

3D 世界用[可玩路径](../../app-domain-toolkit/references/incremental-production.md#world-3d-playable-path)贯通空间风险、模型首件和正式替换。在现有模块方案、执行单元及证据中关联实际用例。场景合同核对必要空间与生产材料，已绑定生产总范围时由现有路径覆盖记录核对实际步骤顺序和结果。

<a id="world-camera-designs"></a>

## V2 场景设计与机位预览

V2 用白模、空间规格、相机路径及适用状态规格表达三维空间与机位，不规定机位稿的最低数量。纯 3D 场景没有二维内容时，可用空间、方向和适用状态规格完成 V2。含 HUD、精灵、二维背景或反馈时，图片目标覆盖 V1 确认的当前模块全部二维元素及必要状态；一张能清楚容纳时使用一张，不够时拆分多张，沿用同一场景和共享来源。其他模块只提供理解当前设计所需的空间或交互上下文。

HUD 沿用已有界面目标。非 HUD 的二维内容可在同一 V2 清单用 `scene2dDesignRefs` 按实际张数登记 `{path,sha256}`，无需声明相机或 HUD 目标。同一稿能清楚覆盖 HUD 和其他二维元素时，可以按各自用途引用同一文件。控制器要求 V1 的每项 `element` 绑定 HUD 或 `scene2dDesignRefs` 中的已确认目标，也核对每张已确认二维稿是否有模块条目引用。整组稿件由既有 V2 用户确认覆盖，实际设计表达由用户核对。

需要世界上下文预览时，可在 `visual.moduleDesignRef` 对应的清单登记 `worldViews`；各项声明唯一 `viewId`、当前场景内的 `scopeIds`、三维 `camera.position` 与 `camera.target`、`stateId`、实际 `viewport:{width,height}` 和世界层设计稿 `designRef:{path,sha256}`。不需要预览时可省略 `worldViews`。已登记的视图沿用当前 `SCENE`、白模与全局方向，用户对整份 `moduleDesignRef` 的 V2 确认可覆盖这些视图及原有状态、步骤、转换与进度。

白模向 V2 交接已确认的尺度、路线、碰撞、镜头等空间与功能约束。世界预览和二维稿按全局视觉方向独立设计，V1 白模截图及临时外观禁止作为出稿参考。[正式出稿输入](../../app-creator-workflow/references/workflow.md#v2-design-inputs)

提供世界预览且有常驻 HUD 时，同一清单用 `hudSourceRef:{path,sha256}` 固定共用的可编辑界面源或独立设计图层，每项 `hudTargetId` 引用当前 `visual.hud.targets` 中与状态、视口对应的目标。同状态同视口的不同机位复用同一个 HUD 目标；适配和显隐沿用已确认的规则。无世界预览时可省略预览绑定；无常驻 HUD 时省略 HUD 来源及目标。预览由用户核对实际层序、锚点、样式和界面内容；控制器核对身份、坐标与文件摘要。

V3 从确认的同一空间依据及已有视图按对象和组团拆分模型。V4 可复用符合规格的本地资产、使用项目授权且可用的模型生成 API，或通过 Blender 创建。各来源统一执行模型规格核对、目标引擎导入与消费验证。详见[模型生产交接](../../app-domain-toolkit/references/game-design-exploration.md#production-handoff)。

<a id="persistent-hud"></a>

## 同场景常驻 HUD

3D 世界包含常驻 HUD 时，在同一 `SCENE` 的 `visual.hud` 声明非空 `scopeIds`，并在 V2 起绑定 `globalVisualBaselineRef`、原图片路线的 `targets` 和 `coverageRef`；V5 另绑定同范围 `integrationEvidenceRef`。目标使用真实宿主的 `workItemId`、`objectId/sceneId`、候选、状态及视口，不另建场景或把 HUD 改称瞬态层。HUD 的图片基线、V2 目标、V3 拆解／布局、V4 资源与 V5 实际组合继续走[场景多目标记录](multi-target-visual.md)及对应原生 UI 合同；画面由用户人工检查。世界单方向不是三候选图片基线，已有适用基线和同一次真实用户消息可直接引用，不新设审批。

V1 方案记录是否存在 HUD 和声明范围；新增、移除或变更范围须回 V1 核实。存在 HUD 时在 V2 建立覆盖其本轮范围及必要状态的界面目标；有世界机位预览时按状态与视口引用。HUD 的 V4 资源和确认与世界模型一同归档，V5 验证世界和 HUD 当前组合；空间范围与 HUD 视图身份各自保留。

仅 HUD 返工使用 `hud:V2` 至 `hud:V5` 指明最早受影响阶段，复用未变化的世界空间审查、方向和已归档模型；场景须重新提供与回退阶段一致的领域封套。已有 V3 模型制作依据时，HUD 返工沿用已确认的空间、白模及世界方向，按需更新 HUD 源、关联或上下文预览。空间方案、白模或世界方向变化回普通 V2，模型规格或适用首件变化回相应世界阶段。HUD 变化后的场景组合、运行和显示确认仍在 V5 完成。

## 方向、人工确认和单次审查

全局方向使用[无图基线模板](../templates/world3d-visual-baseline.json)：`designRoute:world-3d`、`directionRef` 和 `selectionReviewRef` 冻结实际方向规格与真实用户消息，不要求虚构图片候选或把规格讨论记成美术成品通过。场景方向必须引用相同方向文件；2D／UI 不得引用此基线绕过原图片候选合同。

单次联合审查记录已有审查结果、依据、问题及处理；阻断问题未解决不能放行；版本变化或修改稿不自动重开完整审美评议，但失败项与实际变化的行为／结构必须定向复验，沿用现有验证证据，不另增审查轮次或批准。空间、方向及最终显示确认各自指向实际对象、当前候选及冻结依据。已有同一次用户决定明确覆盖相关内容时，可复用其真实消息引用，不因此增加人工询问次数；控制器只核对记录，不能证明或伪造用户身份。

V1 方案引用模块空间及适用风险验证；V2 固定确认的模块设计版本，变化按影响返回对应阶段。V4→V5 推进时复用现有阶段归档，固定模型评审、领域合同和证据根；V5 核对历史材料并验证当前正式组合。当前运行、导入和原始输出均须属于实际阶段。

V4、V5 的资源和实际运行证据按控制器当前执行状态归档必要文件版本，并以原路径及摘要区分版本。V1 实际执行已通过时，方案冻结关联白模快照，后续阶段可按原路径及摘要读取历史白模。当前 V5 的正式场景与实际消费模型仍核对当前文件，早期验证结论只覆盖其实际执行范围。

## 风险分流与已有证据复用

V3–V5 场景封套必填 `productionRisk:low` 或 `productionRisk:high`，按本批结构和接入变化判定。已知尺寸、Pivot、碰撞及接口内的外观或纹理调整通常属于低风险，正常批量制作、导入并核对消费者。新接口、通行空间、碰撞、交互、绑定或导入方式变化等高风险批次先完成适用首件验证。高风险首件采用正式模型或必要的最小模型组合，在目标引擎检查本批相关的尺度、连接、材质和交互，验证通过后再扩批。

有效证据覆盖当前范围和版本时直接复用。在当前场景封套用 `modelReuseRef:{path,sha256}` 关联同项目、同技术栈、同场景已完成 V5 的来源工作项。控制器严格检查来源历史材料，并比较单位、模型清单、尺寸、接口及已确认方向，当前模型条目须符合[现行资源评审格式](../schemas/asset-review.schema.json)并与来源已验收条目一致，正式源／输出字节仍须有效。高风险复用需要有效首件及相同白模版本和空间条件；改版前已完成的来源可沿原归档复核首件。来源或依据变化时重新验证受影响范围。

复用覆盖已验证的模型制作、导入及适用首件事实。当前 V1 确认空间与功能方案，V5 完成当前工程检查、模型绑定、正式组合及人工显示确认；适用 `asset-import`／`asset-loading` 证据须有真实结果。资源人工记录可引用仍覆盖同一模型版本的真实来源决定。

## 模型、替换与恢复

空间方案及方向经用户确认、V3 模型规格完成后，由工作项执行者按[正式生产交接](../../app-domain-toolkit/references/game-design-exploration.md#production-handoff)组织建模、按需贴图、分批导入及正式替换。V3 推进时控制器冻结模型规格和生产风险，变化时回 V3 重验。高风险制作在 V4 计划中用 [`sampleRole` 和 `dependsOn`](implementation-execution.md#sample-dependencies)安排一个覆盖本批全部模型 `assetId` 的首件与依赖批次，本批后续单元直接依赖该首件，独立 HUD 样本沿自己的布局依据。先取得绑定代表模型和消费节点的结构化目标引擎运行并完成适用审阅，将通过的结构、材质、导出和接入做法记入任务包，再解锁依赖批次。首件执行结果的 `sampleEvidenceRef`、V4/V5 场景封套的 `sampleRef` 和 V4 资源评审的 `modelSampleRef` 绑定同一文件路径与摘要。没有首件时省略 `sampleRef` 和 `modelSampleRef`。

首件可包含多个需要一起验证的模块，`sampleRef` 以代表模型及真实验证场景登记组合，`sourceRefs` 和 `outputs` 可记录相邻模块。V4 为本批每个冻结模型保留各自的资源评审及导入、消费证据，V5 核对正式引擎场景中的实际绑定。

<a id="model-asset-review"></a>

### V4 模型资源评审

`work.assetReviewRef` 沿用现有资源评审，模型声明 `assetType:model`，绑定真实源／输出路径及摘要、来源类型、导入和消费者证据；AI 模型另冻结生成记录。图片贴图仍按图片资源规则，不能把模型改标为图片或 native-component。实际轴向、Bounds、碰撞几何和性能仍须引擎验证，控制器不从文件存在推断几何还原或美术质量。

RETURN 继续使用原状态机，按影响阶段作废领域封套及相关审查、确认和运行观测，保留未受影响的源文件。重新填写外层封套不能重新绑定已作废确认；设计路线变化必须回到 V1，不能继承旧二维功能基线。功能重验撤销旧 V5 运行确认，普通工程复验不自动重开设计审查。

本版 `reuse-visual` 显式拒绝自动继承 world-3d 阶段批准及跨路线确认；已有有效模型、规格和方向可在当前合同明确引用并重新核对当前范围，不要求重新制作。截图和运行画面仍由用户人工检查，机器测试中的合成协议材料不代表真实引擎、真机或视觉验收已完成。
