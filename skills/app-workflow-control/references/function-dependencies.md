# 功能范围与跨对象依赖

SCENE、PAGE 或 DISPLAY_LAYER 在 V1 验证当前批次实际功能。可直接实施或复用已有功能，是否制作白盒由实际不确定性决定。一个功能可能覆盖多个对象；不要令功能来源依赖这些对象的 V5，否则会形成循环。

对于共享功能，在显示对象的 `visual.functionDependencies` 中按行为范围登记来源工作项及证据。每项填写 `workItemRef.path`、`caseId` 和 `evidenceRef` 的 `{path,sha256}`；一个对象可依赖多个范围，各范围的 `caseId` 必须在该对象内唯一，可使用功能名前缀避免重名。来源必须是同项目、同技术栈、无视觉阶段且已通过的 MODULE 或 INTEGRATION，控制器严格检查它的工程证据和执行状态。

引用的功能证据必须是来源 Evidence Manifest 中的 PASS 文件，内容包含 `schemaVersion: "1.0"`、来源 `workItemId`、`projectId`、`stack`、本行为 `caseId`、`status: "PASS"` 和非空 `objectIds`，其中包含当前显示对象 ID。证据由真实验证产生；SHA 用于检测变更，不能证明人为确认或功能体验已获用户认可。

依赖以唯一 `caseId` 关联来源快照，数组重排和 JSON 字段重排不改变功能范围。项目内等价的相对路径在安全校验后按实际文件身份比较，无需修改原有合同或证据；绝对路径、项目外路径及链接逃逸仍拒绝。来源、行为覆盖或证据内容真实变化时，继续按实际影响重验，不用路径写法变化代替新验证。

一个真实行为证据可关联多个对象，不需要为每个对象重复执行同一验证。对象未声明共享依赖时，在当前工作项完成实际功能实施及工程证据；功能已验证、范围明确时无需额外做白盒。需要用户作出产品取舍时单独保留真实决定，不得由证据文件伪造。

五个技术栈的 DISPLAY_LAYER 功能证据还须绑定单一实际宿主与层类型：直接实现时每个功能执行结果记录 `hostId`、`layerType`；共享功能来源的行为证据也记录相同字段。宿主或类型变化后须针对新上下文重新验证原功能范围并更新基线，不能复用旧宿主的业务通过记录。不同宿主可以共用实现，但各自的验证证据必须与实际宿主一致。

## 导航框架与共享路由

先按可验证行为确定职责：无视觉共享路由 `MODULE` 负责路由注册、跳转、参数、返回和状态恢复；需要跨对象验证时也可使用 `integrationPurpose: feature` 的 `INTEGRATION`。Flutter 的稳定常驻导航框架可在确需独立视觉验收时用 `PAGE` 表达；首页及其他页面各自负责内容。游戏中只把实际存在的大厅、主菜单及内容场景作为 `SCENE`，常驻导航由实际宿主承载，共享导航组件或 Prefab 仅在有真实消费者时提取。正式导航资源由实际对象按照 V3/V4 生产和验收，其他宿主复用已验收资源并验证组合；不能借无视觉模块绕过正式资源门。短暂的弹窗、抽屉、Toast 等是独立 `DISPLAY_LAYER`，每项绑定单一真实宿主；多个宿主可以共用实现，但需按实际宿主分别验证。

例如 `home-to-shop` 可覆盖点击入口、路由到商店、返回首页和需要保留的状态。证据的 `objectIds` 只列实际验证涉及的框架与对象；多个相关对象可以引用同一份已通过的行为证据。使用临时目标时，仅记录和复用已验证的路由通路，不能把占位画面冒充目标页面功能通过。目的地的加载、购买、错误恢复等分别在对应功能范围内验证；无需等待无关场景或目标页面 V5，只有真实运行关系需要时才依赖实际宿主上下文。白盒、临时资源或原型按风险选择，不是阶段门。

公共框架、首页和目标页面各自确认视觉范围；共享框架无需在每个页面重复设计，但每个对象须核对自己与框架的组合。未变化目标按现有同对象视觉复用规则引用确认，不能借共享导航自动继承另一个对象的视觉验收。实际组合后，最终集成记录本批次参与对象和功能基线，重跑路由、状态、返回与显示衔接；遗漏对象或行为不能宣称整条链路通过。共享路由与入口保持单一写入者，避免多个页面工作项并行改写同一份配置。

当前功能证据在推进后仍须可追溯并重验。来源状态、覆盖对象、证据内容或已确认功能行为变化时，先阻断受影响对象并检查影响；涉及功能规则则回到 V1，视觉变化按实际影响处理。最终跨场景用户路径仍在集成验证中使用正式组合重跑，不能以单对象视觉验收代替。

`INTEGRATION` 以 `integrationPurpose` 区分用途：`feature` 是早期功能验证，可以作为 V1 共享来源，不等待场景 V5；`final` 是正式组合后的跨对象回归，不能反向作为 V1 来源。初始化最终集成时使用 `--integration-purpose final`，默认用途为 `feature`。

最终集成在开始实施前通过 `integrationScopeRef: {path,sha256}` 固定预期范围：范围文件包含 `schemaVersion: "1.0"`、`workItemId`、`projectId`、`stack`、`objects: [{objectId,workItemRef:{path,sha256},functionBaselineRef:{path,sha256}}]` 和 `cases: [{caseId,objectIds}]`，对象与行为覆盖均非空且唯一。每个来源必须是当前项目和技术栈已完成 V5 的实际对象，功能基线引用与来源一致。执行状态冻结范围引用，实施后不能静默缩小范围或换绑其他对象版本。

最终集成通过 `integrationEvidenceRef: {path,sha256}` 绑定本工作项 PASS 清单中的回归总记录。总记录包含 `schemaVersion: "1.0"`、`workItemId`、`projectId`、`stack`、`status: "PASS"`、`objects` 和 `cases`，对象及各行为覆盖必须与预先冻结的范围一致。每个对象记录 `objectId`、已完成 V5 的 `workItemRef: {path,sha256}` 和当前 `functionBaselineRef: {path,sha256}`；每个行为记录 `caseId`、`objectIds`、独立实际验证文件 `evidenceRef: {path,sha256}`。行为文件也必须列入本工作项 PASS 清单，并绑定同一工作项、项目、技术栈、行为及对象范围。完成前严格重验每个参与对象及其已冻结功能范围；对象、功能基线或回归证据改变时重新验证受影响范围。

当功能代码变化但确认不影响视觉目标和拆解布局时，可在新的非视觉功能工作项完成真实验证后，提交功能重验规格：`{"visualImpact":"none","reason":"实际影响说明","functionDependencies":[{"workItemRef":{"path":"来源工作项.json"},"caseId":"行为范围","evidenceRef":{"path":"真实行为证据.json","sha256":"实际小写摘要"}}]}`。执行 `refresh-function-baseline --repo <项目路径> --work-item <项目内工作项路径> --spec <项目内规格路径>` 会核验新执行来源并保留未受影响的目标与布局确认，但需要重新完成最终运行验收。不得通过重新计算旧摘要冒充新的功能验证。

V1 由当前工作项直接实现时，V4 或 V5 的 `IMPLEMENTING`、`VALIDATING` 中也可使用 `{"visualImpact":"none","reason":"实际影响说明","localRegression":true}` 提交本地功能重验。先用当前实施包重新执行并完成工程验证，覆盖原 V1 的交付文件和验收命令；控制器检查新执行结果、输出与当前源码并冻结新的内容身份。成功后保持当前阶段和执行状态、保留未受影响的 V2–V4 确认，V5 运行确认须基于新组合重新取得。后续再次修改源码时，通过 implementation 或 engineering 返修建立新的实施及验证记录，再刷新基线；旧记录不可覆盖或作为新回归复用。功能行为或视觉目标、拆解布局实际变化时，应按影响返回相应阶段，不得以 `visualImpact: "none"` 掩盖变化。
