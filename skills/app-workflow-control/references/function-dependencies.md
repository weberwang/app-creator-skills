# 功能范围与跨对象依赖

大场景和跨页面流程先按[分批生产](../../app-domain-toolkit/references/incremental-production.md)确定总范围、当前可验证步骤、状态转移和必要路径；本批 `caseId` 对应实际行为而不是视觉状态标签。批次完成仅证明其范围，最终集成须核对总范围和当前正式组合。

SCENE、PAGE 或 DISPLAY_LAYER 在 V1 确认当前模块完整方案及其功能依赖，可按风险验证或复用已实现的共享功能。V5 验证依赖的真实结果与当前模块组合。一个共享功能可覆盖多个对象，依赖关系按实际来源规划，避免循环。

对于共享功能，在显示对象的 `visual.functionDependencies` 中按行为范围登记来源工作项及证据。每项填写 `workItemRef.path`、`caseId` 和 `evidenceRef` 的 `{path,sha256}`；一个对象可依赖多个范围，各范围的 `caseId` 必须在该对象内唯一，可使用功能名前缀避免重名。来源必须是同项目、同技术栈、无视觉阶段且已通过的 MODULE 或 INTEGRATION，控制器严格检查它的工程证据和执行状态。

引用的功能证据必须是来源 Evidence Manifest 中的 PASS 文件，内容包含 `schemaVersion: "1.0"`、来源 `workItemId`、`projectId`、`stack`、本行为 `caseId`、`status: "PASS"` 和非空 `objectIds`，其中包含当前显示对象 ID。证据由真实验证产生；SHA 用于检测变更，不能证明人为确认或功能体验已获用户认可。

依赖以唯一 `caseId` 关联来源快照，数组重排和 JSON 字段重排不改变功能范围。项目内等价的相对路径在安全校验后按实际文件身份比较，无需修改原有合同或证据；绝对路径、项目外路径及链接逃逸仍拒绝。来源、行为覆盖或证据内容真实变化时，继续按实际影响重验，不用路径写法变化代替新验证。

一个真实行为证据可关联多个对象，不需要为每个对象重复执行同一验证。对象未声明共享依赖时，在当前工作项完成实际功能实施及工程证据；功能已验证、范围明确时无需额外做白盒。需要用户作出产品取舍时单独保留真实决定，不得由证据文件伪造。

选择白盒时遵循[可辨识的功能原型](../../app-creator-workflow/references/readable-functional-prototype.md)：对象、任务、状态与结果应能被理解，检查并入已有功能用例，不新增白盒字段或确认链。模拟数据和临时目标只证明实际执行的机制/通路，来源证据的 `caseId`、`objectIds` 与结论范围须如实对应，不能借占位画面扩大目的地功能或外部服务的通过范围。

各技术栈的 DISPLAY_LAYER 功能证据还须绑定单一实际宿主与层类型：直接实现时每个功能执行结果记录 `hostId`、`layerType`；共享功能来源的行为证据也记录相同字段。宿主或类型变化后须针对新上下文重新验证原功能范围并更新基线，不能复用旧宿主的业务通过记录。不同宿主可以共用实现，但各自的验证证据必须与实际宿主一致。

弹窗与 Toast 按[弹窗公共设计方案](../../app-domain-toolkit/references/reference-domain-display-ownership.md#弹窗公共设计方案)在第 4 阶段确定公共风格，V1 确认模块方案，V2 生成并确认适用模块状态与进度稿。实际宿主提供 V5 正式组合入口；各 DISPLAY_LAYER 保存自己的阶段和证据。设计和资源交付引用写入计划；`visual.functionDependencies` 引用真实非视觉 MODULE 或 feature INTEGRATION 的行为证据。

## 导航框架与共享路由

先按可验证行为确定职责：无视觉共享路由 `MODULE` 负责路由注册、跳转、参数、返回和状态恢复；需要跨对象验证时也可使用 `integrationPurpose: feature` 的 `INTEGRATION`。Flutter、Expo 的稳定常驻导航框架可在确需独立视觉验收时用 `PAGE` 表达；首页及其他页面各自负责内容。游戏中只把实际存在的大厅、主菜单及内容场景作为 `SCENE`，常驻导航由实际宿主承载，共享导航组件或 Prefab 仅在有真实消费者时提取。正式导航资源由实际对象按照 V3/V4 生产和验收，其他宿主复用已验收资源并验证组合；不能借无视觉模块绕过正式资源门。短暂的弹窗、抽屉、Toast 等是独立 `DISPLAY_LAYER`，每项绑定单一真实宿主；多个宿主可以共用实现，但需按实际宿主分别验证。

例如 `home-to-shop` 可覆盖点击入口、路由到商店、返回首页和需要保留的状态。证据的 `objectIds` 只列实际验证涉及的框架与对象；多个相关对象可以引用同一份已通过的行为证据。使用临时目标时，仅记录和复用已验证的路由通路，不能把占位画面冒充目标页面功能通过。目的地的加载、购买、错误恢复等分别在对应功能范围内验证；无需等待无关场景或目标页面 V5，只有真实运行关系需要时才依赖实际宿主上下文。白盒、临时资源或原型按风险选择，不是阶段门。

公共框架、首页和目标页面各自确认视觉范围；共享框架无需在每个页面重复设计，但每个对象须核对自己与框架的组合。未变化目标按现有同对象视觉复用规则引用确认，不能借共享导航自动继承另一个对象的视觉验收。实际组合后，最终集成记录本批次参与对象和功能基线，重跑路由、状态、返回与显示衔接；遗漏对象或行为不能宣称整条链路通过。共享路由与入口保持单一写入者，避免多个页面工作项并行改写同一份配置。

多页面调度按[多页面推进顺序](../../app-domain-toolkit/references/incremental-production.md#多页面推进顺序)先选择本批路径和代表页，再推广已验证的公共方案。代表页 V5 不自动成为其他页面的功能依赖；只等待当前阶段实际消费的行为、接口和视觉规则明确。不同页面可以处于不同 V 阶段，满足依赖和所有权互斥条件时并行；共享实现复用不扩大功能证据范围，也不转移页面视觉确认。

当前功能证据在推进后仍须可追溯并重验。来源状态、覆盖对象、证据内容或已确认功能行为变化时，先阻断受影响对象并检查影响；涉及功能规则则回到 V1，视觉变化按实际影响处理。最终跨场景用户路径仍在集成验证中使用正式组合重跑，不能以单对象视觉验收代替。

## 最终集成验收

游戏与非游戏 App 的 `final` 均先执行[系统覆盖最终闭环](../../app-creator-workflow/references/system-module-coverage.md#最终集成的系统覆盖闭环)：范围必填 `systemCoverageMappings`，逐份来源包核对本批需求、模块和实际消费者，关联最终用例、单元与冻结验收命令。来源包括当前对象包、V1 原包、功能来源重验保留的旧包及共享／生产前批；独立模块用 `systemSources`，总范围中无依赖链的批次用 `productionSources`，不得遗漏已声明批次。开始实施前就严格重验来源，不能只凭 COMPLETE、V5 或同名 case 推断通过。

没有绑定生产总范围的同场景或同页面增量，在 `productionSources` 显式登记需要保留的前批 `{workItemRef:{path,sha256},objectIds:[实际对象ID]}`。历史来源和当前来源须属于同项目、同技术栈、同对象和同类型（`SCENE` 或 `PAGE`）。历史来源须是未绑定总范围、达到 `COMPLETE` 的 V5 工作项，且与当前来源是不同工作项。每个来源只关联自身对象并登记一次。旧包和 V1 来源需求逐项映射到当前最终用例和真实命令。历史材料按冻结版本检查，最新对象和整体验证使用当前版本。原有范围审查核对前批是否登记齐全，`systemSources` 继续承载非视觉系统。

前批页面的原生合同若仍直接冻结正式源码或资源，需要保留可核验的旧版本。原版本不可用时，在当前 `systemCoverage` 中累计需要保留的前批需求，并在当前候选重验，沿现有最终映射关联新证据。

Node.js 无界面服务器采用独立的[模块最终集成证据](../../app-stack-nodejs/references/integration-evidence.md)，来源为同项目、同技术栈已完成的 MODULE，冻结实施包、工程清单和交付文件；不要求 `visual`、V5 或 `functionBaselineRef`。以下显示对象与跨场景音乐规则仅适用于实际视觉栈。

`INTEGRATION` 以 `integrationPurpose` 区分用途：`feature` 可验证早期共享功能，并在 V5 明确复用其真实证据；`final` 是正式组合后的跨对象回归。初始化最终集成时使用 `--integration-purpose final`，默认用途为 `feature`。

最终集成在开始实施前通过 `integrationScopeRef: {path,sha256}` 固定预期范围：范围文件包含 `schemaVersion: "1.0"`、`workItemId`、`projectId`、`stack`、`objects: [{objectId,workItemRef:{path,sha256},functionBaselineRef:{path,sha256}}]` 和 `cases: [{caseId,objectIds}]`，对象与行为覆盖均非空且唯一。每个来源必须是当前项目和技术栈已完成 V5 的实际对象，功能基线引用与来源一致。执行状态冻结范围引用，实施后不能静默缩小范围或换绑其他对象版本。

- **跨场景背景音乐**。项目有跨场景共用的背景音乐时，必须将本项纳入全局集成验收，并在 `integrationScopeRef` 的 `cases` 中登记。在同一正式运行候选中覆盖跨场景切换、返回原场景和重开场景。对每条路径记录前后的曲目、播放进度及播放实例，确认同一首背景音乐从原进度继续，期间始终只有一个背景音乐实例发声。缺少任一路径的运行证据时，本项不得记为通过。

最终集成通过 `integrationEvidenceRef: {path,sha256}` 绑定本工作项 PASS 清单中的回归总记录。总记录包含 `schemaVersion: "1.0"`、`workItemId`、`projectId`、`stack`、`status: "PASS"`、`objects` 和 `cases`，对象及各行为覆盖必须与预先冻结的范围一致。每个对象记录 `objectId`、已完成 V5 的 `workItemRef: {path,sha256}` 和当前 `functionBaselineRef: {path,sha256}`；每个行为记录 `caseId`、`objectIds`、独立实际验证文件 `evidenceRef: {path,sha256}`。行为文件也必须列入本工作项 PASS 清单，并绑定同一工作项、项目、技术栈、行为及对象范围。完成前严格重验每个参与对象及其已冻结功能范围；对象、功能基线或回归证据改变时重新验证受影响范围。

每份行为实际记录同时保存 `unitId`、准确 `command`、`exitCode:0` 与冻结 `outputRef`，并与该单元结果的真实 `commandOutputs.outputFile` 一致；独立日志或未关联的 PASS 文件不能代替。最终范围的来源与需求／设计文件属于保留输入，不能在本次任务中改写或作为结果覆盖。实施后删除范围或改为 `feature` 也会被冻结执行状态阻断。

对于已存在运行功能基线且适用原有功能重验路径的工作项，当功能代码变化但不影响视觉目标和拆解布局时，可在新的非视觉功能工作项完成真实验证后提交重验规格并执行 `refresh-function-baseline`。新 `modulePlanRef` 工作项使用 RETURN 到受影响阶段，再重新实施和验收，不使用历史重刷。不得通过重新计算旧摘要冒充新的功能验证。

使用 `modulePlanRef` 的工作项在功能或方案变化时按影响范围走 RETURN 并重新实施、验证。历史功能基线的本地重验只适用于相应既有工作项；当前 V5 重新取得真实组合及运行确认。
