# 动画单元与共用时间轴

> 通用工作流步骤见[完整规范](../../../../app-domain-toolkit/references/frame-reference-action-timing.md#动画单元与共用时间轴)。

## 动作分析与时间轴

制作前由负责动画或区域的专业设计师按[玩法与意图设计方法](./intent-driven-design.md)建立“观看体验与任务目的 → 表演构思与亮点 → 时间约束 → 姿态与阶段节奏 → 检查点”的推导并保存到内部设计工件，不直接套用阶段比例。先完成可执行的时间轴和资源建议，再向用户说明目标感受、动作依据、节奏与性能取舍；取得用户对当前动作方案的明确确认后，才写正式提示词和制作真实候选：

- 通用工作流步骤见[完整规范](../../../../app-domain-toolkit/references/frame-reference-action-timing.md#动作分析与时间轴)。

方案完成后、真实素材制作前，按[设计理念说明](./intent-driven-design.md#方案完成后阐述设计理念)主动向用户简要解释目标感受、关键动作依据、节奏与资源取舍，并等待用户明确确认当前方案。确认前不编写正式提示词、不生成真实候选或调用图像生成；已存在的生成授权不能替代本次方案确认。多动画任务可继续推导其它明确动作，但每个真实候选都必须落在用户已确认的方案范围内。确认后首次交付真实视频候选/预览或真实图片帧，并附简短检查点；阶段表和推导理由保存在内部工件。仅当玩法事件、时长或行为权限确实缺失且无法从已有规则推导时，询问受影响动作并暂停该动作。实际视频、图片首尾、关键帧及递归父图仍须分别由用户人工确认；真实素材确认可接受素材呈现的时序，但不替代制作前的方案确认。

## 游戏时间先于来源

> 通用工作流步骤见[完整规范](../../../../app-domain-toolkit/references/frame-reference-action-timing.md#游戏时间先于来源)。

同一视频内的独立动画共享来源画布，不要求共享游戏时长或节奏。各组可采用不同总时长、阶段比例、速度变化、停顿、循环周期和 FPS；只有实际玩法需要同步时才约束对应事件，不据此强制全部动作同时开始、同时结束或等长。各区域的有效内容在自己的设计终点结束；短区域不为等待长区域继续生成动作、补定格或重复循环，也不把后续载体时长计入它的帧数、播放时长或动作验收。区域时长和结束方式纳入待确认方案。当前抽帧工具会处理单个区域输入中的全部帧且 `--fps` 同时控制采样和播放；若共享来源包含较长区域的后续区间，应为较短区域准备保留整幅空间布局的派生输入，再只抽取其有效区间，不以报告帧数或声明时长伪造裁切。合批不能为了统一视频时长而拉长短动作、压缩长动作或添加计划外等待。

> 通用工作流步骤见[完整规范](../../../../app-domain-toolkit/references/frame-reference-action-timing.md#游戏时间先于来源)。

| --- | --- |
| 用途类型与视觉依据 | 普通/角色/特效/UI 帧动画、选用的分类参考、真实美术基线的来源与身份、对象性质；设计参数与真实素材验收分开，见[职责边界](./workflow-integration.md#设计与美术的边界) |
| 职业与所有权 | 普通动画、角色、特效或 UI 动效设计职责；混合任务按可独立设计的动画/区域明确职业与文件所有权，交接事件、锚点和跨类型依赖，见 [SKILL.md 执行代理](../../../../app-stack-threejs/references/native-contracts.md#mode-threejs-frame-animation--执行代理) |
| 玩法目的与表现意图 | 触发者/观看者、玩家需要理解或应对的内容、希望表达的性质、既有玩法时间约束；记录适用方法、推导理由和可观察检查点，见[玩法与意图设计方法](./intent-driven-design.md) |
| 来源路线 | 视频抽帧或图片递归补帧、选择依据；是否合批及区域的独立映射 |
| 行为单元与边界 | 名称、触发条件、初态、阶段顺序、终态或循环周期；现有输入/状态机制与生产、运行时分段原因 |
| 每个动画的时长与 FPS | 各动画单元的游戏总时长或循环周期（毫秒）、目标 FPS 与预计帧数，以及游戏特点和玩法时序下的取舍依据；不以视频批次统一时长 |
| 效果与性能取舍 | 目标平台、显示尺寸、关键表现、FPS/帧数/输出 cell、图集规模和已有加载/纹理/并发预算；记录估算与实测差异，见[效果与性能平衡](#效果与性能平衡) |
| 阶段区间与关键姿态 | 每段开始/结束毫秒、运动/过渡/保持意图、关键姿态或关键视觉状态与连接方式；区间覆盖整组，无未说明空档 |
| 事件与衔接 | 事件名称、作用、同一时间轴上的毫秒与目标帧、既有输入/状态衔接窗口；无事件时明确记录无 |
| 前后动作与切换 | 涉及动作/状态交接时记录前置与后续单元、入态/出态、过渡区间和允许切换条件；角色具体判断见[衔接与循环设计](./character-animation.md#衔接与循环设计)；无外部衔接时明确记录无，未定义项保留待确定 |
| 播放与保持 | 明确是否循环；循环、单次、组合、终态保持分别记录，可按任务组合；有意定格的区间、用途、时长或结束条件；循环周期、闭合要求及进入/退出条件，不能把组合等同循环 |
| 锚点与允许位移 | 固定语义根、视角、朝向、允许位移的方向/轨迹/范围及与运行时位置的关系，不把工具默认根点当作设计结论 |
| 运动范围与显示尺寸 | 依据真实美术与完整动作推理运动包络、安全边距、目标显示宽高、输出 cell；区分推断值与实测值，由真实素材检查完整入框；获明确授权的裁剪例外单独记录 |
| 背景与叠加 | 是否保留背景、硬边/真实 Alpha/遮罩或修帧方案；涉及叠加时记录透明度、颜色和混合要求 |
| 类型表现参数 | 重量感、夸张程度、速度变化、停顿和跟随运动的取舍及依据；不适用的项明确不采用 |
| 来源批次与区域 | 批次 ID、画幅、预期/实际宽高、区域 ID 和 x/y/width/height、效果图尺寸推理依据、独立有效时长和输出尺寸；视频在 768p/2K 中比较能覆盖全部动作的条数、总生成时长和整组消耗，记录候选排布与推荐理由；图片沿用自身分辨率约定；视频音轨或独立声音方案 |
| 来源时间映射 | 视频时长独立记录，补齐有效区间与重定时；图片记录目标帧位、关键帧、父图依赖和生成顺序，播放顺序按游戏时间排序 |

预计帧数按游戏时长乘 FPS 计算并记录取整规则，事件映射至可播放帧；量化容差最多一个目标帧间隔，不能丢失关键事件或短促衔接。若当前 FPS 无法表达事件，先调整 FPS 或动作设计并更新方案；尚未确认时纳入待确认方案，已确认后若改变目标感受或核心动作方案则重新说明并确认。不能盲目拉长动作；只有涉及无法推导的玩法时长或行为权限才另行询问。

## 共用质量与优化

先把反馈对应到可观察的问题，再使用当前类型规则调整；共用质量标准如下：

| 标准 | 判断依据与优化方向 |
| --- | --- |
| 可读性 | 在目标显示尺寸下，初态、主要变化、关键姿态/视觉峰值和终态是否可辨；优先调整轮廓、幅度和关键状态，而非单纯加帧 |
| 节奏 | 阶段长度、速度变化和保持是否表达对象性质与任务意图；按阶段调整时间映射，不统一加速或套用蓄力、爆发、固定停顿 |
| 主次关系 | 主对象、关键信息与事件是否先被识别；辅助运动、光效和装饰的强度与出现时点是否符合层次 |
| 连续性 | 相邻阶段、循环接缝或组合连接是否出现未计划的位置、形态、方向或速度跳变；保留有意保持、遮挡和类型允许的跳变 |
| 事件同步 | 可见动作/效果与已有玩法、宿主或 UI 状态事件是否对齐；修正事件表达和帧时序，不用美术方案改触发次数与行为权限 |

> 通用工作流步骤见[完整规范](../../../../app-domain-toolkit/references/frame-reference-action-timing.md#共用质量与优化)。

优化时先区分时间问题与图像问题：视频的阶段过长、事件错位或重复周期先整理有效区间与阶段重定时，最终输入人工验收后抽帧；图片按内部工件的目标槽位重排阶段关键帧和补帧计划。轮廓、姿态、轨迹、颜色与边缘问题修对应帧及相邻帧。同一已确认目标下的局部纠错与细化直接返修并展示前后对照，更新内部时间轴记录；目标感受、核心动作方案、玩法语义或来源路线实质变化时，先重新说明并确认。实际视频或关键帧改变后仍须人工重验受影响素材。两类修正均保留已修图成果并更新来源映射、产物与证据，不以来源缺陷作为最终验收要求。

## 效果与性能平衡

在目标显示尺寸、实际动画播放速度和典型并发情境下选择效果与运行成本的平衡点。先明确必须保留的轮廓、关键姿态、速度反差、事件和衔接，再结合项目目标平台与已有资源预算选择 FPS、帧数及输出 cell。效果与预算无法同时满足时，将受影响表现和取舍建议纳入待确认方案，不自行牺牲核心动作或突破预算。

- **采样与资源尺寸。** 各动画独立选择能读清关键变化的 FPS 和帧数；记录 cell、图集宽高、帧数和压缩文件体积。源图片体积不等于运行时纹理内存；RGBA8 图集可先按宽×高×4 字节估算，再依据实际像素格式、GPU 对齐和 mipmap 设置修正。
- **加载与驻留。** 按实际资源组合核对下载体积、图片解码与纹理上传、加载峰值和纹理驻留；区分估算与运行时实测。共享视频的区域合批只影响来源组织，不证明会共用同一张运行时纹理或降低内存成本。
- **绘制与并发。** 在典型重复播放、最大预期同屏精灵数和透明叠加情境下检查渲染调用、过绘和帧耗时。动画播放 FPS 与游戏渲染帧率是不同参数，减少帧数也不能单独证明绘制成本下降。
- **验证与取舍。** 生产后核对真实图集尺寸、帧数和文件体积；运行态性能按[ThreeJS 测试与性能](../../../../app-stack-threejs/references/native-contracts.md#mode-threejs-game-qa-performance)在已授权环境验证，记录平台、情境、测量证据及未覆盖项。缺少平台预算或实测时标为估算/未验证，不套用跨项目阈值，也不自动启动真机验收。

生成视频的 768p/2K 档位和调用消耗属于制作成本，不能代替运行时图集、纹理和绘制性能检查。没有明确瓶颈或预算证据时，不以提高 FPS、缩小文件或单条预览流畅作为平衡点已成立的结论。
