# 微信小游戏渠道接入

仅在目标包含微信小游戏时使用。小游戏运行在微信宿主及其专用运行环境中；先执行[渠道平台公共接入规范](../channel-platform-integration.md)，再按实际引擎版本读取本专项。普通 Web 包、小程序页面或编辑器预览不能代替小游戏渠道工程和宿主验证，也不能仅凭技术栈名称推断可以导出。

同一导出方案已实际支持多宿主时，按[运行时平台选择](../channel-platform-integration.md#导出方案与运行时平台选择)结合引擎标识和真实小游戏能力选中微信适配器；不为探测环境初始化其他渠道 SDK。微信浏览器中的 H5 与微信小游戏分别识别，不能仅凭 User-Agent 或 `wx` 全局对象调用小游戏 API；若需求实际是 H5，按当前[微信网页 JS-SDK](https://developers.weixin.qq.com/doc/offiaccount/OA_Web_Apps/JS-SDK.html)另核实必要能力，不用本专项冒充 H5 接入。

## 确认接入范围

1. 核对微信平台当前小游戏类目、开发主体、真实 AppID、目标地区、商业模式及对应资质和备案要求。按实际广告变现（IAA）、内购（IAP）及是否涉及其他能力分别核对；不要把某一种资质当作所有游戏固定要求。测试号的能力有限，不能把它当作正式账号上传、发布或商业化验证的证据。
2. 按项目锁定的引擎和版本选择当前官方支持的小游戏适配、构建和开发者工具路线；Unity 采用适用版本的官方适配方案，Cocos 等以实际引擎的导出支持为准。确认渠道工程配置、主包及资源加载方式；只有达到实际需求或平台条件时才安排分包，不固定包体数值或无故引入分包。
3. 按平台当前要求登记业务网络的安全域名、服务端及测试环境，核对 HTTPS、资源下载、合法域名和实际接口可用性；不得将测试域名或凭据默认为正式配置。开发者工具结果、合法域名核查与实际目标宿主运行分别记录。

## 接入与验证

- 登录仅在产品确有账号需求时接入。按小游戏登录合同在客户端获取临时凭证，由可信服务端与微信交换会话；AppSecret、会话密钥和服务端凭据不得写入客户端、日志、截图或源码仓库。测试匿名、取消、过期、断网、重复请求和恢复时，以实际能力为准，不伪造微信身份。
- 按当前官方隐私指引识别实际调用的个人信息相关 API、告知和授权前置，核对声明、同意、拒绝及所选能力的可用路径。平台要求的前置未满足时限制受影响能力并报告，不能冒充同意或提审就绪；不因普通接入擅自扩建无关隐私中心。应用级隐私状态与平台授权分别管理。
- 接入微信小游戏的进入后台/返回前台通知，按实际玩法验证 `onHide`、`onShow` 对输入、计时、音频、广告、网络及资源恢复的影响；重复通知、异步迟到、切后台及返回后不得重复注册、错误发奖或恢复已关闭场景。宿主能力不可用时按用途返回明确结果，不阻塞无关功能。
- 只有确认需要广告时选择微信适用的广告能力。激励广告由用户主动触发，按微信当前完成、关闭、错误回调合同判断结果；提前关闭、失败、取消或未获得有效完成结果不发奖，重复或迟到回调须幂等。客户端回调不是不可伪造的服务端凭证；涉及有价值权益时按平台提供的验证能力和项目风险实现可信核验。
- 只有产品存在适用内购时接入微信当前支持的虚拟支付方案。按主体、类目、目标终端和最新规则核对开通条件与限制；由服务端按选用能力的官方合同核验订单与异步通知，幂等发货并处理取消、失败、重复通知、补单与恢复。没有内购时遵守[内购 SDK 移除规范](../release-readiness.md#内购-sdk-必要性与移除)，不得因渠道存在而预装专用内购 SDK。

## 提审与交付

- 按[发布物料准备](#发布物料准备)交付中文填写稿、图标及九张互不重复的真实截图，沿用公共素材制作和人工显示检查流程。
- 在现有 GDD/TDD、质量记录及发布清单中关联已选渠道、AppID 脱敏身份、引擎/插件版本、开发者工具版本、构建配置、候选内容、适用资质和实际证据。渠道包与素材、隐私说明、备案资料和审核说明须对应当前内容；真实玩法截图按平台要求准备，并交用户人工检查。
- 核对小游戏工程能由当前开发者工具识别、构建和预览；按授权情况验证目标宿主、生命周期、登录、广告、支付及失败路径，分别列出未运行的终端或能力。开发者工具构建成功、源代码上传、审核通过、发布上线分别记录，不能互相替代。
- 平台后台账号配置、上传、提审、正式发布、真实交易、真实广告点击及真机验收须有对应明确授权。缺少工具、账号、资质或环境时记录阻断和可继续的本地工作，不虚构审核或运行结果。

## 发布物料准备

目标包含微信小游戏时，按本项目明确的交付要求准备以下物料，复用[商店文案与展示素材制作](../store-marketing-assets.md#任务安排与完成条件)。数量和分组按本节执行，后台字段、字数、图标及截图的尺寸、格式和体积等技术限制在制作前核对当期后台并记录依据。

| 物料 | 数量与内容要求 |
| --- | --- |
| 正式中文名称 | 1 个，作为发布填写稿中的完整名称，与当前产品内容、品牌及后台登记保持一致 |
| 中文简称 | 1 个，可清楚识别所属游戏，沿用正式名称的品牌含义，按实际后台长度限制编写 |
| 游戏介绍 | 1 份中文介绍，说明游戏类型、玩家目标、核心操作和真实特色，可直接用于填写 |
| 游戏图标 icon | 1 套当前后台所需导出，保留制作源与适用尺寸，突出可辨识的核心角色、道具或品牌元素，缩小后的效果交用户检查 |
| 场景介绍与截图 | 先写 1 份中文场景整体介绍，说明游戏环境、主要界面、关卡或场景特点、玩家目标与主要活动，再集中展示 3 张真实场景截图。截图选取不同环境、关卡或有明显内容差异的场景状态 |
| 玩法介绍与截图 | 先写 1 份完整中文玩法介绍，说明实际操作、规则、目标与关键反馈或结果，再集中展示 3 张真实玩法截图。存在不同玩法时，在介绍中分别说明，并让截图覆盖相应玩法 |
| 游戏系统介绍与截图 | 至少介绍 3 个不同的实际游戏系统，每个系统提供中文名称、功能和使用方式介绍，各配 1 张能说明该系统的截图。完整覆盖下文备案核对中的适用系统 |

### 备案介绍与截图核对

参照微信团队的《小游戏备案攻略》，逐项核对当前实际游戏。该示例发布于 2024-10-09，本次于 2026-11-11 读取，执行备案时复核当前内容与适用流程。[官方审查示例](https://developers.weixin.qq.com/community/minigame/doc/0000aa2fa4ce004604428c9dc63401)

- 场景、玩法、功能系统均需介绍并提供能佐证实际内容的截图。场景和玩法各按“整体介绍在前、截图组在后”组织，先完整说明实际内容，再集中展示各组三张基础截图。场景介绍交代环境、界面、目标和活动，玩法介绍交代操作、规则、目标与成功或失败结果。多种不同玩法在介绍中分别说明，截图组覆盖相应内容，同一玩法的难度变体可合并说明。后台按类目自动生成的类型描述直接核对其一致性。
- 至少覆盖三个不同功能系统。实际存在游戏货币、商城、兑换码、会员或 VIP、道具、红包等可能涉及商业化的系统时，逐项补齐说明和对应截图。按实际机制写清获取途径、消耗用途、兑换或领取条件以及付费情况。所需系统或玩法超过基础选题时，追加介绍与截图并延续全组去重。
- 文案和截图中出现的游戏名称，以及图标中的名称文字，与提审正式名称一致。简称用于后台明确支持的简称字段。名称与实际玩法内容相符，中文用字和命名限制按当前平台要求核对。
- 截图直接从当前实际游戏采集，保留原始文件和运行来源。备案截图排除纯素材图及从视频中截取的画面，全组尺寸一致，文字清晰、无乱码。场景和玩法截图组与各自整体介绍保持内容一致，每个系统的截图与该系统介绍对应。规格由代理检查，清晰度、内容一致性及差异交用户人工确认。
- 核对游戏内主语言为简体中文，大量其他语言内容提供对应翻译。按真实产品核对截图、介绍及游戏中的充值相关内容，存在内购时按已确认的 IAP 资质和备案流程处理，并保持介绍、候选内容与申报一致。
- 备案涉及的文件、签名或盖章信息按当前后台要求核实，游戏名称与提审名称一致。名称含英文或“软件”、涉及授权材料时，核对相应软著资料及授权链要求，在现有发布清单记录缺口。

### 截图选题与全组去重

场景、玩法和系统三组基础交付共九张截图，全组互不重复。其他实际玩法或系统需要追加截图时，纳入同一清单并执行全组去重。采集前在现有素材清单中逐张记录所属分组、要表达的内容、真实场景或系统、状态、操作步骤及预期结果。场景组优先交代环境与关卡差异，玩法组展示玩家操作和结果，系统组展示各系统独有的功能入口、内容或反馈。

每张保留当前候选身份、原始截图、场景或系统及状态来源、最终文件路径和用途。同一原始画面只分配一个截图槽位，换名、裁切、缩放、改格式、调色或叠加不同文字仍按同一画面处理。相邻帧中仅计时、数值或微小动画变化时，应重新选择能表达不同有效内容的时刻。允许在同一真实场景中采集不同内容与状态，交付时逐张说明其独立表达的内容。

代理检查数量、文件可解析性、平台规格、原始来源复用和文件摘要相同项，发现重复后重选实际画面。内容是否有实质差异、是否清楚说明对应玩法或系统，以及最终显示效果由用户人工检查。仅文件摘要不同不足以确认全组无重复。

### 安排与完成条件

策划期准备名称、简称、游戏介绍、场景整体介绍、完整玩法介绍和至少三份系统介绍，并安排基础九张及必要追加截图的选题。交付顺序为场景整体介绍后接场景截图组、完整玩法介绍后接玩法截图组，各系统介绍后接该系统截图。系统介绍覆盖全部适用系统。相关功能和画面稳定后沿正式运行入口采集，按公共规则制作图标及实际需要的截图导出。系统不足三个或截图内容不足时，在现有发布清单记录具体缺口和后续选题，介绍与画面以当前实际内容为依据。

发布准备逐项核对填写稿、图标、场景整体介绍及其后的三张场景截图、完整玩法介绍及其后的三张基础玩法截图、至少三份系统介绍及各自配图，以及覆盖其他实际玩法和适用系统的追加材料，关联当前候选、技术检查和人工确认结果。全部截图的去重同时核对来源与实际内容，缺项及待确认项保留在现有发布材料中。
