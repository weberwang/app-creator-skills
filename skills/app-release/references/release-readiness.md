# 第三方配置、正式环境与候选检查

此规范用于每次构建候选前检查实际生效的服务配置和环境，并在性能检查、优化、图集处理之间作出有依据的选择。内部评审候选可以使用测试服务，但标记必须与实际配置相符；测试环境候选不得标为正式就绪。

仅做检查或候选打包时，使用默认 `RELEASE.releaseIntent=prepare`：完成当前工程验证后，以 `release-preparation` 结果引用真实检查/交付材料即可关闭，结论为“准备完成”。只有实际执行发布才选择 `publish`，并继续核对 F4、精确用户批准和实际 `release-result`。完整收尾规则见[公共流程](../../app-creator-workflow/references/workflow.md#发布准备与实际上线)，准备结果不得描述成已上线。

发布候选中的所有 SDK 同时遵守[隐私流程与 SDK 解耦](../../app-domain-toolkit/references/reference-architecture-sdk-initialization.md#隐私流程与-sdk-解耦)：核对用途策略、未授权及撤回路径和最终包自动启动配置，缺少实际行为证据时明确标记未验证。

包含 Android、iOS/iPadOS 目标时，按[系统启动屏制作与交付](../../app-domain-toolkit/references/system-launch-screen.md)核对最终候选实际包含的原生配置与本地资源、首帧衔接及适用的人工显示结论。输入未变可复用已有有效证据；品牌开场、引导页、应用内加载页不充当系统启动屏验收，缺少原生运行材料时如实标记未验证，不自动真机验收。

## 内购 SDK 必要性与移除

客户端每次准备打包、调整商业能力或依赖时，先按当前候选的实际产品功能和目标平台判断内购 SDK 是否必要，在最终输入冻结前完成处理。没有内购功能时必须移除内购专用 SDK；不能以“以后可能启用”、配置为 false、隐藏购买入口或未调用初始化作为保留理由。本规范不要求无相关能力的服务端或设备端新增内购依赖。

1. **核实功能**：依据当前产品范围、商品/订阅、购买与恢复入口、交易/收据处理及实际调用链，确定是否提供商店内购。订阅、恢复购买或既有权益维护中确实需要客户端内购 SDK 的部分也属于内购功能，不能只按是否显示购买按钮判断；仅广告变现、应用付费下载、普通支付字样或后端权益查询不自动证明需要内购 SDK。功能范围或消费者不明确时记录待核实并查清，不凭猜测删除或判定完成。
2. **检查依赖**：检查直接依赖、锁文件、传递依赖、引擎/平台插件、桥接注册、初始化和原生构建配置，追踪内购 SDK 的实际引入者及运行消费者；源码未调用或包名里没有 IAP 字样不能证明最终包未包含它。
3. **无功能则移除**：使用当前栈的正式依赖/插件管理方式移除内购专用 SDK，更新依赖声明与锁文件，删除只为它存在的初始化、适配/桥接、商店连接、商品占位配置及专用权限/能力声明，处理依赖其类型的无效代码和测试。不得只禁用 UI 或初始化而让 SDK 继续入包；不直接删缓存、生成文件或手改锁文件冒充移除。清理范围遵循项目所有权和[清理规范](../../app-artifact-cleanup/references/project-cleanup.md)。
4. **处理传递与共享依赖**：被其他插件间接带入时，追溯引入方，采用满足实际功能且不包含内购的配置/变体，或调整引入方；不能强行排除依赖导致原生链接、初始化或其他功能损坏。其他支付、广告及确有共享消费者的平台框架按自身用途保留，不能按单个框架名批量删除；如无法移除专用内购 SDK，须记录引入者和阻塞原因，不能将本项标为通过。
5. **有功能则保留必要项**：记录实际内购功能、目标平台、需要保留的 SDK/插件及其消费者，检查购买、取消、失败、恢复、订阅或权益同步中适用的流程。不为凑验证执行真实购买、退款或商店配置修改；这类外部动作仍须对应明确授权，不因规则检查而新增旧版兼容功能。
6. **重新构建并核对实际包**：依赖或配置变化后重新解析/同步并构建受影响平台，检查最终依赖解析和原生链接/打包结果；使用当前平台可用的依赖报告、插件注册结果、产物清单或已解包包内容核实专用 SDK 已移除，不能只靠清单开关或构建成功。复验启动和受影响功能，确认没有失效桥接/初始化、缺失类型或符号；仅 Web 构建不能证明原生包已移除 SDK，未执行的平台标记未验证。

在已有发布清单记录“是否需要、保留或移除项、判断依据及最终候选验证结果”即可，不新增通用表单或机器字段。未提供内购且已确认没有专用 SDK 时，记录核查依据，无需制造卸载任务；移除检查与正式商店资料、服务端数据处置分别处理，不自动删除商品、用户权益、凭据或历史工作流证据。

## 候选清理与交付去向

Expo 沿 [本栈发布规范](../../app-stack-expo/references/verification.md)区分原生构建、Web 导出和按需启用的 OTA。移除原生 SDK 后更新依赖、配置插件及正式原生来源，重新构建核对实际包；不能只发布 JS 更新就宣称原生 SDK 已移除。存在 `.easignore` 时单独核对上传归档中的 `/.agents/` 排除和必需输入，不能假定 `.gitignore` 仍生效；发布候选不依赖开发服务器。构建、更新与提交使用一致且明确的目标环境，密钥不写入客户端公开变量或提交文件。

候选及检查报告按[工作流输出文件规范](../../app-creator-workflow/references/output-files.md)保存实际构建身份、路径和原始输出，采用平台工具原生位置；人工审阅文件、控制记录、制作源与运行资源分别核对发布消费者，不把整个工作流产物目录打进发行包。受公共 `evidenceRoot` 约束的发布检查／交付证据按实际 Schema 保存，不能用外部构建路径直接替代受限证据字段。

最终候选输入冻结前，按[项目清理规范](../../app-artifact-cleanup/references/project-cleanup.md)核对本轮工作流记录和实际项目内容，复用仍覆盖当前输入的盘点、执行与验证结果。清理任务明确目标、修改范围和完成验证；当前代理默认负责，委派或跨角色交接时指定负责人，依赖及交付引用按实际需要补充。未实际执行或未验证的项如实标记，未知候选保留，不能为了候选准备扩大删除授权。

有效计划、执行、确认、原始证据及恢复资料按直接／间接引用保留，本地保留不代表全部进入发布包；临时资源、调试入口、旧包及文档是否打包按实际消费者和已确认用途处理，不从排除发布推导可删除。清理报告、恢复映射、必需原始输出和当前候选仍是交付，不应随临时文件清除。冻结后若清理改变代码／资源／配置或包内选择，原受影响结果过期，重建相应候选并复验；仅核对保留项而输入未变时不无故重建。

## 商店素材交付

面向商店的游戏/客户端候选同时核对[商店截图与宣传图制作](store-marketing-assets.md)：已有平台要求与市场卖点依据、多张真实截图、所需宣传图、可编辑源及平台导出、顺序和用户确认应能关联当前内容。平台核对与脚本可提前安排，正式采集等待相关功能和画面稳定；已有效完成的素材按变化复用，不用“资料齐备”一句代替制作任务及未完成项。

## 盘点第三方服务和生效参数

1. 先冻结候选的提交/快照、平台、渠道、构建 flavor/profile、目标环境和内容版本。记录实际构建的命令、构建机/工具版本、环境名与最终产物身份。
2. 从项目清单和启动代码找出集成：依赖/插件、SDK初始化与调用点、平台工程、配置模板和示例、构建脚本、CI变量名、运行时远程配置字段。覆盖所有打包、启用或能由远程配置打开的服务。可按项目实际情况检查后端/API、认证、分析、崩溃、广告、支付、推送、地图、对象存储、登录、客服等；没有此类服务时写明不适用依据。
3. 对每项集成追踪目标构建的完整生效链：源码默认值与fallback → 编译时定义/构建参数 → flavor/渠道配置 → 环境变量/CI注入 → 平台原生配置 → 启动时覆盖 → 远程配置。按项目和平台实际覆盖优先级解析最后生效值；不得因为 `.env`、示例文件或变量存在就推断最终产物使用了它。
4. 根据项目批准的服务/渠道记录和当前第三方官方配置资料，逐项核对 SDK/插件身份与目标平台支持、配置键、应用/客户端/项目ID、广告应用与广告位ID、分析和崩溃项目、后端/认证/支付/推送端点等适用字段。目标服务未提供期望值、官方资料不能确定含义或运行时覆盖不可见时，写待确认，不能自行填造一个值。
5. 对正式候选逐项核对线上项目身份与服务端点，环境目标、访问控制、权限、发布证书/公钥标识及隐私许可配置。明确排查 debug/development/mock/staging/sandbox 开关、测试广告ID/设备、测试支付、模拟身份、localhost/内网/测试域名、测试证书、开发后端fallback以及远程配置里的测试值。正式域名、release 编译名、`production` 环境标签和签名模式都只是线索，必须与最终有效参数交叉验证。
6. 配置变更和云端/渠道读取仅使用授权的只读凭据或安全的批准记录。不得发起测试购买/付款、真实广告点击、用户数据变更或外部设置修改来证明配置。不要在日志、截图、报告、命令记录里打印密钥、token、私钥、签名材料或完整带凭证URL；只保存脱敏后的服务/参数名、账号或应用ID尾段、来源位置和证据引用。不要对秘密做哈希并放进清单，因为哈希也可能泄露低熵密钥。

每个候选环境都填一行；平台/渠道与覆盖来源分开，期望值来自批准记录，实际值来自对应证据：

| 服务/集成 | 参数名 | 平台/渠道/环境 | 期望身份/脱敏值 | 实际生效身份/脱敏值 | 实际来源及覆盖顺序 | 对照证据 | 结果/待确认项 |
| --- | --- | --- | --- | --- | --- | --- | --- |

使用 `PASS`（来源和有效值均可对照）、`FAIL`（已证明不符）、`待确认`（证据不足/覆盖无法追清）或 `不适用`（写明扫描依据）。未知不能标 PASS。阻止正式运行的 FAIL 或待确认项目列为阻断，不能被 build exit code 或普通 smoke test 抵消。内部候选可以如实标记测试服务与未决配置。

## 性能与图集选择

选择后的性能工作统一按[性能预算、定位与优化复验](../../app-domain-toolkit/references/performance-optimization.md)建立可比基线、定位瓶颈、定向实施和复验；已授权范围内连续推进，不新增逐项审批。图集是独立选择，性能任务不自动包含生成／重打图集或图片改写；无可辨收益或副作用更大的优化按本轮所有权撤回，不能放宽候选预算冒充达标。

在构建候选之前，先报告冻结输入已有的常规检查、性能数据、预算对比、明确缺口和可复现瓶颈；区分发布必需检查、用户已要求的任务与额外优化。基于证据提出是否增加以下工作，并在同一条简短提醒中分别问用户：

1. 是否需要额外做性能检查？说明目标设备/浏览器、负载、构建模式、指标和已有覆盖。
2. 是否需要做性能优化？说明已证明的问题和拟调整范围；问题不成立时明确没有依据推荐优化。
3. 是否需要打包或更新图集？说明当前是否已有图集、目标资源消费者和打包收益/代价。

同一候选的本轮对话已经明确这些选择时直接采用，不重复询问。将每项记录为已选择、明确不做或待用户决定，不把未回答当作同意。未决定的额外检查/优化/图集不得执行，但不阻止按现有授权和当前输入继续构建候选及执行必需的 QA/native 平台门禁；只暂停依赖这些选择的可选工作。若后续选择改变资源/代码输入，重新构建受影响候选并重跑对应检查。没有基准证据或业务需要时不默认优化，也不把额外性能检查或打包图集设成每次发布的强制门。

图集评估以实际 Sprite、UI图标/切片、帧动画和动态加载消费者为单位，检查引用方式、采样/mipmap、透明边缘/padding、色彩空间、压缩格式、最大尺寸、加载/卸载生命周期、GPU/CPU内存、批次收益及目标平台限制。按实际批次、内存和生命周期隔离频繁独立加载或更新的资源，避免把整页截图、大图背景和无关资源一股脑塞进同一 atlas。9-slice/九宫格切片可在消费者和打包格式支持时入图集；保留其 border、切片索引和加载消费者所需元数据，并验证目标布局，不因“九宫格”这一资源类别一概排除。已有图集格式、映射和运行时消费者可保持不变时无需重打。采用当前栈既有图集工具和资产导入流程；Flutter可读取项目中已有 `flutter-asset-atlas` 适配与工具。完成后核对实际消费者能加载其输出，并将新图集带入候选重构建和包体复验。

## 让证据绑定候选

每次修改端点、应用ID、广告/支付/认证配置、flavor、远程配置映射、优化资源、构建参数或图集后，标记受影响的表格行和测试为过期；完成相应对照/构建后再恢复其结果。只展示经过脱敏的服务和环境身份，并将记录绑定到候选快照、平台与渠道。验证不证明未读取的远程值，构建成功不等于第三方配置正确。
