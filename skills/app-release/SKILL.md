# 候选交付与发布准备

目标包含 CrazyGames、微信小游戏、抖音小游戏、Google Play 或 App Store 时，先按[渠道平台接入](references/channel-platform-integration.md)核对已选宿主、地区、应用身份、引擎路线及实际能力，再只读取对应平台专项。需求期安排渠道确认、基础工程打通最小产物、功能期完成适配、最终集成逐渠道验证；发布准备核对当前候选与资料，不把上传／提审／审核通过当作上线。

同一导出方案支持多平台宿主时，按[运行时平台选择](references/channel-platform-integration.md#导出方案与运行时平台选择)复用同一产物，运行时识别平台后仅加载对应 SDK；发布矩阵仍分别记录各宿主的实际验证，平台判断不代替专用引擎适配或原生打包。

微信小游戏、CrazyGames 使用[渠道 SDK 复用资源](references/channel-sdk-reuse.md)，按当前引擎接入渠道专属 API 的具名、强类型具体实现；登录、广告、支付、分享及平台数据按项目使用，不逐项目重写，也不以通用转发代替。网络、文件、音频、渲染、输入等基础接口由引擎提供。Google Play 沿用引擎原生 SDK 接入。

为内部评审或正式发布准备可重现、可识别、可恢复的候选交付物；核实所有实际启用的第三方参数及目标环境，面向商店交付时组织真实截图和宣传图，并让用户决定是否扩展性能检查、优化或图集打包。

执行前阅读[公共执行协议](../app-creator-workflow/references/professional-execution.md)。以下共用步骤不能跳过所选原生适配规定的操作顺序、资源格式与平台边界；必要的用户确认按协议执行。

## 输入

- 已冻结的源代码与版本标识；目标平台、渠道和环境；验证结果及缺陷状态；当前候选的配置与恢复要求。只有任务明确要求升级兼容或数据迁移时，再纳入版本范围、迁移计划与旧数据约束。

## 共用操作步骤

构建与交付按[实际构建输出与候选绑定](references/release-readiness.md#实际构建输出与候选绑定)明确本次真实输出位置及其当前输入依据；不按目录惯例、修改时间或首个存在的旧包猜选候选。工具／SDK 的宣称与实际结果按[能力核实](../app-domain-toolkit/references/tool-capability-verification.md)分别对照。

1. 先明确交付是检查/候选准备还是实际上线：RELEASE 默认 releaseIntent=prepare，以真实 release-preparation 材料及必需工程证据完成准备；实际发布显式使用 publish，并保留 F4、精确批准和实际 release-result。[公共收尾规则](../app-creator-workflow/references/workflow.md#发布准备与实际上线)规定两类结果，准备完成不能标成已发布。
2. 冻结最终候选输入前，客户端按[内购 SDK 必要性与移除](references/release-readiness.md#内购-sdk-必要性与移除)检查实际功能：没有内购功能时移除专用 SDK、依赖及相关接入，有功能时只保留实际所需依赖。按[项目清理任务](../app-artifact-cleanup/references/project-cleanup.md#清理任务拆解与安排时机)核对本轮记录及实际项目内容的清理结果／保留项，确认本地续接、提交与发布去向；未知归属先核实，不为打包越权删除。再按[发布候选与证据约定](../app-creator-workflow/references/professional-conventions.md#release-candidate-evidence)冻结源版本、依赖锁定、构建参数、内容版本与目标矩阵，保证验证绑定同一输入；后续清理改变候选输入时重建受影响产物并复验。
3. 盘点从代码与依赖、平台/渠道构建参数、环境覆盖和远程配置到最终产物的第三方参数生效链，逐项比较目标环境的批准配置并标明证据和不确定项；秘密只通过授权的安全配置通道核对。详细检查见[第三方与正式环境核对规范](references/release-readiness.md)。
4. 汇总已有性能数据、已知瓶颈和资源情况，再提醒用户选择是否需要额外性能检查、性能优化、打包或更新图集；按[候选性能与图集决策](references/release-readiness.md)继续，已有明确选择不重复询问。选中的性能工作遵循[性能预算、定位与优化复验](../app-domain-toolkit/references/performance-optimization.md)，按当前候选同条件比较收益、副作用与受影响回归；性能优化本身不自动授权图集生成或图片改写。
5. 完成提醒后记录每项已选择、明确不做或待决定：已有明确答复时据此冻结最终输入；未答复时保留当前输入，仍按现有授权构建候选并执行必需验证，只暂停依赖未决选择的额外检查或改动。按[发布候选与证据约定](../app-creator-workflow/references/professional-conventions.md#release-candidate-evidence)保存实际命令、工具版本、候选位置、输出校验值、警告和构建日志，不把本地开发服务当成发行包。
6. 验证干净安装、首次启动、核心流程、断网/异常恢复与目标尺寸/包体限制；仅在明确要求兼容/迁移时验证对应升级路径，平台差异分别记录结果。
   面向已选商店或游戏平台交付时，按[商店文案与展示素材制作](references/store-marketing-assets.md#任务安排与完成条件)核对后台字段和槽位，准备可填写文案及所需封面、截图和宣传视频。正式采集绑定稳定版本，成品画面由用户人工确认。仅检查既有候选时核对有效材料与缺口。
7. 为当前候选记录可恢复的备份和恢复步骤；仅当用户明确要求升级兼容或迁移时，才制定受支持版本范围、迁移、回滚及兼容窗口。不可逆或需外部写入时标记阻断并等待相应授权。
8. 在已有发布材料中汇总当前范围的结果、候选位置、验证及恢复入口；检查任务可直接交付检查结论，不因清单名称生成空的发布说明或矩阵。实际候选与发布的合同材料仍须齐备，按[发布候选与证据约定](../app-creator-workflow/references/professional-conventions.md#release-candidate-evidence)区分准备与实际上线。

## 关键边界

- 第三方参数、正式环境和候选来源不能核实的项目标为待确认或阻断，不得仅凭配置标签、正式域名或构建成功宣称正式就绪；秘密不进入日志或交付证据。
- 每次候选都要给出性能检查、优化、图集处理三项明确选择；未获用户选择时不把额外优化或重打图集列作已批准，也不把可选项设为新的强制审批门。
- 候选准备不等于批准发布；不自动上传、购买、签名、发布或修改外部服务。没有明确兼容要求时不新增旧版/API兼容工作，只维护当前候选的备份与恢复路径。
- 引擎导出、浏览器部署、移动应用签名/商店要求由当前栈适配补充。

## 交付

- 按[三项最小约定](../app-creator-workflow/references/output-files.md#每项任务的最小约定)交付当前检查／候选／发布范围的实际结果、文件位置及验证结论，已有材料直接引用。候选身份、真实构建证据、适用平台／配置核对及恢复事实按发布合同保留；无对应产物时不生成占位文件，迁移／兼容材料仅在明确要求时提供，外部动作仍需具体授权。

## 当前技术栈的原生流程

先根据仓库实际依赖与项目配置确认当前 `app-stack-*`，再打开同目录的 [native-adapters.json](native-adapters.json)。按 `when` 选择 `mode`，从 `path` 指向的本栈原生手册中定位 `section` 章节，只读取该模式及其明确需要的脚本、模板和校验器；同栈同能力的多个模式在同一本手册内维护。
使用共用读取工具：`node .agents/skills/app-skill-runtime/read-native-mode.mjs <技术栈> app-release [sourceSkill]`。单模式可省略来源，多模式必须指定清单中的 `sourceSkill`；输出所选章节、直接公共依赖及按需资源路径，不递归加载其他模式。维护本技能仓库时将 `.agents/skills/` 换为 `skills/`。
若 manifest 未列当前栈，继续使用该栈 `app-stack-*` 中的原生规范/索引及适用公共流程；这本身不代表能力缺失。仅当已声明并选中的原生手册或模式章节未随安装提供时才报告阻断。公共工作流只在 `sharedWorkflows[].stacks` 包含当前栈时读取；`onDemand: true` 的参考按当前任务选择，读取器仅列出路径。不要加载其他栈模式或臆造接口；栈未确认且会影响实现时先澄清。
