# 显示对象锚点与显示层分层

本规则适用于正式 Scene、世界对象、屏幕 UI、常驻 HUD 和独立 `DISPLAY_LAYER`。V2 确定分层与对象原点策略，V3 将它们写入布局和显示层合同，V4 按合同装配，V5 用运行证据确认遮挡与输入。

## Scene 与容器显示结构

遵循[公共显示结构约定](../../app-domain-toolkit/references/reference-domain-display-ownership.md#公共显示结构约定)，分别说明 Scene 的 Display List/容器父级、Camera 与可选 DOM 分支，不把代码目录当作运行时显示树。按需使用以下职责，不要求固定容器名称、层数或额外 UI Scene：

```text
Phaser.Game 的实际场景组合
├── 内容 Scene
│   ├── 世界分支 → 地图／角色／世界特效
│   └── 屏幕 UI 分支 → 页面／HUD／导航组件 → 区域 → 功能组件
└── 瞬态层实例（挂到既定容器、专用 Scene 或 DOM 入口）
```

同一对象明确由 Display List 或实际父容器承载，组件拆分按功能而非所有文本/图片分别聚合。屏幕 UI 必须有明确的 Camera/滚动处理及输入坐标映射，容器名称不使其自动脱离世界相机。若采用多 Scene 或 DOM，说明最终显示顺序、暂停边界、事件传播和最上层输入权；显示在上层不等于已阻断下层输入。

主页/大厅 Scene 只拥有自身内容与常驻控件，共享导航控制逻辑不要求新的视觉 Scene。显示层可挂在宿主内，但由独立 DISPLAY_LAYER 实现管理状态和关闭清理，宿主提供稳定接口，不直接读取彼此私有成员。重启或离开 Scene 时解绑监听、定时更新和输入，防止重复创建；共享纹理不随单个实例关闭而误释放。

V1 直接实施或按需用白盒验证导航和实例生命周期；V3 将实际 Scene/Container/GameObject 身份与布局父级、Camera 及 DOM 边界写入现有材料；V5 在正式组合验证切换、打开关闭、状态恢复、resize 及实际命中。结构变化按影响重验，不增加独立的结构审批链。

## 显示对象默认中心锚点

- 可设置原点的显示对象默认使用水平、垂直中心，即 `origin=(0.5, 0.5)`；创建对象或封装组件时显式设置，不能依赖 Phaser 或具体对象类型的隐式默认值。旋转、缩放、碰撞反馈和帧切换应围绕同一稳定中心工作。
- 必须使用其他原点时，逐对象在资源/布局合同记录稳定 ID、`origin` 数值、业务原因和对应的坐标换算，并在运行接入时显式设置。例如满幅背景的边缘对齐、Tilemap 的网格原点或确需左上角作局部坐标基准的对象。不能因为参考图边缘停靠或布局锚点在左上角，就把显示对象的资源原点改成左上角。
- `layout_anchor`、`self_anchor`、`reference_anchor` 决定布局停靠关系；`logicalViewportSpace.coordinateOrigin` 与 `cameraOriginPolicy` 决定坐标系；`animation_offset` 决定反馈位移。这些字段不得代替显示对象 `origin`。Container 或其他不提供资源原点的节点，以子对象局部坐标实现中心枢轴，不伪造 `setOrigin`。
- 序列帧和状态图片要保持统一画布、对象中心与动作物理参照；若动作需要脚底等稳定接触点，用独立的定位参照/局部偏移表达，避免逐帧改动对象原点造成跳动。

## 显示层分层合同

每个场景在 V2 列出实际需要的层及稳定层 ID，按下表从后到前声明可见顺序；无职责的层可以省略。层的根节点、Camera 或 Container、坐标空间、滚动行为、裁切、输入归属、生命周期和负责人必须明确，不能仅靠创建顺序或散落的 `setDepth` 调用决定最终画面。

统一按[游戏层／内容层、HUD、浮窗与弹窗](../../app-domain-toolkit/references/reference-domain-display-ownership.md#游戏层内容层hud浮窗与弹窗)组织：内容 < 屏幕 HUD < 弹窗层 < 浮窗层。多 Scene、Camera 与 DOM 的最终合成也须遵守该关系；非模态面板不能通过局部 depth 置前越过模态，最上层 Toast 提示不改变当前模态输入权。

| 层级职责 | 典型内容 | 关键边界 |
| --- | --- | --- |
| 背景 | 装饰性满幅背景、远景 | 背景适配器负责 cover；不接管世界输入。 |
| 世界后景 | 地图、地面、场景后部遮挡 | 与世界 Camera 和滚动一致。 |
| 世界主体 | 玩家、敌人、道具、交互对象 | 玩法对象与命中归属清晰。 |
| 世界前景与特效 | 前景遮挡、粒子、伤害反馈 | 声明与世界主体的前后关系；特效不抢交互。 |
| 页面内容 | 当前页面主体与功能区域 | 与上述世界分支共同构成游戏层／内容层，不将普通页面区域升为 HUD。 |
| 屏幕 HUD | 常驻导航、信息与操作 | 高于内容，使用屏幕坐标和安全区；不随世界 Camera 意外滚动。 |
| 弹窗层 | 非模态面板，以及成对的模态遮罩与弹窗 | 高于 HUD；非模态面板低于当前模态遮罩，顶层模态及其附属交互接收输入，关闭后恢复。 |
| 浮窗层 | Toast、全局短时反馈 | 高于弹窗层；默认无交互、不抢焦点、不吞输入，保持当前模态隔离。 |

世界空间提示仍归世界深度关系。独立面板复用 `popup` 或实际 `drawer`，Toast 复用 `toast`，仍按独立 DISPLAY_LAYER 管理；附属 Tooltip/下拉跟随所属窗口，不提升到全局浮窗层，不把所有瞬态内容放进同一无差别层。

同一层内使用命名子容器和稳定的局部 `z_index`/`z_order`；跨层比较使用场景声明的层顺序，不能把不同父容器下的局部数值直接比较。弹窗遮罩位于宿主内容之上、弹窗内容之下；多个瞬态层可共存时声明相对顺序、互斥关系及最上层输入权。若使用多 Camera、DOM Overlay 或独立 Scene 承载显示层，合同仍要给出最终合成顺序和输入映射。

V3 的 `regions.z_index`、`layout_nodes.z_order` 和 `display_layer_planning.inventory[].z_order` 必须映射到该层顺序，并在同一父级内保持确定性。V5 正式场景检查背景、世界、HUD、遮罩、弹窗及特效的同屏组合，禁止用一张整屏图代替结构化装配；至少验证代表性状态下的前后遮挡、最上层命中、关闭后宿主输入与焦点恢复，以及 resize 后层顺序和锚点不漂移，并记录当前候选与相关合同身份。
