# 游戏与应用音频

仅在已确认需求包含音频时安排本能力；普通 App 不默认添加点击音、背景音乐或成功提示音。游戏声音表达玩法状态与反馈，非游戏 App 按实际用途处理提示、内容播放、录音及语音功能。

执行前阅读[公共执行协议](../app-creator-workflow/references/professional-execution.md)。以下共用步骤不能跳过所选原生适配规定的操作顺序、资源格式与平台边界；必要的用户确认按协议执行。

## 用途与原生能力分流

- 游戏事件音效按[音效设计与生产](references/sfx-production.md#design)推进，保留玩法、空间、受控变体和动态混音等专项规则。
- 非游戏客户端按[App 音频工作流](../app-domain-toolkit/references/app-audio.md)选择用途、方案、代表用例及生命周期策略；音频功能与声音素材制作分别安排，不强制媒体或录音任务制作游戏音效。
- Flutter、Expo、ESP32 等未在当前 profile 声明 `app-audio` 时，直接读取上述公共参考和当前栈实际原生／插件规范，不调用不存在的原生模式。ESP32 以现有硬件和需求为限；Node.js 无界面服务不按本技能创建客户端音频设施。

## 输入

- 已确认的音频目的、事件／内容来源、页面或场景、状态及会话所有者；适用的可用资源与许可、目标平台、静音／音量偏好、前后台策略及资源预算。游戏另提供玩法事件、空间和声音地标需求。

游戏涉及事件音效设计、制作或返修时，按[音效设计与生产](references/sfx-production.md)交付本批适用的代表样本、正式资源与试听结果。非游戏 App 仅在确需声音素材时安排制作，播放已有内容或录音功能不以音效生产为前置。已有计划与资源登记直接复用。

## 游戏音频操作步骤

1. 逐场景列出音乐、环境层、UI提示、动作反馈与关键事件；为每项写清触发状态、结束条件、可否重复及是否允许被覆盖。
   按[设计](references/sfx-production.md#design)确定声音风格与事件意图；玩法或空间假设尚需验证时，可在相关 V1 前提供代表音效样本，再用真实功能和上下文修订。独立音效交付不以项目工程或视觉阶段为前置。
2. 建立事件到资源的映射，区分一次性、循环、空间化和长音轨；记录资源格式、采样率、时长、循环点、声道和来源许可。
   按[制作与交接](references/sfx-production.md#production)复用合格音频、按需合成本地样本或选择可用外部工具；保留实际资源、来源及可再生产输入。受控变体及事件分层按实际玩法选择，不固定数量或强制逐音审批。
3. 定义总线层级、响度参考、duck/sidechain关系、优先级和并发上限；同类事件密集触发时选择合并、限频或淘汰策略。
4. 由应用级音频服务持有唯一的背景音乐播放实例。切换或重开场景时保留播放进度，重复请求同一首曲目沿用已有实例。场景和对象仅清理自己持有的音频。
5. 逐项在目标运行入口检查触发时序、可听度、混音层级、后台暂停恢复和静音设置，并核算内存与下载体积。连续切场及返回原场景时，验证背景音乐沿原进度继续、重复请求不叠播、离场音效正常清理。
6. 按[试听返修](references/sfx-production.md#audition)分别记录音频文件技术检查、实际运行结果与用户人工听感；单音可先试听，涉及工程接入时再听连续操作及实际场景。依据原始观察局部修订并复验，未运行、未试听或未确认的范围如实保留。

## 关键边界

- 不以脚本或静态配置存在作为音频可听的证明；耳机/设备差异由实际目标平台验证。
- 纯音频任务使用现有 MODULE 或资源实施单元，不要求视觉 V2/V3；同时改变可见表现时继续遵守相关对象的 V0–V5。业务／玩法状态由其权威所有者维护，声音只消费事件。
- 游戏背景音乐、上下文提示音、持续内容播放和录音采用各自已确认的生命周期策略；不把游戏跨场景规则或统一后台暂停强加给所有 App 用途。共享实现可复用，实际平台运行和用户听感分别验收。
- 混音器、音频上下文、浏览器自动播放策略和导入设置按当前栈适配。

## 交付

- 按[三项最小约定](../app-creator-workflow/references/output-files.md#每项任务的最小约定)交付当前范围的结果、涉及文件的实际路径及验证结论；事件／资源映射、来源许可、混音与并发规则、导入预算和触发实现沿用或更新已有材料，不为局部调整重复创建清单。实际运行回归及人工听感结论按适用范围记录；未执行的设备验证或未完成的听感审核如实保留。

## 当前技术栈的原生流程

先根据仓库实际依赖与项目配置确认当前 `app-stack-*`，再打开同目录的 [native-adapters.json](native-adapters.json)。按 `when` 选择 `mode`，从 `path` 指向的本栈原生手册中定位 `section` 章节，只读取该模式及其明确需要的脚本、模板和校验器；同栈同能力的多个模式在同一本手册内维护。
使用共用读取工具：`node .agents/skills/app-skill-runtime/read-native-mode.mjs <技术栈> app-audio [sourceSkill]`。单模式可省略来源，多模式必须指定清单中的 `sourceSkill`；输出所选章节、直接公共依赖及按需资源路径，不递归加载其他模式。维护本技能仓库时将 `.agents/skills/` 换为 `skills/`。
若 manifest 未列当前栈，继续使用该栈 `app-stack-*` 中的原生规范/索引及适用公共流程；这本身不代表能力缺失。仅当已声明并选中的原生手册或模式章节未随安装提供时才报告阻断。公共工作流只在 `sharedWorkflows[].stacks` 包含当前栈时读取；`onDemand: true` 的参考按当前任务选择，读取器仅列出路径。不要加载其他栈模式或臆造接口；栈未确认且会影响实现时先澄清。
