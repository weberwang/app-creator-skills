# 服务器架构规范

## 模块边界

默认先建立可维护的模块化单体；只有真实隔离、伸缩、部署或组织边界需要时才拆服务。已有明确架构沿用实际边界，不借新增接口重建整套应用。按业务能力组织模块，而不是把所有业务堆在全局 `controllers`、`services` 和 `utils` 中。

| 职责 | 应拥有的内容 | 依赖边界 |
| --- | --- | --- |
| 启动与装配 | 配置、依赖创建、路由与消费者注册、启停顺序 | 可以装配具体适配器，不承担业务规则 |
| 传输边界 | HTTP/消息解析、运行时校验、鉴权上下文、响应与错误映射 | 调用业务用例，不直接拼 SQL 或操纵其他模块私有状态 |
| 业务用例 | 操作流程、权限与业务约束、事务边界、并发策略 | 通过明确的数据访问或外部能力契约协作，不依赖 request/response |
| 领域模型 | 状态、规则、不变量与实际需要的值对象 | 不依赖 Web 框架、数据库连接或环境变量 |
| 基础设施适配 | 数据访问、缓存、文件、外部 SDK 与消息传输 | 实现本模块需要的能力，不反向驱动上层业务 |

简单模块可以合并相邻实现文件，不为每个函数制造接口、DTO、Repository 基类和空壳对象。业务复杂时再提取稳定边界；框架的 Controller、Provider、Plugin 或 Middleware 是实现方式，不替代职责设计。

## 目录示例

以下是按职责组织的示例，不要求每个目录都存在：

```text
src/
  main.ts                      # 进程入口与启停
  app.ts                       # 应用装配，可被测试调用
  config/                      # 集中解析后的配置
  modules/
    orders/
      orders.routes.ts         # 传输与运行时输入校验
      orders.service.ts        # 业务用例与事务边界
      orders.model.ts          # 实际需要的实体、规则与类型
      orders.repository.ts     # 本模块的数据访问
      orders.contract.ts       # 跨模块确需公开的能力
  infrastructure/              # 数据库、日志及外部能力的公共适配
  jobs/                        # 已纳入需求的任务/消费者入口
tests/
```

模块私有代码仅在模块内部导入，跨模块只使用公开契约或明确定义的事件。防止模块循环依赖，不以依赖注入容器或全局注册表隐藏循环。多个模块实际稳定复用的能力才放入共享目录，禁止将业务决策散落到通用工具层。

## 状态、事务和生命周期

请求与任务的用户、租户、权限、追踪 ID、取消状态及事务上下文属于本次操作，不存入跨请求共享的可变全局对象。异步上下文工具只用于传播明确上下文，不能把缺失上下文默认为高权限身份。

业务用例拥有事务边界，参与同一事务的数据访问明确使用同一连接或事务上下文。数据库连接池、HTTP 客户端、队列和缓存由装配层创建并统一关闭，避免在每次请求创建永久连接或在模块导入时启动进程/定时任务。具体事务、幂等与任务策略见[数据与任务](data-and-jobs.md)。

区分应用创建与监听端口，测试可装配隔离实例或使用框架的请求注入能力，不能导入模块就连接生产数据库或监听网络。生命周期、就绪和有界关闭见[运行与交付](operations.md)。

## 架构交付

为受影响模块记录职责与非目标、输入输出、状态与资源所有者、公开接口、允许依赖、失败方式、事务与取消边界、验证入口。沿真实用例追踪调用与数据流，不生成与仓库无关的架构图。

第三方 SDK 的独立文件职责复用[公共 SDK 规范](../../app-domain-toolkit/references/reference-architecture-sdk-initialization.md)；这里只适用实际采用的服务端 SDK，移动端广告/归因规则不能证明其支持 Node.js，也不授权创建无需求的隐私或账号系统。
