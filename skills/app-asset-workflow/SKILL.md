# 有设计约束的素材生产

多状态场景和复杂页面按[分批生产](../app-domain-toolkit/references/incremental-production.md#累计对象与视觉增量)连接功能范围与视觉目标；只为需要独立确认的显示差异规划目标，不为每个步骤或数据值强制生图。

接入 [app-creator-workflow](../app-creator-workflow/SKILL.md) 的全局基线与 V0–V5；状态与记录归 [app-workflow-control](../app-workflow-control/SKILL.md)。涉及场景、页面、显示层、功能或机制的显示设计与可见表现新增或修改时，先读取[公共执行协议](../app-creator-workflow/references/professional-execution.md)，从本次增量 V0 定义范围；已有有效目标与素材可复用，不强制重新生图。V1 功能先验证，白盒按需使用；V2 才冻结正式视觉目标。去 AI 味是设计与生产质量问题，不是可由一个提示词、滤镜或检测分数保证的结果。

界面美术应让用户在不阅读文字时，也能理解主要目标、可操作对象及反馈意图；按[无文字意图可读性规范](references/interface-intent.md)设计，并纳入现有候选和组合的人工审阅。正式页面保留必要文案与无障碍标签。

涉及 UI 的拆解、布局图和正式组合时，按[UI 相对布局与定位](../app-ui-layout/references/relative-layout.md)维护布局关系与浮层本体的适用边界，按[还原依据与变更边界](../app-ui-layout/references/relative-layout.md#还原依据与变更边界)区分已确认目标、测量、估计和适配；素材制作不能静默改变已确认的视觉目标。

涉及用户可见文案时，先读取[通用文案原则](../app-domain-toolkit/references/ui-copy-principles.md)，再按当前技术栈完成规格、设计与实现。

首次候选、单素材及后续批次在调用生图工具前都要落实[生成前约束](references/style-and-production.md#生成前约束)。涉及界面的效果图先完成[内容与装饰筛选](references/interface-intent.md#在设计与输出前筛选内容)，并把允许出现的文案和图形写进提示词。

Unity、Cocos、Roblox 任务新增显示元素时，统一遵循[显示元素的编辑器还原](../app-domain-toolkit/references/editor-display-authoring.md)，同步交付正式可编辑源及适用的动态预览。

## 生产闭环

移动平台原生系统启动屏按[系统启动屏制作与交付](../app-domain-toolkit/references/system-launch-screen.md#制作输入与资源交付)在基础工程范围完成设计依据、图标和背景制作、平台资源导出及原生配置接入，画面交用户人工检查。制作源与平台变体沿用现有资源清单，具体执行采用该规范的原生启动屏任务。

任务仅制作商店展示截图或宣传图时，转到[商店素材制作](../app-release/references/store-marketing-assets.md)，复用已确认品牌及游戏视觉；下述运行时对象的 V2/V3、技术导入与 V5 装配不作为宣传图制作步骤。实际游戏截图须真实采集，原图与营销加工图分开，不把宣传图注册为运行资源；修改游戏本身时仍走对应对象流程。

1. **决定表达方式**：先复用合格的现有素材、组件、图标系统与字体。Unity、Cocos、Phaser、Three.js 的静态文本按[静态文本的可见表现](../app-domain-toolkit/references/ui-copy-principles.md#静态文本的可见表现)选择位图字体或独立文字图片，以实际目标效果确定。Flutter、Expo 静态与动态文本优先使用各自原生组件，文字图片按设计需要选择。布局、动态文案、数值、图表和交互控件使用本栈适用的原生能力，静态文字资产绑定到真实控件。插画、照片和纹理按素材路线生产，完整效果图用于确认目标。
2. **建立视觉签名**：在相关功能完成 V1 验证之后、V2 正式目标之前，先核对[产品市场调研](../app-creator-workflow/references/professional-conventions.md#product-market-research)及其设计依据；缺失时交由产品策划补齐，再按[风格与制作规范](references/style-and-production.md)固定轮廓、构图节奏、限定色板、光照/材质、细节密度及产品特征。首次全局基线按 Unity 基准产生三张同内容、同视口、同约束候选，用户选择一张；已有有效选择则复用。玩法验证依赖视觉时可在 V1 先做低成本样本，不冒充已确认的正式目标。普通单素材任务直接展示真实候选，不额外要求文字方案批准。
3. **明确资产角色**：游戏内容或场景无法在一张图中清楚表达时，先按[多张场景设计稿](references/multi-image-scene-design.md)划分目标视图并生成所需设计稿；新场景先设计包含必要上下文的完整关键视图，已有场景保留不变部分并仅调整受影响范围。V2 确认后，在 V3 给可见特征编号并记录原生实现/独立素材/共享素材、消费者、状态、尺寸、背景、边缘、切片与动画要求。先确认拆解图，再单独确认布局图；不要将多项可交互元素烘成一张背景。
4. **代表样本与真实组件试接**：V3 拆解与布局分别确认后，在 V4 前段按[代表性接入与分批协作](#代表性接入与分批协作)选择最能暴露风格与技术风险的部件，制作少量样本并接入正式工程的真实组件骨架；核对技术结果并沿用已有样本人工确认后，再批量扩展。已有可靠方案按当前适用性复用，不强制重复生图。生成或编辑位图调用当前宿主的 imagegen 技能与工具，遵守其源图和委派约束；工具缺失则如实标记阻断，不声称已生成。动画制作前先确认设计理念与动作方案。
5. **受控生产与返修**：用已选样本、紧凑提示词与同一制作规格保持系列一致性；代码与资产按已明确的接口分批推进，每批及时接入检查，不等全部素材完成才开始组件实现。优先编辑出问题的部件，保留已合格部分。按[去 AI 味审阅](references/art-review.md)区分结构错误、风格漂移和工程装配错误，不靠叠形容词或随机重抽图掩盖问题。
6. **技术检查与原生导入**：V4 实际解码格式、尺寸与 Alpha，检查边缘、有效内容边界、切片/帧序、来源许可、预算和正式加载路径。再按所选 `app-stack-*` 执行原生导入并回读；不能用文件存在代替资源可加载。
7. **组合与人工验收**：V5 使用真实控件、文字、交互和正式素材组合；提交运行资料、目标对照和检查点，由用户检查显示效果。跨场景功能在正式组合后还须验证完整路径及状态衔接。代理默认不自动分析截图或代写视觉 PASS；只有明确授权自动视觉验证时才分析，并单独记录授权。

## 代表性接入与分批协作

本节用于实际运行时对象的 V4 样本试接，强化既有代表样本与原生导入步骤，不新增阶段、控制器字段或独立审批。正式样本生产在 V3 的拆解与布局分别确认后进行；V1 为验证机制使用的低成本临时样本仍按功能原型管理，不冒充正式资产或视觉确认。仅制作设计稿、宣传图或尚无运行工程的独立素材任务不强制建立应用骨架；交接已知技术规格并如实保留接入未验证范围。

1. **选风险样本**：在已有素材／布局规格中选择最可能暴露问题的组件或区域，例如复杂列表项、弹窗或 HUD；优先覆盖新的拉伸／切片、文字、交互状态或加载方式，不要求逐素材、逐状态制作样本。复用现有组件与导入方案时核对消费者、尺寸、状态、平台和加载条件，仍有效的事实及验证直接引用；变化部分才补验，旧结果不能冒充当前运行通过。
2. **约定消费接口**：明确真实组件／节点、资源角色及身份、目标尺寸与缩放／切片规则、文字与原生控件责任、必要状态和加载／释放责任；预算沿用已确认约束，不自行设阈值。代码侧负责布局、交互、数据与生命周期，美术侧按规格交付资产；沿用现有任务包、布局与素材清单，不建立第二份接口账本。
3. **在正式工程试接**：复用 V1 已验证机制，在真实原生组件、父子关系和代表性数据下，以少量样本配合占位资源进行受控预览。按风险检查长文案／字号、状态变化、适用安全区／键盘、代表尺寸、切片／缩放／透明合成、真实导入加载及退出清理；需要性能结论时使用适用原生测量。编辑器项目保存正式可编辑源，不靠启动脚本覆盖布局。不得另写脱离正式工程的演示页，也不把组件试接标成整个对象正式装配或 V5 通过。
4. **先修正再扩展**：保留实际条件、命令／操作、技术结果和剩余风险，实际组合画面交用户按已有样本审阅检查。技术失败、环境受限或必要人工确认待定时，暂停依赖该结果的批量扩展，继续不受影响的工作。只返修受影响的资源或实现；确需改变已确认目标、拆解或布局时，按现有 RETURN 与确认规则更新对应范围，不静默改规格。
5. **分批接入与收口**：接口及前置结果明确后，互不冲突的组件代码与素材生产可并行；共享规格、正式场景、原生导入配置和集成点保持单写者及有序交接。每批完成即核对实际资源和消费者，沿用第 6 步的技术检查与原生导入，不把首次加载、适配和状态问题集中推迟到 V5。样本及单批通过不替代 V5 当前完整组合、跨对象回归和用户人工视觉验收。

## 记录与门禁

生成、送审及正式接入前按[工作流输出文件规范](../app-creator-workflow/references/output-files.md)明确实际产物及其位置，沿用本栈原生映射；按需保存媒体、布局数据、生成记录和必要源输入。多候选、重验或合同要求时记录真实批次／版本，不为无相关产物创建占位文件。确认目录不代替真实确认，归档副本不替换冻结原件，正式消费者不从临时／审阅目录加载。

生成、制作、导入、替换或复用素材时，按[资源来源与消费者关联](references/asset-provenance.md)在现有唯一素材清单中关联需求／参考、实际制作来源与处理、正式资源身份和真实消费者；已有事实直接引用，仅更新受影响关系。正式素材完成还须有适用导入回读、运行结果和用户人工显示确认，不由清单或文件存在推断通过。

涉及加载显示时，按[加载显示任务拆解与交接](../app-domain-toolkit/references/reference-domain-display-ownership.md#加载显示任务拆解与交接)明确实际视觉与素材交付及验收；跨角色交接时指定负责人，按实际需要传递有效目标、布局依赖和消费入口。复用合格素材或原生实现时沿用已有依据，不强制新增图片。素材完成后交接实际路径及导入结果，不能用加载服务已实现代替显示设计与资源交付。

生产规格使用 [style-recipe.json](templates/style-recipe.json) 与 [asset-task.json](templates/asset-task.json)，作为控制器记录的支持资料；它们不引入第二套状态。最终基线、素材验收、阶段确认分别使用控制器 templates 中的 `global-visual-baseline`、`asset-review` 与 Work Item 的 `visual.reviews`。真实用户消息只记录来源，不能由代理伪造批准。

V4/V5 的 `assetReviewRef` 绑定当前候选及实际素材；全局基线不能替代单素材质量，素材通过不能替代运行组合验收。技术检查与人工风格判断分开记录，`NOT_RUN/FAIL` 不能提升为 `PASS`。出现需改变已选视觉方向或明显增加成本的取舍时路由 [grilling](../grilling/SKILL.md)，同目标局部返修直接继续。

已有完成的同项目、技术栈和对象时，通过公共控制器 `reuse-visual` 按实现、布局、素材或目标变化复用未受影响的基线与 V2/V3 记录，具体范围见[统一流程](../app-creator-workflow/references/workflow.md#视觉确认的增量复用)。保留原确认文件与真实消息引用；当前相关功能验证、V4 素材导入、V5 组合运行及人工验收仍需完成，全局方向改变时重新定调。

## 本地素材工具

已将 Unity 中不依赖引擎的 PNG 编解码和边缘连通去背景工具提升为一份公共实现。命令见[素材技术处理](references/technical-processing.md)。这些工具只检查或改变明确的像素事实，不能判断“是否有 AI 味”，也不能取代生成/编辑图片的专用工具。

## 技术栈原生能力路由

当前公共流程继续由本技能负责。需要处理目标栈专有的资源结构或实现步骤时，先确认项目的 `app-stack-*`，再读取同目录 [native-adapters.json](native-adapters.json)。manifest列出当前栈时，按 `when` 选择 `mode`，使用 `node .agents/skills/app-skill-runtime/read-native-mode.mjs <技术栈> <当前能力名> [sourceSkill]` 读取对应章节、直接公共依赖及按需资源路径；多模式必须指定 `sourceSkill`，维护本仓库时将 `.agents/skills/` 换为 `skills/`。
manifest未列当前栈时，继续使用该栈的 `app-stack-*` 规范/索引和适用公共流程，不视为能力缺失；只有已声明且选中的专项文件缺失才报告阻断。不得改读其他栈适配或虚构原生API。公共工作流仅在 manifest 的适用栈包含当前栈时读取。
