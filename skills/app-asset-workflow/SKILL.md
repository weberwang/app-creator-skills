# 有设计约束的素材生产

多状态场景和复杂页面按[分批生产](../app-domain-toolkit/references/incremental-production.md#累计对象与视觉增量)连接功能范围与视觉目标；只为需要独立确认的显示差异规划目标，不为每个步骤或数据值强制生图。

接入 [app-creator-workflow](../app-creator-workflow/SKILL.md) 的全局基线与 V0–V5，按[公共执行规范](../app-creator-workflow/references/professional-execution.md)交接；状态与记录归 [app-workflow-control](../app-workflow-control/SKILL.md)。显示设计或可见表现新增及修改从本次 V0 定义范围；已有有效目标与素材可复用，不强制重新生图。正式实现须完成相关 V1 功能验证：3D 世界场景按[实现分流](../app-domain-toolkit/references/game-design-exploration.md#implementation-routes)搭建或复用有效白模，2D 世界及 UI 按原流程选择占位与验证方式。仅设计提案不强制先建设运行工程，但不能冒充已验证的 3D 白模。V2 冻结用户实际选择的目标。去 AI 味是设计与生产质量问题，不是可由一个提示词、滤镜或检测分数保证的结果。

场景、页面、HUD、弹出层、素材和交互显示对象共用[体验、视觉方向与意图表达](references/interface-intent.md#design-basis)这一权威：市场、竞品、受众与参考分析必须按[统一要求](../app-creator-workflow/references/professional-conventions.md#product-market-research)完成或核实复用，缺失或变化部分先补齐；再按本批真实行为、压力和状态形成方向，区分硬约束、方向与探索空间，确定信息、空间归属及必要文字。每次生图按[制作输入与发送前检查](references/style-and-production.md#生成前约束)将适用分析转成真实提示词，后台细节留在工程规格；检查纳入现有审阅。正式页面保留必要文案与无障碍标签。

当前视觉设计稿完成后、提交用户确认前，按[单次用户视角审查](references/art-review.md#当前设计稿的单次用户视角审查)核对真实内容、可编辑结构及可测事实。设计稿截图与运行截图默认交用户人工检查；未经明确授权不得自动分析截图或代写视觉 PASS。代理结构检查不代替人工视觉确认。

游戏世界先按[空间方案与结构检查](../app-domain-toolkit/references/game-design-exploration.md#sequence)确定结构草案、尺度规则和镜头依据；前期在同一场景规格记录必要对象需求，不按稿逐物件切图或生成单体资产，关键视角概念图按需制作。3D 白模／2D 占位的适用范围及人工确认按[实现分流](../app-domain-toolkit/references/game-design-exploration.md#implementation-routes)执行，正式资产按[生产交接](../app-domain-toolkit/references/game-design-exploration.md#production-handoff)处理；偏离依据时回原方案解决，不倒推玩法。实际涉及生图时继续遵守宿主生图技能及图片委派规则。

3D 世界的本批整体空间与方向经人工确认、V3 规格完成后，按上述生产交接安排现有建模、按需贴图、代表样本、分批导入及正式替换职责；本栈声明的能力读取对应原生模式，不能仅登记 `world-3d` 合同后省略实际生产和交接。相关技能或工具未安装／不可用时，记录受影响范围并继续不依赖它的工作。

涉及 UI 的拆解、布局图和正式组合时，按[UI 相对布局与定位](../app-ui-layout/references/relative-layout.md)维护布局关系与浮层本体的适用边界，按[还原依据与变更边界](../app-ui-layout/references/relative-layout.md#还原依据与变更边界)区分已确认目标、测量、估计和适配；素材制作不能静默改变已确认的视觉目标。

V3 从 V2 已确认目标出发，关联适用设计项、状态、真实父子、参照、素材或模型、消费者和选择依据。3D 世界以已确认整体空间、正式视觉目标及模型／材质和替换接口交接，不能强制逐对象切图或生产图片；2D 世界的图片目标按适用的图片拆解与布局规则，游戏 UI 按原编号与确认规则。非游戏 App 的 [Figma 设计流程](../app-ui-layout/references/figma-app-design.md)直接复用已选可编辑节点表达，缺失时定向补齐，不强制重新制作拆解图、布局图或重复审批。适用图片拆解时抽象组件框图不能代替拆解，不能未经逐项分析宣布全部原生或仅需头像，也不能将文字、按钮一律切图；V4 才取得、制作、导入并核实实际来源和加载。

五个游戏栈的 3D 世界 `SCENE` 可显式选用公共[无图 3D 场景合同](../app-workflow-control/references/world3d-scenes.md)：绑定真实白模、单次审查、用户空间与方向确认及模型证据，不要求三张候选图或 V3 拆图／布局图确认。2D、UI 与已选图片目标仍执行各自原合同；旧原生图片工具若不支持该路线，应如实报告其适用限制，不伪造图片、证据或用户确认。不得以 Figma 路线或其他对象类型绕过门禁。

涉及用户可见文案时，先读取[通用文案原则](../app-domain-toolkit/references/ui-copy-principles.md)，再按当前技术栈完成规格、设计与实现。

首次候选、单素材及后续批次在调用生图工具前都要落实[生成前约束](references/style-and-production.md#生成前约束)。涉及界面的效果图先完成[内容与装饰筛选](references/interface-intent.md#在设计与输出前筛选内容)，并把允许出现的文案和图形写进提示词。

Unity、Cocos、Roblox 任务新增显示元素时，统一遵循[显示元素的编辑器还原](../app-domain-toolkit/references/editor-display-authoring.md)，同步交付正式可编辑源及适用的动态预览。

## 生产闭环

移动平台原生系统启动屏按[系统启动屏制作与交付](../app-domain-toolkit/references/system-launch-screen.md#制作输入与资源交付)在基础工程范围完成设计依据、图标和背景制作、平台资源导出及原生配置接入，画面交用户人工检查。制作源与平台变体沿用现有资源清单，具体执行采用该规范的原生启动屏任务。

任务仅制作商店展示截图或宣传图时，转到[商店素材制作](../app-release/references/store-marketing-assets.md)，复用已确认品牌及游戏视觉；下述运行时对象的 V2/V3、技术导入与 V5 装配不作为宣传图制作步骤。实际游戏截图须真实采集，原图与营销加工图分开，不把宣传图注册为运行资源；修改游戏本身时仍走对应对象流程。

1. **决定表达方式**：复用合格的现有素材、组件、图标系统与字体，不适合当前目标体验时创建专属组件。Unity 文本按 [UniText 与 JSON 国际化](../unity-development-workflow/references/text-and-localization.md)实施，先检查安装；Cocos、Phaser、Three.js 静态文本按[静态文本的可见表现](../app-domain-toolkit/references/ui-copy-principles.md#静态文本的可见表现)选择位图字体或独立文字图片。Flutter、Expo 文本优先使用原生组件，文字图片按实际需要选择。插画、照片和纹理按需生成或复用；非游戏 App 先用效果图确认视觉目标，再重建可编辑 Figma，不以整页位图冒充可编辑稿。
2. **建立视觉方向**：按[共同设计依据](references/interface-intent.md#design-basis)在已有任务书形成有理由的层级、排版、构图、功能色及统一关系，复用已确认分析，区分业务硬约束、视觉方向与探索空间。Flutter、Expo 默认先使用 imagegen 技能及当前内置生图工具，按项目规则委派 image_generator，制作一张专业代表页效果图，布局、字体、配色、比例和留白交给模型探索。保留实际图、完整提示词、工具来源及版本、图版本和摘要；交用户人工选稿，反馈先修图再选择。有效已确认且目标未变的图可直接复用；工具或额度不足如实阻塞，用户明确其他路线时记录其指令与范围。选图并授权忠实重建后，真实 Figma 节点核对完成即可提取 V3，不重复要求预览选稿，也不伪填新预览通过；实质改稿重新确认受影响范围。仅用户要求比较时按其数量制作实质不同的候选。ESP32 可在硬件限制内采用；游戏图片保持原三候选，3D 世界按[生产交接](../app-domain-toolkit/references/game-design-exploration.md#production-handoff)执行。分析、生图、修订、选稿和重建均属 V2；仅设计提案无需先建工程。
3. **明确资产角色**：游戏实际采用图片视觉目标时按[多张场景设计稿](references/multi-image-scene-design.md)和适用拆解／布局确认处理；3D 世界模型按已确认场景与[生产交接](../app-domain-toolkit/references/game-design-exploration.md#production-handoff)记录制作和替换规格，游戏 UI 保持原有设计、拆解与布局规则。非游戏 App 从 V2 已选 Figma 节点提取原生实现、独立／共享素材、消费者、状态、尺寸、背景及适用处理规格；稿内信息明确时不再机械绘图或重复确认。交互元素不能烘成背景，独立插画、照片、角色等按需制作。
4. **代表样本与真实组件试接**：V3 交接完成后，在 V4 前段按[代表性接入与分批协作](#代表性接入与分批协作)试接风险较高的真实组件和适用素材，核对后再分批扩展。需生成或编辑位图时调用当前宿主 imagegen 技能与工具并遵守 image_generator 委派；工具缺失如实阻断，不静默改用整页生图。付费生成、购买素材或发布不因工具可用而自动授权。
5. **受控生产与返修**：用已选样本、紧凑提示词与同一制作规格保持系列一致性；代码与资产按已明确的接口分批推进，每批及时接入检查，不等全部素材完成才开始组件实现。先按[审阅与返修](references/art-review.md)判断信息结构、空间语义及视觉语言是否有共同原因，再确定修订范围并保留有效的已确认事实；不靠删个别词、换色、叠形容词或随机重抽图掩盖问题。
6. **技术检查与原生导入**：V4 实际解码格式、尺寸与 Alpha，检查边缘、有效内容边界、切片/帧序、来源许可、预算和正式加载路径。再按所选 `app-stack-*` 执行原生导入并回读；不能用文件存在代替资源可加载。
7. **组合与人工验收**：V5 使用真实控件、文字、交互和正式素材组合；提交运行资料、目标对照和检查点，由用户检查显示效果。跨场景功能在正式组合后还须验证完整路径及状态衔接。代理默认不自动分析截图或代写视觉 PASS；只有明确授权自动视觉验证时才分析，并单独记录授权。

## 代表性接入与分批协作

本节用于实际运行时对象的 V4 样本试接，不新增阶段、控制器字段或逐素材审批。3D 世界在本批整体白模场景与正式视觉方向经人工确认、V3 模型替换规格交接后试接代表模块；游戏图片路线及 UI 沿用原 V3 拆解与布局确认。非游戏 App 以已选 Figma 稿和必要交接为依据，已清楚表达的信息不重复画图和批准。V1 临时样本不冒充正式资产或视觉确认；仅制作设计提案、宣传图或尚无运行工程的独立素材任务不强制建立应用骨架。

1. **选风险样本**：在已有素材／布局规格中选择最可能暴露问题的组件或区域，例如复杂列表项、弹窗或 HUD；3D 世界选择代表建筑、环境模块或设施，先试接正式模型再分批扩展。优先覆盖新的拉伸／切片、文字、交互状态或加载方式，不要求逐素材、逐状态制作样本。复用现有组件与导入方案时核对消费者、尺寸、状态、平台和加载条件，仍有效的事实及验证直接引用；变化部分才补验，旧结果不能冒充当前运行通过。
2. **约定消费接口**：明确真实组件／节点、资源角色及身份、目标尺寸与缩放／切片规则、文字与原生控件责任、必要状态和加载／释放责任；预算沿用已确认约束，不自行设阈值。代码侧负责布局、交互、数据与生命周期，美术侧按规格交付资产；沿用现有任务包、布局与素材清单，不建立第二份接口账本。
3. **在正式工程试接**：复用 V1 已验证机制，在真实原生组件、父子关系和代表性数据下，以少量样本配合占位资源进行受控预览。3D 模型核对尺度、轴向、原点、占地、连接口和稳定身份，以及碰撞／交互代理和实际导入；替换后复验受影响的通行、镜头、遮挡与性能，按[生产交接](../app-domain-toolkit/references/game-design-exploration.md#production-handoff)处理偏差。其他内容按风险检查长文案／字号、状态变化、适用安全区／键盘、代表尺寸、切片／缩放／透明合成、真实导入加载及退出清理；需要性能结论时使用适用原生测量。编辑器项目保存正式可编辑源，不靠启动脚本覆盖布局。不得另写脱离正式工程的演示页，也不把组件试接标成整个对象正式装配或 V5 通过。
4. **先修正再扩展**：保留实际条件、命令／操作、技术结果和剩余风险，实际组合画面交用户按已有样本审阅检查。技术失败、环境受限或必要人工确认待定时，暂停依赖该结果的批量扩展，继续不受影响的工作。只返修受影响的资源或实现；确需改变已确认目标、拆解或布局时，按现有 RETURN 与确认规则更新对应范围，不静默改规格。
5. **分批接入与收口**：接口及前置结果明确后，互不冲突的组件代码与素材生产可并行；共享规格、正式场景、原生导入配置和集成点保持单写者及有序交接。每批完成即核对实际资源和消费者，沿用第 6 步的技术检查与原生导入，不把首次加载、适配和状态问题集中推迟到 V5。样本及单批通过不替代 V5 当前完整组合、跨对象回归和用户人工视觉验收。

## 记录与门禁

生成、送审及正式接入前按[工作流输出文件规范](../app-creator-workflow/references/output-files.md)明确实际产物及其位置，沿用本栈原生映射；按需保存媒体、布局数据、生成记录和必要源输入。多候选、重验或合同要求时记录真实批次／版本，不为无相关产物创建占位文件。确认目录不代替真实确认，归档副本不替换冻结原件，正式消费者不从临时／审阅目录加载。

生成、制作、导入、替换或复用素材时，按[资源来源与消费者关联](references/asset-provenance.md)在现有唯一素材清单中关联需求／参考、实际制作来源与处理、正式资源身份和真实消费者；已有事实直接引用，仅更新受影响关系。正式素材完成还须有适用导入回读、运行结果和用户人工显示确认，不由清单或文件存在推断通过。

涉及加载显示时，按[加载显示任务拆解与交接](../app-domain-toolkit/references/reference-domain-display-ownership.md#加载显示任务拆解与交接)明确实际视觉与素材交付及验收；跨角色交接时指定负责人，按实际需要传递有效目标、布局依赖和消费入口。复用合格素材或原生实现时沿用已有依据，不强制新增图片。素材完成后交接实际路径及导入结果，不能用加载服务已实现代替显示设计与资源交付。

生产规格使用 [style-recipe.json](templates/style-recipe.json) 与 [asset-task.json](templates/asset-task.json)，作为控制器记录的支持资料；它们不引入第二套状态。图片与 UI 路线沿用既有基线、素材评审及阶段确认；`world-3d` 按[无图 3D 场景合同](../app-workflow-control/references/world3d-scenes.md)绑定方向、场景合同和模型评审。真实用户消息只记录来源，不能由代理伪造批准。

V4/V5 的 `assetReviewRef` 绑定当前候选及实际素材；全局基线不能替代单素材质量，素材通过不能替代运行组合验收。技术检查与人工风格判断分开记录，`NOT_RUN/FAIL` 不能提升为 `PASS`。出现需改变已选视觉方向或明显增加成本的取舍时路由 [grilling](../grilling/SKILL.md)，同目标局部返修直接继续。

已有完成的同项目、技术栈和对象时，图片及 UI 路线按[统一流程](../app-creator-workflow/references/workflow.md#视觉确认的增量复用)使用 `reuse-visual`。`world-3d` 暂不自动继承阶段批准，可在当前合同引用并核对有效模型、规格和方向，保留真实来源并按当前范围验证。当前相关功能验证、V4 素材导入、V5 组合运行及人工验收仍需完成。

## 本地素材工具

已将 Unity 中不依赖引擎的 PNG 编解码和边缘连通去背景工具提升为一份公共实现。命令见[素材技术处理](references/technical-processing.md)。这些工具只检查或改变明确的像素事实，不能判断“是否有 AI 味”，也不能取代生成/编辑图片的专用工具。

## 技术栈原生能力路由

当前公共流程继续由本技能负责。需要处理目标栈专有的资源结构或实现步骤时，先确认项目的 `app-stack-*`，再读取同目录 [native-adapters.json](native-adapters.json)。manifest列出当前栈时，按 `when` 选择 `mode`，使用 `node .agents/skills/app-skill-runtime/read-native-mode.mjs <技术栈> <当前能力名> [sourceSkill]` 读取对应章节、直接公共依赖及按需资源路径；多模式必须指定 `sourceSkill`，维护本仓库时将 `.agents/skills/` 换为 `skills/`。
manifest未列当前栈时，继续使用该栈的 `app-stack-*` 规范/索引和适用公共流程，不视为能力缺失；只有已声明且选中的专项文件缺失才报告阻断。不得改读其他栈适配或虚构原生API。公共工作流仅在 manifest 的适用栈包含当前栈时读取。
