# 多张场景设计稿

本规范适用于实际采用图片作为正式视觉目标的场景或 UI；不能仅因为目标属于 3D 世界就强制生成全景、逐物件图片或拆图。3D 世界的白模、人工确认及模型交接按[实现分流](../../app-domain-toolkit/references/game-design-exploration.md#implementation-routes)和[生产交接](../../app-domain-toolkit/references/game-design-exploration.md#production-handoff)执行；公共控制器可显式选择[无图 3D 场景合同](../../app-workflow-control/references/world3d-scenes.md)，不采用本规范的图片目标和 V3 双图门。2D 图片目标及游戏 UI 保留本规范的适用要求；原生旧图片工具若不支持无图合同，按实际能力报告限制，不伪造图片或通过。

## 确定视图范围

关卡结构草案按[方案探索](../../app-domain-toolkit/references/game-design-exploration.md#explore)制作，关键视角概念图按需使用；本规范管理 V1 验证后的图片视觉目标。沿用探索中的区域、地标和视角身份，结合实际验证结果修订覆盖清单；探索图不能直接登记为已确认的 V2 目标。

相关功能先完成 V1 验证；3D 世界按[实现分流](../../app-domain-toolkit/references/game-design-exploration.md#implementation-routes)完成或复用有效白模及本批整体场景人工确认，2D 与 UI 按适用方式验证。采用图片目标时按当前功能影响范围，再根据游戏内容、地图范围、镜头移动、玩家会到达的区域及关键状态判断一张目标视口是否足以清楚表达。新场景图片目标制作包含必要环境和常驻界面的完整关键视图；已有场景复用已确认目标，优先只调整受影响区域并展示足够上下文。仅改变内部逻辑或数值且不影响视觉时不强制生成设计稿。内容多、场景大或状态互斥时，按实际需要及用户指定数量安排可独立审阅的视图；只要一张时选择最有价值的视角，说明未覆盖范围，不自动扩成全套，也不把所有内容缩小、挤进一张图。

在现有场景规格或视觉设计记录中，沿用[视角与状态约定](../../app-domain-toolkit/references/game-design-exploration.md#views)维护视图清单；直接引用同一套空间依据，不另建清单。总览解释整体空间，正常视角检查玩家实际可见内容，两者不能相互替代。以当前任务及玩家路径核对必须展示的玩法、必要常驻 HUD、衔接和未覆盖范围；按本张目的选择少量代表状态。弹窗等瞬态层继续按既有显示层流程处理其宿主上下文，不把互斥状态同时塞入基础场景图。

大场景按[本批连续可玩范围](../../app-creator-workflow/references/readable-functional-prototype.md#大场景本批可玩范围与交接)选择实际视角：区域、路径、状态与图可以多对多关联。覆盖不清楚时补当前连接处或关键遮挡的必要视图，不为每个区域、状态、物品组合都生成图片。各图引用同一正式世界、尺度、镜头依据和共享对象，不能用独立背景图拼出相互脱离的运行区域；未来区域可以保留未覆盖范围，不要求先完成全套设计稿才开始本批制作。

真实游戏视角优先呈现当前行为、可操作目标和下一步空间关系；工程逻辑地块、网格或功能分区无需逐一画出，只有玩法依赖其可见性时才突出。每张静态图只表达代表瞬间；未画出的状态转换、动作和反馈在现有方案交接并由实现后的运行验证覆盖，不能由单图证明。

## 代表性设计稿与完整内容范围

设计稿只表达所选视图及代表状态。动态模板与模型可仅引用本节的范围核对原则，不因此改走图片目标、拆图或确认路线。制作与拆解前，依据现有 GDD、物品／关卡配置和本批交付范围，在已有资源清单及生产计划中核对实际所需的类别、必要状态和消费者；区分本批必须交付与后续计划内容，并关联已展示样例、可复用依据及尚待补充的设计、资源或配置。只补实际差异与缺口，不新增清单、固定数量、状态字段或逐物品表单。

按[稳定机制与内容装配](../../app-creator-workflow/references/readable-functional-prototype.md#mechanism-content-assembly)先区分固定空间与配置驱动内容：前者交接实际布局，后者从代表稿提取组件表现、状态资源和装配约束，接入 V1 已实现的必要机制及正式数据入口。保留冻结图的编号／placement 覆盖与实际模板、实例的对应关系，在该图所声明的数据和状态下验证目标；不将逐图拆解解释为逐关复制固定场景，也不以组件复用跳过既有目标确认和资源合同。

业务类别、画面实例和独立资产数量分别判断：同一部件、状态及规格一致时可以按现有合同共用模板，多实例仍保留各自布局与状态关系；不同类别依据轮廓、尺寸、材质、辨识语义及必要交互状态判断能否复用，跨生产单元共享继续遵守本栈输出独立性和所有权限制。运行时改变的数据、排列与实例数量由正式配置和生成逻辑负责，不能把代表稿的数量或位置硬编码为全部关卡；动态实例按[动态元素](../../app-domain-toolkit/references/editor-display-authoring.md#动态元素)消费同源可编辑模板或生成配置。

代表样例的确认只冻结实际选定的目标及有依据的共性规则，不代表未展示类别和状态均已设计或验收。有效方向、模板与制作规格可复用，剩余内容沿既有 V3 规格交接、V4 代表试接和分批生产补齐；出现新的轮廓、尺度、状态或交互风险时才补必要样例／目标并按原环节确认，不强制把全部类别挤入主图，也不为每个类别重做风格探索。已有图片目标的逐图拆解与布局确认仍按其实际范围执行。

图内覆盖与交付范围分别收口：图片拆解的视觉事实和布局覆盖只记录冻结图实际可见的元素、位置和状态，不为未画出的物品编造 bounds、编号或 coverage；未展示但已纳入本批的内容继续由现有资源清单及生产计划追踪，已有组件所需状态的分析与生产义务不因此省略。逐项核对本批类别／必要状态的资源或生成配置、实际绑定和运行消费者，并按[内容实现检查](../../app-domain-toolkit/references/game-content-playtesting.md#levels)取得新增或受影响类别经正式入口创建、绑定及关键交互的实际结果，其他类别复用仍有效的覆盖证据；资源齐全或代表组合运行不能代替类别可用性。组合、排列、密度与状态切换继续用代表组合及新增风险情境验证，不扩展为全部组合或逐类完整关卡。代表画面完成、资源生产完成和实际运行覆盖完成分别报告，缺失或待人工检查的内容如实保留，不能由某张图或某批样本通过外推为全部完成。

## 生成与确认

首批相关功能的 V1 验证后、V2 之前，首次全局方向按既有流程生成同内容、同视口的三张候选并由用户选择；这三张是方向备选，不是场景覆盖清单。候选分别按[视觉方向](style-and-production.md#三候选选择)定义完整造型和制作路线，共同内容与视角不意味着共同造型。选择并冻结全局基线后，按视图清单生成需要的设计稿，而不是为每张图重新产生三种风格。选定方向的后续图沿用相同的基线、锚点、角色身份、尺度、镜头规则、光照和 UI 语法；图中内容、区域特征和状态可以按各自职责变化。相邻区域保留可辨认的共同地标或其他衔接线索，记录世界位置、方向和共享元素关系，避免把同一对象画成不同身份。

每张图记录其视图身份、目标场景与状态、视口、来源、实际文件和生成记录，并关联清单及全局基线。按真实目标尺寸生成清楚可读的画面；不要用拼贴或长图代替可独立审阅的视口图，也不要把图当作正式运行界面的单张背景。将全套图片和对应范围、衔接及检查要点交给用户人工确认；有遗漏或冲突时只调整受影响的图和记录。未取得实际确认的视图保持未确认，代理不代替用户判断画面通过。

当前设计稿完成后，按[单次用户视角审查](art-review.md#当前设计稿的单次用户视角审查)审查一次、按本轮问题修改，定向复验失败项及实际变化的行为、语义、结构和共享关系后交用户确认；不扩展成对清单中其他图的全量自动审美评议。已有已确认图不因当前稿变化重新审查，截图和视觉质量继续由用户按原规则检查。

## 拆解、实现与验收

每张被指定为正式运行视觉目标的图分别冻结目标及条件，依次完成 V2 目标、V3 拆解和布局确认、V4 资源验收与 V5 正式场景验证。V1 的功能验证可以由相关对象共享，但不能替代每个视觉目标的确认。每张图的区域、布局、状态和证据绑定其对应目标，不能用另一张图的确认或一个代表视图替代。每张图内可以包含基础场景与相应常驻 HUD；瞬态显示层仍走独立的宿主上下文流程。

同一生产批次的同一正式场景只建立一个 SCENE 工作项，并在视觉目标清单中逐视图登记身份、目标和确认；后续增量可使用相同场景身份的新工作项，按[分批生产](../../app-domain-toolkit/references/incremental-production.md#累计对象与视觉增量)维护累计目标和确认来源。每张图使用当前工作项的单目标领域合同；为共享场景文件和资源指定唯一所有权、依赖及顺序，不为每张图创建重复的运行场景。共享对象只建立一份资源及稳定身份，记录各视图中的位置和状态；存在差异时明确是否为允许的状态变化。

同一图片场景工作项的多个目标共用 V 阶段，不把每张图当独立 PAGE 跳阶段；需要持续扩展时沿现有生产批次推进，累计保留仍有效目标和新增／变化目标，按当前路线核对确认与证据。无图 3D 世界范围及其常驻 HUD 分别按[世界场景控制合同](../../app-workflow-control/references/world3d-scenes.md#工作项与依据)与[同场景常驻 HUD](../../app-workflow-control/references/world3d-scenes.md#persistent-hud)登记，不将世界 `scopeIds` 当成图片视图或把 HUD 图片目标充当世界空间覆盖。

在场景整体交付前，逐项核对视图清单、各目标的确认与阶段证据、共享资源及相邻区域的衔接；V5 提供各目标对应的正式运行画面，以及适用的镜头移动或区域切换资料，由用户人工检查。跨场景功能在正式组合后另验证完整路径及状态衔接。未完成或未人工确认的视图明确列为未覆盖，不能以某个视图通过冒充整场景通过。控制器逐目标检查冻结范围、目标文件与各次确认的 SHA-256、领域合同、V5 证据类别及整体衔接确认；它不判断图片内容，实际覆盖与视觉衔接仍由用户人工检查。
