# 风格与制作规范

定义视觉方向或生成素材前，必须按[通用分析的统一执行要求](../../app-creator-workflow/references/professional-conventions.md#product-market-research)核对市场、竞品、受众与参考分析。已有有效结论核实来源时效、版本和本批适用性后直接引用，只补查缺失或变化部分；四项依据不全时先补齐，再推进依赖它的制作。此要求覆盖下述各制作路线，不因候选数量、是否生图或使用 Figma 而省略。

## 视觉签名不是关键词堆叠

从产品主题、目标用户、核心操作和实际观看尺寸出发，确定能复述的两个或三个视觉特征。例如“倾斜切角的厚纸剪影、有限双色印刷、关键信息使用大留白”，比“高级、精美、电影感、8K”更能约束一致性。具体风格由项目选择，不统一规定极简、低饱和、写实或手绘。

制作前依据[设计依据](interface-intent.md#design-basis)明确受众、任务和压力，并将产品定位转为有理由的信息层级、文字可读性、色彩功能、材质及系列一致性方向。区分业务、平台、无障碍与已锁定品牌等硬约束和有依据的视觉方向，以及工具可探索的构图表现；不要将未经验证的具体坐标、字号、色值或组件排列冒充硬约束。App 首次效果图仍由模型探索布局、字体、配色、比例、组件形态和留白；具体制作签名从真实候选提炼并在选定后冻结，随还原逐步补齐尺度规格。

正式美术稿先核对本批代表性内容、信息主次及入口／状态关系已有足够依据；依据不足时按[原型到设计的交接](../../app-creator-workflow/references/readable-functional-prototype.md#design-handoff)定向补齐，不直接继承测试关卡、便捷控件或调试布置，也不以给白模换材质代替产品设计。多方向共用核心内容、代表状态与比较条件，沿用当前路线的候选数量；主方向确定后复用到其他状态，不提前为全部状态生产多套风格资产。

style recipe 至少约定：

- 轮廓与比例：形状语言、透视/机位、重心和尺度关系。
- 色彩与光照：功能色、材质固有色、主光方向及可用对比范围。
- 纹理与细节：表面工艺、笔触/颗粒尺度、边缘规则和真实目标显示尺寸下的细节预算。
- 系列特征：角色脸型/服装、图标笔画、道具透视、环境材质或品牌构图的稳定规则。
- 全局字体：Unity 按 [UniText 与固定 JSON](../../unity-development-workflow/references/text-and-localization.md)确定字体栈与统一样式；无法完整还原的文字效果直接图片生产，图片按 JSON 文案的语言/状态绑定。Cocos、Phaser、Three.js 采用位图文字方案前，按[静态文本规范](../../app-domain-toolkit/references/ui-copy-principles.md#静态文本的可见表现)确定源字体与统一样式，再制作文字图集与图片。
- 实现预算：原生组件、位图、矢量、3D、动画分别承担什么；不在效果图承诺无法交付的细节。

参考图先确认可用来源和实际用途：构图、色彩、轮廓、材质或角色身份。用户提供参考并指定改动时按其已授权范围执行，不无条件再加版权问卷；只有来源、复刻用途或批量范围存在实质歧义时询问。保持参考与正式素材的身份分离。

界面构图、控件与图形语义同时遵循[无文字意图可读性规范](interface-intent.md)，使主要任务和操作关系在去掉文字后仍可辨认；将检查纳入下述已有候选审阅。

## 三候选选择

本节固定三候选用于适用的游戏图片视觉基线路线；3D 世界按[实现分流](../../app-domain-toolkit/references/game-design-exploration.md#implementation-routes)完成本批白模和空间依据的人工确认，再按[生产交接](../../app-domain-toolkit/references/game-design-exploration.md#production-handoff)确定方向与模型依据。游戏 UI 保持原路线。Flutter、Expo 默认按 [Figma App 流程](../../app-ui-layout/references/figma-app-design.md)先生成一张代表页效果图、人工选稿后忠实重建 Figma；只有用户要求比较时才按指定数量制作多方向，已有有效确认图可复用。ESP32 按硬件约束可采用同路。效果图不是正式整屏背景，重建预览未人工检查时不得登记视觉通过。

生成前按上述统一要求核对四项分析及其与当前视觉 brief 的对应关系；三张候选共用同一产品定位与已完成或有效复用的分析结论。

采用本图片路线时，全局首次恰好三张候选，题材内容、构图任务、视口和制作预算保持一致，差异集中于可比较的视觉方向。每张保留主题贴合、受众适配、任务可读、观看舒适和美术完成度五项结果，未审为 NOT_RUN；最终选中候选必须五项均经有效人工确认。候选不能替用户选择，也不能用更细致的渲染掩盖任务不可读。

需要比较多个方向时，在已有视觉 brief 或制作规格中分别定义每个方向的形体与轮廓、角色与物件比例、材质与纹理、明暗阴影与边缘、色彩功能分工、UI 与图标语言，以及可实现的制作路线。共同内容、镜头和预算保证比较条件，不强制共同造型、材质或同一美术参考；不能仅改变配色、光照或风格名称。每张候选的实际提示词都独立、完整描述自身视觉语言，不以大段共同的“圆润、可爱、低模”等词加一句差异代替。选定后才将该方向的签名作为系列生产约束。

将“弱化配色、隐藏候选名称后，是否仍能辨认各方向”作为用户人工比较问题；提示词不同、图片生成成功或文件存在都不能证明风格差异成立。适用的截图和预览仍依既有人工规则检查，未经明确授权不自动分析。

上述正式基线规则不用于扩张前期空间探索的图数。用户明确限定本次交付数量时按其要求执行，不自动补成三张或全套视图；尚未满足的正式基线要求如实保持待定，不把单张探索稿登记为已完成方向选择。

选定后提取制作规范和一个代表样本，后续素材按该样本生成或编辑；不要每个图标、页面和道具另起一份随机画风。三张候选只发生在首次全局方向选择，不要求每项素材生成三版。

代表样本沿用现有素材规格和布局依据交接。在目标显示尺寸与实际背景下，由用户检查视觉效果；代理可核对源帧与有效内容边界、透明留白、导入密度、元素尺寸和祖先变换，排除视觉偏移与重复缩放，并按适用性核对切片边角、边框厚度、透明边缘及真实字体/文案造成的排版变化。不能用放大普通图片掩盖内部图案偏小；按既有规则调整布局或重新生产合适素材，不改变已确认视觉目标。

正式位图按[正式尺寸规范](technical-processing.md#正式位图尺寸)分别约定生成画布、正式输出与逻辑显示尺寸。单素材和批量生产交接都须给出由消费者及密度推导的正式尺寸；工具最小输出尺寸高于所需尺寸时，提示词仍围绕最终观看尺寸控制细节，生成后归一化再导入，不将工具画布限制变成项目资源规格。

现有 `asset-task.json` 的 `designBasis` 按需记录依据，不构成新门禁：`sourceAndVersion` 指向有效设计来源；`valueKind` 使用 `confirmed-target`、`measured`、`estimated` 或 `adaptation-rule` 表明该组值的性质，混合来源时在已有说明中逐项区分。边界、留白和密度使用本栈实际单位，未知保留 `null`，不能填写虚构测量；这些字段是交接说明，未接入校验器时不宣称机器已验证。

## 生成前约束

在首次全局候选、页面或场景效果图、单个素材及批量生成前，先从目标用途和实际显示尺寸确定构图主次、必要对象与细节上限。将适用的结构比例、透视、主光、材质、色板和系列特征写进制作规格和提示词。对局部编辑写明允许变更的部分和要保持的特征；对图标、贴图等非界面资产，明确应包含的主体及边缘要求。

复杂游戏空间先按[关卡与场景方案探索](../../app-domain-toolkit/references/game-design-exploration.md#sequence)形成可审阅结构、尺度与镜头依据并完成适用的结构检查；前期只记录对象需求，不按设计稿逐物件拆图或生图。实际需要图片时再将已定关系写入提示词；清单、方位和风格词不能替代空间设计。后续稿包含已确认共享元素时，按[跨设计稿共享元素](asset-provenance.md#shared-design-elements)实际提供可用的同源参考并明确保持及可变部分；未经确认的候选继续按探索阶段处理。复用有效场景规格，生成偏差按该规范回传处理，不静默改写玩法或空间事实。

界面效果图先按[内容与装饰筛选](interface-intent.md#在设计与输出前筛选内容)整理实际页面状态、真实内容和有用途的装饰。正式场景、页面和显示层的效果图须按[实机运行画面约束](#runtime-view-image)编写提示词。每次生成、编辑或还原均按[生图文案约束](#生图文案约束)写明画面允许出现的文字。

发送界面生图提示词前，按[设计意图与操作层级](interface-intent.md#visual-task-hierarchy)把首选操作、操作归属、显示顺序和视觉主次写进实际发送的内容。用位置、边界、间距、对比或填充具体说明画面如何表达这些关系，并按目标状态核对各入口是否清晰。

游戏场景提示词基于已有信息链写明当前可操作目标、场景线索、真实状态、反馈和必要文字，位置交互按[空间归属与状态](interface-intent.md#信息的空间归属与状态)写明承载面、朝向、空间关联、触发范围及当前显隐状态。白模中的调试标注不进入画面；内部网格、地块和分区仅在玩法需要时可视化，不为展示全部内容挤压实际玩家视角。代表瞬间和动态交接分开，避免声称单图证明动作。

第 5 阶段 V2 的游戏场景、HUD、弹窗和结算等效果图，在实际发送的提示词中应用[玩家视角与广告示意](#player-view-generation)。

调用工具前将本次适用的分析投影为**实际发送的提示词**：产物身份和用途、受众情境及任务、主体与主次、具体视觉方向、代表状态与必要文字、各参考的作用、保持与允许变化的边界、避免项及输出形式。区分需求事实和代理选择；参考来源和选择理由留在已有制作记录中，后台接口、生命周期、路径、节点 ID 等不应变成画面描述。检查有无相互矛盾、挤压主要内容、意外引入角色装饰或功能，以及未经验证地锁死布局；同时确认当前工具适合产物身份：位图探索与素材可用生图，可编辑界面和可运行对象仍需正式原生来源，不以效果图代替。发现冲突或工具不适用时先修订再调用，不保证一次生成达到专业质量。单图只表达一个明确瞬间，动态与其他状态在原有设计交接中说明。

可选地在已有 `asset-task.json` 或 App 效果图来源的 `generationInputs` 中记录结构化准备数据，用 `node .agents/skills/app-domain-toolkit/scripts/visual/generation-prompt.mjs --task <已有 JSON 路径>`（维护本仓库时去掉 `.agents/` 前缀）在标准输出准备提示词和客观问题；该命令不写文件、不调用生图、不登记发送或视觉通过。`artifact` 含 `kind`、`purpose`；`mode` 为 `explore`、`edit` 或 `reproduce`；`sections` 每项含稳定 `id`、`origin`（`fact` 或 `decision`）、真正要发送的 `text`，以及可选追溯 `basis`。适用时使用 `requiredVisibleText`、`references`（每项含 `id`、`role`、`purpose`、`ref`，参考图作用进入提示词，来源标识仅用于追溯）、`preserve`、`allowedChanges`、`avoid` 与 `output`（`format`、`transparentBackground`、`width`、`height`、`aspectRatio`）。`references` 按实际附件调用顺序编号；原图和风格图分别说明作用，实际图片仍须作为附件单独传入，编号不是要画进图片的标签。编辑/还原的原图以 `role: source-target`、局部图以 `source-detail`、风格参考以 `style` 或 `style-anchor` 标示；编辑同时明确保持和允许变化的部分。按实际任务选择字段，不为填表虚构内容；无图、用户提供及复用素材不必准备新提示词。

调用后才将真实发送的完整文本记入已有 `asset-task.prompt`、App 来源 `prompt` 或游戏生成记录 `full_prompt`；游戏正式全局基线仍按原合同附带 canonical 段。声明 `generationInputs` 的 App 生成来源和游戏生成记录校验原子内容、准确文字、参考用途和可确定的输出要求，不强制准备器的包装标签；实际提示词明确逐项编号且用途可确定地交叉对调时报告冲突，未编号或无法确定对应关系的文本不据此断言。游戏记录中的 `reference_inputs`／`actual_reference_inputs` 与 `style_reference_inputs`／`actual_style_reference_inputs` 沿用各自既有身份和组内顺序，声明参考用途时分别核对；没有独立记录的组保持未验证，仅有分组清单不能证明两组之间的总附件顺序。校验不能证明素材曾被发送、内容充分或审美合格。生成结果的结构、系列和组合效果仍沿用现有人工验收。

### 实机运行画面约束

每张正式视觉候选、后续视图及局部改稿的实际发送提示词，都须明确要求「生成一张目标设备正常运行时，用户实际可见的单帧画面设计稿」。逐张写明以下信息，足以对应到已有运行、白模或正式设计依据：

- **实际视口**：目标平台、视口方向及宽高比。游戏使用玩家实际可达的镜头、朝向、画幅和尺度，保留通路、地标与遮挡关系。页面和显示层按实际屏幕边界、安全区和宿主上下文构图。
- **构图原图**：有与目标视图对应的白模截图或运行截图时，必须把原图作为构图参考附件随当次请求实际传入生图工具，并在提示词中按附件编号明确锁定玩法镜头、通路的走向与连通关系，以及关键物件的位置。美术风格可在这些约束内探索。另附风格参考时，分别注明各张图的用途，构图以白模或运行原图为准。沿用现有生成记录保存实际传入的原图及附件顺序。
- **当前状态**：指定玩家或用户所在位置、当前任务及一个可达状态，呈现此时实际可见的对象、操作入口、HUD 和反馈。按原有显隐规则保留必要内容和操作空间，互斥状态分开表达。
- **运行表现**：约束角色和物件比例、渲染方式、光影、特效及细节密度，使其在目标技术栈与资源预算内可实现。保留项目的美术语言和允许探索的部分，参考图仅按指定用途影响画面。
- **输出边界**：只输出视口内的画面。排除概念美术图、主视觉海报、宣传插画、设定板、设备外壳和多视图拼贴的构图表达，以及运行时无法出现的取景、布景、调试标注和装饰性叠层。

生成前核对提示词与当前镜头、布局、状态及平台规格；发现冲突先修订。交付时在既有选稿审阅中请用户人工对照这些依据及适用的构图原图，检查镜头、通路、关键物件位置、操作可读性和能否按规格实现。发现画面偏向宣传构图或脱离实际运行条件时，定向修订后再选稿。前期探索可按需交付概念图，正式选稿使用满足本节要求的画面。单体素材按运行消费者规格制作。生图保留设计稿身份，运行证据来自正式工程实际采集。

### 生图文案约束

按[最少必要文字](../../app-domain-toolkit/references/ui-copy-principles.md#最少必要文字)确定当前画面所需的信息。每张效果图的提示词写明当前场景与可达的业务状态，逐项指定各控件在这一帧显示的图形、数值和文字。同一控件只呈现此时实际生效的状态特征，互斥的状态变体分开出图或在既有设计交接中说明。不同状态稿复用[同一控件的状态表达](../../app-domain-toolkit/references/ui-copy-principles.md#control-state-expression)中约定的布局和图形基准。

**发送前必须逐项检查可见文字。** 对照当前画面，将实际要发送的提示词中的每项可见文字和数值逐项判断。若省去其中一项后，按钮、图标、数字和当前上下文仍能清楚表达操作、条件和结果，就从可见文字清单和提示词正文的画面描述中删去该项。动作词和倍率说明同样适用。保留用户识别状态、作出决定或执行操作所需的最短表达。

在实际发送的提示词中逐项列出允许出现的原文、示例数值、位置和次数。相同内容确需在多处显示时逐处指定。只按清单的内容与次数呈现，省略参考图中的其他文字，以及内部规格、设计说明和仅供辅助技术使用的名称。操作前必须知道的条件或后果仍无法由画面表达时，将所需短文案纳入清单。清单为空时明确写「画面无文字，不加标签、占位字或伪文字」。使用既有结构化准备数据时，可将准确原文和示例数值写入 `requiredVisibleText`，在 `sections` 写入当前状态、位置、次数及只绘制清单内容或无文字的指令。

选稿后的忠实还原和局部编辑，以已确认目标中属于本图或本部件的文案及当前允许的修改范围确定清单。需要在其他图层或运行时绘制的文字按既有归属交接。

### 玩家视角与广告示意

第 5 阶段 V2 游戏模块生图时，从玩家在当前可达状态下实际看到的画面写提示词。先说清玩家此刻需要看懂什么、能做什么、会看到什么反馈，再指定承载这些信息的对象、图形、位置关系及状态变化。优先让场景、图标、构图和数值传达信息，只保留玩家理解当前状态、做决定或继续操作所需的最短文字。设计说明、评审标注和玩法规则细节留在方案中。

画面涉及已规划的广告入口时，在提示词中明确要求在对应按钮或入口内放一个清晰可辨的无字广告图标，作为次要视觉提示。仅用该图标表示广告属性，画面不出现「广告」「观看广告」「AD」等提醒玩家有广告的文字，也不另加广告说明、文字角标或提示条。保留玩家需要知道的奖励、倍率或操作结果。图标含义不清时，优先调整图形、位置和分组。无障碍名称按实际动作、条件和奖励交接。

例如结算稿可在提示词中写「以金币图标和 +20 显示本次奖励。可选奖励按钮内并排放置小号无字广告图标和 x3。主按钮只显示『下一关』。画面仅显示上述数值和按钮文案。」

### 选稿后的正式生图

正式静态单图按初始化冻结的[单图路线与 SVG 还原](../../app-domain-toolkit/references/svg-single-image-reconstruction.md)生产。两条路线使用同一份[视觉、尺寸及验收规范](../../app-domain-toolkit/references/svg-single-image-reconstruction.md#正式静态单图共同交付规范)。默认 SVG 重绘，源稿经用户人工确认后导出 PNG。初始化明确选定直接生图时执行本节的提示词、实际附件、去背与记录要求。SVG 路线记录独立可编辑源、源稿确认、导出和成品身份。

V3 为待生图部件绑定已确认的 V2 原图和部件编号，以原图像素记下部件边界。小部件或整图里难以辨认的细节须附同一原图的对应局部图，原图仍一起发送。提示词逐项保留当前部件可确认的构图、轮廓、比例、关键色、材质、光影和装饰，按任务明确允许变化的部分。全局视觉基线用于保持系列一致性。首次候选仍按探索规则生成。

正式 AI 位图复用已有 `asset-task.json` 或原生生成记录，V4 以 `assetReview.assets[].generationRecord` 及 `generationRecordSha256` 绑定同一份实际记录的 JSON，`designItemIds` 引用当前拆解设计项。记录包含 `assetId`、`candidateId`、`referenceTarget`（已确认原图路径）、`region: {id, bounds: {x, y, width, height}, requiresDetail}`（`id` 对应一个设计项）、`generationInputs`（`reproduce` 或 `edit`）、实际发送的完整 `prompt`、`actualReferenceInputs`（按实际调用顺序的 `{path, sha256}`）、`runtimePath` 和由消费者规格推导的 `runtimeSize`。各栈的既有生成记录可直接补齐这些字段。核对实际附件顺序、内容指纹、当前目标与最终解码尺寸；缺原始发送信息的产物保持未验证。结构校验以真实调用记录为依据，画面的还原结果由用户按既有 V4/V5 流程对照确认。

## 紧凑提示词

按“视觉用途 → 必要内容与结构 → 已选视觉特征 → 关键限制 → 输出规格”写最终提示词。PRD、流程 ID、审查理由、路径和长篇实现说明留在内部资料，不送入画面。

示例：

```text
为纸艺探险游戏制作侧视医疗包图标，显示于 64 像素背包格。
保留倾斜切角、厚纸层叠和两色印刷，形体清楚、右上方柔光。
只画一个完整医疗包，中央十字清晰。画面无文字，不加标签、占位字或伪文字。
透明背景，正方形 PNG；边缘不带背景色或落地阴影。
```

非游戏 App 代表页示例（实际内容与方向依据项目替换）：

```text
生成一张手机正常运行时用户实际可见的当前任务页设计稿，按 9:19.5 竖屏视口构图并留出系统安全区。以任务卡和主按钮的分组表达任务与操作，以字阶和留白帮助用户快速辨认下一项工作。当前是正常、有内容的状态，只绘制任务卡“准备材料”和主按钮“查看任务”，按原文各显示一次。参考图只用于确定品牌图标的身份，允许探索布局和比例。输出视口内的单帧画面，排除设备外框、宣传排版、假数据和无关装饰。
```

反例：“设计一张高级精致的 App，加入各种统计和装饰。”它既没有真实任务与状态，也未经授权添加内容。游戏 HUD 的反例是“做炫酷战斗界面，所有状态一直显示”：它忽略当前动作、紧急判断和遮挡。应按实际战斗状态说明关键威胁与可用行动的主次、哪些信息仅在相关状态显示及其视觉体系，并在真实运行中核对，不能由单图证明交互。单素材的反例是“做一个高级图标，包含说明文字和复杂背景”；正确做法是明确图标主体、系列形体和用途，只在需要时要求透明背景与无文字。

已有自动付款扩建机制的场景示例（只应用于确有该机制的项目，金额和视角按真实规格替换；随提示词传入对应的白模截图原图和风格参考图）：

```text
生成一张游戏正常运行时玩家实际可见的单帧场景设计稿。参考图1是白模截图原图，用于锁定玩法镜头、地面尺度、通路走向及连通关系、付款区与待解锁地面的位置和连接。当前状态为角色刚进入扩建付款区，角色靠近贴地费用区，费用区沿地面透视并连接待解锁地面，金币图标旁显示剩余金额 100。
参考图2用于保持角色身份和纸艺材质。沿用参考图1的空间关系，探索剪纸拼贴的切角轮廓、厚纸叠层和粗纤维边缘。地面与费用区以明度区分，余额使用强调色，金币图标采用平面剪影。只呈现当前状态需要的对象与金额，排除白模标签、悬浮说明牌和额外设施。
按目标视口输出一帧可玩场景画面，排除宣传海报式取景、额外说明版面和多视图拼贴。
```

自动扣款、退出及恢复状态留在原设计与实现交接中，不发送为画面内容；单图不证明交互已运行。

多方向比较时，以每个候选独立写出的视觉特征替换上例的剪纸方向，并在制作规格中分别记录可行路线，而不是只在共同提示词后加一个风格名称。

例如，同一付款区、玩家位置和视口的两个独立方向段可分别写成：

```text
采用剪纸拼贴：不规则切角轮廓，角色头部约占身高三分之一、设施略高于角色；厚纸叠层与粗纤维纹理，平面阴影清晰、边缘有手工切痕；暖色地面供通行，深色费用区标识交互，亮色只强调余额；UI 与金币图标使用平面剪影及粗线。用分层位图和原生文字制作。
```

```text
采用陶制微缩模型：圆柱与薄板组合的稳定轮廓，角色接近写实头身比例、设施宽而低；哑光釉面带少量颗粒，柔和体积阴影与干净无描边边缘；中性色地面供通行，费用区以清晰明度区分，余额使用单一强调色；UI 与金币图标采用浅浮雕几何形态。用模块化模型、材质和原生文字制作。
```

每次实际调用都须把共同任务及当前方向完整合并发送；示例本身不指定项目风格，也不能代替用户对实际候选差异的判断。

透明是实际像素需求，不能用棋盘格背景代替；图标制作尺寸与运行尺寸分别记录。不要把“no AI”当成具体制作约束，也不通过“增加噪点、做旧、滤镜”统一掩饰生成痕迹。

## 拆解与系列生产

每项资产有稳定 assetId、目标对象、可见特征编号、消费者和状态；同一共享资产只生产一次。参考图中的主要形状、材质、边框和空间关系必须有生产或原生实现归属，不能在拆解时无意简化丢失。

游戏分别约定角色/道具/场景/UI/特效/贴图的一致性；App 分别约定品牌插画、图标、照片和空状态。真实文案、功能图表和数据用原生组件，不把生成图中的假文字和假数据接入正式页面。3D 世界在整体场景人工确认后按[生产交接](../../app-domain-toolkit/references/game-design-exploration.md#production-handoff)制作或复用模型，高风险批次先验证首件；模型、UV、材质、骨骼与动画走技术栈 DCC 交接，不能把平面效果图冒充可用模型。若现有控制器或原生模式不支持实际选定路线，报告阻断及未验证范围，不能伪造图片、确认或机器通过。
