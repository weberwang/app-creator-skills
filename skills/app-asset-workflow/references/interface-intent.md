# 体验、视觉方向与意图表达

本参考是游戏与非游戏 App 的共同设计依据，覆盖场景、页面、HUD、弹出层、素材和可交互显示对象；各技能引用本处，各栈补充原生制作与验证方法。分析留在已有 GDD、任务书、布局规格或素材任务，不新增报告、状态或审批。按本次增量选择深度：局部修改只追踪受影响的行为、状态及消费者，复用有效依据，不等待全项目设计完毕再推进代表页或场景。

<a id="design-basis"></a>

## 从真实行为形成视觉方向

制作前先读取已有需求、实现、接口与状态合同，主动找出遗漏、冲突及体验风险。按当前任务明确以下适用内容，已有结论直接引用：

原型输入先按[验证依据与正式设计交接](../../app-creator-workflow/references/readable-functional-prototype.md#design-handoff)区分测试夹具、代表性内容与正式设计依据。测试数据和便捷操作只提供其覆盖的行为证据，不能自动锁定产品内容、入口、坐标或布局；本批设计采用什么、在何种状态服务用户，留在现有规格的关键取舍中，复用已明确且仍有效的约束。

按[稳定机制与内容装配](../../app-creator-workflow/references/readable-functional-prototype.md#mechanism-content-assembly)识别本批组件、可变数据及固定制作部分。设计稿交接外观、信息层级、必要状态和布局规则，并关联实际机制及数据槽；例如列表条目或配置驱动关卡中的实例只表达所选数据情境，其数量和排列不自动成为所有内容的固定要求。固定结构与已确认目标在适用条件下仍忠实实现，动态范围通过相同组件与正式数据验证，不从代表稿反向重写业务规则。

- 用户是谁、主要任务及使用压力；实际操作顺序中每步需要的信息、动作与反馈，高频、低频、危险及有时效性的操作。
- 正常、等待、空内容、失败、中断与恢复等适用状态，以及输入设备、屏幕、文字、内容密度、平台和无障碍限制。
- 游戏侧重核心操作、镜头、空间辨识、HUD 干扰、战斗压力和手柄／键鼠／触屏；App 侧重阅读、输入、导航、键盘与任务连续性。不能把页面构图套给游戏空间，或把宣传画要求套给操作界面。

先明确本批任务、需要判断的信息、可执行动作，以及信息和入口何时出现，再决定布局与视觉表达。按真实使用频率与状态区分常驻、情境出现、设置内访问和首次引导；不为展示功能完整把所有入口同时塞进主界面，也不为简洁隐藏必要操作。布局或状态关系不清楚时才补最小必要预览，表达已清楚时直接复用并推进，不强制完整白模或独立布局页。

用户描述是需求输入，不能代替代理的设计判断。默认完成有依据的选择；只有实质影响范围、成本或体验的取舍才澄清。主动比较关键方案的收益与代价：合并入口可能增加步骤，隐藏控件可能损害可发现性，动态按钮需要明确当前动作，减少 HUD 可能损害紧急判断，强化材质或角色可能干扰阅读。默认形成一个理由充分的方案；候选数量沿用当前路线，不能靠加稿代替判断，也不能把更少、更简洁直接等同于更好。

先明确产品定位与希望传达的感受，再将其转为可执行判断，而非只写“专业、高级、精致、友好”：

- **层级**：第一眼看什么，主要内容、当前动作及次要信息如何区分。
- **排版**：以真实内容确定可读性、字阶、行宽、行距和密度，兼顾语言与字体放大。
- **构图与空间**：分组、比例、留白、节奏、视觉重心及操作空间如何服务任务。
- **色彩与材质**：功能含义、对比及轮廓关系如何稳定表达状态，避免仅靠颜色区分。
- **统一关系**：图标、插画、角色、环境、背景、控件及动效共用哪些形态、边缘、材质和反馈原则。

参考分析必须执行，与市场、竞品、受众分析共同遵守[统一执行与复用要求](../../app-creator-workflow/references/professional-conventions.md#product-market-research)。实际查阅相关参考，记录来源、观察到的规律、适用条件、为何采纳或舍弃，并转成当前任务的依据；已有结论经来源、版本和本批适用性核对后可以直接引用，只补查缺失或变化部分，不要求重复找参考或重做报告。缺少分析或有效复用依据时先补齐，再推进依赖它的设计与制作；链接清单与直接照搬外观均不能替代分析。文档、真实节点与经授权的图像分别按其证据范围使用，不借参考分析绕过人工看图要求。插画精细度、装饰数量和画面复杂度不等于专业质量。

在已有输入中区分 **硬约束**（真实业务、必要功能、平台、无障碍、内容准确性及用户锁定的品牌）、**视觉方向**（有依据的风格、层级、一致性原则）与 **探索空间**（允许工具决定的构图和表现细节）。保留有依据的具体约束，不提前用未经验证的坐标、字号、配色或组件排列写死答案；探索有方向，忠实还原按已选来源执行。方向选定后逐步明确可还原尺度与规格，不能一直停留在形容词。

每次生图将适用结论转成[实际发送的制作提示词](style-and-production.md#生成前约束)：源事实与代理选择分明，画面相关业务转为可见内容，后台与生命周期留在工程规格。保存当次真实提示词、选择理由及来源到已有记录，准备文本不表示已发送或已生成。

<a id="capability-semantics"></a>

## 核对能力与动作语义

基于实际实现与合同区分现有能力、拟新增能力和待验证行为，不为补齐画面虚构接口、键盘行为或运行结果。关键控件明确触发条件、当前动作、可用性、反馈、完成条件及异常处理；图标、文案和结果一致，暂停、停止、取消、重试、返回与恢复不可混用。合并入口或切换动作时，按[交互职责](../../app-domain-toolkit/references/ui-interaction.md)确定唯一所有者、优先级、草稿／焦点／上下文、重复触发、处理中与结果未知处理，并明确原有能力保留、替换或移除的决定；不默认引入兼容方案。

例如 App 上传尚无取消接口时，不能绘制取消按钮并声称已支持；游戏工具选中后自动工作时，用对象状态表达进行中，不能常驻重复点击按钮。必要的停止、失败恢复或精确信息仍应按真实能力提供。

<a id="layout-space"></a>

## 用真实内容核对布局与空间

制作与交付都检查真实父子关系、内容撑高、主轴与交叉轴、滚动归属、层级和输入命中范围。用当前真实内容及适用极值检查窄屏、短屏、长文、大字、安全区、键盘和焦点变化，确认文字与关键操作未被意外裁切，消息／列表项／面板无高度计算遮挡，合并操作后仍有阅读和输入空间，状态变化不产生不必要位移或误触。

尺寸按平台和项目决定；参考视口不是所有设备的固定尺寸。说明剩余空间如何分配、不足时如何换行、增高或滚动。有意叠放需明确层序、可见性和输入归属；2D／3D 世界按尺度、镜头、通行、遮挡与空间关系验证，不能套 UI 矩形不相交规则。具体布局与原生实现按[相对布局](../../app-ui-layout/references/relative-layout.md)及本栈规范执行。

例如 App 长消息应参与父容器撑高，键盘弹出后主要输入仍可达；把参考图高度固定给所有消息会造成覆盖。游戏树冠可有意遮住部分地形，但若遮住当前交互目标则需调整视线或显隐，不能简单以投影矩形相交判错。

<a id="bounded-review"></a>

## 交付前有界复核与定向返修

沿主要任务推演一次完整操作，再选一个适用的高压或异常情境：当前状态与下一步是否清楚，装饰、分组和入口是否妨碍主任务，是否多出步骤、隐藏操作、误导反馈或空间不足，字体、图标、插画、材质和控件是否属同一体系，结构核对是否覆盖真实父子边界及关键关系。代理主动核对真实节点、内容与合同中的基础问题，不能把发现基础设计缺陷留给用户。

本复核并入既有设计稿[单次用户视角审查](art-review.md#当前设计稿的单次用户视角审查)及原有交付检查。返修后自主定向复验失败项及实际变化的行为、状态、语义和结构，必要时重推受影响路径；不重复未变化部分的全量审美评议，不新增轮次、报告、审批或自动审美评分。无截图分析授权时通过需求、节点、布局和行为合同推演；实际图像判断留给用户，不以“用户视角”绕过人工看图规则。结构检查、工程验证与人工视觉结论分开，工具成功、文件存在或节点数量不代替体验与视觉验收。

先诊断产品定位、信息结构／空间语义、视觉方向、提示词、生成结果、还原实现或运行适配中的原因，再定向修订。标签过多不只删几个词，方向相似不只换颜色，布局错误不归咎生图模型；也不把全部质量问题归为约束过多。保留有效方向、未受影响的确认及已完成部分，不无依据推翻视角、玩法、空间关系或重生整套稿。既有确认按作用域复用，不把概念接受记成还原结果已看过，也不重复批准未变化的同一目标。

游戏与应用的界面美术优先用视觉线索表达场景、主要目标、可操作对象、动作和状态变化。按[最少必要文字](../../app-domain-toolkit/references/ui-copy-principles.md#最少必要文字)补足视觉尚不能明确传达的信息。制作与审阅时结合目标用户、既有组件约定和实际显示尺寸判断，不把陌生图标当作天然通用语言。

## 在设计与输出前筛选内容

前端页面、原生组件、HUD 和效果图从当前状态的真实任务、主操作及必要信息开始。在画草图、写提示词或实现可见界面前，先确定每块内容和视觉元素的用途。输出前在现有设计稿、布局规格、组件或提示词中复核，删掉仅用来填充版面或模仿常见模板的元素。局部调整只检查受影响范围，已确认目标中的内容变更按原有还原规则处理。

游戏在已有 GDD、场景规格或设计记录中先串起“玩家需要判断什么 → 场景提供什么线索 → 玩家可以做什么 → 操作后有什么反馈 → 仍需保留哪些精确信息”。结合实际机制，以场景、物件、角色动作、空间关系和状态反馈承担表达，再决定文字。每项可见文字都说明补充了画面尚未表达的什么信息；白模调试标签、阶段说明、任务解释和操作提示不能直接搬入正式视觉稿。金额、数量、错误原因、确认信息及无障碍语义等仍按需要保留。

例如，已有捕鱼机制可用冰面或水面、鱼与工具动作关联位置、阶段和结果；已有销售机制可用鱼货、交易台、容器与交易反馈表达交易；已有扩建机制可用付款区域与待扩建地面的空间关系表达入口。例子只用于解释已有玩法，不额外引入建筑、NPC、按钮、装饰或机制。

- 按[最少必要文字](../../app-domain-toolkit/references/ui-copy-principles.md#最少必要文字)筛选当前状态的可见文案，按[表达选择](../../app-domain-toolkit/references/ui-copy-principles.md#表达选择)确定呈现方式和时机。
- 装饰须服务于层级、状态反馈、空间分组或已确认的产品风格。删掉没有这些用途的卡片套框、玻璃效果、渐变、光晕、徽标、假图表和填充头像。内容少时允许留白，以比例、间距和对齐组织画面；有明确用途的插画、纹理和动效可以保留。

## 信息的空间归属与状态

按交互语义区分世界物件、地面区域、角色附属表现、场景浮层和屏幕 HUD。与位置有关的交互信息优先靠近实际操作对象，在现有设计中说明承载面、朝向、空间归属、触发范围与显示状态。例如已有站入区域自动付款机制时，可用贴地费用区、金币图标和剩余金额表达，费用区与地面共享透视并连接待解锁区域；不能随意改成悬浮说明牌或屏幕卡片。屏幕级信息及确需远距离可见的提示按实际语义选择位置。

按实际机制选择承载位置，不要求每类都新增元素：

- **世界物件**：表达对象性质及其可操作状态。
- **地面区域**：表达位置范围及适用的站入费用。
- **角色附属表现**：表达持有、选中、作业状态或携带结果。
- **场景浮层**：承载锚定对象的短时反馈，约定遮挡和离开时的显隐。
- **屏幕 HUD**：承载全局持续精确信息或导航，不挪走位置相关的交互信息。

按实际玩法覆盖未选择、已选择、进行中、完成、离开与恢复等适用状态及必要异常，交接元素何时出现、消失或改变。选择工具后自动作业时，不常驻暗示反复点击的动作按钮；进度优先利用对象变化、覆盖范围、剩余目标和操作结果，仅存在明确的信息缺口时增加进度条或说明文字。单张概念图只表现代表瞬间，动态行为在方案中交接并在实现后验证，静态图不证明动画或交互成立。

## 用画面表达任务

- **主次明确**：通过大小、轮廓、对比、留白、分组和位置关系，让主要目标及当前可执行动作先被看见；装饰不抢占主操作的注意力，也不伪装成可点击控件。
- **对象与动作相关**：图形、道具、图标与操作对象建立明确联系，复用用户熟悉的视觉约定。例如收集物与容器、滑块与轨道、对象与可放置区域之间应有可见关系；避免用随机符号或抽象插画代替功能含义。
- **可操作性可辨认**：按钮、拖拽把手、滑动区域、切换项、可放置区域和不可操作装饰有足够差异；仅靠一行说明才能发现的操作，需要调整形态、布局或情境线索。
- **状态有差异**：选中、未选中、禁用、焦点、加载、成功与失败按[同一控件的状态表达](../../app-domain-toolkit/references/ui-copy-principles.md#control-state-expression)区分。颜色与动效作为补充。减少动态效果、静音或存在色觉差异时，关键状态仍须可辨认。
- **变化有因果**：让输入对象、移动方向、目标位置和结果建立联系，反馈贴近操作发生处。相关反馈继续遵循公共 [app-feedback](../../app-feedback/SKILL.md)，不让装饰性动画替代真实操作结果。
- **系列语义稳定**：同一图形、颜色角色、控件形态和空间关系在不同页面表达相同含义；不同意图不套用难以区分的装饰模板。跨文化或陌生领域的符号需要结合上下文检查。

具体视觉风格仍按项目的视觉签名维护。具象、抽象、像素、写实或原生组件均可采用；关键是形式能够支持实际任务。

## 将去字检查放进现有审阅

将无文字判断纳入已有审阅，不新设状态、分数、固定通过比例或批准记录。当前设计稿的适用检查并入[单次用户视角审查](art-review.md#当前设计稿的单次用户视角审查)，不额外开全量审查；修改后按真实合同和节点定向复验受影响行为与结构，视觉判断依原授权交用户。布局与最终运行组合仍由用户按原阶段检查；以下预览步骤按实际需要使用，不为单次设计稿审查强制另做去字图片：

1. 准备同一候选的可恢复预览，只隐藏可见文字，保持原有空间、控件、图形和状态。保留原始版本；不修改正式页面的数据、事件、可访问名称或业务逻辑，也不把文字重新烘焙成图片绕过检查。
2. 由用户或目标受众在目标尺寸下人工观察，不先用文字解释布局意图，说明“当前是什么场景、主要要做什么、哪里能操作、操作后会发生什么、现在是什么状态”。检查相关的正常、选中、禁用、加载及成功/失败状态。
3. 记录具体误判，例如把装饰当按钮、混淆主要与次要动作、找不到操作对象、看不出成功或失败；定位到轮廓、层级、图形语义、位置关系或状态差异后返修。当前设计稿按本轮发现修改后交用户确认；后续布局与正式组合按既有阶段复验受影响部分，不作为自动重复设计审查。
4. 恢复真实文案，按[最少必要文字](../../app-domain-toolkit/references/ui-copy-principles.md#最少必要文字)复核当前界面，并检查适用状态切换前后的布局、控件尺寸、命中范围和可访问语义。设计时核对可编辑稿及布局约定，实际命中按原有运行验收核对。无文字预览仅用于诊断视觉表达。

提供预览或截图及上述观察点，复用已有人工确认。当前设计稿不重复全量评议，定向复验失败项及实际变化仍照常进行；运行截图默认不自动分析，也不据此填写视觉 PASS，尚未人工检查时记录待检查。

## 保留精确信息与无障碍

正式界面保留必要的控件标签、金额与数量、时间、具体错误原因、风险提示、确认信息和用户内容，也保留屏幕阅读器名称、键盘焦点及辅助技术语义。精确信息由可读文字承担，主要任务和交互关系由视觉共同表达；遇到歧义或后果重要的操作，用明确文案与既有确认行为消除歧义。

文字阅读、对话、表单和数据内容本身就是任务时，检查内容层级、入口、操作及状态是否直观，不要求用户在文字隐藏后仍能知道具体内容。不通过删文案、增加陌生图标、夸大动效或遮蔽风险来满足这一原则。
