# 系统与模块覆盖

适用于游戏、非游戏 App、设备 GUI 与服务器的新增项目和增量实施。沿用现有需求、GDD／产品 brief、技术设计、Work Plan、Implementation Package 与执行证据，不新增控制器状态或逐模块审批。纯查询、文案或注释仍按原规则处理；仅设计提案不必为了交设计稿建立实施包，但进入正式实现的工作项必须满足本合同。

## 何时识别与设计

需求阶段从用户目标、完整玩家循环或用户旅程识别必要系统及支持模块；全局基线确定系统关系、主要规则、共享数据与关键风险。不能只按页面、场景、设施或已有目录列任务。已有项目读取实际规则、配置、消费者和测试，只核对本次变化及其依赖，不重做无关系统。

实施前，当前批次涉及的每项需求都必须关联已设计的模块、实施或复用任务及验证。设计至少说明职责和非目标、输入输出、权威状态、关键规则或公式、依赖、适用的边界／异常／恢复、数据与生命周期，以及可观察验收；经济、战斗、成长等按实际机制补齐参数单位、初始值和待验证假设。设计来源可为已有 GDD／技术设计中的章节，不要求一模块一文档。

V1 确认本轮模块的完整规则、范围、流程与进度、状态转换、异常恢复、依赖和验收用例；可用代表切片验证高风险假设。V2/V3 视觉规格不能替代系统设计，V5 按方案完整实现并验收，参数和体验按真实运行及人工试玩校准。

## 从目标反向核对覆盖

在现有需求或设计中梳理“需求 → 系统／模块 → 规则与依赖 → 实施任务 → 验证”。逐条从原始目标及适用异常反向核对，而不是只检查当前任务表里已经出现的内容。原始来源应保留可追溯版本；缩减或改变范围须说明影响及真实决定，不通过删除条目让覆盖率看似完整。

每个已识别模块明确以下一种处置，附理由：

| 状态 | 含义与边界 |
| --- | --- |
| `implement` | 本批实施；已有真实设计来源、实现单元和本批验收命令 |
| `reuse` | 复用有效能力；保留设计与既有证据，并安排当前适用性验证，不把历史 PASS 当当前结果 |
| `defer` | 后续批次处理；说明后置原因和依赖，不能承担本批需求或成为活跃模块的前置 |
| `exclude` | 本期不需要或明确排除；记录依据，不能用来隐藏本批必要能力 |
| `pending` | 实质设计或范围待决定；不能支持本批需求或其依赖，可继续独立工作 |

需求也区分本批 `current`、后续 `later` 与排除 `excluded`，保留理由。每份实施计划至少有一项本批需求，且每项至少关联一个 `implement/reuse` 模块；所有模块至少关联一项需求，活跃模块必须服务本批需求并归入至少一个必查领域，所有执行单元都有实现或验证归属。未决项影响产品方向、体验、成本、平台或风险时沿既有决定流程处理；不要求用户逐项确认领域、模块或表格。

## 游戏按模块推进时反查任务

1. **冻结本批前**，在现有 F1/F2 从总范围和 GDD 逐条走本批真实玩家路径，从进入、执行、判定、反馈、结算到重试／离开。逐步核对适用分支及交接所需的规则、数据配置、UI／素材、平台能力和验收，特别检查已设计的广告位、反馈事件和跨模块接口是否有实际消费者及归属。
2. **拆成能验收的单元**，在 `systemCoverage` 把需求、设计来源、模块、执行单元和精确命令串起来。一个模块可共用或包含多个真实单元，适用的配置、资源、异常与接线应在单元输入、输出及验收中可追踪。调用模块与提供模块分开时，安排实际接线及跨模块用例，验证上下游在真实宿主中的组合。
3. **收本批和开下一批时**，对照冻结来源和实际产出逐项核对已执行的用例、未完成项和下一批前置。仍属于本批必要范围的遗漏补齐并复验，范围或依赖有变化时走原 RETURN；最终集成映射同时覆盖共享功能、独立必要模块和参与的前批。

## 必查领域与适用性

以下是防遗漏的检查视角，不是要求项目新增这些功能。每个领域记录关联模块或有依据的不适用理由；未知不能冒充不适用。局部修复复用已有结论，在理由中说明当前影响范围。

| 范围 | 必查领域及问题 |
| --- | --- |
| 共同 | `flow`：完整入口、主要任务和完成路径；`state-data`：规则、数据与状态所有权；`failure-recovery`：失败、取消、重复、退出与恢复；`persistence`：需要保存什么、何时保存与怎样回读，确实无需保存时说明；`platform`：输入、生命周期、设备／平台限制及真实依赖 |
| 游戏 | `combat`：是否存在战斗／对抗及命中结算；`economy`：资源来源、消耗、容量及异常循环；`progression`：成长、解锁、局内外进程和重试损失；`content`：关卡、波次、任务或生成内容及可达性；`player-feedback`：[关键操作、结果与峰值反馈](domain-production.md#动态反馈)；`advertising`：[广告处置、点位、回退与奖励](domain-production.md#广告体验) |
| 非游戏 App／GUI／服务器 | `identity-access`：是否需要身份、权限或访问控制；`business-rules`：校验、计算、提交、交易和幂等；`content`：真实内容、列表／搜索／编辑及空状态；`integration`：外部服务、协议、设备或跨模块接口及失败边界。无账号、支付或网络需求时明确不适用，不默认引入 |

App 的导航、键盘、焦点、反馈和后台任务按实际用途归入上述领域；游戏的空间、镜头、输入、音频及反馈也需按机制追踪消费者。首次梳理检查共同领域与本栈领域；增量保留有效全局依据，只细化变化及真实前置。

Unity、Cocos、Phaser、Three.js 和 Roblox 的计划必须声明 `player-feedback` 与 `advertising`。本批有相关需求时映射负责实现或复用的模块；未纳入或不适用时记录具体理由及实际适用范围，后续批次保留其真实处置。已选择且属于本批目标的广告位或核心反馈应有可执行的验证。

## 接入现有机器合同

Work Plan 和 Implementation Package 都必填内联 `systemCoverage`，结构见[Schema](../../app-workflow-control/schemas/system-coverage.schema.json)及[最小示例](../../app-workflow-control/templates/system-coverage.json)。记录在已有计划中，不要求再创建独立覆盖文件。

- `requirementsRef`：实际需求／任务范围文件的项目相对路径与 SHA-256；`requirements` 保留需求身份、说明、本批处置和 `moduleIds`。
- `areas`：共同及本栈必查领域，逐项提供 `areaId`、`reason` 和实际 `moduleIds`；无相关模块时数组为空并说明原因。
- `modules`：稳定 `moduleId`、处置 `status`、`reason`、模块 `dependsOn`、冻结 `designRefs`、`implementationUnitIds`、`verifications` 和复用 `evidenceRefs`。
- 每条 `verifications` 的 `unitId/command` 必须指向当前包内真实单元及其准确的 `acceptanceCommands`。实现单元须由同单元或依赖它的后续单元验证；模块前置也须落实到执行单元的依赖，不允许只写文字或只按数组顺序猜测。

`plan` 在写文件前核对覆盖并将其复制进实施包，同时以 `Work Item.planningRef:{path,sha256}` 固定实际计划版本；统一实施包加载再次核对，手写包、轻量模式、非视觉 MODULE、集成与发布准备也不能跳过。同步改写计划与包也不能替换已固定的范围。既有游戏计划在重新校验时缺少必查领域，沿现有 RETURN 流程按实际范围补查并重新冻结。小任务可仅关联一个需求和一个模块，复用已有设计，不要求全项目重新设计；首次做设计的任务只设计本批已明确部分，不用尚未生成的设计文件冒充生产实施依据。

需求、设计及复用证据必须实际存在、非空并匹配摘要；不能引用当前工作项、计划、实施包、结果或执行状态自证。冻结依据与本批可修改路径分开，可引用现有版本或先保存真实快照；需要修改原设计时先规划其版本化输出，不将正在改写的文件同时用作冻结依据。进入 IMPLEMENTING 后，覆盖内容和来源身份一起进入执行快照；删映射、改后置、换来源或改变依赖均会失效，须按原 RETURN 流程重新规划。

`reuse` 的既有工程证据不能是需求或设计文件本身，也不能通过改名或硬链接自证。已有工程没有控制器历史时，引用实际代码消费者、可复现检查及真实工程输出，不要求虚构完成工作项；执行者仍须核对证据实际用途、来源版本和本批适用性。

## 最终集成的系统覆盖闭环

最终范围在 REVIEW／进入实施前严格重验所有参与来源的计划、设计及执行快照，并冻结 `systemCoverageMappings`，结构见[映射 Schema](../../app-workflow-control/schemas/integration-system-coverage.schema.json)及[模板](../../app-workflow-control/templates/integration-system-coverage.json)。每项以 `{sourcePackageRef:{path,sha256},requirementId,moduleIds,objectIds,verifications:[{caseId,unitId,command}]}` 关联一个来源包的当前需求、完整模块集合、实际消费者及本次最终验证；每条最终用例都必须映射，验收命令同时属于本次单元和其系统覆盖声明。

来源包括最终对象当前包、V1 功能基线中的原包、本地及共享来源重验保留的原始系统身份、对象的共享功能来源与已登记生产前批。相同包合并实际消费对象，各项需求分别声明其真实消费者并由相关用例覆盖，需求映射合计不能遗漏该来源的任何消费者；不强迫同包所有需求在每个页面或场景都出现。不能只取最后一个视觉包证明系统已完整集成。

独立必要模块可通过最终范围的 `systemSources:[{workItemRef:{path,sha256},objectIds:[...]}]` 显式登记，不伪装成页面或场景。绑定生产总范围时，来源包必须覆盖范围中每个批次及其对象；没有依赖链的独立前批通过 `productionSources:[{workItemRef:{path,sha256},objectIds:[...]}]` 冻结已完成工作项，并验证同一总范围及真实批次身份。历史检查仅允许其既有业务交付按后批变化，不能替代同一来源被显式登记为当前能力后的严格检查。后续或排除需求保留原理由；属于本次最终目标的后续内容须先完成对应批次并纳入来源，不把未来范围宣称为已交付。

批次完成以严格检查过的工作项实际范围累计：单个视觉来源只证明自身对象，不能通过消费者数组或下游引用冒充同批其他页面／场景；无视觉模块或早期功能集成须验证整批行为。视觉前批与最终视觉来源均须实际完成 V5，不能把已有计划、在 V2 完成的纯设计提案当作生产或运行证据。

实际最终用例记录除了原有身份和状态，还须保存 `unitId`、准确 `command`、`exitCode:0` 与 `outputRef:{path,sha256}`，并匹配当前冻结单元结果中同一命令的真实 `commandOutputs.outputFile`。原生行为、生产范围、Node.js 原始证据及人工显示检查继续执行；机器链路通过不代替这些结论。执行状态双向核对已冻结范围与 `final` 身份，改为 `feature`、删除范围或用未关联日志结案均会阻断。

## 收尾与证明边界

`record`、`unit-check` 和验证／完成迁移复验同一实施包与冻结映射；实际命令、退出码和输出沿用现有执行结果，不另建一套验证结果。失败、未运行与仅计划的检查不得登记通过。收尾从原始需求核对本批结果及仍后置／待决定的部分；最终集成同样检查必要系统的真实组合，不以页面完成、构建成功或本批完成冒充全项目完成。

机器能阻断缺字段、漏必查领域、断开的需求／设计／任务／命令引用、非法前置和冻结来源变化，不能判断需求文本是否完整、设计是否正确或不适用理由是否真实。执行者仍须阅读原始来源并审查反向覆盖、关键规则及依赖，F1/F2 保存实际结论；体验、画面及真实参与者观察沿原人工边界，不宣称绝对不会遗漏。
