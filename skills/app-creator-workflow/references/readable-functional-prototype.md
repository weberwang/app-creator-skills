# V1 可辨识的功能原型

适用于 Unity、Cocos、Phaser、Three.js、Flutter 的 V1 功能实现与验证。白盒、临时资源、白模或 sketch 仍按风险选择；行为明确时可直接实现或复用有效功能验证，不要求额外制作原型。采用可运行白盒时，不能只有无法识别用途的方块：体验者应能理解“这是什么、能做什么、当前状态、操作结果和下一步”。

本规则细化白盒的可读性，不增加阶段、控制器字段、独立证据文件或逐项人工审批。静态白板只用于梳理；操作、时序、碰撞、空间和跨场景运行结论仍须实际验证。规则不授权自动启动真机验收或分析截图。

## 最小可读表现

| 方面 | 按当前功能范围落实 | 示例 |
| --- | --- | --- |
| 对象身份 | 使用简单轮廓、语义名称和必要图标区分角色与用途，不只依赖颜色或编号 | 玩家、敌人、商店、出口，而非方块 A/B |
| 基本形态与空间 | 保留影响功能理解的轮廓、朝向、相对尺度、通行与交互范围 | 门有可识别入口，道路连续，按钮具有可点击外观 |
| 有意义的内容 | 使用能理解任务的示例名称、数量、单位与条件，区分当前值和目标值 | “金币 120”“升级需 100”，而非“数值”“按钮” |
| 状态差异 | 对实际存在的正常、选中、禁用、加载、成功、失败提供可辨差异，颜色配合文字、形状或图标 | 禁用升级入口显示“金币不足”，加载时提供状态提示 |
| 操作反馈 | 为本次需验证的点击、拾取、碰撞、受伤、购买或跳转提供最小反馈 | 金币实际减少、短暂高亮、血量变化、失败原因或 Toast |
| 任务与操作 | 按需提供当前目标、主要操作、必要图例和下一步，避免必须读调试日志才能继续 | “收集 3 把钥匙后进入出口”，说明已声明输入方式 |
| 跨场景衔接 | 说明目的地身份、传递状态、结果与返回入口 | 进入商店保留金币，购买返回后能看到物品变化 |

只覆盖本批次真实存在的对象、状态和行为，不为凑齐表格新增功能。画面对象多时用区域标识、图例或选中/靠近提示减少拥挤，不在每个对象上堆叠全部调试文字。文案沿用项目语言配置，默认中文；原型阶段同样避免把临时中文写死到后续难以替换的位置。

## 临时组件与查看方式

优先复用项目现有按钮、面板、标签、列表、血条和对象标记；确需新增时，用本栈原生图形、文字、简单几何和已有可用资源建立轻量临时样式，按当前需要实现，不预建完整组件库。不因白盒要求启动正式美术生产、生成多套视觉候选或引入新框架。

- **体验视图**：默认呈现可辨对象、任务、控件状态与操作反馈；不依赖开发者讲解内部变量才能完成关键路径。
- **调试视图**：按需显示对象 ID、碰撞框、触发区域、状态、路由或日志；通过已有调试开关、隐藏标签或局部面板查看即可，不强制构建两套独立界面。开启调试信息不能改变被验证的业务行为、命中或计时结论。

层序沿用[显示结构规范](../../app-domain-toolkit/references/reference-domain-display-ownership.md#游戏层内容层hud浮窗与弹窗)：游戏层／内容层 → HUD → 弹窗层 → 浮窗层。Toast 位于最上层，默认不抢焦点、不吞输入；工具面板、模态弹窗与附属下拉的输入边界仍按实际职责处理，不用调试面板替代功能弹窗验收。

## 复用机制与替换表现

尽量在正式工程中复用实际业务状态、输入、导航、碰撞及事件接口，让临时外观通过组件、资源槽或现有样式配置替换；需要隔离实验时说明范围并复用稳定机制，不维护一套与实际工程无关的演示逻辑。临时外观的替换不得偷偷改变规则、点击范围、碰撞或时序。

V1 只验证功能所需的空间、可达性和状态约束；美术风格、精确构图、最终资源尺寸与布局在 V2/V3/V4 按原流程确定。将已经证实的机制约束带入后续视觉设计，但不把白盒几何冻结为正式布局，也不因后续换皮重复确认未变化功能。

已有有效资源可复用；临时素材、模拟数据和占位实现须在运行入口或相关状态及现有验证记录中明确标识。图片继续遵循[源逻辑尺寸、九宫格与背景 cover 规则](../../app-ui-layout/references/relative-layout.md#图片尺寸)，不因是白盒而静默缩放普通图片；原生几何与容器尺寸按功能需求设置。

## V1 检查与记录

采用白盒时，将以下检查并入当前 V1 的实际功能用例和现有验证结果，无需额外清单或单独签字：

1. 能辨认关键对象、当前任务和目的地；必要名称、单位与图例能被实际看到。
2. 能发现主要操作，区分可用、禁用、选中和等待状态；命中与控件显示一致。
3. 操作有真实状态变化或明确失败反馈，能理解下一步及适用的重试/返回方式。
4. 跨场景后身份、参数、状态、结果与返回衔接清楚；弹窗关闭和 Toast 提示不破坏既定输入权。

工程检查可核对状态切换、可见标签、数据变化和输入隔离；是否看得懂、显示是否清楚由用户检查实际运行或提供的截图。未取得的用户判断如实记录，不由机器报告或自动截图分析冒充确认；不额外引入白盒视觉选图与逐项审批。

使用固定测试数据或模拟服务可以验证实际运行的本地机制，但结果必须说明验证数据与边界。例如模拟购买只证明已执行的本地扣款/物品状态或模拟服务流程，不能证明未接入的支付、服务端扣款或真实购买通过；临时目标只证明实际跳转，不证明目的地功能完成。未实现、未执行和不适用项明确区分，不以按钮动画、调试开关或手写 PASS 代替行为。

V1 的检查结果、已证实约束和未决项保存在当前技术设计及现有工程验证材料中，按[功能范围与跨对象依赖](../../app-workflow-control/references/function-dependencies.md)复用真实覆盖范围；不要求跨场景对象先完成 V5。后续真实功能变化按既有功能基线规则重验，V2–V5 仍分别完成目标、拆解布局、资源导入与正式组合验收，不能由白盒通过代替。
