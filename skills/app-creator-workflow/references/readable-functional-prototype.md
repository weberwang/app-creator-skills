# V1 可辨识的功能原型

适用于游戏及非游戏应用的 V1 功能实现、验证与正式设计交接，按当前栈映射等价职责；无界面任务不增加视觉环节。先按不确定性选择数据验证、最小交互原型、布局草案或正式工程试接，复用有效实现与证据，不统一要求完整白模、独立布局页或额外演示工程。游戏世界的真实空间验证继续按[内容分流](../../app-domain-toolkit/references/game-design-exploration.md#implementation-routes)执行；空间、镜头、物理或手感风险需要白模时，在正式工程搭建或复用。采用可交互原型时，体验者应能理解“这是什么、能做什么、当前状态、操作结果和下一步”，不能只有无法识别用途的方块。

本规则细化白盒的可读性，不增加阶段、控制器字段、独立证据文件或逐项人工审批。静态白板只用于梳理；操作、时序、碰撞、空间和跨场景运行结论仍须实际验证。规则不授权自动启动真机验收或分析截图。

## 验证依据与正式设计交接

| 依据 | 用途与边界 |
| --- | --- |
| 测试夹具 | 用于定向验证、异常与极值覆盖、快速复现；固定数据、模拟服务及便捷控件只证明实际覆盖的行为。 |
| 代表性内容 | 对应本批真实使用情境，用于检验信息量、操作压力、内容分布和关键状态；不能由最简单的测试样例或极端用例自动替代。 |
| 正式设计依据 | 用户任务、实际能力范围、状态与入口条件、信息优先级及有效设计决定；只有与这些依据对应的内容才进入正式产品设计。 |

三者可以共享数据与实现，交接时须说明各自用途。测试夹具的数值、标签、控件、坐标和布局不能自动提升为正式要求；重开、语言切换、机制直达等便捷入口也须按真实用户用途与适用状态重新决定保留位置，而非一律保留或删除。已确认的真实空间、交互接口及行为约束按明确范围继续复用。

原型内容进入正式设计时，在已有 GDD、产品 brief、场景或布局规格中说明本批代表情境、关键内容的用户／玩家用途、主要状态与出现条件，以及保留、调整或仅供测试的关键取舍。不逐节点填新表，也不因一次原型截图确认就将全部测试内容、节点位置、正式布局和美术视为已批准。

验证方法只须覆盖当前风险：规则或数据不确定时先验证模型与状态，操作不确定时使用最小交互，布局或状态关系仍不清楚时补最小必要草案或预览；已有表达和证据清楚时直接进入下一步。原型复用真实业务与组件，正式接入仍需在实际宿主验证；不能以独立演示或数据模型通过替代运行结论。先完成本批代表路径，后续仅补新增内容及受影响范围，不等待完整产品规划完毕。

## 最小可读表现

| 方面 | 按当前功能范围落实 | 示例 |
| --- | --- | --- |
| 对象身份 | 先用简单轮廓、姿态、物件关系与必要图标区分角色及用途，不只依赖颜色、编号或名称 | 门洞表达出口；已有交易机制用鱼货、交易台和容器关系表达销售 |
| 基本形态与空间 | 保留影响功能理解的轮廓、朝向、相对尺度、通行与交互范围 | 门有可识别入口，道路连续，按钮具有可点击外观 |
| 有意义的内容 | 场景先表达用途，保留必要金额、数量和单位，明确数值归属及当前值／目标值 | 已有站入付款机制用贴地费用区、金币图标及剩余金额表达，与待解锁地面关联 |
| 状态差异 | 对相关未选、选中、进行、完成、离开与恢复，以及禁用、失败提供可辨变化 | 工具选中后自动作业，以对象变化反馈；失败保留必要原因，不用常驻动作按钮暗示反复点击 |
| 操作反馈 | 为本次需验证的点击、拾取、碰撞、受伤、购买或跳转提供最小反馈 | 金币实际减少、短暂高亮、血量变化、失败原因或 Toast |
| 任务与操作 | 用目标物、路径、操作对象和结果关系表达下一步；文字只补未表达的条件与输入信息 | 钥匙与锁孔对应、拾取后锁孔状态变化，仍需精确数量时显示计数，不直接铺任务解释 |
| 跨场景衔接 | 说明目的地身份、传递状态、结果与返回入口 | 进入商店保留金币，购买返回后能看到物品变化 |

只覆盖本批次真实存在的对象、状态和行为，不为凑齐表格新增功能。先按[信息理解与承载语义](../../app-asset-workflow/references/interface-intent.md)在原方案明确判断、线索、行动、反馈和必要精确信息。对象多时优先用空间分组、轮廓和按状态出现的对象附近反馈减少拥挤；区域图例按沟通需要保留在调试视图，不将全部逻辑地块画成可见格子。文案沿用项目语言配置，默认中文；原型阶段同样避免把临时中文写死到后续难以替换的位置。

## 临时组件与查看方式

优先复用项目现有组件、简单几何和对象反馈；只有任务确需按钮、面板、文字或进度条时才复用对应表现，不把控件清单当作每项机制的默认外观。确需新增时建立轻量临时样式，不预建完整组件库。不因白盒要求启动正式美术生产、生成多套视觉候选或引入新框架。

- **体验视图**：默认呈现可辨对象、当前可执行动作、状态与操作反馈；不依赖开发者讲解内部变量才能完成关键路径。
- **调试视图**：按需显示对象 ID、碰撞框、触发区域、状态、路由或日志；通过已有调试开关、隐藏标签或局部面板查看即可，不强制构建两套独立界面。开启调试信息不能改变被验证的业务行为、命中或计时结论。

层序沿用[显示结构规范](../../app-domain-toolkit/references/reference-domain-display-ownership.md#游戏层内容层hud浮窗与弹窗)：游戏层／内容层 → HUD → 弹窗层 → 浮窗层。Toast 位于常规提示最上层，前台阻塞加载时由[全局加载蒙层](../../app-domain-toolkit/references/reference-domain-display-ownership.md#弹窗按需加载与全局加载状态)覆盖并隔离下层输入；Toast 默认不抢焦点、不吞输入；工具面板、模态弹窗与附属下拉的输入边界仍按实际职责处理，不用调试面板替代功能弹窗验收。

## 大场景本批可玩范围与交接

游戏世界按[分批生产](../../app-domain-toolkit/references/incremental-production.md#选择并完成一批)确定本批代表区域、玩家主路径及其依赖，不以画面是否能放进一张图决定实现范围。以下按本批实际风险并入已有 V1 用例和场景规格，不存在的机制无需补齐，不新增白模阶段、必填表或逐项审批；非空间功能与非游戏 App 不套用区域要求：

- 在同一正式工程中从真实入口走通本批进入、主要操作、状态／数据结果及适用的继续、退出或重试。使用实际角色或操作对象的尺度、输入、镜头和必要碰撞／交互；隔离测试或调试传送只证明对应局部行为，不代替主路径连续运行。
- 与已实现邻区按设计核对入口出口、坐标与尺度、连接口、通行、镜头边界和状态交接；单向连接不强制改为双向。共享接口或场景变化时只回归真实受影响的相邻路径，不能只检查新区域而漏掉已有连接。
- 尚未实现的邻区只明确当前必要的连接位置、接口约束及未覆盖范围，保留有依据的扩展条件；不要求提前完成未来区域、全部关卡或长期机制，也不把空宿主、占位出口或模拟返回记成未来区域已运行。
- 本批涉及动态内容时，按正式物品／关卡配置和同源可编辑模板生成代表类别、数量分布与密度，验证生成、排列、交互及必要状态变化；已有对象池、随机或重试时再检查其重用、复现与恢复。边界夹具仍单独说明用途，不把其极值或固定摆放当作正常体验依据。
- 本批涉及解锁或成长时验证实际出现条件、入口、可执行动作与主要结果；已有暂停、保存／恢复或跨区保留时核对对应状态，未实现机制留作提案。信息与操作先满足本批任务，调试快捷入口不自动进入正式产品设计。
- 密度、碰撞、生成或镜头变化引入实际性能风险时，以本批代表负载检查相关成本并保留采样条件；没有该风险不扩展完整性能专项，不因场景较大就增加流式加载、预取或缓存系统。

交给 V2／后续批次时，在现有规格和验证记录引用正式场景／配置版本、实际覆盖路径、已证实空间与接口约束、代表内容及未决项。空间确认只覆盖本批实际审阅的关系，功能通过只覆盖真实运行行为；可继续复用有效实现，变化部分定向复验。布局与视觉仍按用户任务重新设计，V4/V5 用正式资源检查当前组合，不从白模或旧批次记录推定后续通过。

## 复用机制与替换表现

游戏原型先消费适用的[关卡与场景方案](../../app-domain-toolkit/references/game-design-exploration.md#handoff)，用本批实际路径验证草案中的尺度、通行、交互、遭遇与镜头假设。将不成立的假设及已证实约束交回设计职责修订，形成 V2 输入；概念图可选，经人工确认的真实空间与接口约束按其范围保留为生产依据，不把便于测试的关卡布置整体提升为正式设计基线。

尽量在正式工程中复用实际业务状态、输入、导航、碰撞及事件接口，让临时外观通过组件、资源槽或现有样式配置替换；需要隔离实验时说明范围并复用稳定机制，不维护一套与实际工程无关的演示逻辑。临时外观的替换不得偷偷改变规则、点击范围、碰撞或时序。

V2 正式设计按上述交接重新核对本批任务、信息主次、入口与状态，再决定由何种画面线索承担；白模的调试标签、测试计数、阶段说明、任务解释与临时操作提示不自动成为正式视觉需求。每项保留文字说明仍缺的信息，已确认空间事实与玩法接口继续复用，不能为去标签随意改造场景，也不能仅换材质就声称完成产品信息与体验设计。

V1 验证功能所需的空间、可达性和状态约束；适用的本批整体场景确认只覆盖实际审阅的空间与功能关系，记录中的测试布置不随之成为正式 UI 布局或美术批准。V2–V4 确定正式产品表达、美术方向和生产规格，替换遵守已确认的真实约束；改变占地、接口或路线时只修订受影响范围并按既有环节确认。白模确认不等于美术完成，也不把替换的工程复验变成重复设计审查；各类结论按[验收范围](verification.md#三类验收结论)使用。

已有有效资源可复用；临时素材、模拟数据和占位实现须在运行入口或相关状态及现有验证记录中明确标识。图片继续遵循[源逻辑尺寸、九宫格与背景 cover 规则](../../app-ui-layout/references/relative-layout.md#图片尺寸)，不因是白盒而静默缩放普通图片；原生几何与容器尺寸按功能需求设置。

## V1 检查与记录

采用白盒时，将以下检查并入当前 V1 的实际功能用例和现有验证结果，无需额外清单或单独签字：

1. 能辨认关键对象、当前任务和目的地；物件及空间关系提供线索，必要金额、数量、单位与错误可见。
2. 能发现主要操作，区分可用、禁用、选中和等待状态；命中与控件显示一致。
3. 操作有真实状态变化或明确失败反馈，能理解下一步及适用的重试/返回方式。
4. 跨场景后身份、参数、状态、结果与返回衔接清楚；弹窗关闭和 Toast 提示不破坏既定输入权。

工程检查可核对状态切换、元素显隐、数据变化和输入隔离；是否看得懂、显示是否清楚由用户检查实际运行或提供的截图。未取得的用户判断如实记录，不由机器报告或自动截图分析冒充确认；不额外引入白盒视觉选图与逐项审批。

使用固定测试数据或模拟服务可以验证实际运行的本地机制，但结果必须说明验证数据与边界。例如模拟购买只证明已执行的本地扣款/物品状态或模拟服务流程，不能证明未接入的支付、服务端扣款或真实购买通过；临时目标只证明实际跳转，不证明目的地功能完成。未实现、未执行和不适用项明确区分，不以按钮动画、调试开关或手写 PASS 代替行为。

V1 的检查结果、已证实约束和未决项保存在当前技术设计及现有工程验证材料中，按[功能范围与跨对象依赖](../../app-workflow-control/references/function-dependencies.md)复用真实覆盖范围；不要求跨场景对象先完成 V5。后续真实功能变化按既有功能基线规则重验，V2–V5 仍分别完成目标、拆解布局、资源导入与正式组合验收，不能由白盒通过代替。
