# 统一流程

## 七阶段

产品规格是版本范围依据。规格列有首批可用版本、完整版本或后续版本时，按已规划的各版本交付。施工批次用于组织工作，每批引用目标版本的需求编号。普通流程止于整体验收，另行明确要求的发布按 [app-release](../../app-release/SKILL.md) 独立执行。

| 阶段 | 产出 | 推进条件 | Grilling 时机 |
| --- | --- | --- | --- |
| 1. 商业立项 `commercial-initiation` | 目标用户／玩家、场景、需求或动机依据、变现假设、投入与成功指标 | 明确首期假设和继续、调整或停止的判断依据 | 目标人群、商业模式、预算或交期尚有实质取舍 |
| 2. 产品定义与版本规划 `requirements-scope` | 产品规格、核心路径、需求编号、业务规则、广告阶段、视觉方向与验收条件 | 已规划版本的范围、关键状态和必要依赖可追溯，验收结果可观察 | 规格缺漏、歧义或冲突会改变实现或验收；价格、权益、广告或范围需要取舍 |
| 3. 制作技术方案 `global-baseline` | 技术选型、模块职责、状态归属、接口、数据、平台能力与质量预算 | 关键接口足以指导实施和验证，高风险方案有验证结果或可执行处理 | 技术路线会改变核心体验、平台支持或成本 |
| 4. 基础工程与架构实现 `foundation-engineering` | 可启动、构建、测试的工程与本版公共能力；初期广告统一成功替身；全局视觉方向、代表稿和规范及冻结依据 | 公共能力通过代表性用例，可供模块接入；全局视觉经用户确认并冻结 | 实际限制改变范围、体验或交期；全局方向、可读性或制作成本有实质取舍 |
| 5. 模块实现与体验整合 `scene-production` | 模块完整方案、覆盖状态和进度的 V2 确认稿、V3 拆解、完整功能与体验及验证记录 | V1 完整确定机制、状态、流程和适用组合规则且方案可执行，V2 稿件覆盖全部适用状态及进度并经用户确认，V3–V5 完成拆解、准备、实现和验收 | 机制或组合的触发、结算与交接不清，或状态、文案、广告、反馈存在实质歧义；模块设计与全局方向产生实质冲突 |
| 6. 跨模块集成 `cross-module-integration` | 逐批实际运行结果、跨模块状态用例与回归 | 从真实入口验证本批接线、上下游状态和受影响路径 | 模块规则冲突无法据规格解决，或依赖、性能、视觉偏差要求改变既定计划 |
| 7. 模块集成与整体验收 `global-integration-validation` | 可复现验收版本、逐项需求结果、缺陷与未验证事项 | 目标版本必需范围在同一版本通过，缺陷复验或已确认调整范围；显示与手感按适用人工确认 | 规格冲突、关键缺项或体验偏差需要决定补齐、调整范围或接受已知限制 |

游戏在技术方案确认镜头、渲染、视口和资源预算，基础工程落实场景、输入、HUD、音频及存档前置；非游戏 App 分别落实适配、字体、主题、组件和页面公共能力。第 4 阶段制作代表稿与全局视觉规范，经用户确认后冻结方向；模块稿在 V2 制作。Node.js 同样使用七阶段及跨模块验收，服务端按[原生规范](../../app-stack-nodejs/SKILL.md)使用非视觉 MODULE。

七阶段共用[系统与模块覆盖](system-module-coverage.md)。每轮从原始需求反查模块、实现单元及验收命令。范围、规则或承诺变化先写回产品规格与真实决定，再同步状态、设计、实施和验收。局部任务按[增量影响](professional-conventions.md#incremental-change-impact)复用有效证据。对必要澄清使用 [grilling](../../grilling/SKILL.md)，已明确的缺陷直接修复并复验。

版本整套视觉见[对象闭环](#对象闭环)。游戏大场景、复杂 App 和跨对象路径使用[实际生产范围](../../app-domain-toolkit/references/incremental-production.md)跟踪对象、状态、步骤和转换；目标版本视觉收口应绑定同一冻结总范围。已通过范围的后续制作可按依赖分批，只有用户实际规划的版本才作为产品版本验收。

含客户端界面的新项目在需求及初始化阶段询问支持语言：默认简体中文 `zh-CN`，可选英语 `en`、日语 `ja`、俄语 `ru`、西班牙语 `es`；同时确定默认显示语言。确认后在项目配置中写入 JSON 清单 `{"languages":["zh-CN"],"defaultLanguage":"zh-CN"}`，实际数组以用户选择为准。已有明确选择直接沿用；未收到答复时不把默认选项记为用户确认。既有项目按其已确认的实际语言创建清单，不强制追加中文或限制其他已有语言。

布局合同、翻译、字体、资源及验证按该清单执行，逐语言覆盖；项目范围变更时更新清单及受影响交付。集成时对每个实际本地化合同运行 `node .agents/skills/app-domain-toolkit/scripts/localization/check-project-locales.mjs <项目清单.json> <合同1> [合同2...]`，检查各合同与项目清单的语言集合一致；Cocos 引用式合同使用 `--project-root <项目根> <项目清单> --bind <引用式布局合同> <实际本地化合同>`，后者必须与合同中的 `localization_contract_file` 一致。

Unity 文本及国际化默认使用 [UniText 与固定 JSON 文案配置](../../unity-development-workflow/references/text-and-localization.md)。需求阶段确认语言，全局基线确定初始化与绑定方案；基础工程 `foundation-engineering` / S00 必须按 [S00 国际化验收](../../unity-development-workflow/references/foundation-workflow.md#国际化基础能力验收)完成插件检查、正式 JSON 加载和统一绑定，不等到 HUD 或 V5。具体实现前检查实际安装、依赖、编译及所需绑定能力；安装不正确时由用户选择修复或回退 TMP。所有面向用户的文案消费者只提供文案键和参数，不通过语言条件内联翻译；回退 TMP 仍消费同一 JSON 源。执行 `node .agents/skills/unity-development-workflow/scripts/validate-localization-catalog.mjs <项目清单.json> <文案配置.json>`，并逐语言验证真实加载、启动语言、切换与布局。仅已选择 TMP 并采用 Unity Localization 的项目，使用 `unity command uwt_validate_font_locales --project-path <工程> --plan_path <资产路径> --language_path <项目清单路径> --evidence_path <项目内新报告路径>` 检查真实 TMP 字体计划；其启动观察须由既有初始化代码取得未完成操作后显式调用 `StartupLocaleObservation.Observe(initialization)`。该报告不证明 UniText 或后续语言切换通过；未接线、已完成初始化、未运行或未捕获时标记未验证。先复用已有 Editor，无用户授权不自动发起真机验收；记录真实结果与未覆盖对象，单个合同通过不能代替全项目核对。

初始化同时确认并记录 `orientationPolicy.allowed`：Flutter、Expo 可选 `["portrait"]`、`["landscape"]` 或 `["portrait","landscape"]`；Unity、Cocos、Phaser、Three.js 游戏只能选择一个方向。已有明确选择直接沿用，未选择时先确认，不能用模板默认值代替用户选择。方向配置须落实到原生工程与实际视口策略；桌面/Web 无法锁定窗口比例时保留所选设计方向，提供方向提示或限制入口，不把跨方向窗口变化自动当作第二套适配。方向政策传入页面/场景布局、背景、资源和测试矩阵；Flutter、Expo 双方向需分别制作和冻结视觉目标。

Roblox 根据已确认目标设备、Roblox 客户端支持及实际配置记录方向与输入，分别覆盖适用的屏幕安全区和代表性视口；不将上述四栈单方向默认套到 Roblox，也不为平台客户端制作自有系统启动屏。实际项目支持双方向时分别记录目标与验证，不凭 Studio 模拟宣称真机结果。

## 产品市场调研与视觉设计衔接

首次定义全局视觉方向或生成方向候选前，必须按[通用分析的统一执行要求](professional-conventions.md#product-market-research)完成市场、竞品、受众与参考四项分析，并从相关产品中找美术设定参考。该要求覆盖各技术栈有视觉设计范围的任务及仅制作设计稿的任务。总控核对四项的来源、实际分析或有效复用依据及其与当前视觉 brief 的对应关系后，才按本栈规则安排方向定义与候选制作。局部视觉增量先核对已有结论的来源时效、版本与本批适用性，直接复用有效部分，只补查缺失或变化部分。等待补齐缺口时继续推进独立工作。

## 性能预算与优化闭环

性能工作遵循[性能预算、定位与优化复验](../../app-domain-toolkit/references/performance-optimization.md)：全局基线与架构确定适用预算、目标平台和关键流程，基础工程落实可复现运行、按需采样与资源生命周期，实施按已定位瓶颈定向优化，质量与集成用同条件数据及受影响回归核对收益和成本转移，发布准备汇总当前候选证据。没有明确预算时保留基线及待定目标，不自行设定统一 FPS、内存阈值或将相对改善冒充目标达成。

普通开发不默认开启完整优化专项；已有授权范围内的测量、修复与复验连续执行，发布时额外检查／优化／图集仍分别沿用用户的真实选择。图集、对象池、预取、压缩和质量降级均按测量与取舍采用，不自动生成图集或改写图片；达标后停止，无可辨收益或副作用更大的改动按本轮所有权撤回。性能优化不绕过加载／缓存、视觉变更、测试及受保护操作边界，Node.js 不增加视觉流程，设备采样不以主机数据代替。

## 场景、弹出层与全局加载约束

任务拆解按[加载显示任务拆解与交接](../../app-domain-toolkit/references/reference-domain-display-ownership.md#加载显示任务拆解与交接)覆盖服务／最小视图、正式设计、素材、接入及验证，逐项明确结果、相关路径和完成条件。当前代理默认负责，委派／并行／交接时注明分工，有前置任务或共享消费时再补依赖；已有能力按证据复用，不强制独立工作项，也不能用服务逻辑代替正式画面交付。

各栈场景／页面切换与弹出层按[场景与弹出层统一加载](../../app-domain-toolkit/references/reference-domain-display-ownership.md#场景与弹出层统一加载)共用唯一加载服务与同一个全局显示层：场景切换使用不透明全屏过渡，弹窗首次异步加载使用半透明蒙层，缓存命中且可同步打开时不显示，后台预取与自动重试静默；并发时场景样式优先。基础工程提供随应用宿主就绪的视图及后备入口，独立令牌控制显示和输入隔离，目标资源、必要数据、挂载及输入边界就绪后才结束加载。

场景切换明确请求替代、旧场景保留或受内存限制先卸载的恢复路径，清理旧宿主弹出层、业务任务和独占资源，并隔离迟到回调。弹窗仅在首次打开触发时加载，不批量预加载或预创建；只缓存模板、图片及依赖资源，关闭销毁实例并清理执行活动，重开创建新实例。选中项、输入内容等恢复状态及接口数据由业务层独立管理。功能实施与集成覆盖重复请求、快速切换、场景与弹窗并发、失败／超时／取消、共享资源和输入交接；过渡样式、真实进度提示及正式组合由用户人工确认，不编造百分比或延长等待。

## 错误提示约束

第 4 阶段先定全局基线，再确定所需[弹窗公共方案](../../app-domain-toolkit/references/reference-domain-display-ownership.md#弹窗公共设计方案)和[Toast](../../app-domain-toolkit/references/ui-copy-principles.md#toast-视觉任务)的全局样式。V2 为当前模块生成并确认各适用状态和进度稿，V3–V5 依据确认和实际依赖交付。

实际弹窗和 Toast 使用独立 `DISPLAY_LAYER` 执行 V1–V5，Toast 声明 `layerType=toast`，复用已有有效组件与确认。V1 规划业务及提示状态，V2 生成并确认模块设计，V5 实现验收，最终集成验证各实际宿主的组合。

涉及客户端界面的技术栈遵循[错误提示形式](../../app-domain-toolkit/references/ui-copy-principles.md#错误提示形式)。普通业务错误使用 Toast，需要用户确认的使用弹窗，后台加载和重试失败保持静默。功能方案明确事件分类、文案与确认动作，实现时复用统一提示组件，集成时检查 Toast 每次有效触发独占实例、相同提示不去重且不排队，空闲实例复用与旧回调隔离；按[Toast 上飘与淡出动画](../../app-domain-toolkit/references/ui-copy-principles.md#toast-上飘与淡出动画)实施向上移动 200 个逻辑单位并同步淡出消失的缓动，并核对后台重试不重复打扰；沿用现有功能规格与验证记录，不新增状态机或审批。

## Banner 显示区域

采用原生 MAX Banner 时，在完整游戏区域内叠加显示。禁止缩小游戏渲染区域、改变画面比例或为广告添加内容 inset 与空白占位。覆盖位置只能是背景留白等无有效内容的区域，角色、目标、路径、HUD、文字及操作区域均须避让。动态内容进入覆盖位置时立即隐藏广告，安全位置恢复后再检查显示。具体要求见[Banner 布局、显隐与刷新](../../app-domain-toolkit/references/reference-ad-applovin-max-contract.md#提前规划-ui-布局)；其他渠道按[平台专项](../../app-release/references/channel-platform-integration.md)的实际广告 API 与布局要求执行，不把原生视图规则套到平台托管广告。

## 归因与广告

产品规格区分无广告、初期模拟和后续实际接入。初期仅在已规划触发点调用统一接口，所有调用均返回明确标识的模拟成功；适用的激励返回模拟完成，核对业务状态、权益入账和继续路径。该范围不引入平台广告 SDK 或实际广告展示，最终结果只记接口与模拟成功。后续版本明确纳入真实广告后，才按目标平台接入实际 SDK、测试广告、回退与奖励；后续平台条款仅约束实际接入范围。详细交接见[广告体验设计](domain-production.md#广告体验)和[广告技能](../../app-ad-integration/SKILL.md)。

先按[渠道 SDK 分类与集中选择](../../app-release/references/channel-sdk-selection.md)将本批所有渠道的必接项、可选项、依赖／互斥、材料和复用状态整合为一份清单。有待选项时，等待用户一次多选确认或明确全部不选；此前仅推进只读盘点、方案和不依赖选择的工作，不安装、复制或接线本批必接及可选 SDK。已有完整确认直接复用；确认后按依赖顺序统一实施，法定限制与必要前置不能因可选而跳过。

已选微信小游戏、CrazyGames 或受支持的 TapTap 路线时，基础工程按[渠道 SDK 复用](../../app-release/references/channel-sdk-reuse.md)接入当前引擎的渠道专属具名实现，业务按需调用明确的登录、广告、支付、分享和平台数据接口；不逐项目重写，不只做通用转发，也不接管网络、文件、音频、渲染等基础引擎接口。TapTap 按[运行时专项](../../app-release/references/taptap-runtime-integration.md)将开发者材料、后台服务开通和 Unity C#／Tap 小游戏 TypeScript／Node.js 实现分开接线；其他语言的桥接缺口明确记录。Google Play 按引擎原生 SDK 路线处理，不新增独立渠道层。

所有 SDK 统一遵守[SDK 不阻塞应用流程](../../app-domain-toolkit/references/reference-architecture-sdk-initialization.md#sdk-不阻塞应用流程)：启动入口分别投递即返回，首帧、资源加载、场景切换、结算和继续游戏不等待任何 SDK 或隐私选择。授权不足只跳过相应能力；广告后台预加载，触发展示未就绪立即回退，不设置广告加载页或等待队列，不让广告成为进入下一步的必经条件。

运行时保持基础界面可用，不等于放行受限服务：法律或所选平台要求实名、可玩时段、年龄或消费限制时，前置未满足须限制对应玩法或交易，不得以 SDK 初始化不等待为由开放游客或绕过限制。

Unity、Cocos、Phaser、Three.js 的 Android/iOS 按[移动 SDK 复用](../../app-domain-toolkit/references/mobile-sdk-integration.md)接入确认清单中实际选用的 Firebase Analytics、Firebase Crashlytics、AppsFlyer 及广告聚合；采用原生广告时 AdMob 与 AppLovin MAX 二选一，也可不启用广告。按确认组合复用当前引擎的独立模块和必要共享代码，再接线实际选用的原生依赖与配置；整包安装脚本仅用于其支持且与确认范围一致的完整方案，未选能力不引入、不启动。其他栈按实际引擎能力核实；不因渠道接入自动增加广告或归因。CrazyGames、微信／抖音小游戏使用[对应平台能力](../../app-release/references/channel-platform-integration.md#隐私与商业能力)，不加载不适用的原生 SDK。启动时分别投递任务，业务通过对应能力接口调用；不增加无关 SDK、隐私界面或登录屏障。已采用或官方要求的 CMP（包括 UMP）及其他真实前置必须按锁定平台、版本和流程满足，未满足只限制受影响 SDK，不阻塞游戏或无关任务。广告预加载、刷新和重试均采用非个性化模式，MAX 的[请求适配器](../../app-domain-toolkit/references/reference-ad-applovin-max-contract.md#非个性化广告请求)和平台适配器分别核实配置，不能从非个性化推断所有请求均允许。详见[归因与广告直接启动和调用](../../app-domain-toolkit/references/reference-architecture-sdk-initialization.md#归因与广告直接启动和调用)。

## 隐私流程约束

各栈所有 SDK 均按[隐私流程与 SDK 解耦](../../app-domain-toolkit/references/reference-architecture-sdk-initialization.md#隐私流程与-sdk-解耦)独立于隐私交互和同意状态实现。默认不创建隐私弹窗、隐私中心、同意管理等业务工作项或实现；仅用户明确要求或已确认需求包含时才编排，不擅自移除已有业务。SDK 接入复用现有授权来源与解耦策略接口；无有效授权时只限制需要授权的能力，不自动补建隐私业务。集成与发布核对实际授权约束，业务交互验证仅覆盖确认范围；具体要求见该规范的“工作流接入”。无关 SDK 的初始化不能成为隐私选择前置，需要授权的 SDK 行为也不能因独立启动而提前执行。现有项目仅覆盖受影响用途与能力，不新增审批或另一套流程状态。

## 按任务选择编排

实际工具及接入先按[能力核实](../../app-domain-toolkit/references/tool-capability-verification.md)确认当前工程、操作入口与真实完成结果；仅有 Skill、插件安装或任务受理不代表操作成功。需要运行时按[运行验证与试玩执行](../../app-quality-review/references/runtime-validation.md)复用实例、执行本批路径、采集实际结果并清理本任务资源。V1、V5 与最终组合分别按实际范围验证，不扩大普通小任务或无界面服务的检查范围。

| 任务 | 入口与状态 | 必须保留 |
| --- | --- | --- |
| 事实查询、纯文案或注释 | 直接完成，通常无需 Work Item | 本次差异检查和真实交付说明 |
| 单个本地工程修复 | `init --mode light --type MODULE`，从 REVIEW 开始 | F0范围、F1验收、F2方案质量、F3工程证据，且仅一个独立执行单元 |
| 普通功能、视觉、跨模块或完整项目 | 默认 `standard`，从 INTAKE 开始 | 现有阶段、质量门、原生专业规范及必要人工确认 |

轻量模式减少的是独立状态操作和记录填写，不会自动设置 PASS。它仅接受无视觉生产的 FOUNDATION/MODULE，拒绝项目、集成、发布、设备及其他受保护动作，也不接受多单元或并行依赖。`PROJECT` 初始化进入需求阶段；普通功能及其他工作类型继续按各自阶段起步。

`plan --spec <相对计划路径>` 从实际计划生成身份、顺序、结果路径、实施包与空 Evidence Manifest，并将允许路径收窄为当前单元范围。计划可携带有非空理由的 F0/F1/F2 显式自评；省略时保持原状，不允许注入 F3/F4 或批准。冻结后不能覆盖计划，RETURN 后为变化范围提交新的计划文件。

`record --unit <单元ID> --report <相对报告路径>` 只记录当前实施批次的真实文件、命令、退出码、非空输出及证据路径，失败命令不会生成 PASS。随后使用现有 `unit-check` 校验单元；实施者确认真实工程结论后再登记 F3。记录工具不执行报告里的命令，不生成测试输出、质量结论或用户确认。

`run` 停在 REVIEW 或 IMPLEMENTING 是控制器的执行边界，不是要求用户再次批准普通本地工作。当前任务授权已充分时，由代理继续实施和显式迁移；未决取舍或受保护操作才进入对应用户确认。

受保护动作可在规划时登记，先完成不依赖授权的本地准备；实际执行前按[控制器的 `check-action`](../../app-workflow-control/SKILL.md#cli)逐效果核对动作、目标、明确批准与 F4。该只读检查不执行动作，也不替代用户的明确授权。

## 输出文件规划与交付

实际生成、衍生、替换或复用素材时，按[资源来源与消费者关联](../../app-asset-workflow/references/asset-provenance.md)在现有唯一清单关联需求／参考、必要制作与处理、正式资源身份及真实消费者；已有有效资料直接引用，非素材任务不补空记录。该关联支持增量生产、交接及清理，不代替原生导入、当前运行与人工显示确认。

按[三项最小约定](output-files.md#每项任务的最小约定)明确目标与结果、涉及写入／输出时的路径、完成条件与验证方式，目录映射和已有规则直接引用。当前代理默认负责，委派／并行／交接时注明分工；版本、输入依赖、消费者和保留去向仅在实际需要时补充。交付核对真实文件及适用引用，失败、未生成和未验证项如实列出，不预建空目录或强制报告。

各栈原生目录和工具固定文件名保持其合同，机器证据与人工目录分开，冻结引用不覆盖；任务责任沿用现有实施、采集、质量及清理／发布分工，不新增输出账本或控制器状态。控制器只检查已有字段，完整归档、依赖核对与交付检查由执行者和主编排者负责。

## 项目清理任务与收尾

按[清理任务拆解与安排时机](../../app-artifact-cleanup/references/project-cleanup.md#清理任务拆解与安排时机)安排适用的盘点、记录／项目内容核对、执行和验证，每项明确清理结果、允许范围及完成条件；涉及移动／删除时补充引用与恢复依据，分工和依赖按协作需要注明。实施收尾只核对本轮变化，集成、候选或用户要求提交时再核对相应去向；已有结果直接复用，不重复全仓检查。

工作流记录按[保留与归档规则](../../app-artifact-cleanup/references/project-cleanup.md#工作流记录保留与归档)追踪当前、并行及仍被复用历史工作项的直接／间接依赖，实际项目内容核对源码、配置、场景资源、测试文档和可再生产物的真实消费者。冻结绑定记录保持原路径，不能以删除、重新生成输出或重算摘要伪造历史；临时内容须替换、移除或说明保留用途。任务状态区分已盘点、已执行、已验证及待定，只有清单不能标为已清理；无候选可如实记录无需变更，不为清理制造删除任务。

本地保留、提交选择、发布包选择分别处理，排除提交／发布不授权删除。执行仍以当前有效精确清单、实际授权与无冲突条件为准，核对引用、续接／恢复及受影响工程结果；失败恢复本轮相关改动，不扩大删除范围。沿用现有工作项、控制器与原生工具，不新增自动删除、审批阶段或 schema；任务覆盖由编排者负责，控制器不会自动生成或逐项校验完整清理任务。

## 本地工具目录与项目范围

项目根级 `.agents/` 是本地技能、工具依赖和安装状态目录，不属于业务源码、工作流交付或发布资源。Git 使用 `/.agents/` 忽略整棵目录，不添加文件放行规则、不用 `git add -f` 纳入提交。常规项目变更、候选快照、基线枚举、清理盘点、代码检索和构建输入排除它；在相同 Git 基线下，不因该目录的安装、更新、缓存或未跟踪文件变化本身触发业务返工、重验或提交阻断。排除仅针对项目根目录，不误伤业务子目录内恰好同名的路径；`.gitignore` 等真实项目配置变化仍正常检查，最终发布包若误含工具目录须作为缺陷处理，不能在包检查时跳过掩盖。

仍可按任务读取 `.agents/skills/` 的规范、模板和校验器，执行明确的技能安装/维护与工具自检；这些工具的真实缺失或失败照常报告，不能因目录被忽略就伪造通过。项目实际工作项、确认和证据保存在各自正式路径，不写入 `.agents/` 来隐藏业务改动；根级 `AGENTS.md` 也不属于这个目录。维护本技能源码仓库时，正式 `skills/`、`packages/` 与测试文件保持正常跟踪。

安装器合并目标项目根 `.gitignore`，保留既有规则并确保 `/.agents/` 生效，dry-run 不写文件。忽略规则不会移出已跟踪文件：发现历史跟踪时先核对 `git ls-files -- .agents`；在用户明确要求不跟踪的范围内仅移出该目录的索引并保留本地文件，不删除目录、不重写 Git 历史，也不改其他暂存项。普通安装不自动改 Git 索引；安装来源和版本沿既有说明记录，重新拉取项目后按相同来源安装本地技能。

## 工作流记录与提交范围

Expo 项目额外核对 `.easignore` 的源码上传范围；已有该文件时不能只依赖 `.gitignore` 排除 `.agents/`。CNG 的配置/插件与手工维护的原生工程按本栈正式源规则保留，`.eas/workflows/` 不因点目录命名被当作缓存；构建或 CI 需要的工具通过明确安装步骤提供，不上传本地 `.agents/` 代替依赖安装。

仅在用户明确要求提交时，按当前实际用途逐文件选择工作流记录，而不是提交整个记录目录。保留当前项目运行、构建和验证所需的文件，以及恢复、检查或继续当前工作项及其仍有效依赖所需的记录和引用文件；同时考虑其他仍需续接的工作项与并行任务，不覆盖或移除其必要文件。使用控制器实际 `check` 及适用合同判断哪些记录、执行结果、人工确认和证据仍被消费；目录位置、创建时间或“已完成”标签本身不能证明必要或过时。

已被替代且不再被任何有效工作项、当前验收、运行或构建引用的中间产物，不纳入本次提交。例如无有效引用的旧候选、失败尝试、重复预览、临时日志和过期执行输出。不要仅因文件被记录在历史目录中就提交；也不要仅因文件看起来像中间产物就忽略当前机器门、确认或恢复实际需要的引用。确有必要时保留完整的选择证据及其所引用的候选，不能为缩小提交而篡改确认、删除必需字段或伪造通过。

提交前从当前工作项、规格和实际入口追踪有效引用到具体文件，核对必要文件已在提交或现有 Git 历史中，并逐路径检查待提交差异。失效与归属不能确定时先核实，不能擅自排除可能影响续接的文件。无须提交的文件可留在本地；本规则不授权删除文件、清理他人记录、改写已冻结证据或自动提交。

上述必要引用不包含[本地工具目录](#本地工具目录与项目范围)：规范或命令引用 `.agents/skills/...` 不表示需要把已安装技能纳入 Git。提交核对排除其变更，业务源文件和 `.workflow-control/` 等真实记录仍按实际范围检查。

上述提交判断与[清理范围及交付边界](../../app-artifact-cleanup/references/project-cleanup.md#清理范围与交付边界)分开：Git 历史里存在文件不代表当前工作区所需引用可缺失，不纳入本次提交的本地记录也不能一并删除；发布包另按实际打包消费者核对。保留有效清理记录、恢复映射及验证输出，不在收尾时将本轮交付一起清掉。

## 功能切片与跨对象依赖

游戏世界 `SCENE` 在 V1 开始按[场景与关卡设计任务](../../app-domain-toolkit/references/game-design-exploration.md#v1-scene-design-task)尝试执行设计，核对已有方案与本批范围。新增场景或空间、路线、镜头、关键玩法实质变化时，在当前任务形成或修订草案、尺度、接口与内容需求。有效方案经版本和范围核对后复用，待决问题留在现有产品或任务记录。所有 3D 世界场景在 V1 搭建或复用有效白模，运行验证按风险选择。2D 使用正式工程、功能用例与适用平面布局，纯界面沿原流程。第 4 阶段确认全局方向，V1 确认完整模块方案，V2 生成并确认模块设计，V5 验证完整功能。空间、正式视觉与运行显示按各自范围确认。

游戏创意与核心循环方案形成后，在需求与全局基线阶段按[玩家视角方案审查](../../app-domain-toolkit/references/game-characteristics.md#player-review)检查开始动机、目标理解、行动价值、成败与重试、持续游玩和时间负担。相关机制实现和正式视觉制作前处理方案中已发现的问题，将仍需运行或真实参与者观察的假设交接到 V1 和试玩计划，记录沿用现有 GDD、F1/F2 及 QA 材料。

游戏按[游戏特点识别与专项验证](../../app-domain-toolkit/references/game-characteristics.md)关联特点、规则和风险，V1 覆盖本轮模块方案，必要时验证高风险假设，QA 将必要行为映射到可复现用例。V5 和最终集成验证正式组合与完整游玩周期中受影响的行为。

以可验证的用户行为拆分功能切片，明确目标、主流程、关键状态、必要异常、数据传递、验收范围、真实结果及未决项。一个切片可关联多个场景、页面或显示层，一个对象也可承载多个切片；共享业务规则与状态维护一份，简单单对象任务无需额外建立切片工作项。按当前行为范围关联对象和验证证据，不要求整个项目或无关功能完成。

可按风险选择代表切片验证操作、业务规则、数据变化及异常恢复；沿正式入口明确模块、状态所有者及测试入口。已实现能力持续复用同一工程和公开契约，不在 V5 另写一套已有机制。V1 的推进依据是完整模块方案，模块全部约定功能和状态在 V5 实现验收。

游戏与非游戏应用均按[稳定机制与内容装配](readable-functional-prototype.md#mechanism-content-assembly)先识别机制、可变内容与固定制作边界；本批必要组件与数据消费在功能实施中建立或复用，正式设计交接表现及布局约束后接入同一实现。配置驱动关卡、列表等通过数据变化复用组件，固定空间仍按正式源制作；代表图不固化全部运行实例，不新增阶段或要求全量机制先完成，设计探索仍可按真实依赖推进。

跨场景功能以完整规则、数据和适用状态验证跳转、结果与恢复。共享能力按真实功能来源与宿主验证，局部结果仅证明实际用例。弹窗、Toast 与其他业务对象在统一 V2 确定正式表现，随后按依赖接入。第 6 阶段验证实际跨对象路径、场景切换、状态同步和交接，第 7 阶段核对目标版本整体验收。

导航按行为与显示责任划分，而不是按每个按钮或路由机械建项：共享路由、跳转、返回、参数和状态恢复由非视觉 `MODULE` 或早期 `feature` 集成承担；共用行为由真实证据覆盖相关对象。应用中跨页面常驻、职责稳定且需要独立视觉验收的导航框架可作为 Flutter、Expo 的 `PAGE`，首页内容作为另一 `PAGE`；仅属于首页的导航留在首页。游戏的真实大厅或主菜单使用 `SCENE`，跨场景导航逻辑及资源按需共享，并在实际宿主场景验收，不为常驻导航虚构场景或瞬态层。共享机制不消费正式视觉资源；导航 Prefab、皮肤等正式视觉资源由真实对象按 V3/V4 生产验收，其他宿主复用已验收资源并核对实际组合。导航共享实现、框架、内容和瞬态层分别明确唯一代码及资源所有权，不因复用重复实现。详见[功能范围与跨对象依赖](../../app-workflow-control/references/function-dependencies.md#导航框架与共享路由)。

V1 明确本批规则、操作、空间与镜头风险。所有真实 `world-3d` 场景必须搭建或复用有效白模，运行验证按风险选择；2D 游戏使用平面布局与正式工程，不制作二维白模或可玩的占位白模。常驻 HUD、纯菜单和非游戏 App 按原界面流程推进，不使用白模。涉及操作、时序、碰撞或空间的结论需要实际可运行验证，静态白板不能替代运行结果；功能不等待正式美术。实质取舍与整体空间基线按既有要求等待人工修改或确认。用户检查显示效果，未经明确授权不得自动分析截图或发起真机验收。

采用白盒时，按[可辨识的功能原型](readable-functional-prototype.md)提供有语义的对象、任务、状态与反馈，优先复用轻量原生组件和真实机制；体验视图可理解，调试信息按需查看。可读性检查并入已有 V1 用例，模拟范围如实标识，不增加独立审批，不改变第 4 阶段已冻结的视觉目标。

进入正式设计前按[验证依据与设计交接](readable-functional-prototype.md#design-handoff)区分测试夹具、代表性内容和正式设计依据：功能证据只承接实际验证的行为与约束，先核对本批任务、信息主次和状态入口，再探索美术语言。游戏代表关卡与机制关系按[关卡内容生产](../../app-domain-toolkit/references/game-content-playtesting.md#levels)交接；已有有效决定直接复用，只补本批受影响范围，不将测试场景截图确认外推为全部布局或正式美术批准。

大场景按[本批可玩范围与交接](readable-functional-prototype.md#大场景本批可玩范围与交接)规划本批区域、路径、连接及状态；可按风险验证代表区域。第 4 阶段确认全局方向，V2 生成并确认全部适用模块视图、状态和进度，V3 交接共享部件与消费位置，V4 准备资源，V5 实现并验收当前组合及区域衔接。

3D 场景的代表路径贯穿白模、资源首件、正式组合和跨区回归，按[可玩路径推进](../../app-domain-toolkit/references/incremental-production.md#world-3d-playable-path)核对本轮风险、各阶段实际证据和玩家可观察结果。

## 对象闭环

SCENE 是真实游戏场景及常驻 HUD；PAGE 是 Flutter、Expo 应用页面、ESP32 设备页面，以及实际存在的公共导航框架及其语义状态。框架可以是工作项层面的显示对象，不要求为其虚构新的应用路由。DISPLAY_LAYER 是 modal、popup、drawer、toast 等瞬态层，具有独立 objectId、单一 hostId 和关闭/恢复行为；同一实现跨多个宿主时复用代码和资源，按实际宿主上下文分别验证，不能把一个宿主的结果当作全部宿主通过。宿主只提供运行上下文，不要求宿主 V5 完成、不能替瞬态层完成验收；同一个实施包不能混装三种对象类型。

第 4 阶段按[共同设计依据](../../app-asset-workflow/references/interface-intent.md#design-basis)制作代表稿及全局规范，保存来源、版本、摘要与用户确认并冻结方向。第 5 阶段 V1 确认完整模块方案，V2 基于该方向生成、确认覆盖模块全部适用流程、状态及进度的设计稿，V3 使用该确认的同一设计版本。Flutter、Expo 可按[Figma App 路线](../../app-ui-layout/references/figma-app-design.md)完成模块设计；游戏按其图片或空间路线设计。工具或必要确认缺失时记录受阻。

当前视觉设计稿完成后按[单次用户视角审查](../../app-asset-workflow/references/art-review.md#当前设计稿的单次用户视角审查)核对可编辑结构和已知需求；设计截图与运行截图默认由用户人工检查，未经明确授权不得自动分析截图或代写视觉 PASS。适用的去字与设计质量项归入同一轮，不自动循环评议，不将代理评议登记为人工通过。

| 阶段 | 共同含义 | 关键边界 |
| --- | --- | --- |
| V1 | 确认完整模块方案 | 游戏世界先尝试启动[场景与关卡设计](../../app-domain-toolkit/references/game-design-exploration.md#v1-scene-design-task)，核对当前空间需求与有效方案。按本轮产品规格和实际内容、配置识别机制及变体，确定可达状态与转换、流程及进度、机制组合的触发和结算、异常恢复、依赖接口与验收预期。未决规则先做 grilling 并更新方案，按风险选择原型或运行验证。全部适用规则可执行且无未决问题后进入 V2 |
| V2 | 生成并确认模块设计稿 | 沿用第 4 阶段全局方向，按 V1 确认的当前模块范围展示全部要素、必要状态、流程与进度，供 V3 拆解。图片目标按实际二维内容决定张数。3D 空间用白模、空间规格与相机路径表达，纯 3D 可用空间、方向和适用状态规格完成设计。用户确认后固定版本。业务歧义回 V1，模块稿缺漏在 V2 补齐，全局方向变化回第 4 阶段 |
| V3 | 拆解 V2 已确认的设计稿 | 从本工作项确认的稿件提取组件、布局、文字样式、资源与时序。逐项梳理[需要动画的对象、状态与事件](../../app-domain-toolkit/references/frame-animation-execution.md#v3-animation-inventory)。二维采用帧动画，每个动作从生图和视频抽帧中二选一，采样和播放不超过 24 FPS。3D 交接模型／材质／接口及空间替换规格。游戏图片按原合同分别确认拆解和布局，Figma 提取对应的原生结构 |
| V4 | 准备实现 | 准备、生产和导入资源、共享组件、接口适配及测试数据，按风险验证首件和关键技术点。二维帧动画沿 V3 选定的[来源路线](../../app-domain-toolkit/references/frame-animation-execution.md#source-route-selection)制作并验收实际素材 |
| V5 | 完整实现与模块验收 | 实现本轮全部约定功能并整合文案、广告与反馈；在正式宿主验证输入、状态转换、进度、异常及恢复，人工确认实际显示 |

同一工作项有多张设计稿时，V3 逐张拆解并完成各自适用的确认，同时对齐共享组件、状态差异和依赖顺序。本批稿件全部确认后，工作项进入 V4 准备资源，再在 V5 按依赖顺序接入。

场景与弹窗各自建立工作项，按约定的触发事件、状态数据和宿主接口独立推进。相关实现就绪后，在真实宿主场景联调触发、交互、关闭和恢复流程。具体分工见[弹窗工作项与场景解耦](../../app-domain-toolkit/references/reference-domain-display-ownership.md#弹窗工作项与场景解耦)。

### V1 完整规则与覆盖

V1 主动核对本轮版本和模块的产品资料、玩法、模式、内容、配置及既有实现，从来源梳理机制、变体和适用条件。按实际项目使用的内容单元、环境、模式、难度或角色检查范围，将本轮功能映射到可达状态类别、转换、步骤、进度及生命周期。动态或程序生成内容用生成规则、约束和可达状态类别表达，并覆盖实际可达的边界与组合。

对每条流程确定初始状态、触发动作、处理结果、可继续执行的动作及玩家能感知的反馈。检查同流程机制的组合、同时触发和冲突，明确适用条件、互斥或相互独立的依据、优先级、结算顺序和结果。依玩法确定数据所有者、读写和持久化方式、接口及跨模块交接，覆盖实际适用的暂停、取消、重试、恢复、失败、退出与继续。跨对象转换按生产总范围对齐两端状态，各对象分别承担自己的状态设计与验收。单机制流程不存在组合时记录空集合。

每项规则关联初始条件、动作、预期结果与可复现的验收方式，覆盖正常路径、边界和关键机制组合。对照本轮来源反查遗漏，将机制、状态、流程和组合映射到同一份模块方案，结构化字段及推进检查见[模块阶段门禁](../../app-workflow-control/references/version-visual-gate.md#v1-确认方案)。涉及动作、经营、沙盒、叙事或联机等玩法时，按实际规则核对，不强制项目具备某种类型特有的机制。规则缺失、冲突或存在会改变设计及验收的歧义时做 grilling；将已澄清决定写回产品资料和方案，关闭本轮未决问题后进入 V2。

### 目标版本统一视觉

在[生产总范围](../../app-domain-toolkit/references/incremental-production.md#按需绑定机器范围)登记本版对象、流程步骤、进度、状态和转换。第 4 阶段以代表页或场景确认全局色彩、字体、间距、组件、HUD 或美术规则并冻结基线。V1 明确模块完整状态与进度，V2 为这些适用项生成并确认对应稿件，非游戏 App 按需覆盖导航、加载、空状态、成功、失败与恢复，游戏按需覆盖游玩、结算、重试及关键反馈。动态设计可用关键帧与变化规则表达，多个状态可引用清晰的共享组件规格；逐项建立方案与设计的对应。V2 用户确认模块稿后固定版本供 V3 拆解。业务歧义回 V1 做 grilling，模块稿缺漏在 V2 补齐，全局视觉方向需变更时回第 4 阶段更新并重新确认。

<a id="module-design-decision"></a>

**模块设计方案不明确时。** V2 出稿前先核对 V1 方案、冻结的全局视觉和现有稿件。若仍无法明确会影响出稿或实现的设计，说明具体缺口、受影响的要素或状态，并用现有 grilling 询问用户选择由代理定向调研相关产品和参考，还是由用户人工调整设计稿、标注或提供调整后的方案。若在拆解、资源制作或接入前发现同类缺口，按同一规则处理。等待用户选择及明确设计期间，暂停受影响部分，继续独立任务。选择调研时，将参考和建议提交用户决定。选择人工调整时，等用户给出调整稿或明确指示。将结论写回现有模块方案或 V2 稿件，完成适用的确认后继续。已有依据足以确定设计时按正常阶段推进。

在 V2 确认基础上验证 V5 当前正式模块的布局、操作、状态、文案及广告和反馈；第 6 阶段从真实入口验证上下游状态和当前批次回归；第 7 阶段用同一可复现候选覆盖整个目标版本。显示与手感由用户人工确认，工程证据记录状态、显隐、运行结果及复现条件。

V3 从 V2 已确认目标出发，而非从已有代码反推规格：对游戏 UI／实际图片目标按原合同标注元素或提供源图区域，3D 世界按[模型与替换交接](../../app-domain-toolkit/references/game-design-exploration.md#production-handoff)记录几何、材质与接口，对非游戏 App 可直接引用所选 Figma 真实节点；逐项关联唯一设计项 ID、目标、状态、实现方式、真实组件或素材及消费者，并说明选择依据、真实父子、布局参照和状态变化。抽象框图不能单独证明素材拆解，也不能未经逐项分析宣称全部原生或仅需头像；文字和控件不一律切图。区分目标测量、估计、适配和用户批准的变更；V3 完成交接，V4 才制作与导入实际素材。V5 分别报告结构、工程和人工视觉结论。

还原应保持已确认的比例、信息排列、视觉层级与素材尺寸，不为方便实现或通过测试擅自改变目标。对目标的还原修正和已声明规则内的功能适配可在已有授权内继续；改变视觉目标时记录差异及原因，仅在确需用户取舍时请求确认，不以“适配”或“优化”掩盖设计变更。

游戏世界内容按[正式资产与替换交接](../../app-domain-toolkit/references/game-design-exploration.md#production-handoff)区分模型规格与二维资源，UI／图片还原继续按原合同确认拆解与布局；不以说明更新绕过现有机器门。非游戏 App 的 V3 从已选 Figma 节点取得组件、父子关系、样式、状态及适配；稿内已清楚表达的不再重画低保真图、拆解图、布局图或重复人工批准，仅对缺失信息定向补齐。V4 按[代表性接入与分批协作](../../app-asset-workflow/SKILL.md#代表性接入与分批协作)及实际路线安排适用验证，再分批生产替换；3D 低风险正常导入，高风险先验证首件或复用有效证据。本栈合同将正式宿主装配限定 V5 时，V5 执行最终替换。V5 验证当前正式组合、功能和用户人工显示确认；样本、原型或技术通过不代替验收。

Expo PAGE 的 V1 规划功能、状态、导航及取消／恢复，V2 生成并确认模块设计，V3–V5 按 [Expo 领域合同](../../expo-domain-contracts/references/domain-validation.md)交接与验证，完整功能在 V5 验收。React Native 使用自己的逻辑单位、安全区、键盘和文字缩放；截图由用户人工检查。

Roblox 的 V1 明确 Place 中 Client／Server 输入、规则与状态方案，V2–V5 按 [Roblox 原生合同](../../app-stack-roblox/references/native-contracts.md)设计、交接并实现，V5 在真实运行上下文验证完整功能。正式源需保存并回读；截图由用户人工检查。

Flutter PAGE 的 V1 确认产品语义、状态与完整模块方案，必要时用轻量 sketch 验证风险；V2 生成并确认模块高保真目标，V3 从确认稿推导结构，V5 完整实现并验收。复用组件须符合当前目标的结构、样式及状态；显示效果由用户人工确认。

目标、代表样本、正式资源和 V5 完整组合按既有节点确认实际范围；非游戏 App 的拆解和布局如已由选稿表达，不增加独立图稿及重复确认。样本确认不升级为整页通过，单项替换只影响对应项。发现拆解缺失或实现偏离时 RETURN 至最早受影响阶段，保留历史并作废下游引用。

## 视觉确认的增量复用

新增或修改可见表现，先按[增量显示约束](../../app-domain-toolkit/references/reference-domain-display-ownership.md#新增显示元素的增量约束)在当前模块任务中记录影响范围并完成本轮 V1。布局、外观、可见状态、特效参数和时序按实际变化复核；保留仍有效的设计、素材及验收依据。

图片路线和 Figma App 已有同项目、同技术栈、同工作项类型及对象的 COMPLETE/V5 来源时，可在当前 V1 确认方案后按控制器规则调用 `reuse-visual`。DISPLAY_LAYER 核对宿主与层类型。复用范围内仍有效的稿件及确认，新增或变化的模块设计在 V2 补齐并确认。

仅复用 App 有效已确认效果图时，直接引用冻结视觉来源、图摘要及原确认与范围；不以完整 `reuse-visual` 的 COMPLETE/V5 条件阻止未完成实现的设计复用，也不继承来源的 V4/V5 或工程证据。当前重建及交接仍须核对，目标实质变化才重新选稿。

`world-3d` 不使用本节的 `reuse-visual` 自动继承阶段批准或图片目标清单。按[无图 3D 场景合同](../../app-workflow-control/references/world3d-scenes.md)在当前场景引用仍有效的空间、方向和模型依据，并核对当前范围及真实用户决定；复用有效材料不自动生成确认，也不要求重做未受影响的资源。

图片 SCENE 累计生产且本批需要新增目标时，可按[多目标记录](../../app-workflow-control/references/multi-target-visual.md)显式使用 `--target-ids` 选择未变化来源目标。逐项继承允许的确认，把未继承的目标按本批方案补齐。PAGE／DISPLAY_LAYER 使用单对象复用。当前工作项在 V2 核对全部状态和进度并固定稿件版本后，进入 V3。

| `--impact` | 可继承 | 新工作项起点 | 当前仍需完成 |
| --- | --- | --- | --- |
| `implementation` | 基线、V2 目标、V3 拆解与布局 | V2 | 复核本轮覆盖，沿用有效拆解，完成 V4 准备及 V5 实现验收 |
| `assets` | 基线、V2 目标、V3 拆解与布局 | V2 | 复核本轮覆盖，验证 V4 新素材及 V5 运行组合 |
| `layout` | 基线、V2 目标、V3 拆解 | V2 | 核对 V2 稿，确认 V3 新布局，完成 V4 与 V5 |
| `target` | 全局基线 | V2 | 生成并确认新的模块稿，完成 V3、V4 和 V5 |

影响分类依据实际目标、对象状态、素材和布局关系，由当前执行者明确说明理由，不用文件版本或摘要变化自动推断。游戏图片路线全局视觉方向变化时按原三候选规则重新选择；`world-3d` 沿用冻结方向规格及真实用户确认，变化时按无图合同处理；非游戏 App 按 Figma 规范默认先生成并确认一张效果图，再忠实重建可编辑稿，仅用户明确要求比较时按其数量制作多方向，局部增量可复用有效方向。复用不会继承工程 Evidence、V4/V5 确认或旧执行状态；未变化素材可继续使用。新增状态或交互须重验受影响功能并评估目标与布局；RETURN 撤销受影响确认及下游引用并保留历史文件。

## 持续迭代与可接手收尾

每批实现与审核按[架构模块契约](professional-conventions.md#architecture-module-contracts)检查实际改动是否增加重复规则、状态多写者、私有穿透或生命周期风险，只做保障本次交付所必需的局部重构；按[质量证据与返修复验](professional-conventions.md#quality-evidence-and-retests)沉淀关键行为和缺陷回归测试。测试留在正式项目目录，本轮命令输出沿原证据路径保存，不以报告或静态规范断言替代应用行为测试。

收尾按[验证约定](verification.md)核对适用项，按[当前项目知识](professional-conventions.md#current-project-knowledge)仅更新变化事实，让下一轮可定位入口、运行相关检查并继续修改。面向用户按[精简交付](output-files.md#精简交付)简短反馈，不把内部检查清单扩写成报告。已有 F1/F2/F3 承担交付与质量职责，不新增可维护性分数、账本、阶段或逐项审批，不要求全仓重验或复制全套文档。历史冻结记录保持不变，当前说明引用有效历史依据。

## 独立的发布任务

以下条款只在用户另行明确委托发布准备或实际发布时适用。通用研发的完成条件是模块集成与整体验收，发布工作项独立登记。

候选构建、导出及交付按[实际输出绑定](../../app-release/references/release-readiness.md#实际构建输出与候选绑定)选择本次真实目录或包，不以固定目录顺序、文件名或修改时间猜选旧产物。配置明确时使用对应输出；存在无法核实的歧义时暂停依赖该候选的交付，继续独立检查，不自动清空其他目录或把构建受理当完成。

已选渠道按[渠道接入任务](../../app-release/references/channel-platform-integration.md#接入任务与完成条件)确认平台与能力、验证实际产物和适用的恢复。实际广告仅按目标版本规划接入；准备或发布逐渠道核对当前范围的证据、资质与资料。TapTap 管理与运营另按 [CLI 专项](../../app-release/references/channel-platforms/taptap.md)核实当前能力和身份。平台的必要隐私与授权前置按真实能力适用范围验证。

目标包含商店或游戏平台展示时，安排[商店文案与展示素材制作](../../app-release/references/store-marketing-assets.md#任务安排与完成条件)。策划期可准备字段、卖点和采集脚本。相关功能和画面稳定后制作所需封面、截图及视频，发布准备核对填写稿、导出规格、顺序及用户人工确认。素材审阅沿用现有流程，商店上传、投放和市场实验按实际任务和授权执行。

`RELEASE` 默认 `releaseIntent=prepare`。完成本次检查或候选打包、F0–F3及当前准备材料后，可从 PASSED/INTEGRATING 到 COMPLETE；完成结果标为 `release-prepared`。Evidence Manifest 必须唯一包含 PASS 的 `release-preparation` 记录，它绑定当前工作项、技术栈和 release 阶段，并引用当前证据根下两个独立、非空的交付材料与检查文件。交付可以是准备检查报告或构建产物，不能用结果JSON或manifest自身充当证据。

实际发布选择 `releaseIntent=publish`，继续经过 RELEASE_APPROVAL_REQUIRED、F4、精确批准、RELEASING 和真实 `release-result` 后完成，结果标为 `release-published`。准备模式禁止 `publish` 动作和发布执行状态。签名、上传等其他受保护操作仍分别遵循原有精确授权规则。

## 风险与门禁

| 动作等级 | 范围 |
| --- | --- |
| A0 | 只读调查 |
| A1 | 规格与候选 |
| A2 | 隔离原型 |
| A3 | 授权范围内正式实现和本地验证 |
| A4 | 本地集成、迁移或共享设置变更 |
| A5 | 外部系统、设备、签名和上传 |
| A6 | 发布、付费与不可逆高影响操作 |

A 等级描述风险，不新增授权。安全本地 A4 不自动增加确认；A0–A4 中一旦实际涉及外部写入、付费、真机、破坏性操作等，仍遵守精确授权。

| 门 | 唯一职责 |
| --- | --- |
| F0 | 用户目标、范围、路径和停止条件 |
| F1 | 实际交付满足目标与有效决定 |
| F2 | 当前技术栈的领域质量 |
| F3 | 真实工程证据和有序执行闭环 |
| F4 | 当前高影响操作的精确授权 |

`INTAKE → BASELINE → PROPOSAL → REVIEW → IMPLEMENTING → VALIDATING → PASSED` 是实施主路径；后续按需要集成、准备发布或完成。V 阶段是对象证据进度，不是另一套可绕过门禁的状态机。

失败先原地 repair；候选未变而证据过期时 revalidate；需求/范围/上游视觉目标真实变化时显式 return，影响范围决定恢复点。已授权目标内的实现调整记录在实际交付中，不因合同版本、文件内容或 SHA 差异自动重开确认。

发现已知的轻微偏差时，先记录实际现象及影响，继续不受影响的工作，在阶段结果或最终结果中汇报，不为每一处轻微差异中断并询问。功能失败、明显遮挡、不可读、证据错绑等仍须处理；明确约定的验收条件未满足时如实保留未通过或未决状态，不将继续工作当作验收通过。用户对视觉效果的人工检查和确认仍按既定流程进行，未经明确要求不自动分析截图。
