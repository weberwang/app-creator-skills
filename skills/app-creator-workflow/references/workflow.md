# 统一流程

## 六阶段

沿用 Unity 基准的阶段 ID，`scene-production` 的显示名称扩展为“场景、页面与显示层生产”，不为 Flutter 建立第二套总控。

| 阶段 ID | 目标 | 交付 |
| --- | --- | --- |
| requirements-scope | 确定用户结果和边界 | 目标、非目标、验收、事实与实质待决项 |
| global-baseline | 固定全局方向 | 技术方案、模块依赖、视觉签名和质量预算；视觉首次三候选选择 |
| foundation-engineering | 建立必要基础能力 | 启动、数据、服务、资源加载与有序实施证据 |
| scene-production | 分对象生产 | SCENE、PAGE 或 DISPLAY_LAYER 各自的 V0–V4 |
| global-integration-validation | 验证整体体验 | 导航、生命周期、状态、跨模块交互、资源和性能回归 |
| release | 准备并按授权交付 | 可复现构建、依赖/素材来源、剩余问题与精确放行范围 |

阶段不是强制铺满的目录模板。现有工程局部修复只覆盖受影响工作，不创建空文档、空模块或占位审批。

## 按任务选择编排

| 任务 | 入口与状态 | 必须保留 |
| --- | --- | --- |
| 事实查询、纯文案或注释 | 直接完成，通常无需 Work Item | 本次差异检查和真实交付说明 |
| 单个本地工程修复 | `init --mode light --type MODULE`，从 REVIEW 开始 | F0范围、F1验收、F2方案质量、F3工程证据，且仅一个独立执行单元 |
| 普通功能、视觉、跨模块或完整项目 | 默认 `standard`，从 INTAKE 开始 | 现有阶段、质量门、原生专业规范及必要人工确认 |

轻量模式减少的是独立状态操作和记录填写，不会自动设置 PASS。它仅接受无视觉生产的 FOUNDATION/MODULE，拒绝项目、集成、发布、设备及其他受保护动作，也不接受多单元或并行依赖。`PROJECT` 初始化进入需求阶段；普通功能及其他工作类型继续按各自阶段起步。

`plan --spec <相对计划路径>` 从实际计划生成身份、顺序、结果路径、实施包与空 Evidence Manifest，并将允许路径收窄为当前单元范围。计划可携带有非空理由的 F0/F1/F2 显式自评；省略时保持原状，不允许注入 F3/F4 或批准。冻结后不能覆盖计划，RETURN 后为变化范围提交新的计划文件。

`record --unit <单元ID> --report <相对报告路径>` 只记录当前实施批次的真实文件、命令、退出码、非空输出及证据路径，失败命令不会生成 PASS。随后使用现有 `unit-check` 校验单元；实施者确认真实工程结论后再登记 F3。记录工具不执行报告里的命令，不生成测试输出、质量结论或用户确认。

`run` 停在 REVIEW 或 IMPLEMENTING 是控制器的执行边界，不是要求用户再次批准普通本地工作。当前任务授权已充分时，由代理继续实施和显式迁移；未决取舍或受保护操作才进入对应用户确认。

## 对象闭环

SCENE 是游戏内容及常驻 HUD；PAGE 是应用页面及其语义状态；DISPLAY_LAYER 是 modal、popup、drawer、toast 等瞬态层，具有独立 objectId、hostId 和关闭/恢复行为。宿主只提供运行上下文，不能替瞬态层完成验收。同一个实施包不能混装三种对象类型。

| 阶段 | 共同含义 | 关键边界 |
| --- | --- | --- |
| V0 | 内部识别与分流 | 确定对象、状态、依赖；无需常规人工确认 |
| V1 | 目标定义 | 真实目标图、语义与状态范围；用户确认真实候选 |
| V2 | 拆解与布局 | 先独立确认带编号拆解图，再确认布局图及适配关系 |
| V3 | 正式资源与导入 | 资源总表、实际文件、原生导入和资源级校验；可做临时组合预览 |
| V4 | 正式实现与运行 | 正式宿主接入、布局、输入、状态和连续尺寸变化证据；人工确认实际显示 |

V3 可以制作资源级 Prefab/原子组件，正式宿主装配与布局校准在 V4。基线素材已存在时复用，不为阶段强行生成图片。没有独立位图需求时记录原生组件/矢量路线及资源阶段不适用项，仍验收对象的拆解与布局。

Flutter PAGE 的 V1 先完成产品语义、状态和轻量 sketch 可行性验证，再确认高保真目标；V2 的关系约束可来自 sketch，但不冻结与已确认目标冲突的低保真几何；V4 按 fidelity 验证 Widget 关系、文本缩放、键盘、安全区与真实交互。页面不使用游戏世界坐标作为布局依据。

## 视觉确认的增量复用

已有同项目、同技术栈、同工作项类型和对象的 COMPLETE/V4 来源时，可在新工作项 V0、尚未冻结计划前调用 `reuse-visual`。DISPLAY_LAYER 还核对宿主与层类型。工具验证原记录和已有用户消息，只引用原文件，不改写原确认，也不生成新的视觉批准。

| `--impact` | 可继承 | 新工作项起点 | 当前仍需完成 |
| --- | --- | --- | --- |
| `implementation` | 基线、V1目标、V2拆解与布局 | V2 | V3当前导入证据与确认、V4当前运行及人工验收 |
| `assets` | 基线、V1目标、V2拆解与布局 | V2 | 更新素材的V3检查与确认、V4当前组合验收 |
| `layout` | 基线、V1目标、V2拆解 | V1 | V2新布局确认、V3与V4 |
| `target` | 仅全局基线 | V0 | 新V1目标，以及V2、V3、V4 |

影响分类依据实际目标、对象状态、素材和布局关系，由当前执行者明确说明理由，不用文件版本或摘要变化自动推断。全局视觉方向变化时不复用旧基线，重新完成首次三候选选择。复用不会继承工程 Evidence、V3/V4确认或旧执行状态；未变化素材可由原生流程继续使用实际文件。RETURN 仍只撤销实际受影响的确认，并同步清理复用来源声明。

## 发布准备与实际上线

`RELEASE` 默认 `releaseIntent=prepare`。完成本次检查或候选打包、F0–F3及当前准备材料后，可从 PASSED/INTEGRATING 到 COMPLETE；完成结果标为 `release-prepared`。Evidence Manifest 必须唯一包含 PASS 的 `release-preparation` 记录，它绑定当前工作项、技术栈和 release 阶段，并引用当前证据根下两个独立、非空的交付材料与检查文件。交付可以是准备检查报告或构建产物，不能用结果JSON或manifest自身充当证据。

实际发布选择 `releaseIntent=publish`，继续经过 RELEASE_APPROVAL_REQUIRED、F4、精确批准、RELEASING 和真实 `release-result` 后完成，结果标为 `release-published`。准备模式禁止 `publish` 动作和发布执行状态。签名、上传等其他受保护操作仍分别遵循原有精确授权规则。

## 风险与门禁

| 动作等级 | 范围 |
| --- | --- |
| A0 | 只读调查 |
| A1 | 规格与候选 |
| A2 | 隔离原型 |
| A3 | 授权范围内正式实现和本地验证 |
| A4 | 本地集成、迁移或共享设置变更 |
| A5 | 外部系统、设备、签名和上传 |
| A6 | 发布、付费与不可逆高影响操作 |

A 等级描述风险，不新增授权。安全本地 A4 不自动增加确认；A0–A4 中一旦实际涉及外部写入、付费、真机、破坏性操作等，仍遵守精确授权。

| 门 | 唯一职责 |
| --- | --- |
| F0 | 用户目标、范围、路径和停止条件 |
| F1 | 实际交付满足目标与有效决定 |
| F2 | 当前技术栈的领域质量 |
| F3 | 真实工程证据和有序执行闭环 |
| F4 | 当前高影响操作的精确授权 |

`INTAKE → BASELINE → PROPOSAL → REVIEW → IMPLEMENTING → VALIDATING → PASSED` 是实施主路径；后续按需要集成、准备发布或完成。V 阶段是对象证据进度，不是另一套可绕过门禁的状态机。

失败先原地 repair；候选未变而证据过期时 revalidate；需求/范围/上游视觉目标真实变化时显式 return，影响范围决定恢复点。已授权目标内的实现调整记录在实际交付中，不因合同版本、文件内容或 SHA 差异自动重开确认。
