# 统一流程

## 六阶段

沿用 Unity 基准的阶段 ID，`scene-production` 的显示名称扩展为“场景、页面与显示层生产”，不为 Flutter、Expo 等应用栈建立第二套总控。

Node.js 服务器沿用这些公共阶段 ID，需求定义服务结果，全局基线确定技术/数据与质量约束，基础工程及 MODULE 实现业务，最终集成验证实际模块组合，RELEASE 准备交付。`scene-production` 与 V0–V5 仅用于实际显示对象，不为服务端创建伪页面、视觉基线、素材或截图门禁；下文界面语言、方向、布局、Toast、弹窗和广告显示条款也只在实际客户端界面存在时适用。服务端采用 [Node.js 原生规范](../../app-stack-nodejs/SKILL.md)。

| 阶段 ID | 目标 | 交付 |
| --- | --- | --- |
| requirements-scope | 确定用户结果和边界 | 目标、非目标、验收、事实与实质待决项 |
| global-baseline | 确定全局约束 | 产品市场调研与定位依据、技术方案、模块依赖、目标视口和质量预算；适用游戏先探索关卡与场景方案，正式视觉选择延后 |
| foundation-engineering | 建立必要基础能力 | 启动、最小运行宿主、公共显示挂载入口、数据、服务与资源加载 |
| scene-production | 按功能切片分对象生产 | 先完成所需[公共 Toast 前置视觉任务](../../app-domain-toolkit/references/ui-copy-principles.md#toast-前置视觉任务)，再实现业务模块及各对象的 V0–V5 |
| global-integration-validation | 验证整体体验 | 导航、生命周期、状态、跨模块交互、资源、性能及[跨场景背景音乐回归](../../app-workflow-control/references/function-dependencies.md#最终集成验收) |
| release | 准备并按授权交付 | 可复现构建、依赖/素材来源、剩余问题与精确放行范围 |

阶段不是强制铺满的目录模板或全项目同步关卡。按可验证的功能切片分批推进，具备条件的对象可先进入视觉设计；游戏大场景及 App 多状态、多步骤流程按[分批生产](../../app-domain-toolkit/references/incremental-production.md)明确总范围、首批选择、当前结果及整体收口。现有工程局部修复只覆盖受影响工作，不创建空文档、空模块或占位审批。

App 多页面采用[多页面推进顺序](../../app-domain-toolkit/references/incremental-production.md#多页面推进顺序)：相关 V1 通过后统一视觉方向，优先选择能验证主要共享组件、关键状态和适配风险的代表页完成 V2–V5，再推广到其余页面。每个 `PAGE` 按自身依赖独立推进；接口与方案明确、所有权互斥时可提前并行，不等待全部页面到达相同 V 阶段。共享实现可复用，各页视觉确认和正式组合验收分别完成。

每轮先按[增量影响与复用范围](professional-conventions.md#incremental-change-impact)沿真实行为和消费者确定实施、复用与回归范围。新项目在正式工程中先完成一条纵向功能切片，再扩展其他路径；有视觉对象时采用“V1 功能骨架 → V2 目标 → V3 拆解与布局确认 → V4 少量样本试接、验证后分批生产并完善代码 → V5 完整组合验收”。不把基础工程扩展成全部基础设施建设，也不把美术全部完成作为开始写代码的条件；无界面服务继续按模块与接口推进。

含客户端界面的新项目在需求及初始化阶段询问支持语言：默认简体中文 `zh-CN`，可选英语 `en`、日语 `ja`、俄语 `ru`、西班牙语 `es`；同时确定默认显示语言。确认后在项目配置中写入 JSON 清单 `{"languages":["zh-CN"],"defaultLanguage":"zh-CN"}`，实际数组以用户选择为准。已有明确选择直接沿用；未收到答复时不把默认选项记为用户确认。既有项目按其已确认的实际语言创建清单，不强制追加中文或限制其他已有语言。

布局合同、翻译、字体、资源及验证按该清单执行，逐语言覆盖；项目范围变更时更新清单及受影响交付。集成时对每个实际本地化合同运行 `node .agents/skills/app-domain-toolkit/scripts/localization/check-project-locales.mjs <项目清单.json> <合同1> [合同2...]`，检查各合同与项目清单的语言集合一致；Cocos 引用式合同使用 `--project-root <项目根> <项目清单> --bind <引用式布局合同> <实际本地化合同>`，后者必须与合同中的 `localization_contract_file` 一致。Unity 项目既有初始化代码取得尚未完成的 Localization 初始化操作后，显式调用 `StartupLocaleObservation.Observe(initialization)`，观察器不主动启动初始化；再使用 `unity command uwt_validate_font_locales --project-path <工程> --plan_path <资产路径> --language_path <项目清单路径> --evidence_path <项目内新报告路径>` 读取真实字体计划，并核对当前运行中 Localization 初始化后的首个语言。未接线、初始化已完成、未运行或未捕获时标记未验证，不把 Editor 当前语言冒充启动结果。该报告不证明后续业务切换语言的行为。先检查并复用已有 Editor；没有用户授权时不自动发起真机验收。记录真实命令、结果和未覆盖对象；单个合同通过不能替代全项目核对。

初始化同时确认并记录 `orientationPolicy.allowed`：Flutter、Expo 可选 `["portrait"]`、`["landscape"]` 或 `["portrait","landscape"]`；Unity、Cocos、Phaser、Three.js 游戏只能选择一个方向。已有明确选择直接沿用，未选择时先确认，不能用模板默认值代替用户选择。方向配置须落实到原生工程与实际视口策略；桌面/Web 无法锁定窗口比例时保留所选设计方向，提供方向提示或限制入口，不把跨方向窗口变化自动当作第二套适配。方向政策传入页面/场景布局、背景、资源和测试矩阵；Flutter、Expo 双方向需分别制作和冻结视觉目标。

Roblox 根据已确认目标设备、Roblox 客户端支持及实际配置记录方向与输入，分别覆盖适用的屏幕安全区和代表性视口；不将上述四栈单方向默认套到 Roblox，也不为平台客户端制作自有系统启动屏。实际项目支持双方向时分别记录目标与验证，不凭 Studio 模拟宣称真机结果。

## 产品市场调研与视觉设计衔接

首次定义全局视觉方向或生成方向候选前，必须按[产品市场调研](professional-conventions.md#product-market-research)完成来源核实、竞品对比和设计依据交接，覆盖各技术栈及仅制作设计稿的任务。总控核对调研结论已进入当前视觉 brief 后，才按本栈规则安排方向定义与候选制作；已有有效调研和基线按实际变化补查与复用。

## 性能预算与优化闭环

性能工作遵循[性能预算、定位与优化复验](../../app-domain-toolkit/references/performance-optimization.md)：全局基线与架构确定适用预算、目标平台和关键流程，基础工程落实可复现运行、按需采样与资源生命周期，实施按已定位瓶颈定向优化，质量与集成用同条件数据及受影响回归核对收益和成本转移，发布准备汇总当前候选证据。没有明确预算时保留基线及待定目标，不自行设定统一 FPS、内存阈值或将相对改善冒充目标达成。

普通开发不默认开启完整优化专项；已有授权范围内的测量、修复与复验连续执行，发布时额外检查／优化／图集仍分别沿用用户的真实选择。图集、对象池、预取、压缩和质量降级均按测量与取舍采用，不自动生成图集或改写图片；达标后停止，无可辨收益或副作用更大的改动按本轮所有权撤回。性能优化不绕过加载／缓存、视觉变更、测试及受保护操作边界，Node.js 不增加视觉流程，设备采样不以主机数据代替。

## 场景、弹出层与全局加载约束

任务拆解按[加载显示任务拆解与交接](../../app-domain-toolkit/references/reference-domain-display-ownership.md#加载显示任务拆解与交接)覆盖服务／最小视图、正式设计、素材、接入及验证，逐项明确结果、相关路径和完成条件。当前代理默认负责，委派／并行／交接时注明分工，有前置任务或共享消费时再补依赖；已有能力按证据复用，不强制独立工作项，也不能用服务逻辑代替正式画面交付。

各栈场景／页面切换与弹出层按[场景与弹出层统一加载](../../app-domain-toolkit/references/reference-domain-display-ownership.md#场景与弹出层统一加载)共用唯一加载服务与同一个全局显示层：场景切换使用不透明全屏过渡，弹窗首次异步加载使用半透明蒙层，缓存命中且可同步打开时不显示，后台预取与自动重试静默；并发时场景样式优先。基础工程提供随应用宿主就绪的视图及后备入口，独立令牌控制显示和输入隔离，目标资源、必要数据、挂载及输入边界就绪后才结束加载。

场景切换明确请求替代、旧场景保留或受内存限制先卸载的恢复路径，清理旧宿主弹出层、业务任务和独占资源，并隔离迟到回调。弹窗仅在首次打开触发时加载，不批量预加载或预创建；只缓存模板、图片及依赖资源，关闭销毁实例并清理执行活动，重开创建新实例。选中项、输入内容等恢复状态及接口数据由业务层独立管理。功能实施与集成覆盖重复请求、快速切换、场景与弹窗并发、失败／超时／取消、共享资源和输入交接；过渡样式、真实进度提示及正式组合由用户人工确认，不编造百分比或延长等待。

## 错误提示约束

统一 Toast 按[前置视觉任务](../../app-domain-toolkit/references/ui-copy-principles.md#toast-前置视觉任务)在最小宿主就绪后、业务模块实现之前交付。使用独立 `DISPLAY_LAYER`、`layerType=toast` 执行 V0–V5，复用已有有效组件与确认。实施计划先安排宿主和 Toast，再安排业务模块接入统一接口，最终集成验证各实际宿主的组合。

涉及客户端界面的技术栈遵循[错误提示形式](../../app-domain-toolkit/references/ui-copy-principles.md#错误提示形式)。普通业务错误使用 Toast，需要用户确认的使用弹窗，后台加载和重试失败保持静默。功能方案明确事件分类、文案与确认动作，实现时复用统一提示组件，集成时检查 Toast 每次有效触发独占实例、相同提示不去重且不排队，空闲实例复用与旧回调隔离；按[Toast 上飘与淡出动画](../../app-domain-toolkit/references/ui-copy-principles.md#toast-上飘与淡出动画)实施向上移动 200 个逻辑单位并同步淡出消失的缓动，并核对后台重试不重复打扰；沿用现有功能规格与验证记录，不新增状态机或审批。

## Banner 显示区域

采用原生 MAX Banner 时，在完整游戏区域内叠加显示。禁止缩小游戏渲染区域、改变画面比例或为广告添加内容 inset 与空白占位。覆盖位置只能是背景留白等无有效内容的区域，角色、目标、路径、HUD、文字及操作区域均须避让。动态内容进入覆盖位置时立即隐藏广告，安全位置恢复后再检查显示。具体要求见[Banner 布局、显隐与刷新](../../app-domain-toolkit/references/reference-ad-applovin-max-contract.md#提前规划-ui-布局)；其他渠道按[平台专项](../../app-release/references/channel-platform-integration.md)的实际广告 API 与布局要求执行，不把原生视图规则套到平台托管广告。

## 归因与广告

已选微信小游戏或 CrazyGames 时，基础工程按[渠道 SDK 复用](../../app-release/references/channel-sdk-reuse.md)接入当前引擎的渠道专属具名实现，业务按需调用明确的登录、广告、支付、分享和平台数据接口；不逐项目重写，不只做通用转发，也不接管网络、文件、音频、渲染等基础引擎接口。Google Play 按引擎原生 SDK 路线处理，不新增独立渠道层。

所有 SDK 统一遵守[SDK 不阻塞应用流程](../../app-domain-toolkit/references/reference-architecture-sdk-initialization.md#sdk-不阻塞应用流程)：启动入口分别投递即返回，首帧、资源加载、场景切换、结算和继续游戏不等待任何 SDK 或隐私选择。授权不足只跳过相应能力；广告后台预加载，触发展示未就绪立即回退，不设置广告加载页或等待队列，不让广告成为进入下一步的必经条件。

Unity、Cocos、Phaser、Three.js 的 Android/iOS 按[移动 SDK 复用](../../app-domain-toolkit/references/mobile-sdk-integration.md)接入 Firebase 统计、事件与异常、AppsFlyer 归因，以及 AdMob 或 AppLovin MAX 二选一的顶层广告聚合；先使用安装脚本复制当前引擎的具体实现，再接线实际原生依赖与配置。其他栈按实际引擎能力核实；不因渠道接入自动增加广告或归因。CrazyGames、微信／抖音小游戏使用[对应平台能力](../../app-release/references/channel-platform-integration.md#隐私与商业能力)，不加载不适用的原生 SDK。启动时分别投递任务，业务通过对应能力接口调用；不增加无关 SDK、隐私界面或登录屏障。已采用或官方要求的 CMP（包括 UMP）及其他真实前置必须按锁定平台、版本和流程满足，未满足只限制受影响 SDK，不阻塞游戏或无关任务。广告预加载、刷新和重试均采用非个性化模式，MAX 的[请求适配器](../../app-domain-toolkit/references/reference-ad-applovin-max-contract.md#非个性化广告请求)和平台适配器分别核实配置，不能从非个性化推断所有请求均允许。详见[归因与广告直接启动和调用](../../app-domain-toolkit/references/reference-architecture-sdk-initialization.md#归因与广告直接启动和调用)。

## 隐私流程约束

各栈所有 SDK 均按[隐私流程与 SDK 解耦](../../app-domain-toolkit/references/reference-architecture-sdk-initialization.md#隐私流程与-sdk-解耦)独立于隐私交互和同意状态实现。默认不创建隐私弹窗、隐私中心、同意管理等业务工作项或实现；仅用户明确要求或已确认需求包含时才编排，不擅自移除已有业务。SDK 接入复用现有授权来源与解耦策略接口；无有效授权时只限制需要授权的能力，不自动补建隐私业务。集成与发布核对实际授权约束，业务交互验证仅覆盖确认范围；具体要求见该规范的“工作流接入”。无关 SDK 的初始化不能成为隐私选择前置，需要授权的 SDK 行为也不能因独立启动而提前执行。现有项目仅覆盖受影响用途与能力，不新增审批或另一套流程状态。

## 按任务选择编排

实际工具及接入先按[能力核实](../../app-domain-toolkit/references/tool-capability-verification.md)确认当前工程、操作入口与真实完成结果；仅有 Skill、插件安装或任务受理不代表操作成功。需要运行时按[运行验证与试玩执行](../../app-quality-review/references/runtime-validation.md)复用实例、执行本批路径、采集实际结果并清理本任务资源。V1、V5 与最终组合分别按实际范围验证，不扩大普通小任务或无界面服务的检查范围。

| 任务 | 入口与状态 | 必须保留 |
| --- | --- | --- |
| 事实查询、纯文案或注释 | 直接完成，通常无需 Work Item | 本次差异检查和真实交付说明 |
| 单个本地工程修复 | `init --mode light --type MODULE`，从 REVIEW 开始 | F0范围、F1验收、F2方案质量、F3工程证据，且仅一个独立执行单元 |
| 普通功能、视觉、跨模块或完整项目 | 默认 `standard`，从 INTAKE 开始 | 现有阶段、质量门、原生专业规范及必要人工确认 |

轻量模式减少的是独立状态操作和记录填写，不会自动设置 PASS。它仅接受无视觉生产的 FOUNDATION/MODULE，拒绝项目、集成、发布、设备及其他受保护动作，也不接受多单元或并行依赖。`PROJECT` 初始化进入需求阶段；普通功能及其他工作类型继续按各自阶段起步。

`plan --spec <相对计划路径>` 从实际计划生成身份、顺序、结果路径、实施包与空 Evidence Manifest，并将允许路径收窄为当前单元范围。计划可携带有非空理由的 F0/F1/F2 显式自评；省略时保持原状，不允许注入 F3/F4 或批准。冻结后不能覆盖计划，RETURN 后为变化范围提交新的计划文件。

`record --unit <单元ID> --report <相对报告路径>` 只记录当前实施批次的真实文件、命令、退出码、非空输出及证据路径，失败命令不会生成 PASS。随后使用现有 `unit-check` 校验单元；实施者确认真实工程结论后再登记 F3。记录工具不执行报告里的命令，不生成测试输出、质量结论或用户确认。

`run` 停在 REVIEW 或 IMPLEMENTING 是控制器的执行边界，不是要求用户再次批准普通本地工作。当前任务授权已充分时，由代理继续实施和显式迁移；未决取舍或受保护操作才进入对应用户确认。

受保护动作可在规划时登记，先完成不依赖授权的本地准备；实际执行前按[控制器的 `check-action`](../../app-workflow-control/SKILL.md#cli)逐效果核对动作、目标、明确批准与 F4。该只读检查不执行动作，也不替代用户的明确授权。

## 输出文件规划与交付

实际生成、衍生、替换或复用素材时，按[资源来源与消费者关联](../../app-asset-workflow/references/asset-provenance.md)在现有唯一清单关联需求／参考、必要制作与处理、正式资源身份及真实消费者；已有有效资料直接引用，非素材任务不补空记录。该关联支持增量生产、交接及清理，不代替原生导入、当前运行与人工显示确认。

按[三项最小约定](output-files.md#每项任务的最小约定)明确目标与结果、涉及写入／输出时的路径、完成条件与验证方式，目录映射和已有规则直接引用。当前代理默认负责，委派／并行／交接时注明分工；版本、输入依赖、消费者和保留去向仅在实际需要时补充。交付核对真实文件及适用引用，失败、未生成和未验证项如实列出，不预建空目录或强制报告。

各栈原生目录和工具固定文件名保持其合同，机器证据与人工目录分开，冻结引用不覆盖；任务责任沿用现有实施、采集、质量及清理／发布分工，不新增输出账本或控制器状态。控制器只检查已有字段，完整归档、依赖核对与交付检查由执行者和主编排者负责。

## 项目清理任务与收尾

按[清理任务拆解与安排时机](../../app-artifact-cleanup/references/project-cleanup.md#清理任务拆解与安排时机)安排适用的盘点、记录／项目内容核对、执行和验证，每项明确清理结果、允许范围及完成条件；涉及移动／删除时补充引用与恢复依据，分工和依赖按协作需要注明。实施收尾只核对本轮变化，集成、候选或用户要求提交时再核对相应去向；已有结果直接复用，不重复全仓检查。

工作流记录按[保留与归档规则](../../app-artifact-cleanup/references/project-cleanup.md#工作流记录保留与归档)追踪当前、并行及仍被复用历史工作项的直接／间接依赖，实际项目内容核对源码、配置、场景资源、测试文档和可再生产物的真实消费者。冻结绑定记录保持原路径，不能以删除、重新生成输出或重算摘要伪造历史；临时内容须替换、移除或说明保留用途。任务状态区分已盘点、已执行、已验证及待定，只有清单不能标为已清理；无候选可如实记录无需变更，不为清理制造删除任务。

本地保留、提交选择、发布包选择分别处理，排除提交／发布不授权删除。执行仍以当前有效精确清单、实际授权与无冲突条件为准，核对引用、续接／恢复及受影响工程结果；失败恢复本轮相关改动，不扩大删除范围。沿用现有工作项、控制器与原生工具，不新增自动删除、审批阶段或 schema；任务覆盖由编排者负责，控制器不会自动生成或逐项校验完整清理任务。

## 本地工具目录与项目范围

项目根级 `.agents/` 是本地技能、工具依赖和安装状态目录，不属于业务源码、工作流交付或发布资源。Git 使用 `/.agents/` 忽略整棵目录，不添加文件放行规则、不用 `git add -f` 纳入提交。常规项目变更、候选快照、基线枚举、清理盘点、代码检索和构建输入排除它；在相同 Git 基线下，不因该目录的安装、更新、缓存或未跟踪文件变化本身触发业务返工、重验或提交阻断。排除仅针对项目根目录，不误伤业务子目录内恰好同名的路径；`.gitignore` 等真实项目配置变化仍正常检查，最终发布包若误含工具目录须作为缺陷处理，不能在包检查时跳过掩盖。

仍可按任务读取 `.agents/skills/` 的规范、模板和校验器，执行明确的技能安装/维护与工具自检；这些工具的真实缺失或失败照常报告，不能因目录被忽略就伪造通过。项目实际工作项、确认和证据保存在各自正式路径，不写入 `.agents/` 来隐藏业务改动；根级 `AGENTS.md` 也不属于这个目录。维护本技能源码仓库时，正式 `skills/`、`packages/` 与测试文件保持正常跟踪。

安装器合并目标项目根 `.gitignore`，保留既有规则并确保 `/.agents/` 生效，dry-run 不写文件。忽略规则不会移出已跟踪文件：发现历史跟踪时先核对 `git ls-files -- .agents`；在用户明确要求不跟踪的范围内仅移出该目录的索引并保留本地文件，不删除目录、不重写 Git 历史，也不改其他暂存项。普通安装不自动改 Git 索引；安装来源和版本沿既有说明记录，重新拉取项目后按相同来源安装本地技能。

## 工作流记录与提交范围

Expo 项目额外核对 `.easignore` 的源码上传范围；已有该文件时不能只依赖 `.gitignore` 排除 `.agents/`。CNG 的配置/插件与手工维护的原生工程按本栈正式源规则保留，`.eas/workflows/` 不因点目录命名被当作缓存；构建或 CI 需要的工具通过明确安装步骤提供，不上传本地 `.agents/` 代替依赖安装。

仅在用户明确要求提交时，按当前实际用途逐文件选择工作流记录，而不是提交整个记录目录。保留当前项目运行、构建和验证所需的文件，以及恢复、检查或继续当前工作项及其仍有效依赖所需的记录和引用文件；同时考虑其他仍需续接的工作项与并行任务，不覆盖或移除其必要文件。使用控制器实际 `check` 及适用合同判断哪些记录、执行结果、人工确认和证据仍被消费；目录位置、创建时间或“已完成”标签本身不能证明必要或过时。

已被替代且不再被任何有效工作项、当前验收、运行或构建引用的中间产物，不纳入本次提交。例如无有效引用的旧候选、失败尝试、重复预览、临时日志和过期执行输出。不要仅因文件被记录在历史目录中就提交；也不要仅因文件看起来像中间产物就忽略当前机器门、确认或恢复实际需要的引用。确有必要时保留完整的选择证据及其所引用的候选，不能为缩小提交而篡改确认、删除必需字段或伪造通过。

提交前从当前工作项、规格和实际入口追踪有效引用到具体文件，核对必要文件已在提交或现有 Git 历史中，并逐路径检查待提交差异。失效与归属不能确定时先核实，不能擅自排除可能影响续接的文件。无须提交的文件可留在本地；本规则不授权删除文件、清理他人记录、改写已冻结证据或自动提交。

上述必要引用不包含[本地工具目录](#本地工具目录与项目范围)：规范或命令引用 `.agents/skills/...` 不表示需要把已安装技能纳入 Git。提交核对排除其变更，业务源文件和 `.workflow-control/` 等真实记录仍按实际范围检查。

上述提交判断与[清理范围及交付边界](../../app-artifact-cleanup/references/project-cleanup.md#清理范围与交付边界)分开：Git 历史里存在文件不代表当前工作区所需引用可缺失，不纳入本次提交的本地记录也不能一并删除；发布包另按实际打包消费者核对。保留有效清理记录、恢复映射及验证输出，不在收尾时将本轮交付一起清掉。

## 功能切片与跨对象依赖

从零复杂游戏或空间、路线、镜头关系实质变化时，在需求／基线和本批对象 V0 按[关卡与场景方案探索](../../app-domain-toolkit/references/game-design-exploration.md#explore)安排关卡设计师与场景设计师。相关 V1 实现前先展示结构草案和关键玩家视角概念图，沿用已有决定处理实质取舍；以本批路径及其关键区域为范围，不要求全游戏设计完毕再开始实现。V1 验证方案中的空间与机制假设，反馈修订后进入 V2 正式目标；探索图不占用正式视觉确认，也不增加 V 阶段。

游戏创意与核心循环方案形成后，在需求与全局基线阶段按[玩家视角方案审查](../../app-domain-toolkit/references/game-characteristics.md#player-review)检查开始动机、目标理解、行动价值、成败与重试、持续游玩和时间负担。相关机制实现和正式视觉制作前处理方案中已发现的问题，将仍需运行或真实参与者观察的假设交接到 V1 和试玩计划，记录沿用现有 GDD、F1/F2 及 QA 材料。

游戏的功能切片按[游戏特点识别与专项验证](../../app-domain-toolkit/references/game-characteristics.md)在现有 GDD/技术设计中关联特点、规则和风险，V1 优先验证影响本切片方案的机制，QA 将其映射到可复现用例及证据。V5 和最终集成重验正式组合与完整游玩周期中受影响的行为；沿用六阶段、V0–V5 和现有记录，不单独为类型识别增加审批或控制器字段。

以可验证的用户行为拆分功能切片，明确目标、主流程、关键状态、必要异常、数据传递、验收范围、真实结果及未决项。一个切片可关联多个场景、页面或显示层，一个对象也可承载多个切片；共享业务规则与状态维护一份，简单单对象任务无需额外建立切片工作项。按当前行为范围关联对象和验证证据，不要求整个项目或无关功能完成。

首条正式切片只建设当前路径必需的基础能力，贯通操作／请求、业务规则、数据变化、可观察反馈、适用异常恢复和可重复验证。V1 优先沿正式入口、模块、状态所有者及测试入口实现；需要隔离探索时明确临时范围和迁入／替换条件，不建立长期平行 Demo。满足正式质量的机制持续演进，后续功能复用同一工程与公开契约，不在 V5 另写一套页面、业务或状态管理。机制复用不表示继承原型几何，也不豁免正式组合回归。

跨场景功能先验证跳转、数据与状态传递、结果和返回等本批次关键链路，再以实际验证覆盖范围支持受影响对象推进。可用临时宿主或白盒，也可直接实现并运行验证；共享功能先在最小上下文验证自身行为，业务模块使用已交付的公共 Toast。Toast 的前置顺序按上文执行，各业务对象的正式画面按自身进度完成。对象只等待会影响本次视觉范围的行为明确；局部结果不能冒充整条链路通过。正式组合后在集成阶段再次验证完整跨对象流程，并检查场景切换、状态同步和对象衔接。

导航按行为与显示责任划分，而不是按每个按钮或路由机械建项：共享路由、跳转、返回、参数和状态恢复由非视觉 `MODULE` 或早期 `feature` 集成承担；共用行为由真实证据覆盖相关对象。应用中跨页面常驻、职责稳定且需要独立视觉验收的导航框架可作为 Flutter、Expo 的 `PAGE`，首页内容作为另一 `PAGE`；仅属于首页的导航留在首页。游戏的真实大厅或主菜单使用 `SCENE`，跨场景导航逻辑及资源按需共享，并在实际宿主场景验收，不为常驻导航虚构场景或瞬态层。共享机制不消费正式视觉资源；导航 Prefab、皮肤等正式视觉资源由真实对象按 V3/V4 生产验收，其他宿主复用已验收资源并核对实际组合。导航共享实现、框架、内容和瞬态层分别明确唯一代码及资源所有权，不因复用重复实现。详见[功能范围与跨对象依赖](../../app-workflow-control/references/function-dependencies.md#导航框架与共享路由)。

V1 的白盒按风险选择，不是必经产物：玩法、手感、空间、时序或复杂流程存在不确定性时可用白板、临时资源、白模或可运行原型；行为明确时可直接实现或复用仍有效的功能验证。涉及操作、时序、碰撞或空间的结论需要实际可运行验证，静态白板不替代运行结果。现有明确授权及需求已足够时继续实施；确有玩法、交互或范围取舍时记录用户的真实决定，不伪造确认或新增逐步审批。用户检查显示效果，未经明确授权不得自动分析截图或发起真机验收。

采用白盒时，按[可辨识的功能原型](readable-functional-prototype.md)提供有语义的对象、任务、状态与反馈，优先复用轻量原生组件和真实机制；体验视图可理解，调试信息按需查看。可读性检查并入已有 V1 用例，模拟范围如实标识，不增加独立审批，也不提前冻结 V2 风格或 V3 精确布局。

## 对象闭环

SCENE 是真实游戏场景及常驻 HUD；PAGE 是 Flutter、Expo 应用页面、ESP32 设备页面，以及实际存在的公共导航框架及其语义状态。框架可以是工作项层面的显示对象，不要求为其虚构新的应用路由。DISPLAY_LAYER 是 modal、popup、drawer、toast 等瞬态层，具有独立 objectId、单一 hostId 和关闭/恢复行为；同一实现跨多个宿主时复用代码和资源，按实际宿主上下文分别验证，不能把一个宿主的结果当作全部宿主通过。宿主只提供运行上下文，不要求宿主 V5 完成、不能替瞬态层完成验收；同一个实施包不能混装三种对象类型。

相关功能完成 V1 验证后，在 V2 期间按既有要求选择首次全局视觉方向；已有有效方向可复用，离开 V2 前须完成视觉目标确认。同一游戏场景需要多张设计稿时，先按[多张场景设计稿](../../app-asset-workflow/references/multi-image-scene-design.md)规划视图、目标及本批次覆盖。每张正式目标按对应单目标合同分别记录和验证，最终核对同一正式场景的共享内容与视图衔接；全局三候选只用于选择视觉方向。已有场景优先保留不变部分，仅调整受影响区域并展示必要上下文；新场景先设计能验证功能和布局的完整关键视图。

| 阶段 | 共同含义 | 关键边界 |
| --- | --- | --- |
| V0 | 范围 | 确定对象、状态、功能范围和依赖；适用游戏在 V1 实现前交接结构草案与关键视角概念图，无需常规人工确认 |
| V1 | 功能实现与验证 | 直接实现、复用仍有效的验证或按需采用可辨识白盒；记录实际行为、模拟范围和未决项 |
| V2 | 正式视觉目标 | 以相关已验证行为和状态为输入，用户确认目标图及覆盖范围 |
| V3 | 拆解与布局 | 先独立确认带编号拆解图，再确认布局图及适配关系 |
| V4 | 正式资源与导入 | 先代表样本与真实组件试接，再分批生产、导入和资源级校验；样本不代替 V5 |
| V5 | 正式组合与运行 | 正式宿主接入、布局、输入、状态和连续尺寸变化证据；人工确认实际显示 |

V3 在已有布局规格中按[还原依据与变更边界](../../app-ui-layout/references/relative-layout.md#还原依据与变更边界)补充受影响项，区分已确认目标、测量值、估计值和适配规则；无需另建布局系统或对既有明确规格重复审批。V5 在同一阶段分别进行[基准还原与适配检查](verification.md#三类验收结论)，并报告结构、工程和视觉三类结论。

还原应保持已确认的比例、信息排列、视觉层级与素材尺寸，不为方便实现或通过测试擅自改变目标。对目标的还原修正和已声明规则内的功能适配可在已有授权内继续；改变视觉目标时记录差异及原因，仅在确需用户取舍时请求确认，不以“适配”或“优化”掩盖设计变更。

场景、页面和显示层在 V3 按[节点最小化](../../app-domain-toolkit/references/reference-domain-display-ownership.md#节点最小化)复用已有节点并分别确认拆解与布局。V4 按[代表性接入与分批协作](../../app-asset-workflow/SKILL.md#代表性接入与分批协作)在正式工程的真实组件骨架中试接少量资产，先核对消费规格、状态及适配风险，再扩大相关批次；可以制作资源级 Prefab/原子组件并做受控预览，代码与素材按明确接口并行，不等到 V5 才首次接入。V5 按确认后的最简层级完成正式宿主装配、布局校准和运行核对。功能验证证据可被相关对象引用，但不能替代各对象视觉确认，原型功能通过也不能代替正式组合回归。满足质量要求的机制实现可复用；标记临时素材、测试数据及占位实现，交付前替换或说明保留依据。基线素材已存在时复用，不为阶段强行生成图片。没有独立位图需求时记录原生组件/矢量路线及资源阶段不适用项，仍验收对象的拆解与布局。

Expo PAGE 的 V1 同样先验证功能、状态、导航与取消/恢复；V2–V5 按 [Expo 领域合同](../../expo-domain-contracts/references/domain-validation.md)绑定平台、正式组件源、资源与实际运行。React Native 使用自己的逻辑单位、安全区、键盘和文字缩放，不借用 Flutter Widget 或浏览器 DOM 作为原生证据；截图继续由用户人工检查。

Roblox 的 V1 在当前 Place 的真实 Client/Server 上下文验证输入、规则与状态；V2–V5 按 [Roblox 原生合同](../../app-stack-roblox/references/native-contracts.md)绑定实际 Edit 正式源、对象、资源和目标运行。正式源需保存并回读，Play 克隆或离线合同校验不能替代；截图及显示继续由用户人工检查。

Flutter PAGE 的 V1 先完成产品语义、状态与必要功能验证，可按需使用轻量 sketch；V2 确认高保真目标，V3 的关系约束可来自 sketch，但不冻结与已确认目标冲突的低保真几何；V5 按实际验收模式验证 Widget 关系、文本缩放、键盘、安全区与真实交互，只有明确要求 `exact` 时才强制完整 fidelity 对照。页面不使用游戏世界坐标作为布局依据。

## 视觉确认的增量复用

新增或修改场景、页面、显示层、功能或机制，只要涉及显示元素设计或可见表现，先按[增量显示约束](../../app-domain-toolkit/references/reference-domain-display-ownership.md#新增显示元素的增量约束)从当前增量的 V0 定义范围，再完成 V1 对受影响功能的真实验证。调整既有元素的布局、外观、可见状态、特效参数或时序同样适用；纯非视觉修改按实际影响处理。不将从 V0 开始解释为重做整个宿主，也不强制重新生成设计稿或图片。

已有同项目、同技术栈、同工作项类型和对象的 COMPLETE/V5 来源时，在完成当前适用的 V0/V1 后调用 `reuse-visual`。DISPLAY_LAYER 还核对宿主与层类型。工具验证原记录和已有用户消息，只引用原文件，不改写原确认，也不生成新的视觉批准；旧视觉记录不能替代当前功能验证，亦不能覆盖已变化元素及组合的目标、拆解或布局确认。下表“新工作项起点”指执行复用后的阶段，不是允许跳过当前增量 V0 的入口。

SCENE 累计生产且本批需要新增目标时，可按[多目标记录](../../app-workflow-control/references/multi-target-visual.md)显式使用 `--target-ids` 选择未变化来源目标，逐项继承允许的确认并重新确认当前累计覆盖清单。来源目标继续保留，未选目标与新增目标按本批处理；存在非继承目标时共同阶段停在 V2，不自动跳到 V3。下表起点适用于完整目标集合复用；PAGE／DISPLAY_LAYER 使用原有单对象复用。

| `--impact` | 可继承 | 新工作项起点 | 当前仍需完成 |
| --- | --- | --- | --- |
| `implementation` | 基线、V2目标、V3拆解与布局 | V3 | 当前功能验证、V4当前导入证据与确认、V5当前运行及人工验收 |
| `assets` | 基线、V2目标、V3拆解与布局 | V3 | 当前相关功能验证、更新素材的V4检查与确认、V5当前组合验收 |
| `layout` | 基线、V2目标、V3拆解 | V2 | 当前相关功能验证、V3新布局确认、V4与V5 |
| `target` | 仅全局基线 | V2 | 新V2目标，以及V3、V4、V5；复用前须完成当前相关功能验证 |

影响分类依据实际目标、对象状态、素材和布局关系，由当前执行者明确说明理由，不用文件版本或摘要变化自动推断。全局视觉方向变化时不复用旧基线，重新完成首次三候选选择。复用不会继承工程 Evidence、V4/V5确认或旧执行状态；未变化素材可由原生流程继续使用实际文件。内部实现或数值不改变可见行为时定向功能回归；新增状态或交互须重验受影响功能并评估目标与布局；核心跨场景规则变化先更新对应切片，再逐对象检查影响。RETURN 只撤销实际受影响的确认，并同步清理复用来源声明。

## 持续迭代与可接手收尾

每批实现与审核按[架构模块契约](professional-conventions.md#architecture-module-contracts)检查实际改动是否增加重复规则、状态多写者、私有穿透或生命周期风险，只做保障本次交付所必需的局部重构；按[质量证据与返修复验](professional-conventions.md#quality-evidence-and-retests)沉淀关键行为和缺陷回归测试。测试留在正式项目目录，本轮命令输出沿原证据路径保存，不以报告或静态规范断言替代应用行为测试。

收尾按[验证约定](verification.md)核对适用项，按[当前项目知识](professional-conventions.md#current-project-knowledge)仅更新变化事实，让下一轮可定位入口、运行相关检查并继续修改。面向用户按[精简交付](output-files.md#精简交付)简短反馈，不把内部检查清单扩写成报告。已有 F1/F2/F3 承担交付与质量职责，不新增可维护性分数、账本、阶段或逐项审批，不要求全仓重验或复制全套文档。历史冻结记录保持不变，当前说明引用有效历史依据。

## 发布准备与实际上线

候选构建、导出及交付按[实际输出绑定](../../app-release/references/release-readiness.md#实际构建输出与候选绑定)选择本次真实目录或包，不以固定目录顺序、文件名或修改时间猜选旧产物。配置明确时使用对应输出；存在无法核实的歧义时暂停依赖该候选的交付，继续独立检查，不自动清空其他目录或把构建受理当完成。

已选 CrazyGames、微信小游戏、抖音小游戏、Google Play 或 App Store 时，按[渠道接入任务](../../app-release/references/channel-platform-integration.md#接入任务与完成条件)从需求期确认平台与能力，基础工程验证本栈实际产物，功能期接通适配器及失败恢复，最终集成和候选逐渠道核对证据、资质及资料。平台强制的隐私／授权前置不能因默认不新增隐私业务而跳过；未满足时限制相应能力或候选，不默认扩建无关隐私业务。沿用现有工作项和六阶段，不自动启用全部渠道。

目标包含商店或游戏平台展示时，安排[商店文案与展示素材制作](../../app-release/references/store-marketing-assets.md#任务安排与完成条件)。策划期可准备字段、卖点和采集脚本。相关功能和画面稳定后制作所需封面、截图及视频，发布准备核对填写稿、导出规格、顺序及用户人工确认。素材审阅沿用现有流程，商店上传、投放和市场实验按实际任务和授权执行。

`RELEASE` 默认 `releaseIntent=prepare`。完成本次检查或候选打包、F0–F3及当前准备材料后，可从 PASSED/INTEGRATING 到 COMPLETE；完成结果标为 `release-prepared`。Evidence Manifest 必须唯一包含 PASS 的 `release-preparation` 记录，它绑定当前工作项、技术栈和 release 阶段，并引用当前证据根下两个独立、非空的交付材料与检查文件。交付可以是准备检查报告或构建产物，不能用结果JSON或manifest自身充当证据。

实际发布选择 `releaseIntent=publish`，继续经过 RELEASE_APPROVAL_REQUIRED、F4、精确批准、RELEASING 和真实 `release-result` 后完成，结果标为 `release-published`。准备模式禁止 `publish` 动作和发布执行状态。签名、上传等其他受保护操作仍分别遵循原有精确授权规则。

## 风险与门禁

| 动作等级 | 范围 |
| --- | --- |
| A0 | 只读调查 |
| A1 | 规格与候选 |
| A2 | 隔离原型 |
| A3 | 授权范围内正式实现和本地验证 |
| A4 | 本地集成、迁移或共享设置变更 |
| A5 | 外部系统、设备、签名和上传 |
| A6 | 发布、付费与不可逆高影响操作 |

A 等级描述风险，不新增授权。安全本地 A4 不自动增加确认；A0–A4 中一旦实际涉及外部写入、付费、真机、破坏性操作等，仍遵守精确授权。

| 门 | 唯一职责 |
| --- | --- |
| F0 | 用户目标、范围、路径和停止条件 |
| F1 | 实际交付满足目标与有效决定 |
| F2 | 当前技术栈的领域质量 |
| F3 | 真实工程证据和有序执行闭环 |
| F4 | 当前高影响操作的精确授权 |

`INTAKE → BASELINE → PROPOSAL → REVIEW → IMPLEMENTING → VALIDATING → PASSED` 是实施主路径；后续按需要集成、准备发布或完成。V 阶段是对象证据进度，不是另一套可绕过门禁的状态机。

失败先原地 repair；候选未变而证据过期时 revalidate；需求/范围/上游视觉目标真实变化时显式 return，影响范围决定恢复点。已授权目标内的实现调整记录在实际交付中，不因合同版本、文件内容或 SHA 差异自动重开确认。

发现已知的轻微偏差时，先记录实际现象及影响，继续不受影响的工作，在阶段结果或最终结果中汇报，不为每一处轻微差异中断并询问。功能失败、明显遮挡、不可读、证据错绑等仍须处理；明确约定的验收条件未满足时如实保留未通过或未决状态，不将继续工作当作验收通过。用户对视觉效果的人工检查和确认仍按既定流程进行，未经明确要求不自动分析截图。
