# 工作流输出文件与交付规范

在规划文件产物、调用生成／采集工具、保存审阅材料、交接、验证或清理前读取。适用于七栈的文档、控制记录、候选、媒体、命令输出及发布产物；按需创建文件，不为每个阶段建立空目录、占位报告或另一份输出状态账本。普通问答及无需持久证据的简短审阅可直接在对话交付。

## 每项任务的最小约定

1. **做什么**：目标与预期结果，可以是文件、代码修改、检查结论或调查结果。
2. **改哪里**：涉及修改或文件输出时明确路径，采用现有目录映射及工具约定。
3. **怎样算完成**：验收条件与验证方式；纯文案、注释等 T0 改动可只检查差异，其他改动按适用测试等级验证，不统一要求截图或运行采样。

负责人默认当前代理，只有委派、并行或跨角色交接时才显式指定。已有事实、路径与验证规则直接引用，不逐任务重填，也不要求单独落盘任务说明或报告。

| 信息 | 何时补充 |
| --- | --- |
| 批次／版本 | 多候选、重试、并行、冻结证据、发布或工具合同需要区分身份时 |
| 输入与依赖 | 确有前置资料、接口或任务时，引用实际来源即可 |
| 消费者 | 资源、接口、共享产物或其他下游需要定位消费入口时；普通报告说明用途即可 |
| 保留去向 | 文件生命周期不能由现有目录／合同确定时；提交和发布选择到对应环节核对 |

正式委派任务包和控制器／原生工具的现有必填字段、授权、路径及证据约束继续执行，不因精简省略；本规范不新增通用必填表、ID、哈希或审批。

## 输出分类与唯一位置

先确定类别、真实用途及消费者，再选目录。项目根目录、当前栈原生存放规范和控制器实际输出共同决定位置，不能把一个栈的路径套到其他栈，也不能为目录整齐搬迁已绑定记录。

项目根 `.agents/` 按[本地工具目录边界](workflow.md#本地工具目录与项目范围)保留为本地安装位置，不作为业务产物、证据、制作源或提交/发布输出；技能读取路径不构成 Git 必需引用。实际 `.workflow-control/` 及本栈记录继续按原合同保留。

| 类别 | 存放与消费边界 |
| --- | --- |
| 项目权威文档 | 使用当前项目唯一文档根，新项目默认小写 `docs/`；策划、架构、资源总表等沿用所属合同的固定文件名，一个事实只有一份权威正文，其他位置链接引用 |
| 控制器记录与机器证据 | Work Item、实施包、确认、执行状态和结果使用当前控制器实际生成／声明路径；受限文件及命令输出位于当前工作项真实 `evidenceRoot`，不能用人工审阅目录代替 |
| 临时中间文件 | 下载暂存、转换缓存及可再生工作文件按工作项与批次隔离，不散放项目根；不可恢复的原始输入和已绑定材料不能只存于可清理暂存区 |
| 未送审候选 | 按工作项、实际阶段／单元与候选身份保存，尚未确认不能当作正式资源；送审或成为下游输入前保存到相应保留位置并核对依赖 |
| 人工审阅与运行资料 | 目标图、拆解／布局包、截图、录屏、审阅页和性能原始资料按候选／运行批次保存，人工可读目录不自动成为机器证据根 |
| 已确认的非运行成果 | 使用原生规范的保留目录及独立版本，引用真实确认；复制到 confirmed 目录本身不表示通过，不创建第二份确认账本 |
| 制作源与正式项目内容 | 可编辑制作源、原始媒体与再生产输入按栈保存；代码、场景、配置和正式资源进入实际工程目录，运行消费者不得读取临时、审阅或证据目录 |
| 构建及发布候选 | 使用当前构建／平台工具的实际输出路径与候选身份，和审阅资料、正式可编辑源分开；记录版本、平台、配置和日志，构建完成不等于已发布 |

以下原生路径表为具体栈的权威补充；公共规则不重命名其中固定文件，不修改工具的原子写临时文件、事务日志或测试隔离目录。

| 技术栈 | 产物位置依据 |
| --- | --- |
| Unity | [原生存放规范](../../unity-development-workflow/references/artifact-storage.md)：`Artifacts/` 中间／候选／人工资料，`docs/confirmed/`、`ArtSource/` 与正式 `Assets/` 分工；请求输入与机器采集结果按各自合同分别存放 |
| Cocos | [原生存放规范](../../cocos-game-architecture/references/artifact-storage.md)：`output/`、人工 `evidence/`、`docs/confirmed/`、`assets-source/` 与正式 `assets/` 分工 |
| Phaser | [原生存放规范](../../phaser4-game-architecture/references/artifact-storage.md)：`output/`、人工 `evidence/`、确认及源目录，与正式 Web 资源路径分开 |
| Three.js | [原生存放规范](../../threejs-game-architecture/references/artifact-storage.md)：沿实际资源模块／URL、领域决定记录和原生目录映射保存；不能把领域记录当成公共控制器记录 |
| Flutter | 先读[最小工件矩阵](../../flutter-app-orchestrator/references/artifacts.md)，沿实际页面／资源／构建合同；不为每次单代理任务生成 brief 或独立报告 |
| ESP32、Node.js | 沿实际工程、SDK／构建与服务端合同，在已有技术方案中明确唯一映射；不虚构视觉阶段、原生目录或将固件／服务构建输出当作源文件 |

没有原生固定目录、也没有当前项目映射的新输出，先在已有技术方案中指定位置：临时文件默认 `output/intermediate/<workItemId>/<unit-or-stage>/<batch>/`，未送审候选默认 `output/candidates/<workItemId>/<unit-or-stage>/<candidateId>/`，人工材料默认 `evidence/<workItemId>/reviews/<candidateId>/` 或 `evidence/<workItemId>/validation/<runId>/`。这些仅是缺省人工／临时目录，不是新增控制器路径；无候选、视觉阶段或运行批次时省略不适用层，不为填目录伪造身份。文档、源文件、正式资源与构建输出仍按实际合同指定，不另建平行目录。

## 命名、身份与覆盖边界

- 非工具固定的新增文件／目录默认使用简短、表达用途的 `kebab-case`；显示标题可用中文。工作项、单元、对象、候选、运行及构建 ID 使用真实身份，不能为统一大小写改变 ID 或把文件名当作业务绑定的替代。相同文件名可由已明确的目录上下文区分，不要求在每个文件名重复全部 ID。
- 自由命名的报告／媒体可采用 `<purpose>-<scope>-<run-or-version>.<ext>`，例如 `loading-transition-run-002.png`；工具固定的 `manifest.json`、`execution-state.json`、布局包文件名和预声明 `resultPath` 等保持原合同。不得改名为 `final-final`、用 `latest` 作为冻结证据引用，或仅靠文件修改时间猜测版本。
- 需要批次／版本时，在当前工作项内保持唯一，优先采用工具真实 ID；无工具 ID 时可声明唯一序号，不为普通文件更新额外造 ID。重试、返修和重验按现有合同区分新结果，保留仍有效的失败原始资料，不覆盖后只留下最后一次成功。
- 有效目标、已确认媒体、冻结实施包／结果与证据不覆盖、不以新文件替换旧内容。新增版本通过现有控制器及原生返修／RETURN／证据更新流程绑定；不能只改文件名、重算旧摘要或手填状态制造新验证。可编辑权威文档按其所有者和实际冻结约束更新，不为每次编辑复制一份版本正文。
- 引用字段使用合同允许的项目相对路径及 `/` 分隔符，控制器路径不含 `.`／`..` 路径段、绝对地址或越界链接；工具参数按实际接口传入，交付给用户的本地文件链接使用真实绝对路径。写入前核对允许范围、大小写和同名冲突，有并行写入时再核对写者，不能覆盖他人文件。

## 生成、采集与引用

1. 调用工具前明确目标结果、写入／输出路径和完成条件；按上文触发条件补充其他信息，沿用已有方案或合同即可。工作项及单元允许范围不因目录约定扩大，生成资源与采集证据分别遵循其实际授权和合同。
2. 支持输出参数的工具显式指定目标路径；工具只能返回固定位置或外部生成文件时，读取其实际返回位置，按允许流程保存完整文件和依赖后再登记。不能将预期文件名、远程链接或工具成功状态冒充已存在的本地交付；不得为统一目录自动移动冻结文件或引擎身份文件。
3. 送审或写入合同／清单／确认前保留实际候选及必要输入。布局 PNG、节点／决策 JSON、生成记录、按需 HTML／样式／数据、父帧／原始视频等按实际依赖形成可复核集合，不仅交付一张预览图或一个引用 JSON；目录复制不增加通过状态，归档副本不取代原确认证据。
4. 验收命令原始输出、结果与文件清单按各自 Schema 保存：执行单元结果位于预声明 `resultPath`，且在当前 `evidenceRoot` 内；`Execution Result.files` 列仍存在的实际交付，`deletedFiles` 按需列已删除路径，两者至少一类非空，均须属于单元 `paths`。删除须绑定实施前冻结的真实存在基线，不得申报原本不存在的路径或删除受保护记录；后续重建会使删除结果失效。`commandOutputs[].outputFile` 和公共 Evidence Manifest 的 `items[].path` 位于当前 `evidenceRoot`，不能指向外部人工目录；源码仍保留原生工程位置。
   普通非空原始日志可直接引用。静默成功命令使用非空标准采集 JSON：`schemaVersion="command-capture-v1"`、真实 `command`、`exitCode`、`stdout`、`stderr`；输出字符串可空，命令与退出码须匹配冻结计划和结果。可使用公共独立命令采集脚本实际运行，`plan`/`record` 不代跑。禁止补写虚构成功文本、放宽路径或把结果自身当原始证据；业务合同允许的根外规格或正式资源通过其对应字段引用。
5. 实际解码／解析文件，核对扩展名、格式、非空内容及所需字段，确认引用、资源及媒体依赖可读取；命令记录真实退出码、原始输出和输入版本。截图和录屏采集只证明文件已生成，显示效果交用户检查，未经明确要求不自动分析或代填视觉通过。

目录说明用途，不提供安全或发布隔离。按现有受控配置通道处理秘密，不将凭据或未脱敏用户数据写入报告、日志、媒体、文件名和可发布目录；真实业务数据不因属于输出文件就成为清理对象。

## 输出任务与交付检查

- 规划时采用项目已有目录映射；没有映射的新产物才补充位置，不为每项任务重建方案。
- 生成与交接时提供真实文件，按本次产物核对适用的格式、依赖和身份；下游引用、冻结证据或发布需要的检查不能省略。
- 验证与收尾时按任务风险推荐等级、执行实际检查并报告结果；清理和发布发生时再核对有效引用、保留及包内内容，不把每个小任务都扩展成完整归档／发布检查。

最终在对话或已有报告中说明实际结果、相关文件路径和验证结论；失败、未生成及未验证项如实列出。身份、下游入口及人工确认只在相关合同或显示任务需要时补充，不制造占位文件或重复报告。目录已创建或生成工具成功不能单独判定交付完成。

提交只在用户要求时按[工作流记录与提交范围](workflow.md#工作流记录与提交范围)逐文件选择，发布按实际包清单核对；不整目录暂存或把全部 `output/`、人工 `evidence/` 塞进运行包。清理按[项目清理规范](../../app-artifact-cleanup/references/project-cleanup.md)追踪直接／间接有效依赖，忽略、排除提交、位于临时目录或可再生成均不等于可删。现有冻结路径保留，不以采用本规范为由迁移历史记录或实际清理项目。

本规范是编排、输出与交接约定；控制器继续只校验其现有字段和合同，不自动归档文件、扫描全部依赖或生成上述任务。输出规范检查不能代替真实工程、运行及用户验收。
