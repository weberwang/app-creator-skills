# 专业岗位共用约定

本参考收敛五个技术栈专业岗位反复出现的策划、架构、质量、发布和交接职责。它补充公共执行协议与控制面，不建立第二套 Work Item、阶段、授权或审核状态。状态、执行范围与受保护操作遵循[公共执行规范](professional-execution.md)；岗位任务包与角色分工遵循[协作与交接](handoffs.md)；验证范围遵循[验证约定](verification.md)。

专业适配仍负责各自的产品工件、引擎/API、资源身份、构建命令、平台矩阵、质量等级及领域证据。下文规定这些岗位之间可复用的职责，不能替代栈内合同。

<a id="planning-scope-and-acceptance"></a>

## 策划范围与验收

- 先读取当前任务、项目事实和直接相关的既有工件。区分已确认事实、证据、假设与待决定事项；先从仓库或现有材料消除事实问题，不把建议写成用户决定。
- 为本次变化定义结果、相关依赖、明确排除项和可观察验收条件。新产品与既有产品增量采用各自适用的输出：游戏可维护 GDD，应用可维护产品 brief；不要强行统一二者的内容结构。既有工件只更新受影响部分，并保留相邻系统的影响与回归条件。
- 专业岗位可以在当前任务范围内提议、审查或修订规格；实施前由公共控制面冻结实际实施范围和所有权。只有会改变产品方向、体验、成本、平台或风险的未决取舍才提交 `$grilling`，说明事实、选项及影响、推荐和最迟决定点；推荐不得冒充用户确认。
- 阶段顺序、视觉阶段、领域质量级别及原生工件继续按对应栈规则执行；策划结果不替代控制面状态或证据记录。

<a id="architecture-module-contracts"></a>

## 架构模块契约

- 架构从真实工程、依赖和运行入口出发。按职责划分模块，为模块明确唯一责任所有者、职责与非目标、输入输出、状态所有权、生命周期、公开契约、允许依赖、失败边界和验证入口。
- 沿关键用户流程或游戏事件追踪数据生产、校验、存储、观察、生命周期和恢复责任；选择方案时记录需求依据、复杂度、性能、测试性、迁移成本、平台限制、被拒方案、风险与复审条件。
- 公共模块或资源仅在被多个已确认消费方稳定复用或属于运行必需时建立；避免无明确边界的 `common`、`utils` 与共享资源集合。模块间通过公开服务、状态仓库或消息/数据契约协作，不依赖彼此私有状态。
- 只有写入范围互斥且依赖已满足时才并行实施；共享契约、入口和集成点保持单写者串行。任务内的设计与路径变化要记录影响，并只重验受影响部分；实际数据迁移仍需明确备份、升级、回滚和旧数据处置。
- 本节不规定引擎对象模型、资源加载、渲染循环、平台 API 或工程目录；这些事实由各栈原生规范决定。

<a id="quality-evidence-and-retests"></a>

## 质量证据与返修复验

- 结论绑定被测快照、变更范围、真实目标、运行模式与证据。测试计划把范围内的风险映射到可复现检查；报告说明预期、实际、命令或操作、结果和证据位置。证据只能支持它实际覆盖的模块、流程与平台。
- 没有运行或缺少必要环境/材料时记为未验证、`NOT_RUN` 或领域规定的阻断状态；不把未执行、静态存在、构建面板打开或单个局部烟测写成通过，也不自造用户未定义的性能阈值。
- 启动验证服务前，按同一项目身份、服务类型、运行模式、端口和健康状态检查可复用实例；已有健康实例时复用，确认没有可复用实例后才启动新服务。不得终止项目身份不明或归属不明的进程。
- 缺陷记录区分观察事实、推测根因和建议修复，并保留版本/快照、复现条件、影响、证据与所有者。修复后只重跑失败或实际受影响的检查及必要回归；只有输入事实或快照变化时才重新开启对应检查通道，不以局部复验替代完整矩阵。
- 技术结果、领域专业判断和用户对显示效果/体验的确认分别记录。默认由用户人工检查视觉；除用户明确要求自动分析外，不依据截图自动判定视觉通过。
- 各栈自己的 F/G 级别、审核漏斗顺序、检查工具及平台覆盖范围保持原样，不以统一术语抹平领域差异。

<a id="release-candidate-evidence"></a>

## 发布候选与证据

- 候选由可复现的实际源版本、依赖锁定、构建参数、资源和目标构建命令产生。将候选身份、目标平台/渠道、实际构建与打包结果、日志和验证证据绑定到同一发布任务，避免把不同输入或不同平台的结果混作一个候选。
- 矩阵只列项目实际选择的平台和渠道；每项标记候选包、完成项、阻断项、风险、建议和证据。将实际候选、构建/打包/签名结果及真实命令输出关联到同一 RELEASE Work Item 的 Evidence Manifest。局部基础或关键流程证据只说明相应范围，不能代替最终候选的平台/渠道验证。
- 外部提交、上传或发布前，按[公共执行规范](professional-execution.md)的 `action.approval` 核对用户明确批准的精确目标与动作，并复用已覆盖同一目标和动作的真实用户消息引用，不重复索要相同批准。F4 只按当前 Work Item 和实际结果核对发布门禁；工作项完成不等于已提交或已上架，未执行或缺少证据时不得声称完成。
- 性能检查、性能优化和图集处理按公共发布能力征求用户选择；这不自动成为强制审批门，也不授权未选择的额外变更。各栈特有的构建、签名、商店及渠道参数仍由原生发布清单核实。

<a id="delegation-and-review"></a>

## 委派与独立审核

任务包字段、单写者边界、并行条件、只读审核与结果交接的唯一公共规则见[协作与交接](handoffs.md)。Flutter 原生 Controller/reviewer 流程中，审核者只读并返回统一结论，Controller 是持久 review 记录的唯一写入者；这条角色与记录边界只约束采用该 Flutter 原生流程的工作项，不扩展为其他栈的格式或状态机。具体栈中的角色拓扑、任务模板、风险分级、快照格式和报告路径仍按原生规范；公共入口不得另建角色总控或状态记录。
