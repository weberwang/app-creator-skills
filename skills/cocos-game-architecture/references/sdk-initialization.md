# SDK 统一初始化

项目实际采用的第三方 SDK 按[SDK 文件职责](../../app-domain-toolkit/references/reference-architecture-sdk-initialization.md#文件职责)分文件管理：每个 SDK 使用 `assets/scripts/platform/sdks/<sdk>-sdk.ts`，`assets/scripts/platform/initialize-sdks.ts` 只负责装配并独立投递各管理器任务。唯一应用装配入口调用该模块；应用装配组件可以由启动场景承载，但启动场景不负责具体场景业务初始化。没有采用 SDK 时不创建占位文件，也不因本规范增加 SDK 或依赖。

## 唯一入口与职责

- 入口只投递各 SDK 的独立任务并立即返回，不等待整批初始化。Creator 首帧、Boot 和场景启动不等待 SDK 初始化批次；不得使用等待全部 SDK 的 Promise 门、全局 `allSdksReady` 或其他启动屏障。
- 按[SDK 文件职责](../../app-domain-toolkit/references/reference-architecture-sdk-initialization.md#文件职责)划分装配入口与各 SDK 管理文件；广告服务、隐私模块、Scene、Component 和平台入口不另建初始化状态或恢复逻辑。
- 公共类型、纯配置、原生插件安装和必要宿主配置继续归属原有文件。平台适配器可以封装原生 API 调用细节，但不得在构造函数、模块导入或场景生命周期中自行启动 SDK，也不得持有第二份初始化状态或重试器。
- 广告加载/展示、支付、登录界面、埋点业务和隐私交互仍由各自业务模块管理。SDK 就绪后的广告位加载恢复等运行任务由广告服务持有；业务模块通过已注入的能力接口读取结果或请求对应 SDK 的单独重试。
- SDK 导入不得在模块顶层产生初始化副作用。可选 SDK 的动态加载或调用失败必须在该 SDK 自己的任务中捕获，不得影响共享入口或其他 SDK 任务。

## 独立启动与真实前置

1. 应用装配入口对每个已启用且平台支持的 SDK 分别投递任务。一个 SDK 的配置错误、动态导入失败、同步异常、Promise 拒绝、初始化失败、重试或永不回调，都不能阻止其他 SDK 任务发起。每项任务独立处理拒绝并记录自身结果。
2. 禁止无官方依据的跨 SDK 串行、依赖启动图及等待全部 SDK 完成的 `Promise.all` 门。官方真实前置只限制受影响 SDK；`Promise.allSettled` 可汇总诊断，不能作为游戏启动或无关 SDK 的前置。
3. 每个 SDK 只等待自身真实需要的平台、配置、宿主或桥接条件。条件未满足时只保留该 SDK 的待初始化意图，不让其他 SDK 或首帧陪同等待。不得借登录、隐私界面、广告加载、正式场景或 UI 就绪建立项目级启动屏障。
4. 不得绕过锁定版本官方明确要求的真实前置。如果官方前置使某 SDK 暂时无法独立初始化，记录 SDK、锁定版本、具体前置和来源，只将该 SDK 标记为受限；继续投递其他无关任务，不伪造初始化成功，也不建立全局等待。
5. 广告、支付或跟踪等实际业务动作仍由对应合同检查 SDK 就绪、真实隐私状态和操作条件。解耦初始化不授权提前请求广告或执行其他业务动作；能力未就绪时返回该能力自己的状态。

## 幂等、回调与失败隔离

- 同一应用生命周期、同一有效配置下，每个 SDK 只发起一次初始化；重复入口复用该 SDK 正在进行的请求或已完成状态，不重启其他 SDK。配置替换、禁用或销毁时只使该 SDK 的旧操作和回调失效；迟到或重复回调不得覆盖新状态。
- 只有 SDK 的真实完成回调或官方明确的就绪信号才能确认初始化成功。请求受理、初始化函数返回或其他 SDK 成功都不能代替完成事实；超时本身也不能伪造 SDK 失败或成功。
- 每个 SDK 独立持有初始化请求标识、错误分类、失败次数、deadline 和至多一个恢复 timer。重试只恢复目标 SDK，不重跑其他 SDK。配置错误、平台不支持或官方前置未满足时保留清晰阻断，修正前不盲目循环重试。
- SDK 特有退避、生命周期与条件恢复以该 SDK 合同为准；初始化恢复不得与广告位加载、支付交易或其他运行任务共用计数或 timer。
- 通用工作流步骤见[完整规范](../../app-domain-toolkit/references/reference-architecture-sdk-initialization.md#幂等回调与失败隔离)。

## MAX 与 AppsFlyer

MAX 初始化任务和隐私状态处理由不同模块分别投递，只在锁定平台、版本和流程确有官方前置时等待该条件。自集成 CMP 按官方要求在 MAX 初始化前完成；明确采用内建流程时由 initialize 触发，结束后才接收完成回调，相关 MMP/分析 SDK 按官方前置等待。未满足仅限制依赖该条件的 SDK，游戏与无关任务继续。不擅自新增 CMP；已采用或官方要求的 CMP（包括 UMP）及其真实前置必须遵守。

- 新 MAX 实例首次实际初始化前按[广告合同](../../cocos-game-ad-integration/references/applovin-max-contract.md#max-隐私配置与初始化时序)先读取真实授权快照，并按锁定插件及所选隐私路径映射；只有无有效选择且官方手动标志路径适用时设置 `setHasUserConsent(false)`。同实例重试复用已确定配置，不覆盖已有或后续真实选择。MAX 内建 Terms and Privacy Policy Flow 默认关闭，明确采用时按官方流程启用；通过受支持配置核验最终生效值。
- `hasUserConsent=false` 是 MAX 初始化配置，不是用户同意或拒绝回执，也不代表广告不可用。它本身不阻断 MAX 初始化、广告请求或加载恢复；广告业务仍按其他真实适用的 CMP/TCF、地区、宿主和网络条件处理。
- 项目采用 AppsFlyer 时，在其管理文件实现初始化任务并由统一入口投递。核对锁定插件的 session-ready 及真实隐私前置；无官方依赖时不等待 MAX、广告加载或归因回调，配置、状态和失败恢复各自隔离。
- 官方真实前置若与独立初始化目标冲突，按“独立启动与真实前置”仅报告并阻断对应 SDK；不得谎报 CMP/ATT 结果、套用其他框架 API或扩展为全局等待。

## 交付与验证

在 TDD 与实施包中记录采用的 SDK、目标平台与配置来源、真实前置、完成信号、状态所有者、失败分类、初始化重试所有者及业务使用边界。没有实际需求时不安装未采用的 SDK。

目标项目的定向验证覆盖：两个 SDK 独立投递；不存在官方依赖时单个 SDK 抛错、拒绝、失败或不回调不阻止其他 SDK 与首帧；重复入口、配置切换和迟到回调；平台不支持及 SDK 自身官方前置；单 SDK 重试不重跑其他 SDK；广告运行期重试与 SDK 初始化恢复互相隔离。采用 MAX/AppsFlyer 时分别核验默认关闭与明确采用内建流程的配置及真实回调、适用的 MMP 等待；覆盖已有授权快照和无有效选择的手动 `false` 路径，并核验 AppsFlyer 按自身官方条件实际启动。

> 通用工作流步骤见[完整规范](../../app-domain-toolkit/references/reference-architecture-sdk-initialization.md#交付与验证)。
